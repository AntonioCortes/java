Seguridad en Microservicios: JWT y OAuth2 Resource Server

En una arquitectura distribuida de microservicios, mantener sesiones de usuario en memoria mediante cookies (JSESSIONID) es inviable: requeriría que todas las instancias compartiesen una base de datos centralizada de sesiones (como Redis) o aplicar afinidad de sesiones (Sticky Sessions), lo cual destruye la elasticidad y la tolerancia a fallos.

El estándar moderno de la industria para asegurar microservicios REST es la arquitectura Stateless (Sin Estado) basada en OAuth2 y JSON Web Tokens (JWT). Bajo este paradigma, los microservicios asumen el rol de OAuth2 Resource Servers: reciben peticiones que portan un token JWT en la cabecera Authorization: Bearer <token> y validan la autenticidad del token de forma autónoma mediante criptografía asimétrica (claves públicas JWKS), sin necesidad de consultar una base de datos central en cada petición.

Anatomía de un JSON Web Token (JWT)

Un JWT es una cadena de texto compacta formada por tres partes codificadas en Base64URL separadas por puntos (header.payload.signature):

  • Header (Cabecera): Indica el tipo de token (JWT) y el algoritmo de firma criptográfica utilizado (típicamente RS256 con clave pública/privada RSA).
  • Payload (Cuerpo / Reclamaciones): Contiene los Claims o datos de identidad del usuario: emisor (iss), identificador del usuario (sub), fecha de expiración (exp) y listas de roles o permisos (ej. roles: ["ROLE_ADMIN"]).
  • Signature (Firma): Garantiza matemáticamente que el contenido del token no ha sido alterado por intermediarios ni por el propio usuario.

Analogía del Mundo Real: El Pasaporte Biométrico Internacional

Imagina viajar por múltiples países del mundo (los Microservicios):

  • En lugar de que cada policía de aduanas de cada frontera llame por teléfono al ministerio de tu país de origen para preguntar si existes (consultas a base de datos síncronas lentas), presentas tu Pasaporte Biométrico Oficial (el JWT).
  • El policía introduce el pasaporte en el lector de aduanas: el lector utiliza la Clave Pública internacional de tu país emisor (el JWKS) para verificar matemáticamente el sello digital criptográfico.
  • Si la firma es auténtica y la fecha no ha caducado, el policía sabe con 100% de certeza quién eres y qué visados tienes, autorizando tu entrada en 50 milisegundos sin comunicarse con nadie más.

Caso de Uso Real Estructurado

1. Contexto

Una aplicación móvil se conecta al backend de PetStore. El cliente inicia sesión en el servidor de autenticación (Keycloak / Auth0 / Spring Authorization Server) y obtiene un token JWT válido por 15 minutos.

2. El Problema (Sesiones Tradicionales)

Si se usan cookies de sesión, el cliente debe hablar siempre con la misma máquina. Si una instancia se reinicia, el usuario pierde su sesión. Si 10 microservicios se llaman en cadena, todos tienen que consultar una base de datos de sesiones, creando un cuello de botella letal.

3. La Solución (Con OAuth2 Resource Server)

Cada microservicio valida la firma del JWT en memoria con la clave pública de Keycloak. El token se propaga de forma transparente entre microservicios mediante interceptores de OpenFeign, manteniendo la identidad del usuario en toda la cadena.

Estrategia ¿Cuándo usarlo? ¿Cuándo NO usarlo?
OAuth2 Resource Server con JWT Estándar para APIs REST y arquitecturas de microservicios. Escalabilidad infinita (sin almacenamiento en sesión), interoperabilidad multiplataforma y delegación de autenticación en servidores especializados (Keycloak, Okta, Azure AD). Configuración en application.yml

Para que Spring Boot valide automáticamente las firmas de los tokens JWT, solo es necesario apuntar al emisor (Issuer) del servidor de identidad: 


spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          # URL del Authorization Server (descarga automáticamente las claves públicas JWKS)
          issuer-uri: https://auth.tiendamascotas.com/realms/petstore
          # O bien URL directa al endpoint de certificados públicos
          jwk-set-uri: https://auth.tiendamascotas.com/realms/petstore/protocol/openid-connect/certs

Implementación del Resource Server en Spring Boot 3

1. SecurityFilterChain con Soporte OAuth2 JWT


package com.example.orderservice.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.method.configuration.EnableMethodSecurity;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.config.annotation.web.configurers.AbstractHttpConfigurer;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
@EnableWebSecurity
@EnableMethodSecurity // Habilita @PreAuthorize a nivel de método
public class OAuth2ResourceServerConfig {

    @Bean
    public SecurityFilterChain resourceServerFilterChain(HttpSecurity http) throws Exception {
        http
            .csrf(AbstractHttpConfigurer::disable)
            .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(HttpMethod.GET, "/petshop/pet/**").permitAll()
                .requestMatchers(HttpMethod.POST, "/petshop/orders/**").hasAuthority("SCOPE_orders:write")
                .anyRequest().authenticated()
            )
            // Habilita la validación automática de tokens Bearer JWT
            .oauth2ResourceServer(oauth2 -> oauth2.jwt(Customizer.withDefaults()));

        return http.build();
    }
}

2. Propagación del Token JWT en OpenFeign

Cuando order-service llama a pet-service mediante OpenFeign, debe propagar el token JWT del usuario original para que el segundo servicio conozca su identidad: 


package com.example.orderservice.config;

import feign.RequestInterceptor;
import feign.RequestTemplate;
import jakarta.servlet.http.HttpServletRequest;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpHeaders;
import org.springframework.web.context.request.RequestContextHolder;
import org.springframework.web.context.request.ServletRequestAttributes;

@Configuration
public class FeignClientJwtInterceptor {

    @Bean
    public RequestInterceptor oauth2FeignRequestInterceptor() {
        return (RequestTemplate template) -> {
            ServletRequestAttributes attributes = 
                    (ServletRequestAttributes) RequestContextHolder.getRequestAttributes();

            if (attributes != null) {
                HttpServletRequest request = attributes.getRequest();
                String authorizationHeader = request.getHeader(HttpHeaders.AUTHORIZATION);

                // Si la petición entrante tenía cabecera Bearer, la copia en la llamada de Feign
                if (authorizationHeader != null && authorizationHeader.startsWith("Bearer ")) {
                    template.header(HttpHeaders.AUTHORIZATION, authorizationHeader);
                }
            }
        };
    }
}

Ejemplo: Invocación Segura Protegida por Método con @PreAuthorize


// BUENA PRÁCTICA: Validación automática en el Controller con anotaciones de seguridad declarativas
@RestController
@RequestMapping("/petshop/orders")
public class SecureOrderController {

    @PostMapping
    @PreAuthorize("hasAuthority('SCOPE_orders:create') and hasRole('CLIENTE')")
    public ResponseEntity<OrderDTO> createOrder(
            @RequestBody OrderRequestDTO request,
            @AuthenticationPrincipal Jwt jwt) {

        // Se pueden consultar directamente los claims verificados del token
        String userEmail = jwt.getClaimAsString("email");
        log.info("Creando orden para el usuario verificado: {}", userEmail);

        return ResponseEntity.ok(new OrderDTO());
    }
}
