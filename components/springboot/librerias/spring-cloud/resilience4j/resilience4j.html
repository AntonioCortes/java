Resilience4j y Circuit Breaker

En los sistemas distribuidos y arquitecturas de microservicios, los fallos de red y las caídas parciales son inevitables. Si el microservicio A llama al microservicio B, y este último se congela o sufre un bloqueo de base de datos, las peticiones que llegan a A se acumularán en memoria esperando respuesta (hilos bloqueados en sockets HTTP). En cuestión de segundos, A agotará su pool de conexiones de Tomcat y caerá, provocando una caída en cascada catastrófica que derriba a todos los servicios dependientes.

Resilience4j es una librería ligera y modular de tolerancia a fallos diseñada específicamente para Java funcional y Spring Boot. Actúa como el sucesor moderno y oficial de la descontinuada Netflix Hystrix, proporcionando implementaciones de alta velocidad de los patrones de resiliencia más importantes: Circuit Breaker, RateLimiter, Retry, Bulkhead y TimeLimiter.

La Máquina de Estados del Circuit Breaker

El patrón Circuit Breaker (Cortacircuitos) envuelve las llamadas protegidas y monitoriza su éxito o fracaso a través de una ventana deslizante (Sliding Window) en memoria. Opera bajo tres estados fundamentales:

  • CERRADO (Closed): El circuito está cerrado y la corriente fluye. Todas las llamadas se envían al microservicio remoto con normalidad. Mide la tasa de errores en las últimas N peticiones.
  • ABIERTO (Open): Si el porcentaje de fallos supera el umbral configurado (ej. 50% de errores o respuestas lentas), el circuito salta y se abre. Durante este estado, ninguna llamada física se envía a la red: falla de forma instantánea (Fail-Fast) y ejecuta de inmediato el método de contingencia (Fallback), evitando sobrecargar al servicio remoto agonizante.
  • SEMI-ABIERTO (Half-Open): Una vez transcurrido un periodo de enfriamiento (ej. 10 segundos), el circuito pasa a estado de prueba. Deja pasar un número pequeño y controlado de peticiones (ej. 5 llamadas):
    • Si esas 5 llamadas tienen éxito, asume que el servicio remoto se ha recuperado y el circuito vuelve a CERRADO.
    • Si alguna falla, el circuito vuelve inmediatamente a ABIERTO durante otro ciclo de enfriamiento.

Analogía del Mundo Real: El Interruptor Diferencial del Cuadro Eléctrico

Imagina los enchufes y electrodomésticos de tu hogar:

  • En una instalación sin protección (sin Circuit Breaker), si una tostadora defectuosa sufre un cortocircuito de 220V, los cables de las paredes se sobrecalientan al rojo vivo, la instalación se quema y el fuego se propaga a toda la casa (caída en cascada de microservicios).
  • En una casa moderna con Interruptor Magnetotérmico / Diferencial (el Circuit Breaker), en el microsegundo en que detecta la sobretensión, el interruptor salta con un chasquido mecánico y corta el paso de electricidad a la cocina (estado ABIERTO). El resto de la casa (el salón, el frigorífico, las luces) sigue funcionando con total normalidad.

Caso de Uso Real Estructurado

1. Contexto

En la tienda de mascotas (PetStore), el microservicio order-service se comunica con una pasarela bancaria externa para autorizar cobros con tarjeta durante las compras de adopción.

2. El Problema (Caída en Cascada)

La API del banco sufre una degradación y tarda 30 segundos en responder cada llamada. Cientos de clientes pulsan "Comprar" a la vez. En 10 segundos, todos los hilos de order-service quedan congelados esperando al banco. El servicio se queda sin memoria y se cae, impidiendo que nadie pueda ver el catálogo ni registrarse.

3. La Solución (Con Resilience4j)

Tras fallar 5 llamadas seguidas, el Circuit Breaker se abre en 1 milisegundo. Las siguientes peticiones no esperan los 30s del banco: ejecutan inmediatamente el método fallback, que responde al usuario: "Pago encolado con éxito. Le notificaremos por email".

¿Cuándo usarlo y cuándo NO usarlo?

Patrón de Resiliencia ¿Cuándo usarlo? ¿Cuándo NO usarlo?
Circuit Breaker Llamadas remotas de red a otros microservicios o APIs de terceros propensas a caídas, lentitud o cortes de conexión intermitentes. Llamadas a métodos locales dentro de la misma JVM o lecturas en memoria de variables estáticas (no hay latencia de red que justifique la sobrecarga).
Retry (Reintentos) Fallos transitorios muy breves de red (ej. un paquete TCP perdido o micro-corte de DNS de 50 milisegundos). Debe combinarse siempre con Backoff Exponencial. Errores deterministas de negocio (ej. código HTTP 400 Bad Request o 401 Unauthorized): reintentar 5 veces con la misma contraseña errónea solo empeora la carga.
RateLimiter (Control de Tasa) Proteger endpoints públicos contra abusos de peticiones por segundo (DDoS básico) o adaptarse a los límites de cuota de APIs de pago externas. Como único mecanismo de autenticación o seguridad perimetral.

Diagrama de Estados del Circuit Breaker

El siguiente diagrama ilustra el ciclo de vida y las transiciones automáticas entre los estados del circuito:

Figura 1: Transiciones de estado (Closed, Open, Half-Open) en Resilience4j
Transición Condición Desencadenante Efecto en el Sistema
Closed → Open Tasa de fallos > failureRateThreshold (ej. > 50%). El circuito corta el tráfico hacia la red y ejecuta métodos de Fallback en 0 milisegundos.
Open → Half-Open Transcurrido el tiempo waitDurationInOpenState (ej. 10s). Permite pasar un cupo de prueba (permittedNumberOfCallsInHalfOpenState).
Half-Open → Closed Las llamadas de prueba se completan con éxito. El servicio remoto se considera curado y se restablece el tráfico normal.

Configuración en application.yml


resilience4j:
  circuitbreaker:
    instances:
      paymentCircuitBreaker:
        # Tamaño de la ventana deslizante para calcular el porcentaje de fallos
        slidingWindowSize: 10
        # Porcentaje de fallo a partir del cual el circuito salta a OPEN (50%)
        failureRateThreshold: 50
        # Tiempo que permanece en estado OPEN antes de probar en HALF-OPEN
        waitDurationInOpenState: 10000ms
        # Número de peticiones de prueba permitidas en estado HALF-OPEN
        permittedNumberOfCallsInHalfOpenState: 3
        # Umbral de llamadas lentas (si tardan más de 2 segundos, se cuentan como fallo)
        slowCallDurationThreshold: 2000ms
        slowCallRateThreshold: 50
  retry:
    instances:
      paymentRetry:
        maxAttempts: 3
        waitDuration: 500ms
        enableExponentialBackoff: true
        exponentialBackoffMultiplier: 2

Implementación con @CircuitBreaker y Fallback


package com.example.orderservice.service;

import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker;
import io.github.resilience4j.retry.annotation.Retry;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Service;
import org.springframework.web.client.RestTemplate;

import java.math.BigDecimal;

@Slf4j
@Service
@RequiredArgsConstructor
public class PaymentProcessingService {

    private final RestTemplate restTemplate;

    // 1. Anotación de Circuit Breaker vinculada al nombre de la instancia en application.yml
    @CircuitBreaker(name = "paymentCircuitBreaker", fallbackMethod = "paymentFallback")
    @Retry(name = "paymentRetry")
    public String executePayment(Integer orderId, BigDecimal amount) {
        log.info("Llamando a la pasarela bancaria externa para orden ID: {} ({} €)...", orderId, amount);

        // Si la pasarela bancaria está caída o tarda más de 2s, salta la excepción
        String response = restTemplate.postForObject(
                "https://api.banco.com/v1/charge", 
                amount, 
                String.class);

        return response;
    }

    // 2. Método de contingencia (Fallback)
    // REGLA OBLIGATORIA: Debe tener la misma firma de parámetros que el método original más un parámetro Throwable
    public String paymentFallback(Integer orderId, BigDecimal amount, Throwable ex) {
        log.warn("¡CIRCUITO ACTIVADO! Fallo al procesar pago de orden {}: {}. Ejecutando contingencia.", 
                orderId, ex.getMessage());

        // Respuesta degradada elegante: se encola la transacción para reintento asíncrono en background
        return "PAGO_PENDIENTE_DE_CONFIRMACION";
    }
}

Ejemplo vs Contraejemplo

Contraejemplo: Reintentos Infinitos Inmediatos (Antipatrón Thundering Herd)


// ANTIPATRÓN: Bombardear un servidor colapsado con reintentos sin backoff
public void badExecutePayment() {
    int attempts = 0;
    while (attempts < 100) { // Bucle infinito agresivo
        try {
            callBank();
            break;
        } catch (Exception e) {
            attempts++; // Reintenta inmediatamente sin pausar ni medir fallos
            // ERROR: Si miles de clientes hacen esto a la vez, tiran definitivamente el servidor bancario
        }
    }
}

Ejemplo: Resiliencia Declarativa y Fallo Rápido


// BUENA PRÁCTICA: Falla rápido (Fail-Fast), no agota recursos y protege la experiencia del usuario
@CircuitBreaker(name = "paymentCircuitBreaker", fallbackMethod = "paymentFallback")
public String process() {
    return restTemplate.getForObject("http://BANCO-SERVICE/charge", String.class);
