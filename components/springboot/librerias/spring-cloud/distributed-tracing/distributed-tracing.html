Trazabilidad Distribuida: Micrometer Tracing y Zipkin

En una arquitectura monolítica, una petición de usuario se ejecuta íntegramente dentro de un único proceso de la JVM, por lo que una simple excepción en el archivo de log revela el recorrido completo. En cambio, en una arquitectura de microservicios, una sola acción del usuario (como comprar una mascota) desencadena una cascada de llamadas HTTP y mensajes asíncronos a través de múltiples servicios independientes (API Gateway, Servicio de Pedidos, Servicio de Mascotas, Pasarela de Pagos y RabbitMQ).

Si la petición falla o tarda 4 segundos en responder, determinar qué microservicio provocó el retardo o lanzó el error resulta imposible sin Trazabilidad Distribuida (Distributed Tracing).

En Spring Boot 3+, esta capacidad la proporciona Micrometer Tracing (sucesor oficial de Spring Cloud Sleuth en Spring Boot 2), que inyecta identificadores de correlación en las cabeceras HTTP (estándar W3C / B3) y exporta los datos de latencia a servidores de visualización como Zipkin u OpenTelemetry.

Analogía del Mundo Real: El Código de Seguimiento de un Paquete Internacional

Imagina que compras un producto en una tienda online en Japón con entrega en España:

  • A tu envío se le asigna un Número de Seguimiento Global (el Trace ID). Este número es único y acompaña al paquete durante todo su viaje por el mundo.
  • Cada tramo o escala individual del viaje (vuelo Tokio-Fráncfort, aduana de Madrid, furgoneta de reparto a tu casa) es un Paso o Tramo (el Span ID).
  • Si el paquete sufre un retraso de 3 días, no llamas a ciegas a cada cartero de cada ciudad: introduces el número de seguimiento global en la web del transportista (el Servidor Zipkin) y ves una línea temporal exacta que indica: "Aduana de Madrid: Retenido 72 horas". Identificas la causa raíz al segundo.

Caso de Uso Real Estructurado

1. Contexto

Un cliente finaliza una orden de compra en la tienda de mascotas. La petición viaja: Gateway → order-service → pet-service → base de datos PostgreSQL.

2. El Problema (Logs Aislados)

El cliente recibe un error 500. El equipo de soporte abre los logs de Gateway, order-service y pet-service por separado. Con cientos de peticiones por segundo, es imposible asociar qué línea de log de un servicio corresponde a la petición del cliente.

3. La Solución (Con Micrometer Tracing)

Todas las líneas de log de todos los microservicios incluyen automáticamente el mismo [traceId=a1b2c3d4]. En Zipkin se visualiza el diagrama de cascada mostrando que pet-service demoró 3.8s bloqueado en un bloqueo de tabla SQL.

¿Cuándo usarlo y cuándo NO usarlo?

Enfoque de Observabilidad ¿Cuándo usarlo? ¿Cuándo NO usarlo?
Micrometer Tracing + Zipkin / Jaeger Imprescindible en cualquier arquitectura de más de 2 microservicios. Permite auditoría de rendimiento, diagnóstico de latencia inter-servicio y correlación unificada de errores en logs centralizados (Elasticsearch / Grafana Loki). Aplicaciones monolíticas simples ejecutándose en un único servidor: no hay saltos de red distribuidos y basta con los logs locales.
Sampling al 100% (probability = 1.0) Entornos de desarrollo, pruebas y preproducción donde se desea capturar absolutamente cada llamada para depuración. Sistemas de producción masivos con decenas de miles de peticiones por segundo: el almacenamiento de Zipkin se saturaría. Se recomienda un muestreo del 5% al 10% (probability: 0.1).

Dependencias Necesarias (Spring Boot 3+)

En Spring Boot 3 se utiliza el puente Brave de Micrometer y el reporter de Zipkin:

Maven (pom.xml)


<!-- Starter Actuator para métricas y salud -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>

<!-- Puente de Micrometer Tracing hacia Brave (motor de trazabilidad de Zipkin) -->
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-brave</artifactId>
</dependency>

<!-- Emisor de spans hacia el servidor Zipkin vía HTTP -->
<dependency>
    <groupId>io.zipkin.reporter2</groupId>
    <artifactId>zipkin-reporter-brave</artifactId>
</dependency>

Gradle (build.gradle)


dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-actuator'
    implementation 'io.micrometer:micrometer-tracing-bridge-brave'
    implementation 'io.zipkin.reporter2:zipkin-reporter-brave'
}

Concepto Identificador Significado y Ámbito
Trace (Traza) traceId (ej. a1b2c3d4) El viaje completo de la petición desde que entra al sistema hasta que se completa. Permanece idéntico en todos los microservicios participantes.
Span (Tramo) spanId (ej. 1001, 2002) Una operación individual o bloque de trabajo dentro de un microservicio concreto (ej. llamada HTTP, consulta a base de datos o envío AMQP).
Parent Span parentId El identificador del span padre que originó la llamada, permitiendo a Zipkin reconstruir el árbol jerárquico de ejecución.

Formato de Logs con Correlación Automática

Al incluir las dependencias de Micrometer Tracing, Spring Boot configura automáticamente el MDC (Mapped Diagnostic Context) de Logback / SLF4J, añadiendo el nombre del servicio y los IDs en cada línea de log: 


# Formato: [Nombre-Servicio, TraceId, SpanId]
2026-10-22 21:05:10.123 INFO [order-service,a1b2c3d4e5f6,1001] c.e.o.service.OrderService : Iniciando proceso de orden
2026-10-22 21:05:10.180 INFO [pet-service,a1b2c3d4e5f6,2002] c.e.p.service.PetService     : Validando mascota ID 42 en BD
2026-10-22 21:05:10.210 INFO [order-service,a1b2c3d4e5f6,1001] c.e.o.service.OrderService : Orden completada con éxito

Configuración en application.yml


management:
  tracing:
    sampling:
      # Probabilidad de captura (1.0 = 100% de peticiones en dev / 0.1 = 10% en prod)
      probability: 1.0
  zipkin:
    tracing:
      # Endpoint URL del servidor Zipkin (puerto estándar 9411)
      endpoint: http://localhost:9411/api/v2/spans

logging:
  pattern:
    level: "%5p [${spring.application.name:},%X{traceId:-},%X{spanId:-}]"

Ejecución del Servidor Zipkin con Docker

Para arrancar el panel visual de Zipkin localmente en menos de 10 segundos: 


docker run -d -p 9411:9411 --name zipkin openzipkin/zipkin

Una vez iniciado, accede a http://localhost:9411/zipkin/ para inspeccionar y buscar trazas por servicio, duración o etiquetas.

Ejemplo vs Contraejemplo

Contraejemplo: Trazas Ciega sin Identificador Común (Antipatrón)


// ANTIPATRÓN: Generar UUIDs manuales y pasarlos por parámetro en cada método
public void crearOrden(OrderDTO order) {
    String manualUuid = UUID.randomUUID().toString(); // No se propaga por HTTP ni cabeceras automáticamente
    log.info("Orden " + manualUuid); // Requiere ensuciar cada firma de método con identificadores inventados
}

Ejemplo: Trazabilidad Transparente y Creación de Spans Personalizados


// BUENA PRÁCTICA: Inyección del Tracer de Micrometer para medir bloques de lógica pesados
package com.example.orderservice.service;

import io.micrometer.tracing.Span;
import io.micrometer.tracing.Tracer;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Service;

@Slf4j
@Service
@RequiredArgsConstructor
public class AuditedOrderService {

    private final Tracer tracer;

    public void procesarCalculoComplejo() {
        // Crea un nuevo Span secundario específico para medir este cálculo
        Span newSpan = tracer.nextSpan().name("calculo-tasas-adopcion").start();
        try (Tracer.SpanInScope ws = tracer.withSpan(newSpan.start())) {
            log.info("Ejecutando algoritmo matemático de tasas...");
            Thread.sleep(150); // Simulación de procesamiento
        } catch (Exception e) {
            newSpan.error(e);
        } finally {
            newSpan.end(); // El span se envía a Zipkin con su duración exacta
        }
    }
}
