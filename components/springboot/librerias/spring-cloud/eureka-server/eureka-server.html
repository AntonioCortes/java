Netflix Eureka Server y Client

En una arquitectura de microservicios en la nube, las instancias de los servicios se crean, destruyen, escalan y mueven de servidor de forma constante y dinámica. Asignar direcciones IP y puertos estáticos en archivos de configuración es inviable. Netflix Eureka es el sistema de Registro y Descubrimiento de Servicios (Service Discovery) por excelencia del ecosistema Spring Cloud.

Eureka opera bajo una arquitectura cliente-servidor:

  • Eureka Server: Actúa como un directorio telefónico vivo en memoria donde cada microservicio se registra al arrancar y envía avisos periódicos de actividad (heartbeats).
  • Eureka Client: Librería embebida en cada microservicio que se auto-registra en el servidor, envía latidos cada 30 segundos para renovar su concesión (lease) y descarga una copia local en caché de todas las instancias registradas en el clúster.

Analogía del Mundo Real: La Central de Radio de Taxis

Imagina una flota de taxis en una gran ciudad. Los usuarios (los clientes o microservicios consumidores) necesitan un taxi, pero los coches están en continuo movimiento por diferentes calles y barrios (IPs efímeras de contenedores).

En lugar de que cada cliente llame directamente al teléfono móvil privado de un taxista concreto (IP estática cableada):

  • Existe una Central de Radio y Despacho (el Eureka Server).
  • Cuando un taxista comienza su jornada, sintoniza la radio y dice: "Taxi 42 en servicio" (Auto-registro).
  • Cada minuto, el taxista pulsa el botón del micrófono para confirmar que sigue en ruta (Heartbeat). Si durante 90 segundos no emite señal, la central asume que tuvo una avería y lo retira de la lista de coches disponibles.
  • Cuando un usuario o un hotel solicita un taxi para ir al aeropuerto, consulta a la central cuál es la unidad más cercana y disponible en ese instante (Descubrimiento y Balanceo).

Caso de Uso Real Estructurado

1. Contexto

En la tienda de mascotas (PetStore), el microservicio order-service necesita invocar a pet-service para consultar el inventario de perros y gatos. Para soportar el Black Friday, pet-service escala automáticamente de 2 a 10 réplicas con puertos aleatorios.

2. El Problema (Sin Service Discovery)

Si order-service tuviera que conocer las 10 IPs de antemano, cualquier reinicio o fallo de una máquina requeriría reconfigurar y redesplegar todos los microservicios consumidores. Si una instancia cae, las peticiones dirigidas a su IP congelan el sistema.

3. La Solución (Con Eureka)

Cada una de las 10 réplicas de pet-service se registra automáticamente bajo el nombre lógico común PET-SERVICE. order-service consulta el catálogo de Eureka y reparte el tráfico únicamente entre las réplicas con estado de salud UP.

¿Cuándo usarlo y cuándo NO usarlo?

Solución de Descubrimiento ¿Cuándo usarlo? ¿Cuándo NO usarlo?
Netflix Eureka (Spring Cloud) Despliegues en máquinas virtuales (EC2, servidores propios), entornos híbridos, Docker Compose o arquitecturas nativas de Spring Boot donde se requiera balanceo inteligente en cliente (Client-Side Load Balancing) e integración directa con OpenFeign y Gateway. Sistemas con decenas de lenguajes distintos donde instalar clientes Java no sea posible, o cuando el orquestador subyacente ya gestione el descubrimiento de forma transparente.
Kubernetes DNS / Kube-Proxy Despliegues 100% sobre clústeres de Kubernetes: los Services de K8s proporcionan nombres DNS internos nativos (ej. http://pet-service:8080) con balanceo L4 por iptables o IPVS. Entornos sin Kubernetes (despliegues bare-metal, VPS sencillas) o cuando se requieran decisiones de balanceo complejas en cliente en función de metadatos o zonas de afinidad en Java.

Dependencias Necesarias

Para el Servidor Eureka (eureka-server)


<!-- Dependencia exclusiva del microservicio servidor de Eureka -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-netflix-eureka-server</artifactId>
</dependency>

Para los Microservicios Clientes (pet-service, order-service, gateway)


<!-- Dependencia en cualquier microservicio que deba registrarse o descubrir otros -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-netflix-eureka-client</artifactId>
</dependency>

Anotaciones y Configuración Clave

Anotaciones

  • @EnableEurekaServer: Se coloca sobre la clase principal @SpringBootApplication del proyecto servidor. Inicializa los controladores internos de Eureka, el motor de replicación peer-to-peer y el dashboard web.
  • @EnableDiscoveryClient: Se coloca sobre la clase principal de cualquier microservicio cliente para habilitar el auto-registro y el descubrimiento mediante la abstracción estándar de Spring Cloud (opcional en versiones modernas de Spring Boot si la dependencia está presente en el classpath).

Configuración del Servidor Eureka (application.yml en eureka-server)


server:
  port: 8761

spring:
  application:
    name: eureka-server

eureka:
  client:
    # Como este nodo es el servidor, NO debe intentar registrarse a sí mismo como cliente
    register-with-eureka: false
    # Tampoco debe intentar descargar el catálogo de sí mismo
    fetch-registry: false
    service-url:
      defaultZone: http://localhost:8761/eureka/
  server:
    # Tiempo de espera antes de eliminar instancias que dejaron de emitir heartbeat
    eviction-interval-timer-in-ms: 5000
    enable-self-preservation: true

Configuración del Microservicio Cliente (application.yml en pet-service)


server:
  port: 8081

spring:
  application:
    # Este nombre es el identificador lógico por el que otros microservicios buscarán este servicio
    name: pet-service

eureka:
  client:
    service-url:
      defaultZone: http://localhost:8761/eureka/
    fetch-registry: true
    register-with-eureka: true
  instance:
    # Prefiere registrar la dirección IP en lugar del hostname del contenedor
    prefer-ip-address: true
    lease-renewal-interval-in-seconds: 30
    lease-expiration-duration-in-seconds: 90

Implementación del Servidor Eureka


package com.example.eurekaserver;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.cloud.netflix.eureka.server.EnableEurekaServer;

@SpringBootApplication
@EnableEurekaServer
public class EurekaServerApplication {

    public static void main(String[] args) {
        SpringApplication.run(EurekaServerApplication.class, args);
    }
}

El Modo de Auto-Preservación (Self-Preservation Mode)

Una de las características más críticas de Eureka es el Modo de Auto-Preservación. Si durante un periodo de tiempo Eureka deja de recibir latidos de más del 15% de las instancias registradas, el servidor asume que ha ocurrido una partición de red entre él y los microservicios, y no que todas las instancias han muerto simultáneamente. En consecuencia, congela el catálogo y no elimina ninguna instancia, protegiendo las rutas para que los clientes puedan seguir intentando comunicarse.

Ejemplo vs Contraejemplo

Contraejemplo: Servidor Eureka con Bucles de Conexión Fallidos (Antipatrón)


# ANTIPATRÓN: Olvidar deshabilitar register-with-eureka en un servidor Eureka standalone
server:
  port: 8761
spring:
  application:
    name: eureka-server
# ERROR: Al no incluir 'register-with-eureka: false', el servidor intentará registrarse en sí mismo
# produciendo excepciones continuas de Connection Refused en el log de arranque.

Ejemplo: Configuración Limpia con Verificación de Salud


# BUENA PRÁCTICA: Configuración completa con IP preferida y puerto de Eureka claramente definido
server:
  port: 8761

spring:
  application:
    name: eureka-server

eureka:
  instance:
    hostname: localhost
  client:
    register-with-eureka: false
    fetch-registry: false
    service-url:
      defaultZone: http://${eureka.instance.hostname}:${server.port}/eureka/
