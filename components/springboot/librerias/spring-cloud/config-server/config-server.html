Spring Cloud Config: Servidor y Cliente de Configuración Centralizada

1. ¿Qué es y para qué sirve?

En una arquitectura de microservicios distribuida con decenas de aplicaciones independientes y múltiples entornos (desarrollo local, pruebas, preproducción y producción), gestionar archivos de configuración (application.yml o application.properties) empaquetados dentro del propio archivo JAR genera un grave acoplamiento operativo:

  • Cualquier cambio en una URL de base de datos, credencial, nivel de logging o parámetro de timeout exige recompilar el microservicio, generar una nueva imagen Docker y reiniciar el contenedor.
  • Es extremadamente difícil auditar quién cambió un parámetro, cuándo se modificó o volver a una versión previa sin recurrir a un despliegue completo de código.

Spring Cloud Config proporciona soporte cliente-servidor para almacenar y gestionar de forma centralizada la configuración externa de todas las aplicaciones de un sistema distribuido, desacoplando completamente el ciclo de vida del código del ciclo de vida de la configuración.

Analogía del mundo real: La Torre de Control y la Señal Horaria Central

Imaginemos una flota de 50 barcos navegando por el océano:

  • Sin Config Server: Cada barco tiene un reloj mecánico independiente dentro de la cabina. Si el almirantazgo decide cambiar la hora o la frecuencia de radio de auxilio, debe enviar una lancha a cada barco en alta mar para desmontar el panel de mandos y ajustar el reloj manualmente.
  • Con Spring Cloud Config: Hay un faro central (el Config Server) con una antena de radio. Cada barco (el Config Client), al zarpar, sintoniza la frecuencia del faro y sincroniza su hora y coordenadas. Si el faro emite una actualización, todos los barcos la reciben en directo sin detener su marcha.

2. Caso de Uso Real Estructurado

1. Contexto

Una plataforma de gestión de tiendas de mascotas y clínicas veterinarias compuesta por microservicios (pet-service, adoption-service, billing-service) desplegados en 4 entornos: local, dev, uat y prod.

2. El Problema

Modificar las tarifas de adopción o ajustar los límites de tiempo de reserva de mascotas requiere modificar el código fuente, pasar la batería completa de tests en CI/CD y redesplegar los servicios uno por uno.

3. La Solución

Todas las configuraciones residen en un repositorio Git centralizado. El administrador hace un git commit y git push con las nuevas tarifas y lanza un POST /actuator/refresh: la configuración se actualiza en memoria en milisegundos sin reiniciar.

3. ¿Cuándo usar Spring Cloud Config vs Alternativas?

Solución Ventajas ¿Cuándo usarlo? ¿Cuándo NO usarlo?
Spring Cloud Config Control de versiones Git nativo, cifrado simétrico/asimétrico, refresco dinámico con @RefreshScope y soporte multicapa. Ecosistemas basados fuertemente en Spring Boot, entornos híbridos (on-premise + cloud) o cuando se exige auditoría Git estricta de cambios de configuración. Monolitos simples con una sola instancia o cuando el equipo prefiere no mantener un microservicio adicional.
Kubernetes ConfigMaps y Secrets Nativo en la infraestructura del orquestador, agnóstico del lenguaje de programación. Plataformas 100% nativas en clústeres Kubernetes con servicios políglotas (Java, Go, Python, Node). Desarrollo local en máquina de desarrollador (difícil de simular sin clúster) o cuando se requiere refresco dinámico de Beans Java sin reiniciar pods.
HashiCorp Consul / Vault Alta disponibilidad distribuida, rotación automática de claves secretas y KV Store en memoria ultrarrápido. Sistemas con altos requerimientos de seguridad bancaria, rotación periódica de credenciales de base de datos y topología multi-datacenter. Equipos pequeños donde desplegar y operar un clúster de Consul/Vault supone una complejidad desproporcionada.

4. Dependencias del Proyecto (Maven y Gradle)

4.1. Para el Microservicio Servidor (Config Server)


<!-- pom.xml del Config Server -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-config-server</artifactId>
</dependency>


// build.gradle del Config Server
implementation 'org.springframework.cloud:spring-cloud-config-server'

4.2. Para los Microservicios Clientes (Config Clients)


<!-- pom.xml del Cliente -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-config</artifactId>
</dependency>
<!-- Para refresco dinámico sin reinicio -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>


// build.gradle del Cliente
implementation 'org.springframework.cloud:spring-cloud-starter-config'
implementation 'org.springframework.boot:spring-boot-starter-actuator'

5. Implementación del Config Server

5.1. Clase Principal con @EnableConfigServer

Para habilitar las capacidades de servidor de configuración solo es necesario añadir la anotación @EnableConfigServer: 


package com.example.configserver;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.cloud.config.server.EnableConfigServer;

@EnableConfigServer
@SpringBootApplication
public class ConfigServerApplication {

    public static void main(String[] args) {
        SpringApplication.run(ConfigServerApplication.class, args);
    }
}

5.2. Configuración del Servidor (application.yml)

El servidor se configura para apuntar al repositorio Git donde se encuentran los archivos YAML: 


server:
  port: 8888

spring:
  application:
    name: config-server
  cloud:
    config:
      server:
        git:
          uri: https://github.com/empresa/microservices-config-repo.git
          default-label: main
          clone-on-start: true
          # Para desarrollo local o carpetas del sistema de ficheros:
          # native:
          #   search-locations: classpath:/config,file:///opt/config

5.3. Convención de Nombres de Archivos en el Repositorio Central

El servidor expone configuraciones bajo el patrón de URL /{application}/{profile}[/{label}]. Los archivos en el repositorio Git siguen esta nomenclatura:

  • application.yml: Configuración compartida por todos los microservicios del ecosistema de la tienda de mascotas.
  • pet-service.yml: Configuración base específica del microservicio pet-service para todos sus entornos.
  • pet-service-dev.yml: Configuración de pet-service específica para el perfil dev (sobrescribe la base).
  • pet-service-prod.yml: Configuración de producción para pet-service.

6. Implementación del Config Client

6.1. Vinculación en Spring Boot 3.x (spring.config.import)

A partir de Spring Boot 2.4 y en todo Spring Boot 3.x, la conexión al Config Server se declara en el archivo application.yml del cliente mediante la directiva spring.config.import: 


# application.yml del Microservicio Cliente (Spring Boot 3.x)
spring:
  application:
    name: pet-service
  profiles:
    active: dev
  config:
    import: "optional:configserver:http://localhost:8888"

6.2. Vinculación Legacy en Spring Boot 2.x (bootstrap.yml)

En arquitecturas legadas de Spring Boot 2, el cliente utilizaba una fase previa de arranque configurada en bootstrap.yml: 


# bootstrap.yml (Legacy Spring Boot 2.x)
spring:
  application:
    name: pet-service
  profiles:
    active: local
  cloud:
    config:
      uri: http://localhost:8888
      fail-fast: true
      retry:
        initial-interval: 1500
        max-attempts: 5

7. Refresco en Caliente sin Reinicio: @RefreshScope

Por defecto, los Beans de Spring se instancian como Singleton al arrancar la aplicación y sus atributos inyectados mediante @Value o @ConfigurationProperties no vuelven a cambiar.

Anotando la clase con @RefreshScope (del paquete org.springframework.cloud.context.config.annotation.RefreshScope), Spring envuelve el Bean en un proxy dinámico: 


package com.example.petshop.service;

import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.cloud.context.config.annotation.RefreshScope;
import org.springframework.stereotype.Service;

@Slf4j
@Service
@RefreshScope
public class PetAdoptionPricingService {

    @Value("${petshop.adoption.fee-discount:0.10}")
    private double feeDiscount;

    @Value("${petshop.features.home-delivery-enabled:false}")
    private boolean homeDeliveryEnabled;

    public double calculateFinalAdoptionFee(double baseFee) {
        log.info("Calculando tarifa de adopción con descuento recargado: {}", feeDiscount);
        return baseFee * (1.0 - feeDiscount);
    }
}

Disparar el Refresco en Caliente vía Actuator

Una vez modificado el valor en el repositorio Git, se realiza una petición HTTP POST al endpoint del microservicio cliente: 


# Petición para forzar la recarga de propiedades en el cliente
curl -X POST http://localhost:8080/actuator/refresh

La respuesta HTTP devolverá un array JSON con las propiedades exactas que han sido actualizadas en memoria sin haber detenido el proceso Java ni una sola milésima de segundo.

8. Seguridad y Cifrado de Secretos ({cipher})

Almacenar contraseñas de base de datos o API keys en texto plano en repositorios Git es una mala práctica de seguridad crítica. Spring Cloud Config soporta cifrado simétrico (clave compartida) o asimétrico (par de claves pública/privada RSA). 


# pet-service-prod.yml en el repositorio Git central
spring:
  datasource:
    url: jdbc:postgresql://db.prod.internal:5432/petshopdb
    username: petshop_user
    # La contraseña está cifrada con la clave del Config Server:
    password: '{cipher}AQA7b9zY4K3J1u8...longCipherString...'

Cuando el microservicio cliente descarga la configuración, el Config Server descifra automáticamente el valor utilizando su clave privada y se lo entrega al cliente descifrado sobre una conexión segura TLS/HTTPS.
