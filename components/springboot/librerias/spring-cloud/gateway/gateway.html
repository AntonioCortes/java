Spring Cloud Gateway

En una arquitectura de microservicios, exponer cada servicio directamente a internet con su propia IP y puerto público es un antipatrón crítico: multiplica la superficie de ataque, obliga a los clientes web y móviles a conocer decenas de URLs y dificulta aplicar políticas globales de seguridad, CORS, autenticación y limitación de tasa (Rate Limiting).

Spring Cloud Gateway es el API Gateway reactivo oficial del ecosistema Spring Cloud. Construido sobre Spring WebFlux y el motor no bloqueante Netty (reemplazando al antiguo y bloqueante Netflix Zuul 1.x), actúa como el único punto de entrada perimetral (Single Point of Entry) para todas las peticiones externas, encargándose de enrutar el tráfico dinámicamente hacia los microservicios internos mediante integración nativa con Eureka.

Conceptos Fundamentales de Spring Cloud Gateway

El funcionamiento de Spring Cloud Gateway se basa en tres bloques constructivos:

  • Route (Ruta): La unidad básica de enrutamiento. Se define por un identificador único (ID), una URI de destino (ej. lb://PET-SERVICE), un conjunto de Predicates y una lista ordenada de Filters.
  • Predicate (Predicado / Condición): Una función booleana evaluada contra la petición HTTP entrante (usando la clase ServerWebExchange). Si el predicado devuelve true, la ruta coincide y se ejecuta. Ejemplos: coincidencia de ruta (Path), método HTTP (Method), cabeceras (Header) o parámetros de consulta (Query).
  • Filter (Filtro): Componentes interceptores que permiten inspeccionar o modificar la petición HTTP antes de enviarla al microservicio de destino (pre-filter), o alterar la respuesta HTTP antes de entregarla al cliente (post-filter). Ejemplos: añadir cabeceras, reescribir paths (RewritePath), recortar prefijos (StripPrefix) o conectar cortafuegos (CircuitBreaker).

Analogía del Mundo Real: La Aduana y Control de Pasaportes de un Aeropuerto

Imagina un aeropuerto internacional al que llegan miles de viajeros de todo el mundo:

  • En lugar de que los aviones aterricen en cualquier descampado sin control (exponer microservicios a lo loco a internet), todos los vuelos y pasajeros aterrizan en la Terminal Internacional Única (el API Gateway).
  • En los pasillos de control, los carteles y escáneres evalúan las condiciones de cada pasajero (los Predicados): "¿Viaja a la Unión Europea?", "¿Lleva equipaje de mano?".
  • Antes de dejar pasar a cada pasajero, los agentes aplican los controles (los Filtros): sellan la tarjeta de embarque, revisan la temperatura corporal y adjuntan una etiqueta de seguridad oficial (inyectar cabeceras X-User-Id).
  • Finalmente, la aduana indica la puerta de embarque interna hacia su destino nacional protegido (enrutamiento balanceado lb://PET-SERVICE).

Caso de Uso Real Estructurado

1. Contexto

La aplicación móvil de PetStore necesita consultar mascotas, tramitar pedidos y solicitar facturas a través de un único dominio público unificado: https://api.petstore.com.

2. El Problema (Sin API Gateway)

La App móvil tiene que gestionar 5 URLs distintas (pet.petstore.com:8081, order.petstore.com:8082, etc.). Si se cambia un puerto, hay que actualizar la App en Google Play y App Store. Hay que configurar CORS, SSL y autenticación en cada microservicio por separado.

3. La Solución (Con Spring Cloud Gateway)

Toda petición llega al puerto 8080 del Gateway. Las peticiones a /api/v1/pets/** se enrutan dinámicamente a las réplicas sanas de PET-SERVICE en Eureka, aplicando CORS centralizado y validación de tokens JWT en la frontera.

¿Cuándo usarlo y cuándo NO usarlo?

Solución de Gateway ¿Cuándo usarlo? ¿Cuándo NO usarlo?
Spring Cloud Gateway Estándar oficial para arquitecturas Spring Boot / Spring Cloud. Alto rendimiento asíncrono no bloqueante sobre Netty, integración nativa con Eureka (lb://), configuración declarativa en YAML o fluida en Java. Incompatible con spring-boot-starter-web tradicional (Tomcat) en el mismo proyecto: Spring Cloud Gateway requiere la pila reactiva de Spring WebFlux. No se deben mezclar dependencias de Tomcat y Gateway.
Netflix Zuul 1.x Proyectos legados muy antiguos de Spring Cloud (Zuul 1 usaba un hilo por conexión síncrona bloqueante). Completamente descontinuado y eliminado en versiones modernas de Spring Cloud.
NGINX / Kong / Envoy / Traefik Infraestructuras multinube o políglotas gestionadas por equipos de operaciones/DevOps independientes del código Java. Cuando se requiera implementar filtros complejos con lógica de negocio Java, inyección de beans de Spring o integración directa con el catálogo de Eureka.

Diagrama de Enrutamiento Perimetral

El siguiente diagrama muestra cómo Spring Cloud Gateway evalúa los predicados y aplica filtros antes de despachar a los microservicios:

Figura 1: Enrutamiento dinámico perimetral con Spring Cloud Gateway
Elemento Rol Responsabilidad Técnica
Frontend / SPA «cliente» Envía peticiones a la URL única del Gateway (ej. http://gateway:8080/api/v1/pets/1).
Route Predicate Handler «evaluador» Evalúa si la ruta coincide con Path=/api/v1/pets/** y el método HTTP.
GatewayFilter Factory «transformador» Reescribe la ruta mediante RewritePath, añade cabeceras seguras (X-Gateway-Trace) o aplica limitadores de tasa.
LoadBalancerClientFilter «enrutador lb://» Resuelve lb://PET-SERVICE en Eureka y reenvía el paquete HTTP a una instancia saludable.

Configuración Declarativa en application.yml


server:
  port: 8080

spring:
  application:
    name: api-gateway
  cloud:
    gateway:
      # Descubrimiento automático de rutas registradas en Eureka
      discovery:
        locator:
          enabled: true
          lower-case-service-id: true
      # Definición de rutas explícitas con predicados y filtros
      routes:
        # 1. Ruta para el microservicio de mascotas
        - id: pet-service-route
          uri: lb://PET-SERVICE
          predicates:
            - Path=/api/v1/pets/**
            - Method=GET,POST,PUT,DELETE
          filters:
            # Reescribe /api/v1/pets/5 -> /petshop/pet/5 antes de enviar al servicio interno
            - RewritePath=/api/v1/pets/(?<segment>.*), /petshop/pet/$\{segment}
            - AddRequestHeader=X-Gateway-Source, SpringCloudGateway

        # 2. Ruta para el microservicio de órdenes
        - id: order-service-route
          uri: lb://ORDER-SERVICE
          predicates:
            - Path=/api/v1/orders/**
          filters:
            - RewritePath=/api/v1/orders/(?<segment>.*), /orders/$\{segment}

      # Configuración global de CORS
      globalcors:
        cors-configurations:
          '[/**]':
            allowedOrigins: "https://www.tiendamascotas.com"
            allowedMethods:
              - GET
              - POST
              - PUT
              - DELETE
            allowedHeaders: "*"

Configuración Fluida en Código Java (RouteLocator)

Alternativamente, las rutas pueden definirse mediante código Java tipado: 


package com.example.gateway.config;

import org.springframework.cloud.gateway.route.RouteLocator;
import org.springframework.cloud.gateway.route.builder.RouteLocatorBuilder;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class GatewayRoutesConfig {

    @Bean
    public RouteLocator customRouteLocator(RouteLocatorBuilder builder) {
        return builder.routes()
                .route("pet_route_java", r -> r
                        .path("/api/v1/pets/**")
                        .filters(f -> f
                                .rewritePath("/api/v1/pets/(?<segment>.*)", "/petshop/pet/${segment}")
                                .addResponseHeader("X-Response-Engine", "Spring-Cloud-Gateway")
                        )
                        .uri("lb://PET-SERVICE")
                )
                .build();
    }
}

Filtro Global Personalizado (GlobalFilter)

Los filtros globales se ejecutan en todas y cada una de las rutas del Gateway, siendo ideales para medir latencias o registrar auditorías: 


package com.example.gateway.filter;

import lombok.extern.slf4j.Slf4j;
import org.springframework.cloud.gateway.filter.GatewayFilterChain;
import org.springframework.cloud.gateway.filter.GlobalFilter;
import org.springframework.core.Ordered;
import org.springframework.stereotype.Component;
import org.springframework.web.server.ServerWebExchange;
import reactor.core.publisher.Mono;

@Slf4j
@Component
public class LoggingGlobalFilter implements GlobalFilter, Ordered {

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        long startTime = System.currentTimeMillis();
        String path = exchange.getRequest().getURI().getPath();
        log.info("[GATEWAY REQUEST] {} {}", exchange.getRequest().getMethod(), path);

        // Continúa la cadena y ejecuta lógica de post-filtro al completar la respuesta
        return chain.filter(exchange).then(Mono.fromRunnable(() -> {
            long duration = System.currentTimeMillis() - startTime;
            log.info("[GATEWAY RESPONSE] {} completado en {} ms con estado {}", 
                    path, duration, exchange.getResponse().getStatusCode());
        }));
    }

    @Override
    public int getOrder() {
        return Ordered.LOWEST_PRECEDENCE;
    }
}
