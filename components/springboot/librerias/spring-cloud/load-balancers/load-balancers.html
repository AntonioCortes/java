Spring Cloud LoadBalancer

En las arquitecturas distribuidas de microservicios, una técnica fundamental para garantizar la alta disponibilidad y evitar cuellos de botella es el balanceo de carga en el lado cliente (Client-Side Load Balancing). En lugar de forzar a que todo el tráfico pase por un balanceador central de hardware o software intermedio (Server-Side Load Balancer, como un proxy inverso o un F5), el propio microservicio consumidor es quien conoce el catálogo de réplicas disponibles y decide a cuál de ellas enviar cada petición.

Spring Cloud LoadBalancer es la librería oficial, moderna y reactiva introducida por el equipo de Spring para reemplazar por completo a la biblioteca obsoleta y descontinuada Netflix Ribbon (eliminada a partir de Spring Cloud 2020.0).

Analogía del Mundo Real: El Repartidor de Cartas

Imagina una partida de póquer o de cartas en una mesa con varios jugadores (las Instancias del Servicio):

  • En un sistema de balanceo en servidor tradicional, todos los jugadores deberían hacer una fila en una única puerta central para que un portero les asigne un asiento de uno en uno (creando una cola masiva y un único punto de fallo).
  • En el balanceo en cliente con Spring Cloud LoadBalancer, el crupier o repartidor (el microservicio cliente) tiene a la vista a todos los jugadores y reparte las cartas de forma rotatoria una a una (Round-Robin): una carta para el jugador A, la siguiente para el B y la siguiente para el C. Si un jugador abandona la mesa (instancia caída informada por Eureka), el repartidor simplemente se lo salta y continúa con los demás sin detener la partida.

Caso de Uso Real Estructurado

1. Contexto

En la tienda de mascotas (PetStore), el servicio pet-service cuenta con 3 réplicas en los puertos 8081, 8082 y 8083 para atender miles de peticiones simultáneas de adopción.

2. El Problema (Sin Balanceo o con Ribbon Obsoleto)

Sin balanceador, el cliente siempre invoca la primera IP que responde, saturando la réplica 8081 mientras las otras dos están inactivas. Usar la antigua librería Ribbon genera incompatibilidades con Spring Boot 3 y bloquea hilos de forma síncrona innecesaria.

3. La Solución (Con Spring Cloud LoadBalancer)

El cliente consulta la lista viva en Eureka y distribuye uniformemente un 33.3% del tráfico a cada instancia mediante algoritmos reactivos no bloqueantes, aislando automáticamente cualquier nodo que falle.

¿Cuándo usarlo y cuándo NO usarlo?

Mecanismo de Balanceo ¿Cuándo usarlo? ¿Cuándo NO usarlo?
Spring Cloud LoadBalancer (Lado Cliente) Comunicación interna servicio a servicio (East-West traffic). Elimina el salto de red adicional hacia un balanceador intermedio, evita cuellos de botella de hardware y permite decisiones de enrutamiento personalizadas en Java (zonas de afinidad, versiones canary). Tráfico externo procedente de internet (North-South traffic). Los usuarios anónimos en sus navegadores no pueden ejecutar Spring Cloud LoadBalancer y requieren un API Gateway o balanceador perimetral.
Server-Side Load Balancer (AWS ALB / NGINX / F5) Punto de entrada perimetral público para recibir el tráfico de internet hacia el API Gateway o aplicaciones monolíticas. Para cada salto interno entre 50 microservicios: multiplicar saltos de balanceadores de red físicos incrementa drásticamente la latencia y los costes de infraestructura.

Dependencias Necesarias


<!-- Starter oficial de Spring Cloud LoadBalancer -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-loadbalancer</artifactId>
</dependency>

Nota: Si tu proyecto ya incluye spring-cloud-starter-openfeign o spring-cloud-starter-gateway, la dependencia de LoadBalancer ya viene incluida transitivamente por defecto.

Anotación @LoadBalanced

La anotación @LoadBalanced (paquete org.springframework.cloud.client.loadbalancer.LoadBalanced) se coloca sobre un método @Bean que retorna un RestTemplate o un WebClient.Builder.

Su función es inyectar un Interceptor de Cliente HTTP (LoadBalancerInterceptor) que traduce el nombre lógico del host (ej. http://PET-SERVICE/api/...) a la dirección IP física y puerto de una instancia concreta antes de emitir la trama por el socket de red.

Implementación con RestTemplate y WebClient

Paso 1: Definir los Beans Balanceados


package com.example.orderservice.config;

import org.springframework.cloud.client.loadbalancer.LoadBalanced;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.client.RestTemplate;
import org.springframework.web.reactive.function.client.WebClient;

@Configuration
public class LoadBalancerConfig {

    // 1. RestTemplate tradicional con balanceo automático
    @Bean
    @LoadBalanced
    public RestTemplate loadBalancedRestTemplate() {
        return new RestTemplate();
    }

    // 2. WebClient reactivo moderno con balanceo automático
    @Bean
    @LoadBalanced
    public WebClient.Builder loadBalancedWebClientBuilder() {
        return WebClient.builder();
    }
}

Paso 2: Consumo en la Capa de Servicio


package com.example.orderservice.service;

import com.example.orderservice.dto.PetDTO;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Service;
import org.springframework.web.client.RestTemplate;

@Slf4j
@Service
@RequiredArgsConstructor
public class PetDiscoveryService {

    private final RestTemplate restTemplate;

    public PetDTO fetchPetBalanced(Integer petId) {
        // En lugar de IP física, se usa el nombre lógico registrado en Eureka
        String serviceUrl = "http://PET-SERVICE/petshop/pet/" + petId;

        log.info("Llamando a URL balanceada: {}", serviceUrl);
        // LoadBalancer sustituye 'PET-SERVICE' por '10.0.1.5:8081', '10.0.1.6:8082', etc.
        return restTemplate.getForObject(serviceUrl, PetDTO.class);
    }
}

Algoritmos de Balanceo Soportados

  • Round-Robin (Por defecto): Reparto estrictamente circular y equitativo. Cada llamada se entrega a la siguiente instancia de la lista ordenada.
  • Random: Elección pseudo-aleatoria de instancia. Útil en escenarios donde el número de peticiones es muy elevado y estadísticamente el reparto resulta homogéneo sin necesidad de sincronización atómica de contadores.

Configuración en application.yml


spring:
  cloud:
    loadbalancer:
      ribbon:
        enabled: false # Deshabilita Ribbon explícitamente en proyectos heredados
      cache:
        enabled: true
        ttl: 35s # Duración de la caché local de instancias de Eureka
      health-check:
        interval: 25s # Frecuencia de comprobación de salud de instancias

Ejemplo: Configuración Limpia con Spring Cloud LoadBalancer


// BUENA PRÁCTICA: Inyección del Builder balanceado reactivo
@Service
public class OrderService {

    private final WebClient webClient;

    public OrderService(@LoadBalanced WebClient.Builder builder) {
        this.webClient = builder.baseUrl("http://PET-SERVICE").build();
    }

    public PetDTO getPet(Integer id) {
        return webClient.get()
                .uri("/petshop/pet/{id}", id)
                .retrieve()
                .bodyToMono(PetDTO.class)
                .block();
    }
}
