Spring Data: Arquitectura y Modelado de Datos (Relacional vs NoSQL)

1. ¿Qué es Spring Data y para qué sirve?

Spring Data es un proyecto paraguas dentro del ecosistema de Spring cuya misión es proporcionar un modelo de acceso a datos consistente, unificado y desacoplado de la tecnología de almacenamiento subyacente. A través de su núcleo común (Spring Data Commons), estandariza interfaces de repositorio (como Repository, CrudRepository o PagingAndSortingRepository), derivación automática de consultas a partir de firmas de métodos, evaluación de expresiones de paginación y ordenación, y mecanismos de auditoría automatizada.

Analogía del mundo real

Imaginemos un sistema internacional de enchufes modulares: la clavija interna (el cargador del dispositivo o código de negocio) siempre tiene la misma interfaz estándar, pero al viajar a diferentes países (bases de datos relacionales, almacenes de documentos o caches en memoria) solo necesitamos encajar el adaptador adecuado (el starter de Spring Data JPA, Spring Data MongoDB o Spring Data Redis). El dispositivo sigue recibiendo electricidad sin necesidad de reescribir su circuitería interna.

Caso de uso real estructurado

  • Contexto: Sistema de gestión clínica veterinaria donde se registran mascotas (Pet), sus propietarios y su historial médico.
  • El Problema (Sin Spring Data): Desarrollar a mano código JDBC repetitivo (boilerplate), abrir y cerrar conexiones, mapear manualmente ResultSet a objetos Java, gestionar transacciones con commits manuales y reescribir consultas SQL específicas para cada motor (PostgreSQL vs Oracle vs MongoDB).
  • La Solución (Con Spring Data): Definir entidades mediante anotaciones estándar, declarar una interfaz que extienda de JpaRepository o MongoRepository y dejar que el framework autogenere en tiempo de ejecución las implementaciones óptimas, soporte de transacciones y optimizaciones de consulta.
Figura 1: Arquitectura unificada de Spring Data Commons hacia persistencia Relacional y Documental
Criterio Bases de Datos Relacionales (JPA / PostgreSQL / Oracle) Bases de Datos NoSQL Documentales (MongoDB)
Modelo de Datos Tablas rígidas, filas, columnas y claves foráneas (integridad referencial). Colecciones y documentos BSON/JSON jerárquicos (esquema flexible y polimórfico).
Normalización vs Desnormalización Normalización (evitar redundancia mediante joins y tablas intermedias). Desnormalización (embebido de subdocumentos para lectura en un único acceso).
Garantías Transaccionales ACID estricto de forma nativa a nivel de motor. Atomicidad por documento; soporte de transacciones multi-documento mediante Replica Sets.
Cuándo usarlo Dominios con reglas de negocio estrictas, relaciones complejas muchos a muchos y reportes analíticos con joins. Catálogos cambiantes, eventos, registros médicos anidados, alta tasa de escritura o escalabilidad horizontal masiva.
Cuándo NO usarlo Datos no estructurados con atributos altamente volátiles o esquemas que mutan a diario. Sistemas bancarios o contables que exigen integridad referencial rígida y claves foráneas en cascada.

3. Modelado de Datos: Mismo Caso de Uso en Relacional y NoSQL

Para garantizar máxima claridad y coherencia en toda la documentación, modelamos exactamente la misma entidad de negocio (la mascota Pet de nuestra clínica veterinaria) en ambos paradigmas con sus respectivos atributos: identificador, nombre, especie, edad, estado de vacunación y fecha de admisión.

3.1. Modelo Relacional (JPA con PostgreSQL)

En bases de datos relacionales estándar como PostgreSQL, la entidad se mapea a una tabla física (pets) mediante @Entity y @Table. La clave primaria utiliza la estrategia GenerationType.IDENTITY apoyada en columnas BIGSERIAL o GENERATED ALWAYS AS IDENTITY. El atributo booleano se persiste de forma nativa en una columna de tipo BOOLEAN. 


package com.example.petshop.model.relational;

import jakarta.persistence.*;
import lombok.*;
import java.time.LocalDate;

@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
@ToString
@EqualsAndHashCode(onlyExplicitlyIncluded = true)
@Entity
@Table(name = "pets")
public class PetEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @EqualsAndHashCode.Include
    private Long id;

    @Column(name = "name", nullable = false, length = 100)
    private String name;

    @Column(name = "species", nullable = false, length = 50)
    private String species;

    @Column(name = "age", nullable = false)
    private int age;

    @Column(name = "vaccinated", nullable = false)
    private boolean vaccinated;

    @Column(name = "admission_date", nullable = false)
    private LocalDate admissionDate;
}

3.2. Particularidad de Dialecto: Adaptación para Oracle Database

En bases de datos Oracle (especialmente versiones anteriores a 23c), existen dos diferencias arquitectónicas críticas frente a PostgreSQL:

  1. Inexistencia de tipo SQL BOOLEAN nativo: Las columnas para valores lógicos se definen típicamente como CHAR(1) con restricciones de chequeo CHECK (VACCINATED IN ('Y', 'N')) o ('T', 'F'). En Java se resuelve limpiamente mediante un conversor JPA (AttributeConverter).
  2. Estrategia de Secuencias (GenerationType.SEQUENCE): Oracle gestiona los identificadores mediante secuencias independientes creadas en el esquema (CREATE SEQUENCE PET_SEQ START WITH 1 INCREMENT BY 1), requiriendo @SequenceGenerator.
Figura 2: Adaptación del tipo Boolean a CHAR(1) y generación por secuencia para Oracle DB 

package com.example.petshop.converter;

import jakarta.persistence.AttributeConverter;
import jakarta.persistence.Converter;

/**
 * Conversor JPA para compatibilidad con Oracle DB:
 * Mapea Boolean de Java a CHAR(1) ('Y' o 'N') en la base de datos.
 */
@Converter(autoApply = false)
public class BooleanToCharConverter implements AttributeConverter<Boolean, String> {

    @Override
    public String convertToDatabaseColumn(Boolean attribute) {
        if (attribute == null) {
            return "N";
        }
        return attribute ? "Y" : "N";
    }

    @Override
    public Boolean convertToEntityAttribute(String dbData) {
        if (dbData == null) {
            return false;
        }
        return "Y".equalsIgnoreCase(dbData.trim()) || "T".equalsIgnoreCase(dbData.trim()) || "1".equals(dbData.trim());
    }
}

Entidad adaptada para Oracle utilizando la secuencia y el conversor: 


package com.example.petshop.model.oracle;

import com.example.petshop.converter.BooleanToCharConverter;
import jakarta.persistence.*;
import lombok.*;
import java.time.LocalDate;

@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
@ToString
@EqualsAndHashCode(onlyExplicitlyIncluded = true)
@Entity
@Table(name = "PETS")
public class PetOracleEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "pet_seq_gen")
    @SequenceGenerator(
        name = "pet_seq_gen",
        sequenceName = "PET_SEQ",
        allocationSize = 1 // allocationSize = 1 evita saltos de números en la secuencia
    )
    @EqualsAndHashCode.Include
    private Long id;

    @Column(name = "NAME", nullable = false, length = 100)
    private String name;

    @Column(name = "SPECIES", nullable = false, length = 50)
    private String species;

    @Column(name = "AGE", nullable = false)
    private int age;

    @Convert(converter = BooleanToCharConverter.class)
    @Column(name = "VACCINATED", nullable = false, length = 1)
    private boolean vaccinated;

    @Column(name = "ADMISSION_DATE", nullable = false)
    private LocalDate admissionDate;
}

3.3. Modelo Documental (MongoDB con Spring Data MongoDB)

En MongoDB, no existen tablas ni columnas rígidas. La clase se marca con @Document(collection = "pets") y su identificador suele ser un String (que almacena un ObjectId de 12 bytes en hexadecimal). Los tipos booleanos son ciudadanos de primera clase en BSON (formato binario de JSON), y si la mascota tiene detalles clínicos complementarios, se modelan como un subdocumento embebido sin requerir una tabla intermedia. 


package com.example.petshop.model.nosql;

import lombok.*;
import org.springframework.data.annotation.Id;
import org.springframework.data.mongodb.core.mapping.Document;
import org.springframework.data.mongodb.core.mapping.Field;
import java.time.LocalDate;

@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
@ToString
@EqualsAndHashCode(onlyExplicitlyIncluded = true)
@Document(collection = "pets")
public class PetDocument {

    @Id
    @EqualsAndHashCode.Include
    private String id;

    @Field("name")
    private String name;

    @Field("species")
    private String species;

    @Field("age")
    private int age;

    @Field("vaccinated")
    private boolean vaccinated;

    @Field("admissionDate")
    private LocalDate admissionDate;
}

4. Contraejemplos y Antipatrones de Modelado

Contraejemplo 1: Simular relaciones relacionales con @DBRef en MongoDB

Intentar usar MongoDB como si fuera una base de datos relacional vinculando documentos mediante @DBRef provoca llamadas en cascada del cliente, perdiendo el beneficio de la lectura en una sola operación. 


// ANTIPATRÓN: Destruye el rendimiento en MongoDB simulando joins
@Document(collection = "pets")
public class BadPetDocument {
    @Id
    private String id;
    
    // Provoca consultas cliente adicionales para resolver cada referencia
    @DBRef
    private OwnerDocument owner; 
}

Contraejemplo 2: Almacenar JSON no indexado en columnas de texto relacionales sin necesidad


// ANTIPATRÓN: Guardar un string JSON en columna VARCHAR sin tipos nativos JSONB
@Entity
@Table(name = "pets")
public class BadPetEntity {
    @Id
    private Long id;
    
    // Impide índices eficientes, validaciones de esquema y consultas sobre campos anidados
    @Column(name = "extra_data_json", length = 4000)
    private String rawJsonPayload;
}

6. Tipos Avanzados de PostgreSQL con Hypersistence Utils (Hibernate Types)

Bases de datos avanzadas como PostgreSQL ofrecen tipos de datos nativos extraordinariamente potentes que no existen en el estándar ANSI SQL básico ni en la especificación genérica de JPA:

  • Tipo inet / cidr: Diseñado específicamente para almacenar y validar direcciones de red IPv4 e IPv6 con operadores nativos de contención de subredes.
  • Tipo jsonb: Formato JSON binario descompuesto que soporta indexación avanzada (índices GIN) y consultas ultra-rápidas sobre campos internos sin parsear el texto completo.
  • Arrays SQL nativos (integer[], varchar[], short[]): Almacenan colecciones simples en una sola columna sin necesidad de crear tablas secundarias ni joins adicionales.

Por defecto, Hibernate estándar no reconoce estos tipos nativos y lanza errores de mapeo o intenta serializarlos como BLOBs binarios opacos de Java. La solución estándar en el ecosistema Java es la librería Hypersistence Utils (antiguamente conocida como hibernate-types, creada por Vlad Mihalcea).

6.1. Analogía del Mundo Real: El Adaptador Trifásico Industrial

Imaginemos un taller donde la red eléctrica doméstica proporciona enchufes normales de 220V (los tipos SQL estándar: VARCHAR, INTEGER, TIMESTAMP). Para conectar una máquina de corte por plasma industrial (el tipo jsonb o inet nativo de PostgreSQL), no puedes forzar la clavija en un enchufe estándar; necesitas un adaptador trifásico industrial de alta precisión (Hypersistence Utils) que conecte la máquina directamente a la potencia del cuadro sin recalentar la instalación ni perder rendimiento.

6.3. Ejemplo de Entidad con Tipos Avanzados de PostgreSQL

A continuación se ilustra una entidad de dispositivo collar IoT de monitorización veterinaria para mascotas que almacena la dirección IP del dispositivo en una columna inet, un array nativo de banderas de alerta biomédica y un payload jsonb con la telemetría y calibración de sensores: 


package com.example.petshop.model.device;

import io.hypersistence.utils.hibernate.type.array.ShortArrayType;
import io.hypersistence.utils.hibernate.type.basic.PostgreSQLInet;
import io.hypersistence.utils.hibernate.type.basic.PostgreSQLInetType;
import io.hypersistence.utils.hibernate.type.json.JsonType;
import jakarta.persistence.*;
import lombok.*;
import org.hibernate.annotations.Type;

import java.io.Serializable;
import java.util.Map;

@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
@ToString
@EqualsAndHashCode(onlyExplicitlyIncluded = true)
@Entity
@Table(name = "pet_health_devices")
public class PetHealthDeviceEntity implements Serializable {

    private static final long serialVersionUID = 1L;

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @EqualsAndHashCode.Include
    private Long id;

    @Column(name = "pet_id", nullable = false)
    private Long petId;

    @Column(name = "device_serial", nullable = false, length = 50)
    private String deviceSerial;

    // Columna nativa de tipo 'inet' de PostgreSQL para la IP del collar inteligente
    @Type(PostgreSQLInetType.class)
    @Column(name = "ip_address", columnDefinition = "inet")
    private PostgreSQLInet ipAddress;

    // Columna de tipo array SQL nativo 'smallint[]' de PostgreSQL para códigos de alerta cardíaca/térmica
    @Type(ShortArrayType.class)
    @Column(name = "alert_flags", columnDefinition = "smallint[]")
    private short[] alertFlags;

    // Columna binaria 'jsonb' con índice GIN en PostgreSQL para parámetros de calibración de sensores
    @Type(JsonType.class)
    @Column(name = "telemetry_settings", columnDefinition = "jsonb")
    private Map<String, Object> telemetrySettings;
}

6.4. Consultas en Spring Data JPA con Claves Compuestas

Cuando se define un repositorio para una entidad con @EmbeddedId (como la pauta de vacunación PetVaccinationScheduleEntity), la clave primaria se parametriza con el tipo de la clase embebida: 


package com.example.petshop.repository;

import com.example.petshop.model.PetVaccinationScheduleEntity;
import com.example.petshop.model.PetVaccinationScheduleId;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.stereotype.Repository;

import java.util.List;

@Repository
public interface PetVaccinationScheduleRepository extends JpaRepository<PetVaccinationScheduleEntity, PetVaccinationScheduleId> {

    // Navegación dentro del objeto embebido @EmbeddedId (id.petId)
    List<PetVaccinationScheduleEntity> findByIdPetId(Long petId);

    // Consulta por mascota y vacuna concreta (id.petId e id.vaccineCode)
    List<PetVaccinationScheduleEntity> findByIdPetIdAndIdVaccineCode(Long petId, String vaccineCode);
}
