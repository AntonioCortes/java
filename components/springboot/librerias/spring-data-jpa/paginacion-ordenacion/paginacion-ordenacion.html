Spring Data: Paginación y Ordenación (Pageable, Page, Slice y Sort)

1. Fundamentos: Por qué la paginación es obligatoria en producción

En aplicaciones empresariales, realizar consultas que devuelvan listas ilimitadas (List<T>) sobre tablas con miles o millones de registros es una de las causas más frecuentes de caídas por OutOfMemoryError (OOM) en la JVM y de saturación de buffers de red y memoria compartida en la base de datos.

Spring Data estandariza la paginación y ordenación en todos sus módulos a través de:

  • Sort: Define uno o múltiples criterios de ordenación (campo, dirección ascendente/descendente, tratamiento de nulos).
  • Pageable: Interfaz que encapsula la petición de paginación (número de página con base 0, tamaño de página y objeto Sort).
  • PageRequest: Implementación canónica creada mediante métodos estáticos de factoría como PageRequest.of(page, size, sort).

2. Las Tres Opciones de Retorno en Spring Data

Spring Data permite devolver tres tipos de estructuras según los requerimientos de la vista o del proceso:

Tipo de Retorno Consultas Ejecutadas en la BD Metadatos Proporcionados Cuándo Usarlo Cuándo NO Usarlo
Page<T> 2 consultas:
1. SELECT ... LIMIT ? OFFSET ?
2. SELECT COUNT(*) FROM ... 		- getTotalElements() (total absoluto de filas)
- getTotalPages() (total de páginas)
- getNumber(), getSize()
- isFirst(), isLast() 		Vistas web tradicionales de backoffice con barra de paginación numérica ("Página 1 de 20") donde el usuario salta a páginas intermedias. Colecciones gigantescas (> 500.000 filas) con alta tasa de escritura. El SELECT COUNT(*) fuerza un escaneo de índice/tabla bloqueante.
Slice<T> 1 única consulta:
Solicita size + 1 elementos.
¡NO hace COUNT(*)! 		- hasNext() (indica si hay más datos)
- hasPrevious()
- getNumber(), getSize() 		Scroll infinito, feeds móviles, aplicaciones reactivas y procesamiento por bloques (batches). Ahorra un 50% de las consultas a la BD. Interfaces donde el usuario necesite conocer de antemano el número total de páginas o elementos existentes.
List<T> con Pageable 1 única consulta:
Aplica únicamente el LIMIT y OFFSET. 		Ninguno. Solo la lista plana de elementos de la página actual. Servicios internos o APIs REST simples que reciben limit y offset sin requerir metadatos de envoltura en el JSON. Vistas interactivas donde el cliente necesite saber si existen más páginas siguientes.

3. Traducción de Dialectos SQL vs NoSQL

Al solicitar la página 2 con tamaño 10 (PageRequest.of(2, 10), es decir, saltar 20 elementos y tomar 10):

  • PostgreSQL / MySQL: Genera LIMIT 10 OFFSET 20.
  • Oracle Database (12c+): Genera OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY.
  • MongoDB: Genera operaciones nativas del cursor: .skip(20).limit(10).

4. Ejemplos Prácticos Completos y Simétricos

A continuación se ilustra la implementación de los repositorios y de los servicios de negocio que consumen la paginación, comparando JPA y MongoDB con el mismo dominio Pet.

4.1. Persistencia Relacional: PostgreSQL / Oracle (Spring Data JPA)

Interfaz de Repositorio JPA:


package com.example.petshop.repository.relational;

import com.example.petshop.model.relational.PetEntity;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Slice;
import org.springframework.data.domain.Sort;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.stereotype.Repository;

import java.util.List;

@Repository
public interface PetPagingJpaRepository extends JpaRepository<PetEntity, Long> {

    // 1. Paginación completa con conteo total (Page)
    Page<PetEntity> findBySpecies(String species, Pageable pageable);

    // 2. Paginación optimizada sin conteo para scroll infinito (Slice)
    Slice<PetEntity> findByVaccinated(boolean vaccinated, Pageable pageable);

    // 3. Paginación directa a lista simple sin metadatos
    List<PetEntity> findByAgeGreaterThan(int age, Pageable pageable);

    // 4. Solo ordenación sin paginar
    List<PetEntity> findBySpecies(String species, Sort sort);
}

Capa de Servicio JPA:


package com.example.petshop.service.relational;

import com.example.petshop.model.relational.PetEntity;
import com.example.petshop.repository.relational.PetPagingJpaRepository;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Slice;
import org.springframework.data.domain.Sort;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Slf4j
@RequiredArgsConstructor
@Service
@Transactional(readOnly = true)
public class PetPagingJpaService {

    private final PetPagingJpaRepository petRepository;

    public void demonstratePagination() {
        // A. Petición con Page: Página 0, 10 elementos por página, ordenados por fecha de admisión descendente
        PageRequest pageRequest = PageRequest.of(0, 10, Sort.by(Sort.Direction.DESC, "admissionDate"));
        Page<PetEntity> petPage = petRepository.findBySpecies("Dog", pageRequest);

        log.info("Elementos en página actual: {}", petPage.getNumberOfElements());
        log.info("Total absoluto de perros en BD: {}", petPage.getTotalElements());
        log.info("Total de páginas disponibles: {}", petPage.getTotalPages());

        // B. Petición con Slice: Página 0, 20 elementos, ordenados alfabéticamente por nombre
        PageRequest sliceRequest = PageRequest.of(0, 20, Sort.by("name").ascending());
        Slice<PetEntity> petSlice = petRepository.findByVaccinated(true, sliceRequest);

        log.info("¿Hay más páginas siguientes?: {}", petSlice.hasNext());
        // petSlice NO ejecuta COUNT(*), reduciendo drásticamente el consumo de CPU en la BD
    }
}

Capa de Servicio MongoDB:


package com.example.petshop.service.nosql;

import com.example.petshop.model.nosql.PetDocument;
import com.example.petshop.repository.nosql.PetPagingMongoRepository;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Slice;
import org.springframework.data.domain.Sort;
import org.springframework.stereotype.Service;

@Slf4j
@RequiredArgsConstructor
@Service
public class PetPagingMongoService {

    private final PetPagingMongoRepository petRepository;

    public void demonstratePagination() {

        PageRequest pageRequest = PageRequest.of(0, 10, Sort.by(Sort.Direction.DESC, "admissionDate"));

        log.info("Total absoluto de documentos en colección: {}", petPage.getTotalElements());
        log.info("Total de páginas disponibles: {}", petPage.getTotalPages());

        // B. Petición idéntica con Slice en MongoDB (.skip(0).limit(21))
        PageRequest sliceRequest = PageRequest.of(0, 20, Sort.by("name").ascending());
        Slice<PetDocument> petSlice = petRepository.findByVaccinated(true, sliceRequest);

        log.info("¿Hay más documentos siguientes?: {}", petSlice.hasNext());
    }
}

5. Contraejemplos y Errores Habituales de Paginación

Contraejemplo 1: Usar Page<T> para Scroll Infinito en Tablas Masivas

En un scroll infinito de una aplicación móvil con 2 millones de registros, invocar Page<T> fuerza a la base de datos a ejecutar SELECT COUNT(*) en cada solicitud de carga. La base de datos relacional gastará hasta el 80% de su tiempo recalculando el total de filas que el usuario nunca llegará a ver en pantalla.

Solución: Cambiar la firma de retorno en el repositorio a Slice<T>.

Contraejemplo 2: Paginación con Desplazamientos Gigantes (Deep Paging)

Ejecutar PageRequest.of(10000, 50) en SQL genera OFFSET 500000 LIMIT 50. La base de datos debe escanear y descartar 500.000 filas en memoria antes de devolver las 50 solicitadas.

Solución: Para colecciones masivas, implementar Keyset Pagination (paginación por cursor) utilizando condiciones de orden: WHERE id > :lastSeenId ORDER BY id ASC LIMIT 50.
