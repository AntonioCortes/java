Spring Data: Rendimiento, Problema N+1 y Concurrencia

1. ¿Qué es el Problema N+1 en Bases de Datos Relacionales?

El problema N+1 es una de las anomalías de rendimiento más destructivas en aplicaciones que utilizan JPA y Hibernate. Ocurre cuando el código recupera una lista de N entidades principales y luego, al acceder a una relación secundaria (generalmente configurada con carga perezosa FetchType.LAZY), Hibernate emite de forma automática N consultas SQL adicionales individuales para cargar los datos de cada elemento secundario.

Demostración del Fallo N+1 en Logs SQL

Supongamos una entidad propietario (OwnerEntity) con una relación @OneToMany hacia sus mascotas (PetEntity). Al ejecutar ownerRepository.findAll() sobre 100 propietarios: 


-- Consulta inicial 1 (obtiene 100 propietarios):
SELECT * FROM owners;

-- Hibernate ejecuta 100 consultas secundarias al acceder a owner.getPets():
SELECT * FROM pets WHERE owner_id = 1;
SELECT * FROM pets WHERE owner_id = 2;
SELECT * FROM pets WHERE owner_id = 3;
-- ... [97 consultas más] ...
SELECT * FROM pets WHERE owner_id = 100;
-- TOTAL: 1 + 100 = 101 consultas a la base de datos (Problema N+1)
---

2. Soluciones al Problema N+1 en JPA

Estrategia Mecanismo Ventajas y Buenas Prácticas
JOIN FETCH en JPQL Se especifica explícitamente en la consulta @Query("SELECT o FROM OwnerEntity o JOIN FETCH o.pets"). Trae propietarios y mascotas en un único SELECT con LEFT JOIN. Reduce las 101 consultas a exactamente 1 consulta.
@EntityGraph Se anota sobre cualquier método de repositorio: @EntityGraph(attributePaths = {"pets"}). Solución más limpia y recomendada. Permite reutilizar métodos derivados o consultas estándar sin reescribir sentencias JPQL completas.
---

3. ¿Por qué en MongoDB / NoSQL este problema NO existe de la misma manera?

En almacenes documentales como MongoDB, el paradigma de modelado natural es la desnormalización y el embebido. Las mascotas de un propietario se almacenan directamente dentro del mismo documento JSON/BSON del propietario: 


{
  "_id": "64a1b2c3d4e5f67890123456",
  "fullName": "Carlos Morales",
  "phoneNumber": "+34 600 123 456",
  "pets": [
    { "name": "Max", "species": "Dog", "age": 4 },
    { "name": "Luna", "species": "Cat", "age": 2 }
  ]
}

Al consultar los propietarios con ownerMongoRepository.findAll(), el driver de MongoDB recupera los documentos completos con sus mascotas embebidas en una única operación de red (un solo find()). No hay joins ni consultas secundarias N+1.

¿Cuándo sí puede ocurrir en Mongo? Si un desarrollador comete el antipatrón de usar @DBRef entre documentos independientes, forzando al cliente a realizar consultas en bucle.

4. Concurrencia y Bloqueos (Locking): Optimista vs Pesimista

Estrategia Anotación Cómo Funciona Cuándo Usarlo
Bloqueo Optimista @Version private Long version; No bloquea la base de datos a nivel físico. Al hacer UPDATE, comprueba WHERE version = ?. Si otro hilo modificó el registro antes, incrementó la versión y la sentencia afecta a 0 filas, lanzando OptimisticLockingFailureException. Recomendación general por defecto. Alta concurrencia de lectura, baja probabilidad de colisión (JPA y MongoDB).
Bloqueo Pesimista @Lock(LockModeType.PESSIMISTIC_WRITE) Ejecuta SELECT ... FOR UPDATE en PostgreSQL y Oracle. Bloquea físicamente la fila en el motor hasta que la transacción termine. Operaciones críticas donde los conflictos son frecuentes y costosos de reintentar (sistemas de reservas de plazas, carritos con stock limitado).
---

5. Ejemplos Prácticos Completos y Simétricos

5.1. Persistencia Relacional: PostgreSQL / Oracle (Spring Data JPA)


package com.example.petshop.model.relational;

import jakarta.persistence.*;
import lombok.*;
import java.util.ArrayList;
import java.util.List;

@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
@ToString
@EqualsAndHashCode(onlyExplicitlyIncluded = true)
@Entity
@Table(name = "owners")
public class OwnerEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @EqualsAndHashCode.Include
    private Long id;

    @Column(nullable = false)
    private String fullName;

    // Relación perezosa por buena práctica de diseño
    // @ToString.Exclude previene bucles infinitos e invocación accidental de proxy fuera de sesión
    @ToString.Exclude
    @Builder.Default
    @OneToMany(mappedBy = "owner", cascade = CascadeType.ALL, fetch = FetchType.LAZY)
    private List<PetEntity> pets = new ArrayList<>();

    // Bloqueo optimista
    @Version
    private Long version;
}


package com.example.petshop.repository.relational;

import com.example.petshop.model.relational.OwnerEntity;
import jakarta.persistence.LockModeType;
import org.springframework.data.jpa.repository.EntityGraph;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Lock;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;
import org.springframework.stereotype.Repository;

import java.util.List;
import java.util.Optional;

@Repository
public interface OwnerRepository extends JpaRepository<OwnerEntity, Long> {

    // Solución 1 con @EntityGraph: Evita el N+1 resolviendo la relación 'pets' en 1 sola consulta
    @EntityGraph(attributePaths = {"pets"})
    List<OwnerEntity> findAll();

    // Solución 2 con JOIN FETCH explícito en JPQL
    @Query("SELECT o FROM OwnerEntity o JOIN FETCH o.pets WHERE o.fullName = :name")
    Optional<OwnerEntity> findByNameWithPets(@Param("name") String name);

    // Bloqueo Pesimista (SELECT ... FOR UPDATE) para operaciones de reserva crítica
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT o FROM OwnerEntity o WHERE o.id = :id")
    Optional<OwnerEntity> findByIdWithPessimisticLock(@Param("id") Long id);
}

5.2. Persistencia Documental: MongoDB (Spring Data MongoDB)


package com.example.petshop.model.nosql;

import lombok.*;
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.mongodb.core.mapping.Document;
import org.springframework.data.mongodb.core.mapping.Field;
import java.util.ArrayList;
import java.util.List;

@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
@ToString
@EqualsAndHashCode(onlyExplicitlyIncluded = true)
@Document(collection = "owners")
public class OwnerDocument {

    @Id
    @EqualsAndHashCode.Include
    private String id;

    @Field("fullName")
    private String fullName;

    // Subdocumentos embebidos de forma natural: Sin problema N+1 por diseño
    @Builder.Default
    @Field("pets")
    private List<PetDocument> pets = new ArrayList<>();

    // Bloqueo optimista soportado nativamente en Spring Data MongoDB
    @Version
    private Long version;
}


package com.example.petshop.repository.nosql;

import com.example.petshop.model.nosql.OwnerDocument;
import org.springframework.data.mongodb.repository.MongoRepository;
import org.springframework.stereotype.Repository;

import java.util.List;
import java.util.Optional;

@Repository
public interface OwnerMongoRepository extends MongoRepository<OwnerDocument, String> {

    // La recuperación de documentos completos incluye los subdocumentos embebidos en una sola lectura
    List<OwnerDocument> findAll();

    Optional<OwnerDocument> findByFullName(String fullName);
}

6. Contraejemplos y Antipatrones de Rendimiento

Contraejemplo: Usar FetchType.EAGER en Relaciones JPA


// ANTIPATRÓN CATASTRÓFICO: Forzar carga impaciente en la entidad
@Entity
public class BadOwnerEntity {
    @Id
    private Long id;

    // EAGER provocará joins indiscriminados en CUALQUIER consulta, incluso si solo se pide el nombre
    @OneToMany(fetch = FetchType.EAGER)
    private List<PetEntity> pets;
}

Regla de Oro: Configurar siempre FetchType.LAZY en colecciones y utilizar @EntityGraph o JOIN FETCH únicamente en las consultas específicas que requieran cargar los hijos.
