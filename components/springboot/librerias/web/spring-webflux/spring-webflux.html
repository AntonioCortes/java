Spring WebFlux: Programación Reactiva No Bloqueante

1. ¿Qué es y para qué sirve?

Spring Reactive Web (starter spring-boot-starter-webflux en Spring Initializr) es el framework web reactivo oficial de Spring diseñado para construir microservicios y sistemas orientados a eventos de altísimo rendimiento y escala masiva.

A diferencia de Spring MVC tradicional (que asigna un hilo exclusivo del sistema operativo por cada petición entrante bloqueándolo hasta que la operación termine), Spring WebFlux opera sobre un modelo completamente asíncrono y no bloqueante basado en:

  • Servidor Embebido Netty: Motor de red asíncrono basado en un bucle de eventos (Event Loop) que gestiona decenas de miles de conexiones concurrentes con un número muy reducido de hilos (igual al número de núcleos de la CPU).
  • Project Reactor: La implementación de referencia de la especificación Reactive Streams en Java, que introduce dos tipos de datos reactivos fundamentales:
    • Mono<T>: Emite como máximo 1 elemento (o completa vacío / con error). Equivalente asíncrono a Optional<T> o CompletableFuture<T>.
    • Flux<T>: Emite una secuencia asíncrona de 0 a N elementos a lo largo del tiempo, con soporte nativo de Backpressure (el consumidor avisa al productor de cuántos elementos puede procesar para no ser saturado).
  • WebClient: Cliente HTTP reactivo y no bloqueante moderno (sustituto oficial recomendado de RestTemplate).

Analogía del mundo real

Imaginemos una oficina de correos:

  • Spring MVC (Tomcat clásico): Hay 20 ventanillas. Si un cliente pide un paquete que tarda 10 minutos en buscarse en el sótano, el empleado se queda de brazos cruzados esperando en la ventanilla. Si llegan 21 clientes a la vez, el número 21 tiene que esperar en la calle porque no hay hilos libres.
  • Spring WebFlux (Netty reactivo): Hay un único mostrador rápido. El empleado recoge el número de seguimiento, le da un ticket electrónico al cliente y le dice: *"Siéntese, cuando su paquete esté en la cinta sonará su ticket"*. El empleado atiende a 1.000 personas en 5 minutos; a medida que los paquetes llegan del sótano de forma asíncrona, se emite una notificación y se entregan.

2. Caso de Uso Real Estructurado

1. Contexto

Una plataforma de monitorización veterinaria en tiempo real transmite constantes biométricas (pulso cardíaco, oxígeno en sangre) de miles de mascotas hospitalizadas a las pantallas de los veterinarios.

2. El Problema (Con Spring MVC)

Mantener 20.000 conexiones HTTP abiertas en Tomcat para recibir eventos continuos requiere 20.000 hilos del sistema operativo. La JVM consume 20 GB de memoria solo en pilas de hilos (thread stacks) y el servidor cae por OutOfMemoryError: unable to create new native thread.

3. La Solución (Con WebFlux + SSE)

Utilizando un Flux continuo mediante Server-Sent Events (SSE), Netty mantiene las 20.000 conexiones abiertas con tan solo 8 hilos de CPU y menos de 200 MB de memoria RAM.

3. ¿Cuándo usar WebFlux y cuándo NO usarlo?

Criterio Spring MVC (Spring Web) Spring WebFlux (Reactive Web)
Modelo de Ejecución Síncrono y bloqueante (1 hilo por petición en Tomcat). Asíncrono y no bloqueante (Event Loop en Netty).
Concurrencia Óptima Hasta 1.000 - 2.000 peticiones concurrentes. Decenas de miles de conexiones simultáneas con mínima memoria.
Bases de Datos Compatibles JPA / Hibernate tradicional, JDBC bloqueante. R2DBC, MongoDB Reactive, Redis Reactive, Cassandra (deben ser drivers no bloqueantes).
¿Cuándo NO usarlo? Cuando se requiera streaming masivo continuo de datos. Si tu proyecto utiliza JPA/Hibernate tradicional, ya que las llamadas bloqueantes a la base de datos anulan todas las ventajas reactivas.

5. Ejemplo Completo: Controlador Reactivo y Streaming con Server-Sent Events (SSE)


package com.example.petshop.controller.reactive;

import com.example.petshop.dto.PetDTO;
import com.example.petshop.service.reactive.PetReactiveService;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.http.MediaType;
import org.springframework.web.bind.annotation.*;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

import java.time.Duration;

@Slf4j
@RestController
@RequestMapping("/api/v1/reactive/pets")
@RequiredArgsConstructor
public class PetReactiveController {

    private final PetReactiveService petService;

    // 1. Endpoint que retorna un único elemento asíncrono (Mono)
    @GetMapping("/{id}")
    public Mono<PetDTO> getPetById(@PathVariable Long id) {
        log.info("Llegada de petición no bloqueante para mascota: {}", id);
        return petService.findPetById(id);
    }

    // 2. Endpoint de streaming en tiempo real (Server-Sent Events)
    // Emite una mascota cada segundo de forma continua hacia el navegador/cliente
    @GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<PetDTO> streamPets() {
        log.info("Iniciando canal SSE de streaming de mascotas...");
        return petService.findAllPets()
                .delayElements(Duration.ofSeconds(1)) // Simula flujo temporal continuo
                .doOnCancel(() -> log.info("Cliente desconectado del canal SSE"));
    }

    // 3. Creación reactiva con Mono
    @PostMapping
    public Mono<PetDTO> createPet(@RequestBody Mono<PetDTO> petDtoMono) {
        return petDtoMono.flatMap(petService::savePet);
    }
}

6. Contraejemplo y Error Fatal: Mezclar Código Bloqueante en WebFlux


// ANTIPATRÓN CATASTRÓFICO: Ejecutar código bloqueante dentro de un operador reactivo
@GetMapping("/bad-stream")
public Flux<PetDTO> badReactiveMethod() {
    return Flux.range(1, 100)
            .map(id -> {
                // ERROR MORTAL: Thread.sleep o consultas JDBC bloqueantes
                // detienen el Event Loop de Netty. Con 4 llamadas simultáneas,
                // TODAS las peticiones del microservicio entero se congelan.
                try { Thread.sleep(2000); } catch (InterruptedException e) {}
                return new PetDTO(...);
            });
}

Solución: Utilizar siempre operadores no bloqueantes nativos como delayElements(Duration) o delegar operaciones bloqueantes legacy en un scheduler aislado mediante publishOn(Schedulers.boundedElastic()).
