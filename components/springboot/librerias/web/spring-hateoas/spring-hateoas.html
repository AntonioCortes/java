Spring HATEOAS: APIs RESTful Nivel 3 y Enlaces de Hipermedia

1. ¿Qué es y para qué sirve?

En el Modelo de Madurez de Richardson para APIs REST, existen cuatro niveles (Nivel 0: POX/SOAP, Nivel 1: Recursos con URLs, Nivel 2: Verbos HTTP como GET/POST/PUT/DELETE y Nivel 3: Controles de Hipermedia / HATEOAS).

Spring HATEOAS (starter spring-boot-starter-hateoas en Spring Initializr) es la librería que permite implementar el Nivel 3 de Richardson: cada respuesta JSON no solo incluye los datos del recurso, sino también un bloque de enlaces de navegación inteligentes (_links) que indican al cliente qué acciones o transiciones de estado puede realizar a continuación.

  • Desacoplamiento Total de URLs: El cliente frontend no necesita memorizar o construir URLs complejas a mano; simplemente navega siguiendo los enlaces devueltos por el servidor (formato estándar HAL - Hypertext Application Language).
  • Navegación Dinámica según el Estado: Si una mascota ya ha sido adoptada, el servidor omite el enlace "adopt" y muestra solo "medical-history", guiando la interfaz de usuario automáticamente.
  • WebMvcLinkBuilder: Utilidad de Spring que genera enlaces fuertemente tipados vinculados directamente a métodos de controladores, evitando URLs rotas si se refactorizan rutas.

Analogía del mundo real

Imaginemos un cajero automático bancario:

  • En un sistema sin HATEOAS, el cajero es una pantalla de terminal antigua donde tienes que teclear de memoria el comando /cuenta/123/retirar?cantidad=50. Si te equivocas de sintaxis, falla.
  • Con HATEOAS, introduces la tarjeta e inmediatamente la pantalla te muestra botones claros: [Consultar Saldo], [Retirar Efectivo], [Transferir]. Si tu saldo es cero, el botón de retirar desaparece automáticamente de la pantalla porque el servidor te guía en función del estado de tu cuenta.

2. Caso de Uso Real Estructurado

1. Contexto

Una plataforma de adopción de mascotas tiene un flujo de estados: Disponible → En Proceso de Adopción → Adoptada → En Seguimiento.

2. El Problema (Sin HATEOAS)

La aplicación frontend tiene que replicar toda la lógica de negocio en JavaScript: si el estado es 'ADOPTADA', ocultar el botón de adoptar, calcular la URL de vacunas a mano y arriesgarse a desincronizaciones cuando la API cambia de versión.

3. La Solución (Con Spring HATEOAS)

La API devuelve el recurso envuelto en EntityModel<PetDTO> con sus hipermedios calculados por el servidor. El cliente simplemente renderiza los botones a los que apuntan los enlaces _links.

3. ¿Cuándo usar HATEOAS y cuándo NO usarlo?

Escenario Recomendación Motivo
APIs públicas de gran escala o sistemas con flujos de estado complejos donde se busque desacoplar al 100% el frontend del enrutamiento de URLs. USAR Spring HATEOAS Permite cambiar rutas en el servidor sin romper las aplicaciones cliente y autodescribe las acciones disponibles.
Microservicios internos de alta velocidad, streaming reactivo o APIs CRUD simples. NO usar HATEOAS Añade una sobrecarga innecesaria en el tamaño del payload JSON y en el cálculo de enlaces para servicios simples.

5. Ejemplo Completo: Controlador con Enlaces de Hipermedia HAL


package com.example.petshop.controller.hateoas;

import com.example.petshop.dto.PetDTO;
import com.example.petshop.service.PetService;
import lombok.RequiredArgsConstructor;
import org.springframework.hateoas.EntityModel;
import org.springframework.hateoas.IanaLinkRelations;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import static org.springframework.hateoas.server.mvc.WebMvcLinkBuilder.linkTo;
import static org.springframework.hateoas.server.mvc.WebMvcLinkBuilder.methodOn;

@RestController
@RequestMapping("/api/v1/hateoas/pets")
@RequiredArgsConstructor
public class PetHateoasController {

    private final PetService petService;

    @GetMapping("/{id}")
    public ResponseEntity<EntityModel<PetDTO>> getPetWithHypermedia(@PathVariable Integer id) {
        PetDTO pet = petService.findById(id);

        // Envolvemos el DTO con enlaces de navegación
        EntityModel<PetDTO> resource = EntityModel.of(pet);

        // 1. Enlace a sí mismo (self link)
        resource.add(linkTo(methodOn(PetHateoasController.class).getPetWithHypermedia(id))
                .withSelfRel());

        // 2. Enlace a la colección general de mascotas
        resource.add(linkTo(methodOn(PetHateoasController.class).getAllPets())
                .withRel("all-pets"));

        // 3. Enlace condicional: si no está vacunada, se ofrece la acción de vacunar
        if (!pet.isVaccinated()) {
            resource.add(linkTo(methodOn(PetHateoasController.class).vaccinatePet(id))
                    .withRel("vaccinate"));
        }

        return ResponseEntity.ok(resource);
    }

    @GetMapping
    public ResponseEntity<String> getAllPets() { return ResponseEntity.ok("Colección"); }

    @PutMapping("/{id}/vaccinate")
    public ResponseEntity<Void> vaccinatePet(@PathVariable Integer id) { return ResponseEntity.noContent().build(); }
}

6. Contraejemplo: Construir URLs de Enlace a Mano con Cadenas de Texto


// ANTIPATRÓN: Concatenar cadenas de texto para crear hipermedios
Link badLink = Link.of("http://localhost:8080/api/v1/pets/" + id, "self");
// ERROR: Si cambia el host, el puerto, el context-path o la ruta del controlador,
// todos los enlaces devueltos quedan rotos silenciosamente.

Solución: Utilizar siempre WebMvcLinkBuilder.linkTo(methodOn(Clase.class).metodo(...)), que genera las URLs dinámicamente inspeccionando el mapeo real del método en Spring MVC.
