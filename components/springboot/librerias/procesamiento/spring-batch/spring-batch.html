Spring Batch: Procesamiento Masivo por Lotes (ETL)

1. ¿Qué es y para qué sirve?

En aplicaciones empresariales, a menudo es necesario procesar millones de registros sin intervención humana: generar liquidaciones contables a medianoche, sincronizar catálogos de proveedores desde ficheros CSV gigantescos de varios gigabytes o migrar bases de datos legadas.

Spring Batch (starter spring-boot-starter-batch en Spring Initializr) es el framework robusto y probado de Spring diseñado específicamente para el procesamiento por lotes masivo (*Batch Processing* / ETL - Extract, Transform, Load).

  • Procesamiento Orientado a Trozos (Chunk-Oriented Processing): No lee un millón de registros de golpe a memoria (lo que provocaría OutOfMemoryError). Procesa los datos en bloques pequeños (ej. de 100 en 100), abriendo una transacción de base de datos para cada trozo (*chunk*).
  • Tolerancia a Fallos y Reintentos: Si en un fichero de 500.000 líneas la línea 240.115 está corrupta, Spring Batch puede configurarse para ignorar (*skip*) ese registro fallido, registrarlo en un log de incidencias y continuar procesando las demás líneas sin abortar el trabajo completo.
  • Reanudación Automática (Restartability): Si la máquina se apaga a mitad de un proceso de 5 horas, Spring Batch consulta sus tablas de metadatos (BATCH_JOB_EXECUTION) y reanuda el trabajo exactamente en el punto donde se interrumpió sin duplicar los registros ya insertados.

Analogía del mundo real

Imaginemos una fábrica embotelladora de leche:

  • Un enfoque ingenuo (un bucle for en Java) intentaría meter 100.000 litros de leche de golpe en una sola botella gigantesca; el cristal revienta y se inunda la nave.
  • Spring Batch es la cinta transportadora industrial:
    • El ItemReader toma botellas vacías de la caja de una en una.
    • El ItemProcessor las esteriliza y llena de leche (transformación de datos).
    • El ItemWriter empaqueta cajas de 12 botellas (el *chunk* o lote) y las sella con el precinto oficial (hace commit de la transacción). Si una botella sale rota, un sensor la expulsa a la papelera (estrategia *skip*) y la cinta sigue funcionando sin detener la fábrica entera.

2. Caso de Uso Real Estructurado

1. Contexto

Todas las noches a las 02:00 AM, la federación de clínicas veterinarias recibe un archivo CSV de 5 millones de registros con el censo nacional de vacunas administradas.

2. El Problema (Sin Spring Batch)

Un desarrollador lee el archivo con un bucle simple while(scanner.hasNext()) dentro de una transacción @Transactional. Al llegar a la línea 800.000, la base de datos aborta por Transaction Log Full, la memoria RAM colapsa y la aplicación cae, perdiéndose 3 horas de procesamiento.

3. La Solución (Con Spring Batch)

Un Job de Spring Batch procesa bloques de 1.000 registros con transacciones atómicas independientes. Tarda 40 minutos, tolera líneas malformadas y guarda la auditoría de ejecución en base de datos.

3. ¿Cuándo usar Spring Batch y cuándo NO usarlo?

Escenario Recomendación Motivo
Procesamiento nocturno o periódico de archivos grandes (CSV, XML, JSON), migraciones de millones de registros o facturación masiva. SIEMPRE usar Spring Batch Garantiza gestión de memoria en streaming, transacciones acotadas, reanudación tras fallos y auditoría completa.
Procesar una única petición REST interactiva donde un usuario espera respuesta inmediata en su navegador. NO usar Spring Batch Spring Batch está diseñado para procesamiento asíncrono en segundo plano por lotes, no para responder llamadas síncronas de baja latencia.

5. Anatomía de la Arquitectura de Spring Batch

En Spring Batch 5 (Spring Boot 3), la configuración se realiza mediante beans inyectando JobRepository y PlatformTransactionManager: 


package com.example.petshop.batch;

import com.example.petshop.dto.PetDTO;
import com.example.petshop.model.relational.PetEntity;
import jakarta.persistence.EntityManagerFactory;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.batch.core.Job;
import org.springframework.batch.core.Step;
import org.springframework.batch.core.job.builder.JobBuilder;
import org.springframework.batch.core.repository.JobRepository;
import org.springframework.batch.core.step.builder.StepBuilder;
import org.springframework.batch.item.ItemProcessor;
import org.springframework.batch.item.ItemReader;
import org.springframework.batch.item.ItemWriter;
import org.springframework.batch.item.database.builder.JpaItemWriterBuilder;
import org.springframework.batch.item.file.builder.FlatFileItemReaderBuilder;
import org.springframework.batch.item.file.mapping.BeanWrapperFieldSetMapper;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.io.ClassPathResource;
import org.springframework.transaction.PlatformTransactionManager;

import java.time.LocalDate;

@Slf4j
@Configuration
@RequiredArgsConstructor
public class PetImportBatchConfig {

    private final JobRepository jobRepository;
    private final PlatformTransactionManager transactionManager;
    private final EntityManagerFactory entityManagerFactory;

    // 1. Reader: Lee registros del archivo CSV línea a línea
    @Bean
    public ItemReader<PetDTO> petItemReader() {
        return new FlatFileItemReaderBuilder<PetDTO>()
                .name("petCsvReader")
                .resource(new ClassPathResource("import/pets.csv"))
                .delimited()
                .names("name", "species", "age")
                .fieldSetMapper(new BeanWrapperFieldSetMapper<>() {{
                    setTargetType(PetDTO.class);
                }})
                .build();
    }

    // 2. Processor: Transforma el DTO y aplica lógica de negocio y validación
    @Bean
    public ItemProcessor<PetDTO, PetEntity> petItemProcessor() {
        return dto -> {
            // Regla de limpieza y normalización
            String cleanName = dto.getName().trim().toUpperCase();
            return PetEntity.builder()
                    .name(cleanName)
                    .species(dto.getSpecies())
                    .age(dto.getAge() != null ? dto.getAge().intValue() : 0)
                    .vaccinated(true)
                    .admissionDate(LocalDate.now())
                    .build();
        };
    }

    // 3. Writer: Inserta entidades en bloques en PostgreSQL mediante JPA
    @Bean
    public ItemWriter<PetEntity> petItemWriter() {
        return new JpaItemWriterBuilder<PetEntity>()
                .entityManagerFactory(entityManagerFactory)
                .build();
    }

    // 4. Step: Ensambla Reader, Processor y Writer con transacciones por chunks de 100
    @Bean
    public Step importPetsStep(ItemReader<PetDTO> reader, 
                              ItemProcessor<PetDTO, PetEntity> processor, 
                              ItemWriter<PetEntity> writer) {
        return new StepBuilder("importPetsStep", jobRepository)
                .<PetDTO, PetEntity>chunk(100, transactionManager)
                .reader(reader)
                .processor(processor)
                .writer(writer)
                .faultTolerant()
                .skip(Exception.class)
                .skipLimit(10) // Tolera hasta 10 registros corruptos antes de fallar
                .build();
    }

    // 5. Job: Flujo general del lote
    @Bean
    public Job importPetsJob(Step importPetsStep) {
        return new JobBuilder("importPetsJob", jobRepository)
                .start(importPetsStep)
                .build();
    }
}

6. Contraejemplo y Error Fatal: Cargar Millones de Filas en Memoria con findAll()


// ANTIPATRÓN: Intentar procesar un lote usando JPA findAll() tradicional
@Scheduled(cron = "0 0 2 * * ?")
public void badBatch() {
    // ERROR MORTAL: Si hay 2 millones de mascotas en la tabla,
    // petRepository.findAll() intentará instanciar 2 millones de entidades en memoria.
    // La JVM consumirá el 100% de CPU en Garbage Collection y caerá con OutOfMemoryError.
    List<PetEntity> allPets = petRepository.findAll(); 
    for (PetEntity p : allPets) {
        actualizarEstado(p);
    }
}

Solución: Utilizar siempre Spring Batch con lectores paginados o basados en cursores (JpaPagingItemReader o RepositoryItemReader) que procesan lotes acotados sin saturar la memoria heap.
