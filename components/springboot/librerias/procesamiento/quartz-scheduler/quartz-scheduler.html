Quartz Scheduler: Programación Avanzada de Tareas en Clúster

1. ¿Qué es y para qué sirve?

En Spring Boot existen dos formas principales de programar tareas periódicas (cron jobs):

  • @Scheduled simple de Spring: La anotación básica incluida en Spring Core. Las tareas se gestionan puramente en la memoria RAM de la instancia de la aplicación.
  • Quartz Scheduler (starter spring-boot-starter-quartz en Spring Initializr): El motor de programación empresarial de nivel industrial. Permite programar tareas complejas y, crucialmente, persistir los trabajos y disparadores en la base de datos (soporte de JobStoreTX o JobStoreCMT).

¿Por qué @Scheduled falla en microservicios y Quartz es obligatorio?

En entornos modernos con Kubernetes o Docker Swarm, las aplicaciones nunca corren en una sola máquina; se despliegan con 2, 5 o 10 réplicas por motivos de alta disponibilidad.

  • Si usas @Scheduled(cron = "0 0 8 * * ?") con 4 réplicas en Kubernetes, las 4 réplicas ejecutarán la tarea a las 08:00 AM al mismo tiempo, cobrando cuatro veces a los clientes o enviando cuatro emails duplicados.
  • Quartz en modo Clúster utiliza bloqueos a nivel de base de datos (tablas QRTZ_LOCKS y QRTZ_TRIGGERS): cuando llega la hora de ejecución, una sola de las 4 réplicas adquiere el bloqueo y ejecuta el trabajo, mientras las demás continúan en espera. Si la réplica que estaba ejecutando el trabajo cae inesperadamente, otra réplica del clúster detecta el fallo (misfire) y lo completa.

Analogía del mundo real

Imaginemos un campanario con varios campaneros:

  • Con @Scheduled, hay 4 campaneros sordos en la torre con su propio reloj de pulsera. A las 12:00 en punto, los 4 se tiran a la cuerda y tocan la campana al mismo tiempo con un estruendo ensordecedor y descoordinado.
  • Con Quartz en Clúster, hay una única cuerda con un cerrojo central: a las 12:00, el primer campanero que llega coge la cuerda, echa el pestillo y toca la campana limpiamente; los otros tres ven que el cerrojo está ocupado y continúan barriendo la torre.

2. Caso de Uso Real Estructurado

1. Contexto

Un microservicio de suscripciones veterinarias mensuales factura a los clientes el día 1 de cada mes a las 06:00 AM, desplegado en 3 pods en Kubernetes.

2. El Problema (Con @Scheduled simple)

Las 3 réplicas despiertan a la vez a las 06:00 AM. Se cobran 3 cuotas mensuales simultáneas a cada cliente en su tarjeta bancaria, provocando reclamaciones masivas y bloqueos bancarios.

3. La Solución (Con Quartz Clustered)

Quartz persiste el Trigger en PostgreSQL con isClustered = true. Un único pod ejecuta la facturación; los demás pods reconocen la reserva y descansan.

3. ¿Cuándo usar @Scheduled vs Quartz Scheduler?

Característica @Scheduled (Spring Básico) Quartz Scheduler
Almacenamiento Solo en memoria RAM (se pierde todo al reiniciar). Persistente en Base de Datos SQL (tablas QRTZ).
Soporte Multi-Instancia / Clúster No (se ejecuta en todas las réplicas duplicándose). Sí (ejecución única coordinada en clúster).
Modificación de Tareas en Caliente No (requiere recompilar o reiniciar). Sí: Permite pausar, reanudar y reprogramar triggers dinámicamente vía API.
Curva de Configuración Mínima (solo una anotación). Media (requiere scripts de tablas SQL y configuración).

5. Configuración de Quartz en Clúster (application.yml)


spring:
  quartz:
    job-store-type: jdbc # Persistencia en base de datos para modo clúster
    jdbc:
      initialize-schema: always # Crea las tablas QRTZ_* automáticamente si no existen
    properties:
      org.quartz.jobStore.isClustered: true # Activa la coordinación entre múltiples réplicas
      org.quartz.jobStore.clusterCheckinInterval: 20000 # Chequeo de latido entre pods cada 20 segundos

6. Ejemplo Completo: Creación de un Job y un Trigger con Quartz y Lombok

A. Implementación del Trabajo (Job)


package com.example.petshop.quartz;

import lombok.extern.slf4j.Slf4j;
import org.quartz.Job;
import org.quartz.JobExecutionContext;
import org.quartz.JobExecutionException;
import org.springframework.stereotype.Component;

@Slf4j
@Component
public class MonthlySubscriptionBillingJob implements Job {

    @Override
    public void execute(JobExecutionContext context) throws JobExecutionException {
        String podName = System.getenv().getOrDefault("HOSTNAME", "local-instance");
        log.info("Iniciando trabajo de facturación mensual en la instancia clúster: {}", podName);

        try {
            // Lógica de cobro a clientes
            processBilling();
            log.info("Facturación mensual finalizada con éxito");
        } catch (Exception e) {
            log.error("Fallo durante la facturación", e);
            throw new JobExecutionException(e);
        }
    }

    private void processBilling() {
        // Cobro en pasarela de pagos
    }
}

B. Configuración de JobDetail y CronTrigger


package com.example.petshop.quartz;

import org.quartz.*;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class QuartzConfig {

    // 1. Definición del JobDetail (Metadatos del trabajo)
    @Bean
    public JobDetail billingJobDetail() {
        return JobBuilder.newJob(MonthlySubscriptionBillingJob.class)
                .withIdentity("monthlyBillingJob", "billingGroup")
                .withDescription("Trabajo mensual de cobro recurrente")
                .storeDurably() // Permanece en la BD incluso si no tiene triggers asociados
                .build();
    }

    // 2. Definición del Trigger (Horario de ejecución con expresión Cron)
    @Bean
    public Trigger billingJobTrigger(JobDetail billingJobDetail) {
        return TriggerBuilder.newTrigger()
                .forJob(billingJobDetail)
                .withIdentity("monthlyBillingTrigger", "billingGroup")
                // Se ejecuta a las 06:00 AM el día 1 de cada mes
                .withSchedule(CronScheduleBuilder.cronSchedule("0 0 6 1 * ?")
                        .withMisfireHandlingInstructionFireAndProceed())
                .build();
    }
}

7. Contraejemplo y Error Frecuente: Usar @Scheduled en Clúster sin Mecanismo de Bloqueo


// ANTIPATRÓN EN ARQUITECTURAS DISTRIBUIDAS (KUBERNETES):
@Scheduled(cron = "0 0 6 1 * ?")
public void badClusteredScheduled() {
    // PELIGRO: Si tienes 5 réplicas desplegadas en Kubernetes,
    // este método se disparará 5 VECES a la vez a las 06:00 AM en los 5 pods distintos.
    cobrarCuotaMensual();
}

Solución: Utilizar Quartz Scheduler con JDBC JobStore o librerías de bloqueo distribuido como ShedLock sobre bases de datos relacionales o Redis.
