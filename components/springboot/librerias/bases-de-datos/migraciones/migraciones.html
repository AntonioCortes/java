Control de Versiones y Migraciones de Base de Datos (Flyway y Liquibase)

1. ¿Qué son y para qué sirven?

En entornos de desarrollo empresarial y despliegue continuo (CI/CD), la base de datos no puede modificarse manualmente mediante scripts improvisados ni confiando en la generación automática de Hibernate (ddl-auto: update).

Spring Initializr ofrece integración nativa con las dos herramientas estándar de la industria para el control de versiones de esquemas SQL:

  • Flyway: La herramienta más extendida y sencilla. Se basa en scripts SQL planos versionados (ej. V1__crear_tablas.sql, V2__anadir_columna_edad.sql) que se guardan en el repositorio de código junto a la aplicación y se ejecutan automáticamente en orden estricto durante el arranque de Spring Boot.
  • Liquibase: Herramienta agnóstica de base de datos basada en conjuntos de cambios (Changesets) definidos en XML, YAML, JSON o SQL. Permite especificar cambios de esquema abstractos que Liquibase traduce automáticamente al dialecto SQL de cualquier motor (PostgreSQL, Oracle, MySQL, SQL Server), con soporte avanzado para rollbacks automatizados.

Analogía del mundo real

Imaginemos un historial de revisiones de Git aplicado a la estructura de un rascacielos: los arquitectos no van a la obra cada mañana a derribar tabiques o picar columnas sin planos previos. Cada cambio estructural queda registrado en un libro de bitácora oficial numerado: *"Revisión 1: cimientos de hormigón"*, *"Revisión 2: instalación de cableado eléctrico"*. Si una revisión falla o ya fue aplicada, el capataz (Flyway o Liquibase) comprueba la tabla de auditoría (flyway_schema_history), detecta qué cambios faltan por aplicar y ejecuta únicamente las revisiones pendientes de forma segura e irreversible.

2. Caso de Uso Real Estructurado

1. Contexto

Una aplicación de banca veterinaria tiene entornos de Desarrollo, Pruebas (QA), Preproducción y Producción con réplicas activas en Kubernetes.

2. El Problema (Uso de ddl-auto=update)

Un desarrollador renombra un atributo en una entidad Java. Al arrancar en producción, Hibernate crea una columna nueva y deja la antigua con datos desincronizados, provocando inconsistencias, bloqueos de tablas y pérdida de datos irreversible.

3. La Solución (Con Flyway o Liquibase)

Se desactiva Hibernate DDL (ddl-auto: validate). Cada cambio viaja en un script SQL versionado revisado por el equipo de BD. Todos los entornos aplican exactamente el mismo script con total trazabilidad y cero sorpresas.

3. ¿Cuándo usar Flyway vs Liquibase?

Criterio Flyway Liquibase
Formato Principal SQL Puro (fácil de leer y escribir por cualquier desarrollador o DBA). XML, YAML, JSON o SQL (abstracción independiente del motor).
Curva de Aprendizaje Muy baja: solo requiere saber SQL y la convención de nombres de archivo. Media/Alta: requiere aprender la estructura de tags de los changesets.
Soporte Multi-Base de Datos Los scripts SQL deben adaptarse si se migra de base de datos (ej. de Postgres a Oracle). Excelente: un mismo changeset YAML genera la sentencia adaptada a Oracle, Postgres o MySQL.
Rollback Automático Disponible únicamente en la versión Enterprise/Teams (de pago). Soportado nativamente en la versión gratuita Open Source (etiqueta <rollback>).

5. Estructura y Nomenclatura de Scripts en Flyway

Los scripts SQL de Flyway se ubican por defecto en src/main/resources/db/migration/ y siguen una convención estricta:

  • Prefijo V (Versión): Scripts versionados que se ejecutan una única vez en orden ascendente (ej. V1__crear_tabla_mascotas.sql, V2__crear_tabla_vacunas.sql).
  • Prefijo U (Deshacer / Undo): Scripts de compensación o marcha atrás.
  • Prefijo R (Repetibles): Scripts que se ejecutan cada vez que su contenido (checksum) cambia (ideal para vistas SQL, procedimientos almacenados y triggers).
  • Separador __: Dos barras bajas consecutivas obligatorias separan la versión de la descripción legible.

Ejemplo: V1__init_schema.sql


CREATE TABLE pets (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    species VARCHAR(50) NOT NULL,
    age INT,
    vaccinated BOOLEAN NOT NULL DEFAULT FALSE,
    admission_date DATE NOT NULL DEFAULT CURRENT_DATE
);

CREATE INDEX idx_pets_species ON pets(species);

Ejemplo: V2__add_owner_contact.sql


ALTER TABLE pets ADD COLUMN owner_phone VARCHAR(20);
ALTER TABLE pets ADD COLUMN chip_number VARCHAR(50) UNIQUE;

6. Configuración en Spring Boot (application.yml)


spring:
  # Desactivar la generación destructiva de Hibernate
  jpa:
    hibernate:
      ddl-auto: validate # Solo valida que las entidades coincidan con la BD creada por Flyway
    show-sql: false

  # Configuración de Flyway
  flyway:
    enabled: true
    baseline-on-migrate: true # Si la base de datos ya tenía tablas previas
    locations: classpath:db/migration
    out-of-order: false # No permite aplicar scripts antiguos desordenados

7. Contraejemplo y Peligro Mortal en Producción

Contraejemplo: Usar ddl-auto=create o ddl-auto=update en Entornos Reales


# ANTIPATRÓN MORTAL EN PRODUCCIÓN:
spring:
  jpa:
    hibernate:
      ddl-auto: create-drop # O ddl-auto: update
      # PELIGRO: create-drop borra todas las tablas al reiniciar el microservicio.
      # update nunca borra columnas eliminadas (huérfanos silenciosos) y bloquea tablas grandes.

Regla de Oro de Producción: Configurar siempre spring.jpa.hibernate.ddl-auto=validate y delegar el 100% del ciclo de vida del esquema en Flyway o Liquibase.
