Bases de Datos NoSQL y Caché en Spring Boot (MongoDB, Redis y Elasticsearch)

1. ¿Qué son y para qué sirven?

En arquitecturas modernas, no todos los datos encajan eficientemente en tablas relacionales con restricciones rígidas de clave foránea. Spring Initializr ofrece integraciones oficiales de Spring Data para los principales motores NoSQL y sistemas de caché en memoria:

  • Spring Data MongoDB: Base de datos NoSQL documental líder. Almacena registros como documentos BSON (JSON binario) flexibles y semiestructurados. Ideal para catálogos dinámicos, historiales de eventos, perfiles de usuario y carritos de compra donde el esquema evoluciona constantemente.
  • Spring Data Redis: Almacén de datos en memoria ultrarrápido (latencias inferiores a 1 milisegundo). Se utiliza como Caché distribuida (mediante la abstracción @Cacheable), gestor de sesiones web (Spring Session), colas Pub/Sub ligeras y almacenamiento de estructuras de datos clave-valor (hashes, conjuntos, listas).
  • Spring Data Elasticsearch: Motor distribuido de indexación y búsqueda Full-Text basado en Apache Lucene. Permite realizar búsquedas difusas (fuzzy search), autocompletado, agregaciones analíticas complejas y filtrado de millones de registros en milisegundos.

Analogía del mundo real

Imaginemos un hospital veterinario de gran envergadura:

  • PostgreSQL / Base Relacional: El libro oficial de facturación contable y cobros con tarjeta (todo debe cuadrar al céntimo bajo estrictas reglas contables ACID).
  • MongoDB: El historial clínico de cada mascota (cada animal tiene un historial diferente: análisis de sangre, vacunas, fotos de radiografías, cirugías previas; un esquema rígido de columnas fijas sería inviable).
  • Redis: La pizarra magnética rápida de la sala de urgencias (contiene la lista inmediata de pacientes en triaje de los últimos 15 minutos; se lee y borra en un segundo para no ir al archivo general).
  • Elasticsearch: El buscador temático de la biblioteca médica (encuentra cualquier informe veterinario que contenga la palabra "fractura de fémur" aunque esté mal escrita).

2. Caso de Uso Real Estructurado

1. Contexto

Una tienda online de mascotas con 500.000 usuarios concurrentes consulta el catálogo de productos y calcula recomendaciones personalizadas en tiempo real.

2. El Problema (Solo con Base Relacional)

Cada vez que un usuario abre la portada, la base de datos relacional ejecuta 10 sentencias SELECT con múltiples JOIN para cargar categorías y promociones. El motor SQL colapsa bajo 10.000 peticiones por segundo y el tiempo de respuesta supera los 4 segundos.

3. La Solución (Con MongoDB + Redis)

El catálogo se almacena como documentos en MongoDB y las respuestas frecuentes se cachean en Redis con @Cacheable. El 95% de las lecturas se resuelven en memoria en menos de 2 milisegundos sin tocar el disco.

3. ¿Cuándo usar cada tecnología NoSQL y cuándo NO usarlas?

Tecnología NoSQL ¿Cuándo usarla? ¿Cuándo NO usarla?
Spring Data MongoDB Documentos con estructuras jerárquicas y anidadas (ej. carritos de compra, registros de sensores, historiales clínicos, catálogos multiatributo). Sistemas con transacciones financieras multi-tabla complejas donde la integridad referencial y las claves foráneas estrictas sean obligatorias por ley.
Spring Data Redis Caché de consultas lentas, limitación de tasa (Rate Limiting), sesiones web compartidas entre réplicas de microservicios y bloqueos distribuidos (Redlock). Como base de datos principal de almacenamiento a largo plazo sin un almacenamiento persistente secundario, o para consultas analíticas con filtros complejos.
Spring Data Elasticsearch Buscadores con autocompletado, filtrado facetado por múltiples criterios, búsqueda en lenguaje natural y agregación de logs. Como sistema transaccional de registro (System of Record) para operaciones de inserción y modificación de alta frecuencia.

5. Anotaciones Clave de Spring Data NoSQL

Anotación Librería Propósito y Uso
@Document(collection = "nombre") Spring Data MongoDB Mapea una clase Java a una colección de documentos en MongoDB.
@Id Spring Data Commons Marca el identificador único del documento (representado como String u ObjectId en Mongo).
@Field("nombre_json") Spring Data MongoDB Define el nombre de la clave dentro del documento BSON/JSON almacenado.
@EnableCaching Spring Context Habilita la infraestructura de caché distribuida en toda la aplicación Spring Boot.
@Cacheable(value = "cacheName", key = "#id") Spring Context / Redis Intercepta la llamada al método: si el resultado ya existe en Redis, lo devuelve de inmediato sin ejecutar el método; si no, ejecuta el método y guarda el valor en Redis con un TTL (tiempo de vida).
@CacheEvict(value = "cacheName", key = "#id") Spring Context / Redis Invalida y elimina la entrada correspondiente de la caché de Redis tras un UPDATE o DELETE.

6. Ejemplos de Implementación con Lombok

A. Documento y Repositorio MongoDB


package com.example.petshop.model.nosql;

import lombok.AllArgsConstructor;
import lombok.Builder;
import lombok.Getter;
import lombok.NoArgsConstructor;
import lombok.Setter;
import lombok.ToString;
import org.springframework.data.annotation.Id;
import org.springframework.data.mongodb.core.mapping.Document;
import org.springframework.data.mongodb.core.mapping.Field;

import java.util.List;
import java.util.Map;

@Document(collection = "pet_medical_records")
@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
@ToString
public class PetMedicalRecordDocument {

    @Id
    private String id;

    @Field("pet_code")
    private String petCode;

    private String petName;
    private List<String> allergies;
    
    // Esquema flexible semiestructurado: atributos dinámicos
    private Map<String, Object> clinicalNotes;
}


package com.example.petshop.repository.nosql;

import com.example.petshop.model.nosql.PetMedicalRecordDocument;
import org.springframework.data.mongodb.repository.MongoRepository;
import org.springframework.data.mongodb.repository.Query;
import org.springframework.stereotype.Repository;

import java.util.List;
import java.util.Optional;

@Repository
public interface PetMedicalRecordMongoRepository extends MongoRepository<PetMedicalRecordDocument, String> {

    Optional<PetMedicalRecordDocument> findByPetCode(String petCode);

    // Consulta nativa en sintaxis JSON de MongoDB
    @Query("{ 'allergies': ?0 }")
    List<PetMedicalRecordDocument> findPetsWithAllergy(String allergy);
}

B. Servicio con Caché en Memoria con Redis


package com.example.petshop.service.cache;

import com.example.petshop.model.nosql.PetMedicalRecordDocument;
import com.example.petshop.repository.nosql.PetMedicalRecordMongoRepository;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.cache.annotation.CacheEvict;
import org.springframework.cache.annotation.Cacheable;
import org.springframework.stereotype.Service;

@Slf4j
@Service
@RequiredArgsConstructor
public class PetMedicalService {

    private final PetMedicalRecordMongoRepository mongoRepository;

    // 1. Consulta con caché en Redis: las lecturas posteriores se resuelven en milisegundos desde RAM
    @Cacheable(value = "medical_records", key = "#petCode")
    public PetMedicalRecordDocument getRecordByPetCode(String petCode) {
        log.info("Accediendo a MongoDB para consultar el historial de: {}", petCode);
        return mongoRepository.findByPetCode(petCode)
                .orElseThrow(() -> new RuntimeException("Historial no encontrado para código: " + petCode));
    }

    // 2. Invalida la entrada en Redis cuando se modifica el historial para evitar datos obsoletos
    @CacheEvict(value = "medical_records", key = "#document.petCode")
    public PetMedicalRecordDocument updateRecord(PetMedicalRecordDocument document) {
        log.info("Actualizando historial en MongoDB e invalidando caché en Redis: {}", document.getPetCode());
        return mongoRepository.save(document);
    }
}

7. Contraejemplos y Antipatrones

Contraejemplo: Falta de TTL en Redis (Saturación de Memoria OOM)


# ANTIPATRÓN: Guardar en Redis sin tiempo de vida (TTL)
spring:
  cache:
    type: redis
    # Si no se configura time-to-live, las claves se acumulan infinitamente
    # hasta que Redis agota la memoria RAM del servidor y rechaza nuevas peticiones (OOM Crash).

Solución: Configurar siempre un TTL (Time-To-Live) prudente y políticas de expulsión (ej. allkeys-lru) en application.yml: 


spring:
  cache:
    type: redis
    redis:
      time-to-live: 3600000 # 1 hora de expiración automática
      cache-null-values: false
