Spring for RabbitMQ (AMQP): Mensajería y Enrutamiento Flexible

1. ¿Qué es y para qué sirve?

Spring for RabbitMQ (starter spring-boot-starter-amqp en Spring Initializr) proporciona una integración robusta con RabbitMQ, el broker de mensajería tradicional basado en el estándar AMQP (Advanced Message Queuing Protocol).

A diferencia de Kafka (donde los productores publican directamente en particiones de Topics), en RabbitMQ la arquitectura se basa en el desacoplamiento mediante Intercambiadores (Exchanges) y Colas (Queues):

  • Exchanges: Reciben los mensajes de los productores y los enrutan hacia una o más colas según reglas lógicas:
    • Direct Exchange: Enruta a la cola que coincida exactamente con la Routing Key.
    • Fanout Exchange: Difusión masiva (*broadcast*): reenvía el mensaje a todas las colas vinculadas sin evaluar ninguna clave.
    • Topic Exchange: Enrutamiento inteligente con comodines (ej. pet.order.* o pet.#).
    • Headers Exchange: Enruta evaluando las cabeceras del mensaje en lugar de la clave.
  • Colas (Queues): Almacenan los mensajes en memoria (o en disco) hasta que los consumidores los extraen y confirman su procesamiento mediante un ACK (Acknowledgement). Una vez confirmado, el mensaje se elimina de la cola.

Analogía del mundo real

Imaginemos la oficina central de clasificación de correos:

  • El productor mete una carta en el buzón general.
  • El Exchange es el clasificador central que mira la etiqueta de la carta: *"Urgente - Madrid"*.
  • Si la regla es Direct, la deposita en la saca específica de Madrid. Si la regla es Fanout (un aviso de emergencia general), hace 50 fotocopias y echa una en cada saca del país.
  • El repartidor (el Consumidor) llega, toma las cartas de su saca (la Cola), las reparte y firma el albarán (el ACK). Una vez firmada la entrega, la carta ya no ocupa espacio en la saca.

2. Caso de Uso Real Estructurado

1. Contexto

Una tienda de animales procesa pedidos con pagos, generación de facturas PDF pesadas y envíos de paquetería.

2. El Problema (Procesamiento síncrono)

Generar el PDF de la factura tarda 4 segundos. El cliente se queda esperando con la pantalla congelada durante el proceso de compra y si el generador de PDF falla, la compra entera se marca como errónea.

3. La Solución (Con RabbitMQ)

El pedido se guarda y se deposita un mensaje ligero en la cola invoice-generation-queue. El microservicio de PDFs procesa la cola en segundo plano; el cliente recibe su confirmación inmediata en 50 milisegundos.

3. ¿Cuándo usar RabbitMQ y cuándo NO usarlo?

Escenario Recomendación Motivo
Tareas asíncronas pesadas en segundo plano (generación de PDFs, procesamiento de imágenes, importación de ficheros Excel). SIEMPRE usar RabbitMQ Garantiza entrega fiable, reparto equitativo de carga entre trabajadores y reintentos con Dead Letter Exchange.
Enrutamiento complejo con patrones y comodines hacia diferentes colas departamentales. USAR RabbitMQ (Topic Exchange) Sus capacidades de enrutamiento son muy superiores y flexibles a las de Kafka.
Streaming masivo de telemetría de millones de sensores IoT o reproducción histórica de eventos (Replay). NO usar RabbitMQ (Usar Apache Kafka) RabbitMQ no está diseñado para retener históricos ni para volúmenes de millones de eventos continuos en disco.

5. Configuración de Topología AMQP en Spring Boot


package com.example.petshop.config;

import org.springframework.amqp.core.*;
import org.springframework.amqp.support.converter.Jackson2JsonMessageConverter;
import org.springframework.amqp.support.converter.MessageConverter;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class RabbitMqConfig {

    public static final String EXCHANGE_NAME = "petshop.direct.exchange";
    public static final String QUEUE_NAME = "petshop.invoice.queue";
    public static final String ROUTING_KEY = "petshop.invoice.generate";

    // 1. Definición del Intercambiador Directo
    @Bean
    public DirectExchange petDirectExchange() {
        return new DirectExchange(EXCHANGE_NAME, true, false);
    }

    // 2. Definición de la Cola persistente
    @Bean
    public Queue invoiceQueue() {
        return QueueBuilder.durable(QUEUE_NAME)
                .deadLetterExchange("petshop.dlx.exchange") // Redirige a DLX si falla
                .deadLetterRoutingKey("petshop.invoice.deadletter")
                .build();
    }

    // 3. Enlace (Binding) entre el Exchange y la Cola mediante la Routing Key
    @Bean
    public Binding invoiceBinding(Queue invoiceQueue, DirectExchange petDirectExchange) {
        return BindingBuilder.bind(invoiceQueue)
                .to(petDirectExchange)
                .with(ROUTING_KEY);
    }

    // 4. Conversor JSON automático para payloads de mensajes
    @Bean
    public MessageConverter jsonMessageConverter() {
        return new Jackson2JsonMessageConverter();
    }
}

6. Productor y Consumidor de Mensajes con Lombok

A. Productor (RabbitTemplate)


package com.example.petshop.producer;

import com.example.petshop.config.RabbitMqConfig;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.amqp.rabbit.core.RabbitTemplate;
import org.springframework.stereotype.Service;

import java.io.Serializable;

@Slf4j
@Service
@RequiredArgsConstructor
public class InvoiceMessageProducer {

    private final RabbitTemplate rabbitTemplate;

    public void sendInvoiceRequest(InvoiceRequestMessage message) {
        log.info("Depositando mensaje de factura en RabbitMQ para orden: {}", message.orderId());
        rabbitTemplate.convertAndSend(
                RabbitMqConfig.EXCHANGE_NAME,
                RabbitMqConfig.ROUTING_KEY,
                message
        );
    }

    public record InvoiceRequestMessage(String orderId, String customerEmail, double amount) implements Serializable {}
}

7. Contraejemplo y Error Fatal: Reintentos Infinitos (Poison Pill)


// ANTIPATRÓN: Consumidor que lanza una excepción no controlada sin Dead Letter Queue configurada
@RabbitListener(queues = "my-queue")
public void badConsumer(String message) {
    // Si el mensaje está corrupto (Poison Pill), el consumidor falla,
    // RabbitMQ reencola el mensaje inmediatamente y vuelve a entregarlo en un bucle infinito
    // saturando la CPU al 100% y llenando los discos con logs de error.
    throw new RuntimeException("Payload corrupto imposible de procesar");
}

Solución: Configurar siempre un límite de reintentos en application.yml (spring.rabbitmq.listener.simple.retry.max-attempts=3) y redirigir los mensajes venenosos a una Dead Letter Queue (DLQ) para su posterior inspección humana.
