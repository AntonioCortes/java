Estructura y Arquitectura de Aplicaciones en Spring Boot

1. Las Tres Capas Principales de la Arquitectura

Un proyecto de Spring Boot se divide típicamente en tres capas arquitectónicas fundamentales que delimitan responsabilidades y garantizan el desacoplamiento:

  • Capa API (Presentación / Web): Contiene todo lo relativo a la exposición pública de la aplicación. En ella residen los controladores REST (@RestController), los objetos de transferencia de datos (DTO - Data Transfer Object), los manejadores globales de excepciones (@RestControllerAdvice), los filtros de seguridad, interceptores y validadores de entrada.
  • Capa de Servicios (Lógica de Negocio): Contiene la lógica pura del dominio, el procesamiento de reglas de negocio, la coordinación y orquestación de operaciones transaccionales (@Transactional), las comunicaciones entre microservicios (mediante clientes Feign o RestTemplate/WebClient) y la publicación de eventos asíncronos en colas (RabbitMQ / Kafka).
  • Capa de Acceso a Datos (Persistencia / Infraestructura): Contiene los componentes responsables de interactuar con el motor de base de datos relacional o documental. En esta capa se ubican las interfaces de repositorios (JpaRepository, MongoRepository), las entidades persistentes (@Entity, @Document), convertidores de tipos y clases DAO (Data Access Object).

2. Estrategias de Organización de Paquetes en el Proyecto

Spring Framework no impone una estructura de carpetas rígida por defecto, permitiendo adoptar la convención que mejor se adapte al tamaño, escala y ciclo de vida del proyecto:

2.1. Organización por Funcionalidad o Dominio (Package-by-Feature / Vertical Slices)

Recomendada por la documentación oficial de Spring y en proyectos orientados a Domain-Driven Design (DDD). Agrupa todas las clases de un mismo dominio de negocio dentro de un paquete común, facilitando la modularización y la extracción futura a microservicios independientes: 


com
 +- example
     +- petshop
         +- PetShopApplication.java   # Clase principal de arranque en el paquete raíz
         |
         +- customer
         |   +- Customer.java
         |   +- CustomerController.java
         |   +- CustomerService.java
         |   +- CustomerRepository.java
         |
         +- pet
         |   +- Pet.java
         |   +- PetController.java
         |   +- PetService.java
         |   +- PetRepository.java
         |
         +- order
             +- Order.java
             +- OrderController.java
             +- OrderService.java
             +- OrderRepository.java
Estructura organizada por funcionalidad (Package-by-Feature)

2.2. Organización Tradicional por Capas Técnicas (Package-by-Layer)

Agrupa los artefactos según su rol técnico (todos los controladores juntos, todos los servicios juntos, todos los repositorios juntos). Es muy popular en microservicios pequeños o medianos con un alcance de dominio bien delimitado: 


com
 +- example
     +- petshop
         +- PetShopApplication.java   # Clase principal en el paquete raíz
         |
         +- controller
         |   +- CustomerController.java
         |   +- PetController.java
         |   +- OrderController.java
         |
         +- service
         |   +- CustomerService.java
         |   +- PetService.java
         |   +- OrderService.java
         |
         +- repository
         |   +- CustomerRepository.java
         |   +- PetRepository.java
         |   +- OrderRepository.java
         |
         +- model / entity
             +- Customer.java
             +- Pet.java
             +- Order.java

3. La Anotación @SpringBootApplication y el Component Scanning

Todo proyecto de Spring Boot cuenta con una clase principal que contiene el método main utilizado para arrancar el contenedor. Esta clase se marca con la anotación @SpringBootApplication: 


package com.example.petshop;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class PetShopApplication {

    public static void main(String[] args) {
        SpringApplication.run(PetShopApplication.class, args);
    }
}
Clase de arranque con @SpringBootApplication

Composición Interna de @SpringBootApplication

Meta-Anotación Propósito y Mecanismo Interno
@SpringBootConfiguration Identifica la clase como una clase de configuración equivalente a @Configuration de Spring, permitiendo declarar beans con @Bean.
@EnableAutoConfiguration El núcleo de la magia de Spring Boot: examina el classpath (los JARs añadidos en Maven o Gradle) y registra automáticamente los beans de infraestructura mediante condiciones como @ConditionalOnClass o @ConditionalOnMissingBean (ej. si detecta el driver de Postgres y Spring Data JPA, autoconfigura el DataSource y el EntityManagerFactory).
@ComponentScan Escaneo jerárquico de paquetes: Activa la búsqueda automática de clases marcadas con @Component, @Service, @Repository y @RestController. Regla Crítica: Solo escanea el paquete donde se encuentra la clase principal y todos sus subpaquetes descendientes.

4. Inicializadores de Arranque: CommandLineRunner y ApplicationRunner

Si se necesita ejecutar código específico nada más finalizar el arranque del microservicio (como precargar datos de prueba o validar conectividad externa), Spring Boot ofrece las interfaces CommandLineRunner y ApplicationRunner: 


package com.example.petshop.config;

import com.example.petshop.model.relational.PetEntity;
import com.example.petshop.repository.relational.PetJpaRepository;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.boot.CommandLineRunner;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import java.time.LocalDate;

@Slf4j
@RequiredArgsConstructor
@Configuration
public class DataInitializerConfig {

    private final PetJpaRepository petRepository;

    @Bean
    public CommandLineRunner initDatabase() {
        return args -> {
            log.info("Verificando catálogo inicial de mascotas...");
            if (petRepository.count() == 0) {
                petRepository.save(PetEntity.builder()
                        .name("Thor")
                        .species("Dog")
                        .age(2)
                        .vaccinated(true)
                        .admissionDate(LocalDate.now())
                        .build());
                log.info("Mascota inicial creada con éxito en la base de datos.");
            }
        };
    }
}

5. Contraejemplos y Antipatrones de Estructura

Contraejemplo: Ubicar la Clase Principal en un Subpaquete Interno


# ANTIPATRÓN CATASTRÓFICO: La clase principal está dentro de un subpaquete
com.example.petshop
 +- controller
 |   +- PetController.java      # ¡NUNCA SERÁ ESCANEADO!
 +- service
 |   +- PetService.java         # ¡NUNCA SERÁ ESCANEADO!
 +- config
     +- PetShopApplication.java # ERROR: Solo escaneará 'com.example.petshop.config.*'

Consecuencia técnica: Todas las peticiones HTTP a /petshop/pet devolverán 404 NOT FOUND y las inyecciones de servicio fallarán con NoSuchBeanDefinitionException, porque @ComponentScan no escanea paquetes hermanos o superiores.

Solución Obligatoria: La clase @SpringBootApplication debe ubicarse siempre en el paquete raíz (com.example.petshop).
