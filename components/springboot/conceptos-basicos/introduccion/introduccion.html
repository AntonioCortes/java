Introducción a Spring Boot

Spring Boot makes it easy to create stand-alone, production-grade Spring based Applications that you can "just run".

1. ¿Qué es Spring Boot y qué problema resuelve?

Spring Boot es una extensión del framework Spring que elimina la complejidad de configuración tradicional (*boilerplate* y configuración XML masiva). Su objetivo fundamental es permitir a los desarrolladores construir aplicaciones y microservicios listos para producción con un esfuerzo de arranque mínimo, aplicando el principio de convención sobre configuración (opinionated defaults).

Analogía del mundo real

Construir una aplicación con el Spring clásico tradicional equivalía a comprar un mueble de piezas sueltas sin instrucciones: había que seleccionar manualmente el servidor web (Tomcat o Jetty), configurar el despachador de peticiones (DispatcherServlet), conectar las librerías de JSON (Jackson) y configurar a mano los conversores y transacciones. En cambio, Spring Boot es como comprar un electrodoméstico listo para enchufar y encender ("just run"): incluye el servidor web embebido internamente, detecta las librerías añadidas en el archivo de construcción y autoconfigura la infraestructura sin intervención manual.

2. Estereotipos de Spring: La Anotación @Component y sus Especializaciones

El contenedor de Inversión de Control (IoC) de Spring autodetecta las clases marcadas con la anotación @Component mediante el escaneo de paquetes (Component Scanning), registrándolas como Spring Beans en el contexto de la aplicación para poder inyectarlas donde se necesiten. Tiene las mismas funcionalidades base que las etiquetas especializadas @Service, @Controller y @Repository, pero estas últimas añaden semántica arquitectónica y comportamientos adicionales:

Anotación Capa Arquitectónica Comportamiento Especial y Propósito
@Component Genérica / Utilitaria Anota cualquier clase gestionada por el contenedor IoC que no encaje de forma estricta en las capas MVC tradicionales (ej. convertidores, clientes de colas, componentes auxiliares).
@Service Capa de Negocio (Servicios) Indica que la clase encapsula lógica de negocio, orquestación de operaciones y demarcación transaccional (@Transactional). No añade traducción de excepciones, pero comunica semánticamente el rol en la arquitectura limpia.
@Repository Capa de Persistencia (DAOs / Acceso a Datos) Encapsula el acceso y manipulación de datos en la base de datos. Añade traducción automática de excepciones: intercepta excepciones de bajo nivel del driver JDBC o Hibernate y las traduce de forma transparente a la jerarquía de excepciones de Spring (DataAccessException).
@Controller / @RestController Capa Web / Presentación (API) Mapea peticiones HTTP, gestiona rutas REST, procesa payloads de entrada y devuelve vistas HTML (@Controller) o datos JSON/XML planos (@RestController).

3. Ciclo de Vida de un Bean en Spring Boot

Cuando el contenedor de Spring arranca la aplicación, cada componente atraviesa un ciclo de vida rigurosamente ordenado:

  1. Instanciación: El contenedor llama al constructor del Bean (o ejecuta el método factory @Bean).
  2. Inyección de Dependencias: Spring inyecta todos los colaboradores requeridos (mediante inyección por constructor o campos).
  3. Interfaces "Aware": Si el Bean implementa interfaces como BeanNameAware o ApplicationContextAware, Spring le entrega acceso al contexto.
  4. Inicialización (@PostConstruct): Se ejecuta el método anotado con @PostConstruct (definido en la especificación Jakarta Annotations). En este punto, todas las dependencias ya están inyectadas y listas para ser utilizadas con total seguridad.
  5. Fase Activa: El Bean está en servicio atendiendo peticiones concurrentes en la aplicación.
  6. Destrucción (@PreDestroy): Justo antes de que el contexto de Spring se apague (por ejemplo, al detener el microservicio), se ejecuta el método anotado con @PreDestroy para liberar recursos, cerrar conexiones de red o finalizar hilos en segundo plano de forma limpia.

Ejemplo Completo del Ciclo de Vida


package com.example.petshop.component;

import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Component;

@Slf4j
@Component
public class CacheWarmupComponent {

    public CacheWarmupComponent() {
        log.info("[PASO 1 - Constructor] Instanciando CacheWarmupComponent. Las dependencias aún no están inyectadas.");
    }

    @PostConstruct
    public void init() {
        log.info("[PASO 2 - @PostConstruct] Componente completamente inicializado con dependencias listas.");
        log.info("Cargando catálogo inicial de mascotas en la memoria caché...");
    }

    public void executeTask() {
        log.info("[PASO 3 - Uso] Ejecutando operación de negocio con el componente activo.");
    }

    @PreDestroy
    public void cleanup() {
        log.info("[PASO 4 - @PreDestroy] Apagando aplicación. Vaciando cachés y cerrando conexiones abiertas...");
    }
}
Ejemplo de gestión del ciclo de vida de un bean con @PostConstruct y @PreDestroy ---

4. Ámbitos de los Beans (Bean Scopes)

Por defecto, todos los beans en Spring son Singleton (una única instancia por contenedor). Sin embargo, Spring permite modificar el alcance del bean mediante la anotación @Scope:

Ámbito (Scope) Instancias Creadas Cuándo Usarlo Cuándo NO Usarlo
singleton (por defecto) 1 única instancia compartida por todo el ApplicationContext. Para servicios, repositorios y controladores sin estado mutable (*stateless*). Clases que mantengan variables de estado que muten por usuario o petición HTTP (provocaría condiciones de carrera concurrentes).
prototype Una nueva instancia cada vez que se solicita el bean con getBean() o se inyecta. Objetos con estado mutable específico de una operación o que no sean seguros para hilos (*thread-safe*). Servicios pesados o DAOs sin estado (desperdicia memoria y tiempo de CPU creando objetos idénticos).
request Una instancia por cada petición HTTP entrante. Se destruye al finalizar la respuesta. Contextos de auditoría de petición (IP de origen, ID de correlación de traza, tiempo de inicio de la llamada). Aplicaciones no web o procesos batch en segundo plano.
session Una instancia por cada sesión HTTP de usuario (mantenida entre múltiples peticiones). Carritos de la compra en aplicaciones con renderizado en servidor tradicional o preferencias de usuario. Arquitecturas de microservicios REST modernas sin estado (*stateless* con JWT).
---

5. Cuándo Usar y Cuándo NO Usar Cada Estereotipo

Anotación Cuándo Usarla Cuándo NO Usarla
@Component Para utilidades generales, interceptores, scheduled tasks (@Scheduled) o clientes de colas de mensajería (RabbitMQ / Kafka). En clases de acceso a base de datos (usar @Repository) o servicios de negocio (usar @Service).
@Repository En interfaces o clases que acceden a tablas, índices o colecciones persistentes. En controladores o servicios que no realizan operaciones directas de almacenamiento.
@Service En clases donde reside la lógica pura, cálculos de precios, validaciones y orquestación. En clases puramente técnicas sin lógica de negocio o en DTOs.

6. Contraejemplos y Antipatrones Frecuentes

Contraejemplo 1: Ejecutar Lógica que Depende de Spring en el Constructor


// ANTIPATRÓN: Intentar usar dependencias o consultar la BD en el constructor
@Component
public class BadInitializationComponent {

    private final PetRepository petRepository;

    public BadInitializationComponent(PetRepository petRepository) {
        this.petRepository = petRepository;
        // ERROR: Aunque petRepository esté asignado, el contexto de Spring aún no ha finalizado
        // de configurar proxies transaccionales ni conexiones. Puede provocar fallos silenciosos.
        this.petRepository.count(); 
    }
}

Solución: Mover la lógica de arranque a un método anotado con @PostConstruct o implementar ApplicationRunner.

Contraejemplo 2: Estado Mutable en un Bean Singleton


// ANTIPATRÓN CATASTRÓFICO: Variable de estado mutable en un Singleton compartido
@Service
public class UnsafePetService {

    // PELIGRO: Todos los hilos concurrentes que invoquen el servicio compartirán esta variable.
    // El usuario B verá los datos del usuario A (Race Condition y fuga de datos).
    private String currentLoggedInUser; 

    public void processAdoption(Long petId, String username) {
        this.currentLoggedInUser = username; // Mutación insegura
        // ...
    }
}

Solución: Mantener los servicios estrictamente sin estado (*stateless*), pasando el usuario como argumento local del método o leyéndolo de forma segura para hilos mediante ThreadLocal (como hace SecurityContextHolder).
