Inyección de Dependencias (Dependency Injection)

1. ¿Qué es la Inyección de Dependencias y el Principio IoC?

La Inyección de Dependencias (Dependency Injection - DI) es un patrón de diseño y un mecanismo fundamental de Spring Framework que materializa el principio de Inversión de Control (Inversion of Control - IoC): separa la responsabilidad de crear las instancias de los objetos de su uso dentro de la lógica de negocio.

En lugar de crear manualmente las instancias de las clases mediante el operador new (lo que genera un acoplamiento rígido entre componentes), las dependencias se declaran como contratos o interfaces y el Contenedor IoC de Spring se encarga de instanciarlas, resolverlas e inyectarlas automáticamente en tiempo de ejecución. De esta forma, se reduce drásticamente el acoplamiento entre las diferentes partes de la aplicación y se mejora la flexibilidad, la mantenibilidad y la testabilidad.

Analogía del mundo real

Imaginemos una lámpara de escritorio:

  • Sin Inyección de Dependencias (Acoplamiento fuerte): La lámpara viene de fábrica con una bombilla incandescente soldada a los cables internos. Si la bombilla se funde o queremos probar una bombilla LED de bajo consumo o una luz tenue para pruebas, tenemos que destruir la lámpara entera.
  • Con Inyección de Dependencias (Acoplamiento débil): La lámpara tiene un casquillo estándar (la interfaz o contrato). La persona que usa la lámpara puede "inyectarle" cualquier bombilla que encaje en el casquillo (una bombilla real halógena, una LED inteligente o una bombilla simulada en un laboratorio de pruebas). La lámpara funciona sin saber qué marca concreta de bombilla tiene conectada.

2. Las Tres Formas de Inyectar Dependencias en Spring

Existen tres formas de inyectar dependencias por medio de la anotación @Autowired en Spring:

  1. Inyección por Constructor (Estándar recomendado por el equipo de Spring).
  2. Inyección por Atributo o Campo (Field Injection).
  3. Inyección por medio del método Set (Setter Injection).
---

2.1. Inyección por Atributo (Field Injection)

Consiste en colocar la anotación @Autowired directamente sobre el atributo privado de la clase: 


@Service
public class PetServiceFieldInjection {

    @Autowired
    private PetJpaRepository petRepository;

    public Optional<PetEntity> findById(Long id) {
        return petRepository.findById(id);
    }
}
Ejemplo de inyección de dependencia por atributo

¿Por qué está desaconsejada en código moderno? Aunque es muy corta de escribir, presenta graves inconvenientes arquitectónicos:

  • Viola el encapsulamiento: Requiere que Spring utilice reflexión interna para modificar atributos privados.
  • Impide la inmutabilidad: Los campos no pueden declararse como final, lo que permite que el objeto mute accidentalmente después de su inicialización.
  • Dificulta los tests unitarios puros: En un test unitario con JUnit 5 sin Spring, es imposible pasar un mock a este atributo a menos que se recurra a reflexión compleja (ReflectionTestUtils) o se levante el pesado contexto de Spring.
  • Oculta el exceso de dependencias: Facilita que una clase acabe inyectando 10 repositorios distintos sin que el desarrollador perciba la violación del Principio de Responsabilidad Única.
---

2.2. Inyección por Setter (Método Set)

La dependencia se suministra a través de un método setter público anotado con @Autowired: 


@Service
public class PetServiceSetterInjection {

    private NotificationService notificationService;

    @Autowired
    public void setNotificationService(NotificationService notificationService) {
        this.notificationService = notificationService;
    }

    public void notifyAdoption(String petName) {
        if (notificationService != null) {
            notificationService.sendNotification(petName);
        }
    }
}
Ejemplo de inyección de dependencia por medio del método Set

Cuándo usarla: Únicamente para dependencias opcionales o que admitan reconfiguración dinámica en caliente en tiempo de ejecución. Si la dependencia es obligatoria para el funcionamiento de la clase, usar setter es peligroso porque permite que el objeto quede a medio instanciar y lance NullPointerException.

---

2.3. Inyección por Constructor (El Estándar Moderno Recomendado)

Las dependencias se declaran como atributos private final y se reciben como parámetros en el constructor de la clase: 


@Service
public class PetServiceConstructorManual {

    private final PetJpaRepository petRepository;
    private final NotificationService notificationService;

    // A partir de Spring Framework 4.3, si la clase solo tiene un constructor,
    // la anotación @Autowired es 100% opcional y Spring la aplica automáticamente.
    public PetServiceConstructorManual(PetJpaRepository petRepository, 
                                       NotificationService notificationService) {
        this.petRepository = petRepository;
        this.notificationService = notificationService;
    }
}

Forma Idiomática y Limpia con Project Lombok (@RequiredArgsConstructor)

Para eliminar el código repetitivo del constructor manual respetando las directrices de diseño del proyecto, se utiliza la anotación @RequiredArgsConstructor de Lombok sobre la clase, la cual genera automáticamente en tiempo de compilación el constructor exacto para todos los campos marcados como final: 


package com.example.petshop.service;

import com.example.petshop.repository.relational.PetJpaRepository;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Service;

@Slf4j
@RequiredArgsConstructor
@Service
public class PetServiceImpl implements PetService {

    // Las dependencias son inmutables (final) y se inyectan automáticamente en el constructor generado por Lombok
    private final PetJpaRepository petRepository;
    private final NotificationService notificationService;

    // Métodos de negocio...
}
Inyección por constructor idiomática con Lombok @RequiredArgsConstructor

Ventajas indiscutibles de la Inyección por Constructor:

  1. Testabilidad superior: En tests unitarios con JUnit 5 o Mockito se instancia la clase de forma trivial con new PetServiceImpl(mockRepo, mockNotification) sin necesidad de reflection ni de arrancar el framework.
  2. Inmutabilidad garantizada: Los campos final previenen que las dependencias sean reasignadas o corrompidas una vez instanciado el bean.
  3. Imposibilidad de estados corruptos: Un objeto nunca puede existir a medio construir; el compilador de Java exige suministrar todas las dependencias requeridas para crear la instancia.
  4. Detección temprana de dependencias circulares: Si la clase A necesita a B y B necesita a A, Spring detecta el ciclo inmediatamente al arrancar la aplicación y falla de forma temprana (Fail-Fast), evitando bucles infinitos en ejecución.

4. Desambiguación y Otras Anotaciones de Inyección

Spring proporciona anotaciones complementarias para afinar el comportamiento de la inyección de dependencias:

  • @Qualifier("nombreBean"): Permite desambiguar qué bean concreto inyectar cuando existen dos o más implementaciones de la misma interfaz registradas en el contenedor (evita la excepción NoUniqueBeanDefinitionException). 
    
@Service
public class OrderService {
    private final PaymentGateway paymentGateway;

    public OrderService(@Qualifier("paypalGateway") PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }
}
  • @Primary: Se coloca sobre una clase de implementación para indicar que es la opción preferente por defecto cuando hay varios candidatos y el llamador no especifica ningún @Qualifier.
  • @Value("${propiedad:valorDefecto}"): Permite inyectar valores escalares (cadenas, enteros, booleanos) procedentes del archivo de configuración (application.yml) o variables de entorno: 
    
@Component
public class ReportConfig {
    @Value("${app.reports.max-records:500}")
    private int maxRecords;
}
  • @Resource: Anotación estándar de Jakarta EE (JSR-250) que inyecta dependencias asociándolas prioritariamente por nombre de bean en lugar de por tipo.

5. Contraejemplos y Antipatrones de Inyección

Contraejemplo: Dependencia Circular Oculta por Field Injection


// ANTIPATRÓN: Servicio A inyecta a B por campo, y B inyecta a A por campo
@Service
public class ServiceA {
    @Autowired
    private ServiceB serviceB; // Spring intentará resolverlo tardíamente
}

@Service
public class ServiceB {
    @Autowired
    private ServiceA serviceA; // Dependencia circular encubierta
}

Por qué es un problema: Las dependencias circulares delatan un grave error de diseño arquitectónico (acoplamiento bidireccional indebido). Con inyección por constructor, Spring Boot bloquea el arranque inmediatamente con BeanCurrentlyInCreationException, obligando a desacoplar el código extrayendo la lógica común a un tercer servicio o utilizando eventos de aplicación (ApplicationEventPublisher).
