Manejo de Excepciones en Spring Boot

En aplicaciones web y APIs REST empresariales construidas con Spring Boot, el manejo adecuado y uniforme de errores es un pilar fundamental de la robustez, seguridad y experiencia de desarrollo. En lugar de atrapar excepciones manualmente en cada capa o método de controlador mediante bloques repetitivos, Spring MVC ofrece una arquitectura de intercepción global desacoplada basada en AOP (Aspect-Oriented Programming) a través de la anotación @RestControllerAdvice.

Analogía del Mundo Real: El Mostrador Central de Reclamaciones

Imagina unos grandes almacenes o una tienda de mascotas. En cada mostrador, los cajeros y dependientes (los Controladores REST) y los veterinarios del almacén (los Servicios) se dedican exclusivamente a su trabajo: registrar adopciones, tramitar cobros o inventariar productos. Si un cliente solicita una mascota que ya no existe o su tarjeta no tiene fondos, el cajero no improvisa una solución extraña ni discute con el cliente; simplemente declara la incidencia formal (lanza una excepción) y la deriva al Mostrador Central de Atención al Cliente e Incidencias (el @RestControllerAdvice). Este mostrador especializado conoce exactamente el protocolo oficial de la empresa, redacta una hoja estandarizada de reclamación con fecha, código de motivo y pasos a seguir, y se la entrega al cliente en un formato uniforme y comprensible.

Caso de Uso Real Estructurado

1. Contexto

Una API REST de gestión de mascotas (PetStore) expone endpoints para consultar mascotas por identificador (GET /petshop/pet/{id}) y crear nuevas mascotas con validación estricta de campos (POST /petshop/pet).

2. El Problema (Sin la solución)

Cada método de cada controlador se llena de bloques try-catch (Exception e) duplicados. Si un error no se captura, Spring devuelve por defecto un código 500 Internal Server Error con el stacktrace completo de Java, exponiendo nombres de tablas, paquetes y versiones a atacantes externos (vulnerabilidad de Information Disclosure), mientras que otros métodos devuelven cadenas de texto planas sin estructura JSON.

3. La Solución (Con @RestControllerAdvice)

Los controladores y servicios quedan limpios de bloques try-catch. Las excepciones de dominio (ej. PetNotFoundException) o validaciones (MethodArgumentNotValidException) burbujean de forma natural y son interceptadas por una clase centralizada que emite siempre un JSON estructurado con el código de estado HTTP canónico (404, 400, 409, etc.).

¿Cuándo usarlo y cuándo NO usarlo?

Mecanismo / Enfoque ¿Cuándo usarlo? ¿Cuándo NO usarlo?
@RestControllerAdvice + @ExceptionHandler Enfoque recomendado por defecto para cualquier API REST o microservicio. Permite centralizar la traducción de cualquier excepción (de negocio, validación, base de datos) a un contrato JSON unificado con cabeceras y códigos HTTP personalizados. No aplicable en aplicaciones web tradicionales basadas en renderizado de vistas MVC con servidor (JSP, Thymeleaf) donde se prefiera devolver páginas HTML de error en lugar de JSON (en ese caso usar @ControllerAdvice simple devolviendo vistas o ErrorController).
@ResponseStatus en la clase Excepción Para excepciones de negocio muy sencillas y estáticas donde el código HTTP y el mensaje siempre son idénticos (ej. @ResponseStatus(HttpStatus.NOT_FOUND) public class PetNotFoundException). Cuando se necesita devolver un cuerpo JSON dinámico con listas de campos erróneos, marcas de tiempo (timestamp) o contexto específico de la petición.
ResponseStatusException (Spring 5+) Para lanzar errores puntuales y rápidos en prototipos o endpoints sencillos sin necesidad de declarar una clase Exception específica: throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Mascota no existe"). En arquitecturas empresariales medianas o grandes: dispersa los códigos HTTP por los servicios de negocio, acopla la capa de servicio a clases de Spring Web y dificulta mantener contratos JSON estandarizados.
Bloques try-catch en Controladores Únicamente cuando se requiere realizar una acción de compensación o recuperación inmediata local y continuar el flujo normal devolviendo un resultado 200 OK alternativo. Antipatrón absoluto para devolver códigos de error o formatear respuestas HTTP. Genera código espagueti duplicado, oculta fallos reales y rompe el principio de responsabilidad única (SRP).

Dependencias Necesarias

El soporte para @RestControllerAdvice y el manejo de excepciones web está incluido de forma nativa en el starter web de Spring Boot. Si además se gestionan validaciones de entrada con anotaciones como @NotBlank, @Min o @Size, se requiere el starter de validación:

Maven (pom.xml)


<!-- Starter Web de Spring Boot (incluye Spring MVC y soporte de @RestControllerAdvice) -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>

<!-- Starter de Validación de Jakarta / Hibernate Validator (opcional pero recomendado) -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>

Gradle (build.gradle)


dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-validation'
}

El siguiente diagrama ilustra cómo fluye una petición cuando ocurre un error en la capa de negocio, demostrando cómo @RestControllerAdvice actúa como una red de seguridad perimetral que intercepta la excepción antes de que alcance al cliente:

Figura 1: Flujo de intercepción global de excepciones con @RestControllerAdvice y @ExceptionHandler
Participante Rol / Estereotipo Responsabilidad en el Manejo de Excepciones
Cliente HTTP «cliente / front-end» Realiza una petición REST (ej. GET /petshop/pet/99) y recibe una respuesta con código de estado HTTP adecuado (ej. 404 NOT_FOUND) y un cuerpo JSON con el error estructurado.
PetController «controlador REST» Punto de entrada de la petición HTTP. Delega inmediatamente en PetService sin envolver en bloques try-catch, permitiendo que las excepciones de negocio fluyan libremente.
PetServiceImpl «capa de servicio» Ejecuta la lógica de negocio y persistencia. Si no halla el registro solicitado en la base de datos, lanza una excepción de dominio no chequeada (throw new PetNotFoundException(99)).
GlobalExceptionHandler «interceptor global de excepciones» Clase anotada con @RestControllerAdvice. Sus métodos con @ExceptionHandler capturan tipos concretos de excepciones, generan trazas de log con SLF4J y devuelven un ResponseEntity<ErrorResponseDTO> seguro al cliente.
ErrorResponseDTO «DTO de contrato de error» Objeto inmutable que define el formato JSON público devuelto al cliente (timestamp, código HTTP, mensaje de negocio legible, ruta URL de la petición y lista opcional de errores de validación de campos).

Anotaciones y Clases Clave del Framework

Anotaciones de Spring MVC

  • @ControllerAdvice: Anotación propia de Spring Framework ubicada en el paquete org.springframework.web.bind.annotation.ControllerAdvice.

    Especialización de @Component que permite declarar métodos de intercepción compartidos entre múltiples controladores de la aplicación (mediante @ExceptionHandler, @InitBinder y @ModelAttribute). Por defecto aplica a todos los controladores registrados en el contexto, aunque puede filtrarse mediante parámetros como basePackages, assignableTypes o annotations.

  • @RestControllerAdvice: Anotación propia de Spring Framework ubicada en el paquete org.springframework.web.bind.annotation.RestControllerAdvice.

    Anotación compuesta que combina @ControllerAdvice y @ResponseBody. Es la opción estándar para APIs REST, ya que garantiza que el valor devuelto por cada método manejador de excepción sea automáticamente serializado a JSON/XML en el cuerpo de la respuesta HTTP sin requerir @ResponseBody en cada método.

  • @ExceptionHandler: Anotación propia de Spring Framework ubicada en el paquete org.springframework.web.bind.annotation.ExceptionHandler.

    Marca un método dentro de una clase consejo (advice) o dentro de un controlador concreto para manejar una o más familias de excepciones. Sus opciones principales son:

    • value: Array de clases de excepción que este método es capaz de interceptar (ej. @ExceptionHandler({PetNotFoundException.class, UserNotFoundException.class})). Si se omite, Spring infiere el tipo a partir del parámetro del método.
  • @ResponseStatus: Anotación propia de Spring Framework ubicada en el paquete org.springframework.web.bind.annotation.ResponseStatus.

    Permite asociar un código de estado HTTP predeterminado a un método o a una clase de excepción personalizada. Acepta los parámetros code o value (ej. HttpStatus.NOT_FOUND) y opcionalmente reason (cadena estática de motivo).

Clases y Modelos de Error

  • ResponseEntity<T>: Clase de org.springframework.http.ResponseEntity que representa la respuesta HTTP completa, incluyendo código de estado (HttpStatus), cabeceras (HttpHeaders) y cuerpo serializable (body).
  • MethodArgumentNotValidException: Excepción de org.springframework.web.bind.MethodArgumentNotValidException lanzada automáticamente por Spring cuando un parámetro anotado con @Valid falla en sus restricciones de Bean Validation. Contiene el objeto BindingResult que detalla cada campo erróneo y su mensaje de validación.
  • ProblemDetail (RFC 7807 / RFC 9457): Clase introducida en Spring Framework 6 y Spring Boot 3 ubicada en org.springframework.http.ProblemDetail. Proporciona una especificación estándar de la IETF para representar errores en APIs HTTP con campos predefinidos: type (URI del tipo de error), title, status, detail e instance.

Implementación Práctica Paso a Paso

Paso 1: DTO Estándar de Respuesta de Error

Definimos el modelo de datos que recibirán los clientes cuando ocurra cualquier fallo en la API: 


package com.example.petstore.dto;

import com.fasterxml.jackson.annotation.JsonInclude;
import lombok.Builder;
import lombok.Getter;

import java.time.LocalDateTime;
import java.util.List;

@Getter
@Builder
@JsonInclude(JsonInclude.Include.NON_NULL)
public class ErrorResponseDTO {

    private final LocalDateTime timestamp;
    private final int status;
    private final String error;
    private final String message;
    private final String path;
    private final List<FieldErrorDTO> fieldErrors;

    @Getter
    @Builder
    public static class FieldErrorDTO {
        private final String field;
        private final String message;
        private final Object rejectedValue;
    }
}

Paso 2: Excepción de Negocio Personalizada

Creamos excepciones específicas para el dominio que hereden de RuntimeException (excepciones no chequeadas), evitando la necesidad de declarar throws en interfaces y firmas de métodos: 


package com.example.petstore.exception;

import lombok.Getter;

@Getter
public class PetNotFoundException extends RuntimeException {

    private final Integer petId;

    public PetNotFoundException(Integer petId) {
        super(String.format("No existe ninguna mascota con el identificador: %d", petId));
        this.petId = petId;
    }
}

Paso 3: Manejador Global Centralizado (@RestControllerAdvice)

Implementamos la clase interceptora con métodos dedicados a cada tipo de fallo: excepciones de dominio, validaciones de beans y fallback genérico para imprevistos: 


package com.example.petstore.exception;

import com.example.petstore.dto.ErrorResponseDTO;
import jakarta.servlet.http.HttpServletRequest;
import lombok.extern.slf4j.Slf4j;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.time.LocalDateTime;
import java.util.List;

@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    // 1. Manejo de recurso no encontrado (404 Not Found)
    @ExceptionHandler(PetNotFoundException.class)
    public ResponseEntity<ErrorResponseDTO> handlePetNotFound(
            PetNotFoundException ex, 
            HttpServletRequest request) {

        log.warn("Recurso no encontrado: {} en ruta {}", ex.getMessage(), request.getRequestURI());

        ErrorResponseDTO error = ErrorResponseDTO.builder()
                .timestamp(LocalDateTime.now())
                .status(HttpStatus.NOT_FOUND.value())
                .error(HttpStatus.NOT_FOUND.getReasonPhrase())
                .message(ex.getMessage())
                .path(request.getRequestURI())
                .build();

        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(error);
    }

    // 2. Manejo de errores de validación de Bean Validation (400 Bad Request)
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponseDTO> handleValidationErrors(
            MethodArgumentNotValidException ex, 
            HttpServletRequest request) {

        log.warn("Fallo de validación en {} campos al invocar {}", ex.getFieldErrorCount(), request.getRequestURI());

        List<ErrorResponseDTO.FieldErrorDTO> fieldErrors = ex.getBindingResult()
                .getFieldErrors()
                .stream()
                .map(field -> ErrorResponseDTO.FieldErrorDTO.builder()
                        .field(field.getField())
                        .message(field.getDefaultMessage())
                        .rejectedValue(field.getRejectedValue())
                        .build())
                .toList();

        ErrorResponseDTO error = ErrorResponseDTO.builder()
                .timestamp(LocalDateTime.now())
                .status(HttpStatus.BAD_REQUEST.value())
                .error(HttpStatus.BAD_REQUEST.getReasonPhrase())
                .message("La petición contiene datos inválidos o incompletos")
                .path(request.getRequestURI())
                .fieldErrors(fieldErrors)
                .build();

        return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(error);
    }

    // 3. Fallback genérico para errores no controlados (500 Internal Server Error)
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponseDTO> handleGenericException(
            Exception ex, 
            HttpServletRequest request) {

        // Se registra el stacktrace completo internamente en logs para auditoría técnica
        log.error("Excepción no controlada procesando petición en {}: ", request.getRequestURI(), ex);

        // NUNCA devolver el mensaje técnico de ex ni el stacktrace al cliente público
        ErrorResponseDTO error = ErrorResponseDTO.builder()
                .timestamp(LocalDateTime.now())
                .status(HttpStatus.INTERNAL_SERVER_ERROR.value())
                .error(HttpStatus.INTERNAL_SERVER_ERROR.getReasonPhrase())
                .message("Ha ocurrido un error interno en el servidor. Por favor, contacte con soporte.")
                .path(request.getRequestURI())
                .build();

        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(error);
    }
}

Ejemplo vs Contraejemplo

Contraejemplo: Cómo NO gestionar las excepciones (Antipatrón)

En el siguiente código, el controlador captura las excepciones a mano con bloques try-catch, devuelve formatos incoherentes y expone vulnerabilidades de seguridad: 


// ANTIPATRÓN: Código contaminado con try-catch, estados HTTP incorrectos y fuga de stacktraces
@RestController
@RequestMapping("/petshop/pet")
public class BadPetController {

    private final PetService petService;

    public BadPetController(PetService petService) {
        this.petService = petService;
    }

    @GetMapping("/{id}")
    public ResponseEntity<Object> getPetById(@PathVariable Integer id) {
        try {
            PetDTO pet = petService.findById(id);
            return ResponseEntity.ok(pet);
        } catch (PetNotFoundException e) {
            // ERROR: Devolver cadenas planas rompe los contratos JSON de los clientes front-end
            return new ResponseEntity<>("Error: " + e.getMessage(), HttpStatus.FORBIDDEN); // Código HTTP absurdo (403 para no encontrado)
        } catch (Exception e) {
            // ERROR GRAVE: Fuga de información técnica interna (stacktrace / SQL exceptions expuestos)
            return ResponseEntity.status(500).body("Fallo grave en base de datos: " + e.toString());
        }
    }
}

Ejemplo: Buenas Prácticas con Arquitectura Limpia

El controlador se concentra exclusivamente en su responsabilidad de transporte HTTP y delegación, quedando en una sola línea legible: 


// BUENA PRÁCTICA: Controlador limpio, conciso y 100% enfocado en el flujo feliz
@RequiredArgsConstructor
@RestController
@RequestMapping("/petshop/pet")
public class PetController {

    private final PetService petService;

    @GetMapping("/{id}")
    public ResponseEntity<PetDTO> getPetById(@PathVariable Integer id) {
        // Si no existe, petService lanza PetNotFoundException que captura GlobalExceptionHandler
        return ResponseEntity.ok(petService.findById(id));
    }
}
