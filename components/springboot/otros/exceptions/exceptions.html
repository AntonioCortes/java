Manejo de Excepciones en Spring Boot

En aplicaciones web y APIs REST empresariales construidas con Spring Boot, el manejo adecuado y uniforme de errores es un pilar fundamental de la robustez, seguridad y experiencia de desarrollo. En lugar de atrapar excepciones manualmente en cada capa o método de controlador mediante bloques repetitivos, Spring MVC ofrece una arquitectura de intercepción global desacoplada basada en AOP (Aspect-Oriented Programming) a través de la anotación @RestControllerAdvice.

Analogía del Mundo Real: El Mostrador Central de Reclamaciones

Imagina unos grandes almacenes o una tienda de mascotas. En cada mostrador, los cajeros y dependientes (los Controladores REST) y los veterinarios del almacén (los Servicios) se dedican exclusivamente a su trabajo: registrar adopciones, tramitar cobros o inventariar productos. Si un cliente solicita una mascota que ya no existe o su tarjeta no tiene fondos, el cajero no improvisa una solución extraña ni discute con el cliente; simplemente declara la incidencia formal (lanza una excepción) y la deriva al Mostrador Central de Atención al Cliente e Incidencias (el @RestControllerAdvice). Este mostrador especializado conoce exactamente el protocolo oficial de la empresa, redacta una hoja estandarizada de reclamación con fecha, código de motivo y pasos a seguir, y se la entrega al cliente en un formato uniforme y comprensible.

Caso de Uso Real Estructurado

1. Contexto

Una API REST de gestión de mascotas (PetStore) expone endpoints para consultar mascotas por identificador (GET /petshop/pet/{id}) y crear nuevas mascotas con validación estricta de campos (POST /petshop/pet).

2. El Problema (Sin la solución)

Cada método de cada controlador se llena de bloques try-catch (Exception e) duplicados. Si un error no se captura, Spring devuelve por defecto un código 500 Internal Server Error con el stacktrace completo de Java, exponiendo nombres de tablas, paquetes y versiones a atacantes externos (vulnerabilidad de Information Disclosure), mientras que otros métodos devuelven cadenas de texto planas sin estructura JSON.

3. La Solución (Con @RestControllerAdvice)

Los controladores y servicios quedan limpios de bloques try-catch. Las excepciones de dominio (ej. PetNotFoundException) o validaciones (MethodArgumentNotValidException) burbujean de forma natural y son interceptadas por una clase centralizada que emite siempre un JSON estructurado con el código de estado HTTP canónico (404, 400, 409, etc.).

¿Cuándo usarlo y cuándo NO usarlo?

Mecanismo / Enfoque ¿Cuándo usarlo? ¿Cuándo NO usarlo?
@RestControllerAdvice + @ExceptionHandler Enfoque recomendado por defecto para cualquier API REST o microservicio. Permite centralizar la traducción de cualquier excepción (de negocio, validación, base de datos) a un contrato JSON unificado con cabeceras y códigos HTTP personalizados. No aplicable en aplicaciones web tradicionales basadas en renderizado de vistas MVC con servidor (JSP, Thymeleaf) donde se prefiera devolver páginas HTML de error en lugar de JSON (en ese caso usar @ControllerAdvice simple devolviendo vistas o ErrorController).
@ResponseStatus en la clase Excepción Para excepciones de negocio muy sencillas y estáticas donde el código HTTP y el mensaje siempre son idénticos (ej. @ResponseStatus(HttpStatus.NOT_FOUND) public class PetNotFoundException). Cuando se necesita devolver un cuerpo JSON dinámico con listas de campos erróneos, marcas de tiempo (timestamp) o contexto específico de la petición.
ResponseStatusException (Spring 5+) Para lanzar errores puntuales y rápidos en prototipos o endpoints sencillos sin necesidad de declarar una clase Exception específica: throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Mascota no existe"). En arquitecturas empresariales medianas o grandes: dispersa los códigos HTTP por los servicios de negocio, acopla la capa de servicio a clases de Spring Web y dificulta mantener contratos JSON estandarizados.
Bloques try-catch en Controladores Únicamente cuando se requiere realizar una acción de compensación o recuperación inmediata local y continuar el flujo normal devolviendo un resultado 200 OK alternativo. Antipatrón absoluto para devolver códigos de error o formatear respuestas HTTP. Genera código espagueti duplicado, oculta fallos reales y rompe el principio de responsabilidad única (SRP).

Dependencias Necesarias

El soporte para @RestControllerAdvice y el manejo de excepciones web está incluido de forma nativa en el starter web de Spring Boot. Si además se gestionan validaciones de entrada con anotaciones como @NotBlank, @Min o @Size, se requiere el starter de validación:

Maven (pom.xml)


<!-- Starter Web de Spring Boot (incluye Spring MVC y soporte de @RestControllerAdvice) -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>

<!-- Starter de Validación de Jakarta / Hibernate Validator (opcional pero recomendado) -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>

Gradle (build.gradle)


dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-validation'
}

Diagrama de Arquitectura y Flujo de Intercepción Global

El siguiente diagrama ilustra cómo fluye una petición cuando ocurre un error en la capa de negocio, demostrando cómo @RestControllerAdvice actúa como una red de seguridad perimetral que intercepta la excepción antes de que alcance al cliente:

Figura 1: Flujo de intercepción global de excepciones con @RestControllerAdvice y @ExceptionHandler
Participante Rol / Estereotipo Responsabilidad en el Manejo de Excepciones
Cliente HTTP «cliente / front-end» Realiza una petición REST (ej. GET /petshop/pet/99) y recibe una respuesta con código de estado HTTP adecuado (ej. 404 NOT_FOUND) y un cuerpo JSON con el error estructurado.
PetController «controlador REST» Punto de entrada de la petición HTTP. Delega inmediatamente en PetService sin envolver en bloques try-catch, permitiendo que las excepciones de negocio fluyan libremente.
PetServiceImpl «capa de servicio» Ejecuta la lógica de negocio y persistencia. Si no halla el registro solicitado en la base de datos, lanza una excepción de dominio no chequeada (throw new PetNotFoundException(99)).
GlobalExceptionHandler «interceptor global de excepciones» Clase anotada con @RestControllerAdvice. Sus métodos con @ExceptionHandler capturan tipos concretos de excepciones, generan trazas de log con SLF4J y devuelven un ResponseEntity<ErrorResponseDTO> seguro al cliente.
ErrorResponseDTO «DTO de contrato de error» Objeto inmutable que define el formato JSON público devuelto al cliente (timestamp, código HTTP, mensaje de negocio legible, ruta URL de la petición y lista opcional de errores de validación de campos).

Anotaciones y Clases Clave del Framework

Anotaciones de Spring MVC

  • @ControllerAdvice: Anotación propia de Spring Framework ubicada en el paquete org.springframework.web.bind.annotation.ControllerAdvice.

    Especialización de @Component que permite declarar métodos de intercepción compartidos entre múltiples controladores de la aplicación (mediante @ExceptionHandler, @InitBinder y @ModelAttribute). Por defecto aplica a todos los controladores registrados en el contexto, aunque puede filtrarse mediante parámetros como basePackages, assignableTypes o annotations.

  • @RestControllerAdvice: Anotación propia de Spring Framework ubicada en el paquete org.springframework.web.bind.annotation.RestControllerAdvice.

    Anotación compuesta que combina @ControllerAdvice y @ResponseBody. Es la opción estándar para APIs REST, ya que garantiza que el valor devuelto por cada método manejador de excepción sea automáticamente serializado a JSON/XML en el cuerpo de la respuesta HTTP sin requerir @ResponseBody en cada método.

  • @ExceptionHandler: Anotación propia de Spring Framework ubicada en el paquete org.springframework.web.bind.annotation.ExceptionHandler.

    Marca un método dentro de una clase consejo (advice) o dentro de un controlador concreto para manejar una o más familias de excepciones. Sus opciones principales son:

    • value: Array de clases de excepción que este método es capaz de interceptar (ej. @ExceptionHandler({PetNotFoundException.class, UserNotFoundException.class})). Si se omite, Spring infiere el tipo a partir del parámetro del método.
  • @ResponseStatus: Anotación propia de Spring Framework ubicada en el paquete org.springframework.web.bind.annotation.ResponseStatus.

    Permite asociar un código de estado HTTP predeterminado a un método o a una clase de excepción personalizada. Acepta los parámetros code o value (ej. HttpStatus.NOT_FOUND) y opcionalmente reason (cadena estática de motivo).

Clases y Modelos de Error

  • ResponseEntity<T>: Clase de org.springframework.http.ResponseEntity que representa la respuesta HTTP completa, incluyendo código de estado (HttpStatus), cabeceras (HttpHeaders) y cuerpo serializable (body).
  • MethodArgumentNotValidException: Excepción de org.springframework.web.bind.MethodArgumentNotValidException lanzada automáticamente por Spring cuando un parámetro anotado con @Valid falla en sus restricciones de Bean Validation. Contiene el objeto BindingResult que detalla cada campo erróneo y su mensaje de validación.
  • ProblemDetail (RFC 7807 / RFC 9457): Clase introducida en Spring Framework 6 y Spring Boot 3 ubicada en org.springframework.http.ProblemDetail. Proporciona una especificación estándar de la IETF para representar errores en APIs HTTP con campos predefinidos: type (URI del tipo de error), title, status, detail e instance.

Implementación Práctica Paso a Paso: El Ciclo de Vida Completo del Error

Para comprender con total claridad cómo funciona el sistema de excepciones en Spring Boot, a continuación se desglosa el proceso de principio a fin: desde la definición del contrato de error y la creación de la excepción de dominio, pasando por el momento exacto en el que el código de negocio decide lanzar el error, hasta la intercepción en el manejador global y la respuesta JSON final entregada al cliente.

Paso 1: DTO Estándar de Respuesta de Error (ErrorResponseDTO)

Definimos el modelo de datos inmutable que recibirán los clientes cuando ocurra cualquier fallo en la API, asegurando una estructura JSON homogénea y predecible: 


package com.example.petshop.dto;

import com.fasterxml.jackson.annotation.JsonInclude;
import lombok.Builder;
import lombok.Getter;

import java.time.LocalDateTime;
import java.util.List;

@Getter
@Builder
@JsonInclude(JsonInclude.Include.NON_NULL)
public class ErrorResponseDTO {

    private final LocalDateTime timestamp;
    private final int status;
    private final String error;
    private final String message;
    private final String path;
    private final List<FieldErrorDTO> fieldErrors;

    @Getter
    @Builder
    public static class FieldErrorDTO {
        private final String field;
        private final String message;
        private final Object rejectedValue;
    }
}

Paso 2: Creación de las Excepciones de Negocio Personalizadas

Creamos excepciones específicas para nuestro dominio que hereden de RuntimeException (excepciones no chequeadas o unchecked). Al no ser chequeadas, evitamos contaminar las interfaces y firmas de métodos con la cláusula throws, permitiendo que la excepción viaje libremente por la pila de llamadas hasta el interceptor global: 


package com.example.petshop.exception;

import lombok.Getter;

// Excepción lanzada cuando una mascota solicitada no existe en la base de datos
@Getter
public class PetNotFoundException extends RuntimeException {

    private final Integer petId;

    public PetNotFoundException(Integer petId) {
        super(String.format("No existe ninguna mascota con el identificador: %d", petId));
        this.petId = petId;
    }
}

Creamos también una segunda excepción de negocio para conflictos por registros duplicados: 


package com.example.petshop.exception;

// Excepción lanzada cuando se intenta registrar una mascota que ya existe
public class DuplicatePetException extends RuntimeException {

    public DuplicatePetException(String message) {
        super(message);
    }
}

Paso 3: ¿En qué momento se lanza el error? (Capa de Servicio PetServiceImpl)

Aquí es donde ocurre la decisión de negocio. La capa de servicio es la encargada de verificar las reglas del sistema y consultar los repositorios. Si una condición requerida no se cumple, el servicio instancia y lanza explícitamente la excepción utilizando la palabra reservada throw: 


package com.example.petshop.service;

import com.example.petshop.dto.PetDTO;
import com.example.petshop.exception.DuplicatePetException;
import com.example.petshop.exception.PetNotFoundException;
import com.example.petshop.model.relational.PetEntity;
import com.example.petshop.repository.relational.PetJpaRepository;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Slf4j
@Service
@RequiredArgsConstructor
public class PetServiceImpl implements PetService {

    private final PetJpaRepository petRepository;

    @Override
    @Transactional(readOnly = true)
    public PetDTO findById(Integer id) {
        log.info("Buscando mascota con identificador: {}", id);

        // =========================================================================
        // ¡MOMENTO EXACTO DEL LANZAMIENTO (CASO 1: RECURSO NO ENCONTRADO)!
        // petRepository.findById() devuelve un Optional<PetEntity>.
        // Si el Optional está vacío (.isEmpty()), orElseThrow() ejecuta la lambda
        // e invoca inmediatamente: throw new PetNotFoundException(id);
        // =========================================================================
        PetEntity entity = petRepository.findById(Long.valueOf(id))
                .orElseThrow(() -> {
                    log.warn("Fallo de negocio: la mascota con ID {} no existe en la base de datos", id);
                    return new PetNotFoundException(id);
                });

        return toDto(entity);
    }

    @Override
    @Transactional
    public PetDTO registerPet(PetDTO petDTO) {
        log.info("Intentando registrar nueva mascota: {}", petDTO.getName());

        // =========================================================================
        // ¡MOMENTO EXACTO DEL LANZAMIENTO (CASO 2: CONFLICTO DE REGLA DE NEGOCIO)!
        // Comprobamos si ya existe una mascota con el mismo nombre en la tienda.
        // Si existe, se lanza explícitamente DuplicatePetException.
        // =========================================================================
        if (petRepository.existsByName(petDTO.getName())) {
            log.warn("Conflicto de negocio: ya existe una mascota llamada {}", petDTO.getName());
            throw new DuplicatePetException("Ya existe una mascota registrada con el nombre: " + petDTO.getName());
        }

        PetEntity entity = toEntity(petDTO);
        PetEntity saved = petRepository.save(entity);
        return toDto(saved);
    }

    private PetDTO toDto(PetEntity entity) {
        return PetDTO.builder()
                .id(entity.getId().intValue())
                .name(entity.getName())
                .species(entity.getSpecies())
                .age(entity.getAge() != null ? entity.getAge().shortValue() : null)
                .vaccinated(entity.isVaccinated())
                .admissionDate(entity.getAdmissionDate())
                .build();
    }

    private PetEntity toEntity(PetDTO dto) {
        return PetEntity.builder()
                .name(dto.getName())
                .species(dto.getSpecies())
                .age(dto.getAge() != null ? dto.getAge().intValue() : null)
                .vaccinated(dto.isVaccinated() != null && dto.isVaccinated())
                .admissionDate(dto.getAdmissionDate())
                .build();
    }
}

¿Qué sucede exactamente en la máquina virtual (JVM) cuando se ejecuta throw new PetNotFoundException(id)?

  1. Interrupción inmediata del flujo secuencial: La ejecución del método findById se detiene en seco en esa línea exacta. La llamada a toDto(entity) nunca llega a ejecutarse.
  2. Gestión transaccional: Si el método estuviera modificando datos en una transacción (@Transactional), Spring marcaría la transacción para rollback automático, deshaciendo cualquier cambio pendiente en la base de datos.
  3. Burbujeo por la pila de llamadas (Call Stack): La excepción abandona el método del servicio y viaja hacia arriba, regresando a quien invocó al servicio: el controlador REST.

Paso 4: El Controlador REST (PetController) - Delegación Limpia sin try-catch

En una arquitectura limpia con Spring Boot, el controlador NO debe contener bloques try-catch. Simplemente delega en el servicio y retorna la respuesta exitosa. Si el servicio lanza una excepción, esta atraviesa el controlador de forma transparente: 


package com.example.petshop.controller;

import com.example.petshop.dto.PetDTO;
import com.example.petshop.service.PetService;
import jakarta.validation.Valid;
import lombok.RequiredArgsConstructor;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.servlet.support.ServletUriComponentsBuilder;

import java.net.URI;

@RestController
@RequestMapping("/petshop/pet")
@RequiredArgsConstructor
public class PetController {

    private final PetService petService;

    @GetMapping("/{id}")
    public ResponseEntity<PetDTO> getPetById(@PathVariable Integer id) {
        // =========================================================================
        // Invocamos al servicio directamente.
        // Si el ID no existe, petService.findById() LANZA PetNotFoundException.
        // El controlador NO atrapa la excepción; esta sale del método getPetById()
        // y alcanza el núcleo de Spring MVC (DispatcherServlet).
        // =========================================================================
        PetDTO pet = petService.findById(id);
        return ResponseEntity.ok(pet);
    }

    @PostMapping
    public ResponseEntity<PetDTO> createPet(@Valid @RequestBody PetDTO petDTO) {
        // =========================================================================
        // ¡MOMENTO EN QUE SE LANZA EL ERROR DE VALIDACIÓN (@Valid)!
        // Si el JSON entrante tiene campos inválidos (ej. name en blanco o age < 0),
        // el interceptor de Bean Validation de Spring MVC lanza AUTOMÁTICAMENTE
        // la excepción MethodArgumentNotValidException ANTES de entrar al método.
        // El cuerpo de este método ni siquiera llega a ejecutarse.
        // =========================================================================
        PetDTO created = petService.registerPet(petDTO);
        URI location = ServletUriComponentsBuilder.fromCurrentRequest()
                .path("/{id}")
                .buildAndExpand(created.getId())
                .toUri();
        return ResponseEntity.created(location).body(created);
    }
}

Paso 5: La Intercepción Centralizada (@RestControllerAdvice y @ExceptionHandler)

Cuando una excepción sale del controlador sin haber sido capturada, el DispatcherServlet de Spring MVC consulta el contenedor de Spring buscando clases anotadas con @RestControllerAdvice. Al encontrar nuestra clase GlobalExceptionHandler, busca el método que tenga un @ExceptionHandler compatible con el tipo de excepción lanzada: 


package com.example.petshop.exception;

import com.example.petshop.dto.ErrorResponseDTO;
import jakarta.servlet.http.HttpServletRequest;
import lombok.extern.slf4j.Slf4j;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.time.LocalDateTime;
import java.util.List;

@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    // =========================================================================
    // 1. Intercepta PetNotFoundException lanzada desde PetServiceImpl.findById()
    // Transforma la excepción de dominio en un código HTTP 404 NOT_FOUND canónico.
    // =========================================================================
    @ExceptionHandler(PetNotFoundException.class)
    public ResponseEntity<ErrorResponseDTO> handlePetNotFound(
            PetNotFoundException ex, 
            HttpServletRequest request) {

        log.warn("Excepción interceptada: {} en la ruta {}", ex.getMessage(), request.getRequestURI());

        ErrorResponseDTO error = ErrorResponseDTO.builder()
                .timestamp(LocalDateTime.now())
                .status(HttpStatus.NOT_FOUND.value())
                .error(HttpStatus.NOT_FOUND.getReasonPhrase())
                .message(ex.getMessage())
                .path(request.getRequestURI())
                .build();

        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(error);
    }

    // =========================================================================
    // 2. Intercepta DuplicatePetException lanzada desde PetServiceImpl.registerPet()
    // Transforma el conflicto de negocio en un código HTTP 409 CONFLICT canónico.
    // =========================================================================
    @ExceptionHandler(DuplicatePetException.class)
    public ResponseEntity<ErrorResponseDTO> handleDuplicatePet(
            DuplicatePetException ex, 
            HttpServletRequest request) {

        log.warn("Conflicto de duplicidad interceptado: {} en {}", ex.getMessage(), request.getRequestURI());

        ErrorResponseDTO error = ErrorResponseDTO.builder()
                .timestamp(LocalDateTime.now())
                .status(HttpStatus.CONFLICT.value())
                .error(HttpStatus.CONFLICT.getReasonPhrase())
                .message(ex.getMessage())
                .path(request.getRequestURI())
                .build();

        return ResponseEntity.status(HttpStatus.CONFLICT).body(error);
    }

    // =========================================================================
    // 3. Intercepta MethodArgumentNotValidException lanzada automáticamente por Spring
    // cuando un payload con @Valid no cumple las restricciones de validación.
    // =========================================================================
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponseDTO> handleValidationErrors(
            MethodArgumentNotValidException ex, 
            HttpServletRequest request) {

        log.warn("Fallo de validación Bean Validation: {} errores en {}", 
                ex.getFieldErrorCount(), request.getRequestURI());

        List<ErrorResponseDTO.FieldErrorDTO> fieldErrors = ex.getBindingResult()
                .getFieldErrors()
                .stream()
                .map(field -> ErrorResponseDTO.FieldErrorDTO.builder()
                        .field(field.getField())
                        .message(field.getDefaultMessage())
                        .rejectedValue(field.getRejectedValue())
                        .build())
                .toList();

        ErrorResponseDTO error = ErrorResponseDTO.builder()
                .timestamp(LocalDateTime.now())
                .status(HttpStatus.BAD_REQUEST.value())
                .error(HttpStatus.BAD_REQUEST.getReasonPhrase())
                .message("La petición contiene datos inválidos o incompletos")
                .path(request.getRequestURI())
                .fieldErrors(fieldErrors)
                .build();

        return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(error);
    }

    // =========================================================================
    // 4. Fallback de seguridad: Captura cualquier error no controlado (NullPointer, SQL, etc.)
    // Genera log con el stacktrace técnico y devuelve un 500 genérico y seguro al cliente.
    // =========================================================================
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponseDTO> handleGenericException(
            Exception ex, 
            HttpServletRequest request) {

        // Se registra el stacktrace técnico en el sistema interno de logs para depuración
        log.error("Error no controlado procesando petición en {}: ", request.getRequestURI(), ex);

        // NUNCA exponer detalles internos, nombres de tablas ni versiones al exterior
        ErrorResponseDTO error = ErrorResponseDTO.builder()
                .timestamp(LocalDateTime.now())
                .status(HttpStatus.INTERNAL_SERVER_ERROR.value())
                .error(HttpStatus.INTERNAL_SERVER_ERROR.getReasonPhrase())
                .message("Ha ocurrido un error interno en el servidor. Por favor, contacte con soporte.")
                .path(request.getRequestURI())
                .build();

        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(error);
    }
}

Paso 6: Peticiones HTTP Reales y Respuestas JSON Obtenidas por el Cliente

A continuación se ilustran los tres escenarios prácticos en acción, mostrando la petición HTTP enviada, en qué punto exacto saltó el error y la respuesta recibida por el cliente:

Escenario A: Búsqueda de Mascota Inexistente (404 Not Found)

  1. Petición del cliente: GET /petshop/pet/99
  2. Momento del error: PetServiceImpl.findById(99) consulta la base de datos, recibe Optional.empty() y ejecuta throw new PetNotFoundException(99).
  3. Intercepción: GlobalExceptionHandler.handlePetNotFound(...) captura la excepción.
  4. Respuesta HTTP entregada al cliente (Código 404):

{
  "timestamp": "2026-10-23T10:45:12.345678",
  "status": 404,
  "error": "Not Found",
  "message": "No existe ninguna mascota con el identificador: 99",
  "path": "/petshop/pet/99"
}

Escenario B: Registro de Mascota con Nombre Duplicado (409 Conflict)

  1. Petición del cliente: POST /petshop/pet con cuerpo {"name": "Rocky", "species": "Dog", "age": 4} cuando "Rocky" ya existe en la base de datos.
  2. Momento del error: PetServiceImpl.registerPet(...) comprueba petRepository.existsByName("Rocky"), que devuelve true, y ejecuta throw new DuplicatePetException(...).
  3. Intercepción: GlobalExceptionHandler.handleDuplicatePet(...) captura la excepción.
  4. Respuesta HTTP entregada al cliente (Código 409):

{
  "timestamp": "2026-10-23T10:46:05.112233",
  "status": 409,
  "error": "Conflict",
  "message": "Ya existe una mascota registrada con el nombre: Rocky",
  "path": "/petshop/pet"
}

Escenario C: Payload con Errores de Validación Bean Validation (400 Bad Request)

  1. Petición del cliente: POST /petshop/pet con cuerpo inválido (nombre en blanco y edad negativa): 
    
{
  "name": "",
  "species": "Cat",
  "age": -5
}
  2. Momento del error: Spring MVC ejecuta el validador de @Valid antes de invocar a PetController.createPet(...), detecta violaciones en @NotBlank y @Min(0), y lanza automáticamente MethodArgumentNotValidException. El controlador ni siquiera se ejecuta.
  3. Intercepción: GlobalExceptionHandler.handleValidationErrors(...) extrae la lista de campos con error.
  4. Respuesta HTTP entregada al cliente (Código 400):

{
  "timestamp": "2026-10-23T10:47:30.987654",
  "status": 400,
  "error": "Bad Request",
  "message": "La petición contiene datos inválidos o incompletos",
  "path": "/petshop/pet",
  "fieldErrors": [
    {
      "field": "name",
      "message": "El nombre de la mascota es obligatorio y no puede estar en blanco",
      "rejectedValue": ""
    },
    {
      "field": "age",
      "message": "La edad de la mascota no puede ser negativa",
      "rejectedValue": -5
    }
  ]
}

Paso 7: Problem Details (RFC 7807 / RFC 9457) en Spring Boot 3

En Spring Boot 3+ (Spring Framework 6+), además de crear DTOs personalizados como ErrorResponseDTO, se dispone de soporte nativo para el estándar oficial RFC 7807 (Problem Details for HTTP APIs) a través de la clase org.springframework.http.ProblemDetail.

Podemos activar el formato RFC 7807 estándar en todo el microservicio mediante configuración en application.yml: 


spring:
  mvc:
    problemdetails:
      enabled: true

O bien construirlo explícitamente dentro de nuestro GlobalExceptionHandler: 


@ExceptionHandler(PetNotFoundException.class)
public ProblemDetail handlePetNotFoundRfc7807(PetNotFoundException ex) {
    ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    problem.setTitle("Mascota No Encontrada");
    problem.setType(URI.create("https://api.petshop.com/errors/not-found"));
    problem.setProperty("petId", ex.getPetId());
    problem.setProperty("timestamp", LocalDateTime.now());
    return problem;
}

Ejemplo vs Contraejemplo

Contraejemplo: Cómo NO gestionar las excepciones (Antipatrón)

En el siguiente código, el controlador captura las excepciones a mano con bloques try-catch, inventa códigos HTTP arbitrarios y expone fallos internos de base de datos a atacantes externos: 


// ANTIPATRÓN: Código contaminado con try-catch, estados HTTP incorrectos y fuga de stacktraces
@RestController
@RequestMapping("/petshop/pet")
public class BadPetController {

    private final PetService petService;

    public BadPetController(PetService petService) {
        this.petService = petService;
    }

    @GetMapping("/{id}")
    public ResponseEntity<Object> getPetById(@PathVariable Integer id) {
        try {
            PetDTO pet = petService.findById(id);
            return ResponseEntity.ok(pet);
        } catch (PetNotFoundException e) {
            // ERROR: Devolver cadenas planas rompe los contratos JSON de los clientes front-end
            return new ResponseEntity<>("Error: " + e.getMessage(), HttpStatus.FORBIDDEN); // Código HTTP absurdo (403 para no encontrado)
        } catch (Exception e) {
            // ERROR GRAVE: Fuga de información técnica interna (stacktrace / SQL exceptions expuestos)
            return ResponseEntity.status(500).body("Fallo grave en base de datos: " + e.toString());
        }
    }
}

Ejemplo: Buenas Prácticas con Arquitectura Limpia

El controlador se concentra exclusivamente en su responsabilidad de transporte HTTP y delegación, quedando en una sola línea legible: 


// BUENA PRÁCTICA: Controlador limpio, conciso y 100% enfocado en el flujo feliz
@RequiredArgsConstructor
@RestController
@RequestMapping("/petshop/pet")
public class PetController {

    private final PetService petService;

    @GetMapping("/{id}")
    public ResponseEntity<PetDTO> getPetById(@PathVariable Integer id) {
        // Si no existe, petService lanza PetNotFoundException que captura GlobalExceptionHandler
        return ResponseEntity.ok(petService.findById(id));
    }
}

Criterio Manejo Manual con try-catch (Antipatrón) Intercepción Global con @RestControllerAdvice (Buena Práctica)
Responsabilidad del Controlador Mezcla transporte HTTP con formateo de errores y lógica de compensación (viola el Principio de Responsabilidad Única - SRP). Controlador limpio, conciso y enfocado al 100% en el camino feliz.
Consistencia del Contrato JSON Respuestas dispares según el desarrollador (cadenas de texto plano, errores vacíos o códigos HTTP inventados como 403 para no encontrado). Esquema JSON inmutable, uniforme y predecible para todos los clientes (front-end, móviles, microservicios).

Mantenibilidad y Reutilización (DRY) Bloques try-catch repetidos en cada método de cada controlador del microservicio. Un único punto centralizado de cambio para toda la aplicación; añadir una nueva excepción requiere solo un método en el advice.
