Configuración en Spring Boot

En Spring Boot, la configuración es el núcleo operativo que define cómo se instancian, configuran, enlazan e inyectan los objetos que componen una aplicación. A través del contenedor de Inversión de Control (IoC) y la Inyección de Dependencias (DI), Spring permite reemplazar el acoplamiento rígido de la creación manual de instancias mediante new por una arquitectura modular y declarativa en código Java basada en las anotaciones @Configuration y @Bean.

Junto con la configuración de beans en Java, Spring Boot aporta un potente sistema de externalización de propiedades (archivos application.yml / application.properties, variables de entorno y perfiles de ejecución con @Profile) y vinculación tipada mediante @ConfigurationProperties.

Analogía del Mundo Real: El Cuadro Eléctrico de un Edificio Inteligente

Imagina la instalación eléctrica de un moderno edificio de oficinas o de una clínica veterinaria. En una instalación caótica y arcaica (el equivalente a usar new Objeto() en cada rincón del código), cada bombilla, ordenador, frigorífico o bomba de agua fabricaría su propio generador o llevaría un cable directo a la calle, sin control de voltaje, sin fusibles compartidos y sin posibilidad de sustitución.

En cambio, un edificio inteligente cuenta con un Cuadro Eléctrico Centralizado (la clase @Configuration):

  • El cuadro central define las tomas de corriente y los suministros homologados disponibles para todo el edificio (los métodos @Bean).
  • Si un aparato necesita corriente o agua (una clase @Service), simplemente se conecta al enchufe estándar habilitado en la pared (inyección de dependencias), sin importarle cómo se genera la electricidad.
  • El cuadro cuenta con selectores de modo según el momento (los Perfiles / @Profile): en modo "Diurno / Laboral" (prod) activa la iluminación completa y la climatización de alta potencia, mientras que en modo "Pruebas / Mantenimiento" (dev o test) conmuta a generadores auxiliares o simuladores de bajo consumo.
  • Los interruptores termomagnéticos (las condiciones @Conditional) solo activan los circuitos de refrigeración si detectan que los motores correspondientes están físicamente conectados.

Caso de Uso Real Estructurado

1. Contexto

En el backend de la tienda de mascotas (PetStore), los servicios necesitan mapear entidades a DTOs con ModelMapper, consumir APIs externas de pasarelas de pago con RestTemplate y aplicar reglas de negocio con límites de tiempo y monedas configurables por entorno.

2. El Problema (Sin @Configuration)

Los desarrolladores ejecutan new ModelMapper() y new RestTemplate() dentro de cada método de servicio. Se crean cientos de instancias idénticas en memoria (desperdicio de RAM), no se pueden configurar timeouts globales, y en los tests unitarios es imposible mockear las llamadas HTTP externas. Además, valores como URLs y claves secretas se escriben fijas en el código Java, imposibilitando el despliegue en Kubernetes o Docker sin recompilar.

3. La Solución (Con @Configuration y Beans)

Una clase AppConfig anotada con @Configuration declara los beans únicos (Singleton) de ModelMapper y RestTemplate con sus timeouts y políticas de mapeo ya configuradas. Las variables de entorno se leen de forma tipada, inmutable y segura mediante un Record Java con @ConfigurationProperties y @Validated.

¿Cuándo usarlo y cuándo NO usarlo?

Mecanismo ¿Cuándo usarlo? ¿Cuándo NO usarlo?
@Configuration + @Bean Librerías externas de terceros cuyo código no podemos modificar para añadirles anotaciones de Spring (ej. ModelMapper, ObjectMapper, BCryptPasswordEncoder, clientes HTTP, brokers AMQP), o cuando la creación del objeto requiere lógica algorítmica compleja o constructores con parámetros dinámicos. Para nuestras propias clases de negocio internas (controladores, servicios, repositorios). En su lugar se deben utilizar los estereotipos estándar de detección automática (@Service, @RestController, @Repository, @Component).
@ConfigurationProperties Enfoque recomendado para agrupar y validar conjuntos jerárquicos de propiedades de configuración externas (ej. petstore.timeout-ms, petstore.api-url, petstore.max-items). Admite validación con Bean Validation y generación automática de metadatos para el IDE. Para inyectar un único valor primitivo suelto o puntual en una clase sencilla (en esos casos aislados @Value resulta más directo).
@Value Inyección puntual de una sola propiedad escalar o evaluación rápida de una expresión SpEL (ej. @Value("${server.port:8080}")). Estructuras de configuración complejas o listas anidadas con múltiples claves: no ofrece tipado fuerte, no valida errores tipográficos en el arranque y dispersa las cadenas de configuración por todo el código.
Configuración XML (beans.xml) Mantenimiento de proyectos legacy muy antiguos de Spring 2.x/3.x. Totalmente desaconsejado en proyectos modernos de Spring Boot. Carece de chequeo de tipos en tiempo de compilación y ralentiza la inicialización.

Dependencias Necesarias

El soporte fundamental de @Configuration y @Bean forma parte del núcleo spring-boot-starter. Para habilitar el procesador de metadatos (que proporciona autocompletado en IntelliJ/Eclipse) y la validación de propiedades tipadas se añaden:

Maven (pom.xml)


<!-- Starter básico o web de Spring Boot -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>

<!-- Generador de metadatos de configuración para autocompletado en IDEs (opcional pero muy recomendado) -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-configuration-processor</artifactId>
    <optional>true</optional>
</dependency>

<!-- Validación de propiedades con @Validated (Jakarta Validation) -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>

Gradle (build.gradle)


dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-validation'
    annotationProcessor 'org.springframework.boot:spring-boot-configuration-processor'
}

Anotaciones Clave en Detalle

@Configuration

  • Paquete: org.springframework.context.annotation.Configuration.
  • Propósito: Marca la clase como fuente de definiciones de beans para el contenedor de Spring. Indica que la clase contiene métodos anotados con @Bean.
  • Parámetros y Opciones:
    • proxyBeanMethods (boolean, por defecto true):
      • true (Full Configuration): Spring envuelve la clase en un proxy CGLIB. Si un método @Bean invoca internamente a otro método @Bean dentro de la misma clase, el proxy intercepta la llamada y devuelve siempre la instancia Singleton almacenada en caché en lugar de crear una nueva.
      • false (Lite Configuration): Desactiva el proxy CGLIB para acelerar el arranque y reducir consumo de memoria cuando los métodos @Bean son 100% independientes y no se llaman entre sí.

@Bean

  • Paquete: org.springframework.context.annotation.Bean.
  • Propósito: Se coloca sobre un método dentro de una clase @Configuration. Indica que el valor devuelto por el método debe ser registrado como un Bean gestionado por el contenedor IoC.
  • Parámetros y Ciclo de Vida:
    • name / value: Nombre explícito del bean en el contenedor (por defecto toma el nombre del método Java).
    • initMethod: Nombre del método que se invoca automáticamente tras instanciar y configurar el bean (análogo a @PostConstruct).
    • destroyMethod: Nombre del método de cierre cuando la aplicación se apaga (por defecto detecta automáticamente métodos close() o shutdown()).
  • Ámbitos (Scopes): Por defecto todo bean es Singleton (una única instancia por aplicación). Se puede alterar con la anotación @Scope:
    • "singleton": Una sola instancia compartida para todo el ApplicationContext.
    • "prototype": Crea una nueva instancia cada vez que alguien solicita o inyecta el bean.
    • "request" (Web): Una instancia por cada petición HTTP (@RequestScope).
    • "session" (Web): Una instancia por cada sesión de usuario HTTP (@SessionScope).

@ConfigurationProperties

  • Paquete: org.springframework.boot.context.properties.ConfigurationProperties.
  • Propósito: Vincula un bloque jerárquico de claves de propiedades externas a los atributos de una clase o componentes de un Java Record.
  • Parámetros:
    • prefix: Prefijo común de las claves en el archivo YAML/properties (ej. prefix = "petstore" vinculará petstore.timeout-ms con el atributo timeoutMs mediante conversión kebab-case a camelCase).
  • Buenas Prácticas en Spring Boot 3+: Utilizar Java Records para crear clases de propiedades inmutables y seguras, combinadas con @Validated y anotaciones de Jakarta Validation (@NotNull, @Min, @NotBlank).

@Profile

  • Paquete: org.springframework.context.annotation.Profile.
  • Propósito: Condiciona la activación de una clase @Configuration o un método @Bean a que determinados perfiles de entorno estén activos (ej. @Profile("dev"), @Profile("!prod"), @Profile({"docker", "cloud"})).
  • Activación: Mediante la propiedad spring.profiles.active=dev,h2 o la variable de entorno SPRING_PROFILES_ACTIVE=prod.

Anotaciones Condicionales (@ConditionalOn...)

  • @ConditionalOnProperty(name = "feature.notification.enabled", havingValue = "true"): Registra el bean únicamente si la propiedad existe y coincide con el valor esperado.
  • @ConditionalOnMissingBean(ModelMapper.class): Registra el bean solo si nadie más en la aplicación ha definido ya un bean de ese tipo (clave en starters y librerías autoconfigurables).
  • @ConditionalOnClass(name = "org.postgresql.Driver"): Se activa solo si la clase especificada se encuentra en el classpath de la aplicación.

Paso 2: Record Inmutable con @ConfigurationProperties y @Validated


package com.example.petstore.config;

import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.validation.annotation.Validated;

@Validated
@ConfigurationProperties(prefix = "petstore")
public record PetStoreProperties(
        @Min(value = 500, message = "El timeout no puede ser inferior a 500 ms")
        int timeoutMs,

        @Min(1) @Max(100)
        int maxPetsPerPage,

        @NotBlank(message = "La divisa es obligatoria")
        String currency,

        PaymentProperties payment
) {
    public record PaymentProperties(
            @NotBlank String apiUrl,
            @NotBlank String apiKey
    ) {}
}

Paso 3: Clase de Configuración (@Configuration) con Definición de Beans

Instanciamos y personalizamos componentes de terceros (ModelMapper y RestTemplate) e inyectamos las propiedades externas validadas: 


package com.example.petstore.config;

import org.modelmapper.ModelMapper;
import org.modelmapper.convention.MatchingStrategies;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.boot.web.client.RestTemplateBuilder;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Profile;
import org.springframework.web.client.RestTemplate;

import java.time.Duration;

@Configuration(proxyBeanMethods = true)
@EnableConfigurationProperties(PetStoreProperties.class)
public class AppConfig {

    // 1. Bean de ModelMapper con estrategia estricta
    @Bean
    public ModelMapper modelMapper() {
        ModelMapper mapper = new ModelMapper();
        mapper.getConfiguration()
                .setMatchingStrategy(MatchingStrategies.STRICT)
                .setSkipNullEnabled(true);
        return mapper;
    }

    // 2. Bean de RestTemplate con timeouts configurados desde las propiedades tipadas
    @Bean
    public RestTemplate restTemplate(RestTemplateBuilder builder, PetStoreProperties props) {
        return builder
                .setConnectTimeout(Duration.ofMillis(props.timeoutMs()))
                .setReadTimeout(Duration.ofMillis(props.timeoutMs()))
                .build();
    }

    // 3. Bean condicional para entorno de desarrollo (simulador de pasarela)
    @Bean
    @Profile("dev")
    public String devPaymentBanner() {
        return "MODO DESARROLLO ACTIVO: Pasarela de pagos simulada";
    }
}

Paso 4: Inyección Limpia en el Servicio de Negocio

El servicio de mascotas recibe todos sus componentes y configuraciones a través del constructor, manteniéndose desacoplado y fácil de probar en tests unitarios: 


package com.example.petstore.service;

import com.example.petstore.config.PetStoreProperties;
import com.example.petstore.dto.PetDTO;
import com.example.petstore.entity.Pet;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.modelmapper.ModelMapper;
import org.springframework.stereotype.Service;
import org.springframework.web.client.RestTemplate;

@Slf4j
@Service
@RequiredArgsConstructor
public class PetServiceImpl implements PetService {

    private final ModelMapper modelMapper;
    private final RestTemplate restTemplate;
    private final PetStoreProperties properties;

    @Override
    public PetDTO convertToDTO(Pet pet) {
        log.info("Mapeando mascota ID: {} usando ModelMapper Singleton (timeout configurado: {} ms)", 
                pet.getId(), properties.timeoutMs());

        return modelMapper.map(pet, PetDTO.class);
    }
}

Ejemplo vs Contraejemplo

Contraejemplo: Instanciación Rígida con new y Variables en Código (Antipatrón)


// ANTIPATRÓN: Código acoplado a 'new', sin reutilización, sin timeouts y con URLs cableadas
@Service
public class BadService {

    public void processPetPayment(int petId) {
        // ERROR GRAVE 1: Crear una nueva instancia de ModelMapper en cada petición satura el Garbage Collector
        ModelMapper mapper = new ModelMapper();

        // ERROR GRAVE 2: RestTemplate sin timeouts centralizados puede congelar hilos indefinidamente
        RestTemplate rest = new RestTemplate();

        // ERROR GRAVE 3: Credenciales y URLs fijas a fuego en el código fuente
        String url = "https://api.pagos-veterinaria.com/v1/charge?key=12345";
        rest.postForObject(url, null, String.class);
    }
}

Ejemplo: Configuración Centralizada, Segura y Testeable


// BUENA PRÁCTICA: Inyección por constructor de beans únicos gestionados por Spring
@Service
@RequiredArgsConstructor
public class GoodService {

    private final ModelMapper modelMapper;
    private final RestTemplate restTemplate;
    private final PetStoreProperties properties;

    public void processPetPayment(int petId) {
        // Se reutilizan los beans Singleton preconfigurados con timeouts y certificados
        String endpoint = properties.payment().apiUrl() + "/charge";
        restTemplate.postForObject(endpoint, null, String.class);
    }
