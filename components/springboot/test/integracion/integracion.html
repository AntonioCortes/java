Tests de Integración en Spring Boot (@SpringBootTest y Testcontainers)

1. ¿Qué es un Test de Integración y para qué sirve?

Un Test de Integración verifica que los diferentes módulos, capas y subsistemas de la aplicación funcionen coordinadamente de extremo a extremo: la comunicación HTTP del controlador, la orquestación transaccional de los servicios, el mapeo objeto-relacional de Hibernate y la ejecución física de sentencias en el motor de base de datos.

Analogía del mundo real

Imaginemos el primer vuelo de prueba real de una aeronave: ya se han probado los motores por separado en el laboratorio (Tests Unitarios) y los mandos en el simulador (Tests de Controladores), pero ahora se enciende el queroseno, se activan los trenes de aterrizaje reales y se comprueba si la vibración del motor afecta a los sensores hidráulicos bajo condiciones físicas auténticas.

---

2. Por qué Testcontainers ha sustituido a H2 en Memoria

Durante años, la práctica común en Spring Boot fue utilizar bases de datos en memoria como H2 para las pruebas. En proyectos empresariales modernos, esto se considera un grave antipatrón de diseño debido a:

Criterio Base de Datos H2 en Memoria Testcontainers (Docker Real)
Fidelidad de Dialecto Emula SQL genérico. No soporta tipos nativos como JSONB de Postgres, sintaxis de secuencias específicas de Oracle ni operadores avanzados. 100% idéntico a producción: ejecuta la imagen oficial exacta de PostgreSQL, Oracle Database o MongoDB.
Índices y Restricciones Comportamiento permisivo con tipos de datos y comprobación de claves foráneas no idéntica. Mismas reglas de integridad referencial, bloqueos de concurrencia y tiempos de respuesta reales.
El Síndrome "En mi Test pasa" Altísimo riesgo de pasar los tests en verde pero fallar en producción al desplegar sobre Postgres/Oracle. Cero sorpresas al desplegar: lo que funciona en el test se comporta exactamente igual en el clúster.

4. Estándar de Casos de Prueba para Persistencia y Base de Datos

Siempre que una función interactúe con el almacenamiento persistente, el estándar de calidad exige verificar los siguientes escenarios esenciales y sus contrarios:

Caso Estándar Acción a Probar Resultado Obligatorio a Validar
1. Inserción y Recuperación (Happy Path) Guardar la entidad completa mediante el repositorio y recuperarla por su ID generado. La entidad se persiste con su ID autoincremental asignado y todos los campos coinciden exactamente (isEqualToComparingFieldByField).
2. Violación de Restricción No-Nula Intentar guardar una entidad con campos obligatorios en null (ej. name = null con nullable = false). Se debe lanzar DataIntegrityViolationException y la transacción debe quedar invalidada.
3. Violación de Clave Única (Unique Constraint) Intentar insertar dos registros con el mismo identificador único o código fiscal. El motor debe rechazar el segundo insert con violación de restricción única.
4. Consulta de Elemento Inexistente Invocar findById(idInexistente). Debe retornar Optional.empty() sin lanzar excepciones inesperadas.
5. Consulta con Filtro y Caso Contrario Probar un método de filtro (ej. findByVaccinatedTrue()). Doble verificación: Comprobar que devuelve todas las mascotas vacunadas Y que excluye explícitamente a las no vacunadas.
6. Eliminación en Cascada y Huérfanos Borrar una entidad padre que tenga configurado CascadeType.REMOVE u orphanRemoval = true. Comprobar que todas las entidades hijas asociadas fueron eliminadas físicamente de sus respectivas tablas.

5. Ejemplo Completo: Test de Integración con Testcontainers y @ServiceConnection

En Spring Boot 3.1+, la anotación @ServiceConnection elimina la necesidad de configurar manualmente las propiedades JDBC mediante @DynamicPropertySource. Spring Boot detecta automáticamente el contenedor Docker de Testcontainers (PostgreSQL en este caso) y autoconfigura el DataSource y el ConnectionDetails de la aplicación de prueba: 


package com.example.petshop.integration;

import com.example.petshop.dto.PetDTO;
import com.example.petshop.model.relational.PetEntity;
import com.example.petshop.repository.relational.PetJpaRepository;
import org.junit.jupiter.api.*;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.web.client.TestRestTemplate;
import org.springframework.boot.test.web.server.LocalServerPort;
import org.springframework.boot.testcontainers.service.connection.ServiceConnection;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

import java.time.LocalDate;

import static org.assertj.core.api.Assertions.assertThat;

@Testcontainers
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@DisplayName("Tests de Integración End-to-End con Testcontainers y @ServiceConnection (PostgreSQL)")
class PetIntegrationTest {

    // 1. Contenedor Docker oficial de PostgreSQL gestionado por Testcontainers
    // Con @ServiceConnection (Spring Boot 3.1+), Spring autoconfigura ConnectionDetails automáticamente
    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine");

    @LocalServerPort
    private int port;

    @Autowired
    private TestRestTemplate restTemplate;

    @Autowired
    private PetJpaRepository petRepository;

    @BeforeEach
    void setUp() {
        // Limpiamos la tabla antes de cada test para garantizar aislamiento e idempotencia
        petRepository.deleteAll();
    }

    @Test
    @DisplayName("Flujo Completo E2E: POST crea mascota en Postgres real y GET la recupera")
    void shouldCreateAndRetrievePetEndToEnd() {
        // GIVEN: DTO de entrada para registrar
        String baseUrl = "http://localhost:" + port + "/petshop/pet";
        PetDTO newPet = PetDTO.builder()
                .name("Rocky")
                .species("Dog")
                .age((short) 5)
                .vaccinated(true)
                .admissionDate(LocalDate.now())
                .build();

        // WHEN (Fase 1): Petición HTTP POST real
        ResponseEntity<Void> postResponse = restTemplate.postForEntity(baseUrl, newPet, Void.class);

        // THEN (Fase 1): Respuesta 201 Created y presencia de cabecera Location
        assertThat(postResponse.getStatusCode()).isEqualTo(HttpStatus.CREATED);
        assertThat(postResponse.getHeaders().getLocation()).isNotNull();
        String locationUrl = postResponse.getHeaders().getLocation().toString();

        // THEN (Fase 2): Verificación física directa en la base de datos PostgreSQL real
        assertThat(petRepository.count()).isEqualTo(1L);
        PetEntity entityInDb = petRepository.findAll().get(0);
        assertThat(entityInDb.getName()).isEqualTo("Rocky");
        assertThat(entityInDb.getSpecies()).isEqualTo("Dog");
        assertThat(entityInDb.isVaccinated()).isTrue();

        // WHEN (Fase 3): Petición HTTP GET a la URL indicada en el Location
        ResponseEntity<PetDTO> getResponse = restTemplate.getForEntity(locationUrl, PetDTO.class);

        // THEN (Fase 3): Respuesta 200 OK y coincidencia del contrato DTO
        assertThat(getResponse.getStatusCode()).isEqualTo(HttpStatus.OK);
        PetDTO retrievedPet = getResponse.getBody();
        assertThat(retrievedPet).isNotNull();
        assertThat(retrievedPet.getId()).isEqualTo(entityInDb.getId().intValue());
        assertThat(retrievedPet.getName()).isEqualTo("Rocky");
    }

    @Test
    @DisplayName("Persistencia: findByVaccinatedTrue debe devolver solo mascotas vacunadas y excluir no vacunadas")
    void shouldReturnOnlyVaccinatedPetsAndExcludeUnvaccinated() {
        // GIVEN: Persistimos una mascota vacunada y otra no vacunada
        PetEntity vaccinatedPet = PetEntity.builder()
                .name("Toby")
                .species("Dog")
                .age(2)
                .vaccinated(true)
                .admissionDate(LocalDate.now())
                .build();

        PetEntity unvaccinatedPet = PetEntity.builder()
                .name("Kiko")
                .species("Parrot")
                .age(1)
                .vaccinated(false)
                .admissionDate(LocalDate.now())
                .build();

        petRepository.save(vaccinatedPet);
        petRepository.save(unvaccinatedPet);

        // WHEN: Ejecución de la consulta filtrada
        var vaccinatedList = petRepository.findByVaccinatedTrue();

        // THEN: Aserción estricta de inclusión y exclusión
        assertThat(vaccinatedList)
                .hasSize(1)
                .extracting(PetEntity::getName)
                .containsExactly("Toby")
                .doesNotContain("Kiko");
    }
}

Equivalente Clásico en Spring Boot 2.x - 3.0: @DynamicPropertySource

En versiones previas a Spring Boot 3.1, era necesario registrar manualmente las propiedades dinámicas de conexión de JDBC mediante un método estático anotado con @DynamicPropertySource: 


// Enfoque clásico (Spring Boot 2.x - 3.0) sustituido por @ServiceConnection en 3.1+
@DynamicPropertySource
static void configureProperties(DynamicPropertyRegistry registry) {
    registry.add("spring.datasource.url", postgres::getJdbcUrl);
    registry.add("spring.datasource.username", postgres::getUsername);
    registry.add("spring.datasource.password", postgres::getPassword);
}

6. Cuándo Usar y Cuándo NO Usar Tests de Integración

Escenario Recomendación Motivo Técnico
Validar integración con la base de datos real (transacciones, constraints, migraciones Flyway/Liquibase). SIEMPRE usar Tests de Integración con Testcontainers Es el único entorno donde se prueba el motor real idéntico al clúster de producción.
Probar lógica condicional con 10 caminos diferentes en un algoritmo de cálculo de precios. NO usar Tests de Integración (Usar Unit Tests con JUnit 5) Arrancar la base de datos 10 veces para bifurcaciones simples penaliza innecesariamente los tiempos del pipeline de CI/CD.
Flujos críticos de negocio de extremo a extremo (registro de usuario, checkout de pedido, cobro bancario). USAR Tests de Integración (1 o 2 por flujo principal) Garantiza que la interacción entre todas las capas y la infraestructura externa funciona coordinada.

7. Contraejemplos y Antipatrones en Tests de Integración

Contraejemplo 1: No Limpiar las Tablas entre Tests (Tests Dependientes)


// ANTIPATRÓN: Asume que la base de datos siempre arranca vacía para su test
@Test
void test1() {
    petRepository.save(new PetEntity(...));
    assertEquals(1, petRepository.count()); // Pasa si corre solo
}

@Test
void test2() {
    petRepository.save(new PetEntity(...));
    // FALLO SILENCIOSO O INTERMITENTE: Si test1 corrió antes, count() devolverá 2 en lugar de 1
    assertEquals(1, petRepository.count()); 
}

Solución: Incluir siempre un método @BeforeEach que ejecute petRepository.deleteAll() para garantizar que cada test sea estrictamente autónomo e idempotente.

Contraejemplo 2: Abuso de @DirtiesContext (Destrucción de la Caché de Contexto)


// ANTIPATRÓN CATASTRÓFICO: Destruye el ApplicationContext al terminar cada test
@DirtiesContext(classMode = DirtiesContext.ClassMode.AFTER_EACH_TEST_METHOD)
@SpringBootTest
class SlowIntegrationTest {
    // Provoca que Spring reconstruya el ApplicationContext completo en cada método,
    // multiplicando el tiempo total de la suite de CI/CD de 30 segundos a más de 10 minutos.
}

Solución: En lugar de destruir el contexto con @DirtiesContext, limpiar el estado mutable (tablas de BD, colas en memoria, caches) en métodos @BeforeEach o @AfterEach, permitiendo que Spring reutilice el mismo ApplicationContext.

8. Rendimiento y Optimización de la Caché de Contexto (Spring Test Context Caching)

El Spring Test Framework incorpora un mecanismo extremadamente eficiente denominado Context Caching: una vez que un ApplicationContext se inicializa para un test, Spring lo mantiene en memoria y lo reutiliza para todos los tests subsiguientes que compartan exactamente la misma configuración.

¿Qué elementos forman la clave de la caché del contexto?

Spring calcula un hash identificativo único para cada contexto basándose en:

  • Clases de configuración (@SpringBootTest(classes = ...)).
  • Perfiles activos (@ActiveProfiles("test")).
  • Propiedades personalizadas (@TestPropertySource o @SpringBootTest(properties = ...)).
  • Conjunto de beans simulados (@MockBean o @MockitoBean definidos en la clase de test).
  • Contenedores y conexiones dinámicas (@ServiceConnection).

Patrón de Diseño Recomendado: Clase Base Abstracta de Integración

Para evitar la polución de contexto y garantizar que toda la batería de tests de integración comparta un único contenedor Docker y un único ApplicationContext durante toda la ejecución de Maven/Gradle, se define una clase base abstracta: 


package com.example.petshop.integration;

import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.testcontainers.service.connection.ServiceConnection;
import org.springframework.test.context.ActiveProfiles;
import org.testcontainers.containers.PostgreSQLContainer;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@ActiveProfiles("test")
public abstract class AbstractIntegrationTest {

    // Contenedor estático compartido entre TODAS las clases de test de integración
    // Se levanta una sola vez al inicio y se destruye al apagar la JVM
    @ServiceConnection
    protected static final PostgreSQLContainer<?> POSTGRES = 
            new PostgreSQLContainer<>("postgres:16-alpine");

    static {
        POSTGRES.start();
    }
}

Todas las clases de test de integración concretas deben heredar de AbstractIntegrationTest (ej. class PetControllerIntegrationTest extends AbstractIntegrationTest). De esta manera, el contenedor Docker de PostgreSQL arranca una sola vez y el ApplicationContext se reutiliza al 100%, ejecutando decenas de tests de integración en cuestión de segundos.

7. Tests End-to-End con REST-Assured y Puerto Real (@LocalServerPort)

Mientras que en los tests funcionales de controladores se utiliza RestAssuredMockMvc para evaluar la capa web sin red, en los Tests de Integración End-to-End se arranca un servidor embebido real (Tomcat / Jetty) en un puerto aleatorio libre utilizando webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT.

En este escenario, el cliente REST-Assured estándar (io.rest-assured:rest-assured) abre conexiones TCP/HTTP reales a través del stack de red del sistema operativo, validando el ciclo completo: filtros de seguridad, serialización JSON, lógica de servicios y persistencia física en la base de datos de Testcontainers.

7.2. Ejemplo de Test de Integración E2E con REST-Assured


package com.example.petshop.integration;

import com.example.petshop.dto.PetRequestDTO;
import io.restassured.RestAssured;
import io.restassured.http.ContentType;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.springframework.boot.test.web.server.LocalServerPort;
import org.springframework.http.HttpStatus;

import static io.restassured.RestAssured.given;
import static org.hamcrest.Matchers.*;

@DisplayName("Test de Integración End-to-End con REST-Assured y Testcontainers")
class PetControllerE2ETest extends AbstractIntegrationTest {

    @LocalServerPort
    private int port;

    @BeforeEach
    void setUp() {
        // Vincula REST-Assured al puerto dinámico asignado por Spring Boot al arrancar Tomcat
        RestAssured.baseURI = "http://localhost";
        RestAssured.port = port;
    }

    @Test
    @DisplayName("Debe persistir una mascota en PostgreSQL real y recuperarla vía HTTP GET")
    void shouldPersistAndRetrievePetEndToEnd() {
        // GIVEN: DTO de creación de mascota
        PetRequestDTO requestDto = PetRequestDTO.builder()
                .name("Rocky")
                .species("Canino")
                .age(4)
                .vaccinated(true)
                .build();

        // 1. POST: Creación del recurso en la base de datos real
        Integer createdId = given()
                .contentType(ContentType.JSON)
                .body(requestDto)
        .when()
                .post("/api/v1/pets")
        .then()
                .statusCode(HttpStatus.CREATED.value())
                .body("id", notNullValue())
                .body("name", equalTo("Rocky"))
                .extract()
                .path("id");

        // 2. GET: Recuperación y verificación contra la base de datos real
        given()
        .when()
                .get("/api/v1/pets/" + createdId)
        .then()
                .statusCode(HttpStatus.OK.value())
                .contentType(ContentType.JSON)
                .body("id", equalTo(createdId))
                .body("name", equalTo("Rocky"))
                .body("species", equalTo("Canino"))
                .body("vaccinated", equalTo(true));
    }
}
