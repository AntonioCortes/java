Tests Unitarios en Spring Boot (JUnit 5, Mockito y AssertJ)

1. ¿Qué es un Test Unitario y para qué sirve?

Un Test Unitario es una prueba automatizada que verifica el correcto funcionamiento de la unidad de código más pequeña posible (habitualmente un método dentro de una clase de servicio o utilidad) en completo aislamiento de dependencias externas como bases de datos, redes, sistemas de mensajería o el contenedor de Spring.

Analogía del mundo real

Imaginemos la línea de montaje de un automóvil: antes de ensamblar el motor en el chasis y conectarlo al depósito de gasolina y la transmisión (Test de Integración), los ingenieros prueban los pistones y las bujías de forma aislada en un banco de pruebas de laboratorio usando simuladores eléctricos. Si un pistón falla en el banco de pruebas, no hace falta montar el coche entero para saber que la pieza es defectuosa.

Objetivos clave de los Tests Unitarios

  • Velocidad extrema: Deben ejecutarse en milisegundos (cientos de tests en pocos segundos) al no arrancar el contexto de Spring (ApplicationContext).
  • Determinismo y aislamiento: Un test unitario nunca debe fallar por culpa de una caída de red, una base de datos caída o un puerto ocupado. Todas las dependencias se simulan mediante Mocks.
  • Diseño de código desacoplado: Si una clase es difícil de testear unitariamente, suele indicar que sufre de alto acoplamiento o violación del Principio de Responsabilidad Única (SRP).

2. Dependencias del Proyecto

Spring Boot proporciona el starter unificado spring-boot-starter-test, que incluye automáticamente JUnit 5 (Jupiter), Mockito y AssertJ:

Maven (pom.xml)


<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
</dependency>

Gradle (build.gradle)


dependencies {
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

test {
    useJUnitPlatform()
}

3. Anatomía y Estructura de un Test Unitario

Patrón AAA (Arrange - Act - Assert) / BDD (Given - When - Then)

Todo test unitario debe estructurarse obligatoriamente en tres fases claramente diferenciadas:

  1. Given / Arrange (Preparación): Se preparan los datos de entrada, las instancias necesarias y se configuran los comportamientos esperados de los mocks (ej. qué devolverá el repositorio cuando se le invoque).
  2. When / Act (Acción): Se ejecuta el método concreto que se está probando (la unidad bajo prueba o System Under Test - SUT).
  3. Then / Assert (Verificación): Se comprueba que el resultado devuelto coincide con lo esperado y que los colaboradores fueron invocados con los argumentos exactos o que no sufrieron efectos secundarios indeseados.

Anotaciones Principales de JUnit 5 y Mockito

Anotación Librería Propósito y Buenas Prácticas
@ExtendWith(MockitoExtension.class) Mockito Se coloca sobre la clase de test para inicializar los mocks de forma ultra rápida sin levantar el contexto de Spring.
@Mock Mockito Crea una instancia simulada (mock) de una interfaz o clase colaboradora (ej. repositorios, clientes REST, emisores Kafka).
@InjectMocks Mockito Instancia la clase real que se va a testear (la clase de servicio) e inyecta automáticamente en sus campos o constructor los mocks declarados con @Mock.
@Captor Mockito Declara un ArgumentCaptor<T> para capturar y verificar los argumentos exactos pasados a un método simulado.
@Test JUnit 5 Marca un método como ejecutable de test. En JUnit 5 pertenece al paquete org.junit.jupiter.api.Test (no usar el paquete org.junit.Test de JUnit 4).
@DisplayName("...") JUnit 5 Asigna un nombre legible y descriptivo al test para la salida de reportes en consola e IDEs.
@BeforeEach JUnit 5 Ejecuta código de inicialización antes de cada método @Test para garantizar independencia y estado limpio.
@AfterEach JUnit 5 Ejecuta tareas de limpieza tras la finalización de cada test individual.

4. Estándar de Casos de Prueba Obligatorios (Heurística de Calidad)

Para alcanzar un nivel experto y garantizar cobertura profesional, al testear cualquier método de negocio se debe cubrir siempre el siguiente conjunto de escenarios estándar:

Tipo de Escenario Objetivo de la Prueba Qué se debe Verificar
1. Camino Feliz (Happy Path) Comprueba que el método produce el resultado correcto cuando los datos de entrada son válidos y los colaboradores responden con éxito. El valor devuelto coincide exactamente y los colaboradores esperados fueron invocados con los argumentos previstos (then(repo).should().save(...)).
2. Caso Contrario / Negativo (Negative Path) Comprueba el comportamiento ante un recurso que no existe o una condición que impide la operación. Se lanza la excepción de dominio correspondiente (ej. ResourceNotFoundException) y se asegura que NO se ejecutaron pasos posteriores irreversibles.
3. Casos Límite y Frontera (Boundary Testing) Comprueba cómo reacciona el código ante valores extremos: números negativos, cero, valores máximos permitidos, cadenas vacías o null. El código valida los argumentos y rechaza los datos anómalos de forma controlada sin producir NullPointerException inesperados.
4. Ausencia de Efectos Secundarios Asegura que si una condición preliminar falla, no se interactúa con recursos persistentes ni con servicios de mensajería externa. Verificar con then(collaborator).shouldHaveNoInteractions() que los colaboradores críticos permanecieron intactos.

5. Ejemplo Completo: Test Unitario de PetServiceImpl

A continuación se ilustra el test unitario completo para el servicio de adopción de mascotas, aplicando JUnit 5, BDDMockito, AssertJ y Lombok: 


package com.example.petshop.service;

import com.example.petshop.dto.PetDTO;
import com.example.petshop.exception.PetNotFoundException;
import com.example.petshop.model.relational.PetEntity;
import com.example.petshop.repository.relational.PetJpaRepository;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.ArgumentCaptor;
import org.mockito.Captor;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import java.time.LocalDate;
import java.util.Optional;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;
import static org.mockito.BDDMockito.given;
import static org.mockito.BDDMockito.then;
import static org.mockito.Mockito.never;

@ExtendWith(MockitoExtension.class)
@DisplayName("Tests Unitarios - PetServiceImpl")
class PetServiceImplTest {

    @Mock
    private PetJpaRepository petRepository;

    @Mock
    private NotificationService notificationService;

    @InjectMocks
    private PetServiceImpl underTest;

    @Captor
    private ArgumentCaptor<PetEntity> petArgumentCaptor;

    @Test
    @DisplayName("Camino Feliz: Debe registrar una mascota y notificar si los datos son válidos")
    void shouldRegisterPetSuccessfullyWhenDataIsValid() {
        // GIVEN: Datos preparados
        PetDTO inputDto = PetDTO.builder()
                .name("Max")
                .species("Dog")
                .age((short) 3)
                .vaccinated(true)
                .admissionDate(LocalDate.now())
                .build();

        PetEntity savedEntity = PetEntity.builder()
                .id(1L)
                .name("Max")
                .species("Dog")
                .age(3)
                .vaccinated(true)
                .admissionDate(LocalDate.now())
                .build();

        given(petRepository.save(petArgumentCaptor.capture())).willReturn(savedEntity);

        // WHEN: Ejecución de la unidad
        PetDTO result = underTest.registerPet(inputDto);

        // THEN: Aserciones con AssertJ y verificación con BDDMockito
        assertThat(result).isNotNull();
        assertThat(result.getId()).isEqualTo(1L);
        assertThat(result.getName()).isEqualTo("Max");

        // Verificamos que el argumento capturado tenía los campos correctos antes de persistir
        PetEntity capturedPet = petArgumentCaptor.getValue();
        assertThat(capturedPet.getName()).isEqualTo("Max");
        assertThat(capturedPet.getSpecies()).isEqualTo("Dog");

        // Verificamos que se envió la notificación
        then(notificationService).should().sendWelcomeNotification("Max");
    }

    @Test
    @DisplayName("Caso Contrario: Debe lanzar PetNotFoundException al buscar un ID inexistente")
    void shouldThrowPetNotFoundExceptionWhenIdDoesNotExist() {
        // GIVEN: El repositorio devuelve vacío
        Long nonExistentId = 99L;
        given(petRepository.findById(nonExistentId)).willReturn(Optional.empty());

        // WHEN & THEN: Verificación de excepción esperada
        assertThatThrownBy(() -> underTest.findPetById(nonExistentId))
                .isInstanceOf(PetNotFoundException.class)
                .hasMessageContaining("99");

        // Verificación de seguridad: No se debe enviar ninguna notificación
        then(notificationService).shouldHaveNoInteractions();
    }

    @Test
    @DisplayName("Caso Límite: Debe rechazar el registro si el nombre de la mascota es nulo o vacío")
    void shouldThrowIllegalArgumentExceptionWhenNameIsBlank() {
        // GIVEN: DTO con nombre inválido
        PetDTO invalidDto = PetDTO.builder()
                .name("   ")
                .species("Cat")
                .age((short) 1)
                .build();

        // WHEN & THEN: Falla la validación temprana
        assertThatThrownBy(() -> underTest.registerPet(invalidDto))
                .isInstanceOf(IllegalArgumentException.class)
                .hasMessageContaining("El nombre no puede estar en blanco");

        // Verificamos que NUNCA se invocó al repositorio ni al servicio de notificación
        then(petRepository).should(never()).save(petArgumentCaptor.capture());
        then(notificationService).shouldHaveNoInteractions();
    }
}

6. Cuándo Usar y Cuándo NO Usar Tests Unitarios

Escenario Recomendación Motivo Técnico
Lógica de negocio en Clases de Servicio (cálculos, validaciones, mapeos, orquestación). SIEMPRE usar Tests Unitarios Son ultrarrápidos, aíslan completamente los fallos y permiten cubrir todos los caminos y bifurcaciones condicionales.
Probar consultas SQL nativas complejas o sintaxis de dialectos específicos (PostgreSQL / Oracle). NO usar Tests Unitarios (Usar Slice @DataJpaTest o Testcontainers) Un mock no sabe ejecutar sentencias SQL ni comprueba claves foráneas o tipos de columna reales.
Probar serialización JSON, filtros de seguridad HTTP y validación de endpoints REST. NO usar Tests Unitarios (Usar Slice @WebMvcTest) Se requiere verificar el comportamiento del pipeline de Spring MVC y los interceptores HTTP.
---

7. Contraejemplos y Antipatrones en Tests Unitarios

Contraejemplo 1: Levantar @SpringBootTest para un Test Unitario de Servicio


// ANTIPATRÓN CATASTRÓFICO: Levanta toda la aplicación Spring Boot para probar un método simple
@SpringBootTest
class BadPetServiceTest {

    @Autowired
    private PetServiceImpl petService; // Tarda de 5 a 15 segundos en arrancar el contexto

    @Test
    void testSimpleMethod() {
        // Prueba lenta que ralentiza los pipelines de CI/CD
    }
}

Solución: Utilizar siempre @ExtendWith(MockitoExtension.class) con @Mock y @InjectMocks.

Contraejemplo 2: Aserciones Débiles (Silent Failures)


// ANTIPATRÓN: Aserción insuficiente que no verifica el contenido real
@Test
void badAssertionTest() {
    PetDTO result = petService.registerPet(dto);
    
    // PELIGRO: Pasa si result es un objeto vacío sin rellenar
    assertNotNull(result); 
}

Solución con AssertJ: Verificar todos los atributos clave con métodos fluidos: assertThat(result).isNotNull().extracting(PetDTO::getName, PetDTO::getAge).containsExactly("Max", (short) 3);.
