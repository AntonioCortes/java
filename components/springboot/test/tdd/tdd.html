Desarrollo Guiado por Pruebas (TDD - Test Driven Development)

1. ¿Qué es TDD y cuál es su filosofía?

El Desarrollo Guiado por Pruebas (Test-Driven Development - TDD) no es simplemente una técnica de verificación de calidad; es fundamentalmente una disciplina de diseño de software donde los tests unitarios se escriben antes que el propio código de producción. Los tests actúan como especificación viva y contrato ejecutable del sistema.

Analogía del mundo real

Imaginemos la construcción de columnas en ingeniería civil: los constructores nunca vierten el hormigón al aire esperando que adquiera la forma de columna por arte de magia. Primero construyen un encofrado rígido con las medidas milimétricas exactas (el test unitario), y después vierten el hormigón (el código de producción). El hormigón adopta con precisión la forma del molde y se retira el encofrado con la certeza de que la columna cumple los planos.

2. El Ciclo Red - Green - Refactor

TDD se ejecuta en bucles microscópicos de pocos minutos guiados por tres fases inmutables:

Fase Color Qué se debe Hacer Regla de Oro
1. Red (Rojo) Falla Escribir un pequeño test unitario que describa un único comportamiento nuevo deseado. Ejecutar el test y comprobar que falla (el fallo de compilación cuenta como fallo). No escribir ni una sola línea de código de producción hasta ver el test en rojo por el motivo correcto.
2. Green (Verde) Pasa Escribir la cantidad mínima y más sencilla de código de producción para que el test pase a verde. Está permitido escribir código "feo" o valores fijos si es necesario. Hacer que el test pase lo antes posible sin anticipar requisitos futuros.
3. Refactor (Limpieza) Mejora Mejorar el diseño, eliminar código duplicado, extraer métodos y aplicar principios SOLID y patrones de diseño. La red de seguridad de los tests debe permanecer en verde tras cada cambio estructural.
---

3. Las Tres Leyes de TDD (Robert C. Martin - Uncle Bob)

  1. Primera Ley: No escribirás código de producción hasta que hayas escrito un test unitario que falle.
  2. Segunda Ley: No escribirás más de un test unitario de lo que sea suficiente para fallar; y no compilar es fallar.
  3. Tercera Ley: No escribirás más código de producción del que sea necesario para hacer pasar el test unitario que está fallando.
---

4. Caso Práctico TDD Paso a Paso (Dominio Pet Shop)

Requisito de negocio: Implementar el cálculo de la tasa de adopción de mascotas (AdoptionFeeCalculator).

  • Tarifa base estándar: 100.00 €.
  • Mascotas senior (edad > 7 años): 30% de descuento (tarifa: 70.00 €).
  • Si la edad es negativa: debe lanzar IllegalArgumentException.

Paso 1: Primer Test en Rojo (Fase Red 1)

Escribimos el test para la tarifa base de una mascota joven antes de que la clase calculadora exista: 


package com.example.petshop.tdd;

import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import java.math.BigDecimal;
import static org.assertj.core.api.Assertions.assertThat;

class AdoptionFeeCalculatorTest {

    private final AdoptionFeeCalculator calculator = new AdoptionFeeCalculator();

    @Test
    @DisplayName("Debe cobrar la tarifa base estándar de 100€ para una mascota joven")
    void shouldReturnStandardFeeForYoungPet() {
        // GIVEN
        int age = 3;

        // WHEN
        BigDecimal fee = calculator.calculateFee(age);

        // THEN
        assertThat(fee).isEqualByComparingTo(new BigDecimal("100.00"));
    }
}

Resultado: Falla en compilación porque AdoptionFeeCalculator aún no existe. Cumple la Fase Red.

Paso 2: Código Mínimo en Verde (Fase Green 1)


package com.example.petshop.tdd;

import java.math.BigDecimal;

public class AdoptionFeeCalculator {
    public BigDecimal calculateFee(int age) {
        // Solución mínima para pasar el test
        return new BigDecimal("100.00");
    }
}

Resultado: El test pasa a VERDE.

Paso 3: Segundo Test para Mascota Senior (Fase Red 2)


    @Test
    @DisplayName("Debe aplicar un 30% de descuento para mascotas senior (edad > 7)")
    void shouldApplySeniorDiscountForOldPet() {
        // GIVEN
        int seniorAge = 8;

        // WHEN
        BigDecimal fee = calculator.calculateFee(seniorAge);

        // THEN
        assertThat(fee).isEqualByComparingTo(new BigDecimal("70.00"));
    }

Resultado: Falla porque devuelve 100.00 en lugar de 70.00. Estamos en ROJO.

Paso 4: Implementar Descuento (Fase Green 2)


public class AdoptionFeeCalculator {
    public BigDecimal calculateFee(int age) {
        if (age > 7) {
            return new BigDecimal("70.00");
        }
        return new BigDecimal("100.00");
    }
}

Resultado: Ambos tests pasan a VERDE.

Paso 5: Tercer Test para Validación de Frontera (Fase Red 3)


    @Test
    @DisplayName("Debe lanzar IllegalArgumentException si la edad es negativa")
    void shouldThrowExceptionWhenAgeIsNegative() {
        assertThatThrownBy(() -> calculator.calculateFee(-1))
                .isInstanceOf(IllegalArgumentException.class)
                .hasMessage("La edad de la mascota no puede ser negativa");
    }

Paso 6: Refactorización Profesional con Constantes y Buenas Prácticas (Fase Refactor)

Una vez que todos los tests están en verde, aplicamos diseño limpio extrayendo constantes y formalizando el cálculo: 


package com.example.petshop.tdd;

import java.math.BigDecimal;
import java.math.RoundingMode;

public class AdoptionFeeCalculator {

    private static final BigDecimal BASE_FEE = new BigDecimal("100.00");
    private static final BigDecimal SENIOR_DISCOUNT_PERCENTAGE = new BigDecimal("0.30");
    private static final int SENIOR_AGE_THRESHOLD = 7;

    public BigDecimal calculateFee(int age) {
        if (age < 0) {
            throw new IllegalArgumentException("La edad de la mascota no puede ser negativa");
        }

        if (age > SENIOR_AGE_THRESHOLD) {
            BigDecimal discount = BASE_FEE.multiply(SENIOR_DISCOUNT_PERCENTAGE);
            return BASE_FEE.subtract(discount).setScale(2, RoundingMode.HALF_UP);
        }

        return BASE_FEE.setScale(2, RoundingMode.HALF_UP);
    }
}

5. Cuándo Usar y Cuándo NO Usar TDD

Escenario Recomendación Motivo
Reglas de negocio complejas, motores de precios, deducciones fiscales, validaciones críticas. SIEMPRE usar TDD Garantiza cobertura del 100% de las ramas de decisión y produce código altamente desacoplado.
Corrección de defectos en producción (Bug Fixing). OBLIGATORIO usar TDD Se escribe primero el test que reproduce el bug exacto (en rojo), luego se corrige (en verde) y nunca más vuelve a ocurrir (prevención de regresiones).
Pinchos técnicos o pruebas de concepto exploratorias (Spikes) donde se desconoce la API de una librería. NO usar TDD Se realiza código rápido exploratorio; una vez aprendido el funcionamiento, se descarta el prototipo y se inicia el desarrollo formal con TDD.

6. Contraejemplos y Antipatrones de TDD

Contraejemplo 1: Testear Detalles Privados de Implementación


// ANTIPATRÓN: Test acoplado a la estructura interna en lugar de al contrato público
@Test
void badTddTest() throws Exception {
    // Rompe el encapsulamiento por reflexión para comprobar el valor de una variable privada
    Field field = calculator.getClass().getDeclaredField("internalCounter");
    field.setAccessible(true);
    assertEquals(1, field.get(calculator));
}

Solución: Testear únicamente el comportamiento observable a través de la interfaz pública (caja negra). El test no debe romperse si se refactoriza el interior de la clase sin cambiar las entradas ni salidas.

Contraejemplo 2: Saltarse la Fase de Refactorización

Quedarse perpetuamente en el paso Verde sin limpiar duplicidades convierte el código en una maraña de parches de sentencias if-else. La verdadera calidad de TDD se forja en la fase de refactorización continua.
