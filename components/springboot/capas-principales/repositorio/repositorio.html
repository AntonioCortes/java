Capa de Repositorio (@Repository / Spring Data JPA)

La Capa de Repositorio (o DAO - Data Access Object) es el componente de Spring Boot encargado exclusivamente del acceso y persistencia de datos en la base de datos física. Gracias a Spring Data JPA, los desarrolladores no necesitan escribir sentencias SQL manuales con JDBC ni abrir/cerrar conexiones: basta con declarar una interfaz que extienda de JpaRepository para que Spring genere automáticamente en tiempo de ejecución todas las operaciones CRUD (crear, leer, actualizar, borrar), paginación y consultas avanzadas.

Analogía del Mundo Real: El Archivero del Almacén

Imagina una gran biblioteca histórica:

  • El Servicio (@Service) es el investigador que necesita consultar el libro "Mascota #15". El investigador no sabe en qué sótano, pasillo o estantería física se encuentra guardado el libro físico ni qué llave abre el candado (no necesita conocer sentencias SQL directas).
  • El investigador acude al Archivero (@Repository) y le entrega una ficha de solicitud: findById(15) o findByAgeBetween(1, 5). El archivero baja al almacén (la base de datos relacional), localiza el registro, traduce las filas de bytes en el objeto Java (la Entidad) y se lo entrega limpiamente al investigador.

Jerarquía de Interfaces en Spring Data JPA

Spring Data proporciona una jerarquía escalonada de interfaces según las necesidades del proyecto:

  1. Repository<T, ID>: Interfaz marcadora raíz sin métodos.
  2. CrudRepository<T, ID>: Proporciona las operaciones CRUD estándar: save(), findById(), existsById(), findAll(), count(), deleteById() y delete().
  3. PagingAndSortingRepository<T, ID>: Extiende CrudRepository añadiendo soporte para ordenar (Sort) y paginar grandes volúmenes de datos con Pageable y Page<T>.
  4. JpaRepository<T, ID>: La interfaz más completa y utilizada. Extiende las anteriores y añade métodos propios de JPA como flush(), saveAndFlush(), deleteInBatch() y operaciones en bloque.

Definición Básica: PetRepository

Para crear un repositorio básico de la tienda de mascotas, solo se declara la interfaz indicando la clase de la Entidad (Pet) y el tipo de su clave primaria (Integer):


@Repository
public interface PetRepository extends JpaRepository<Pet, Integer> {
}

Ejemplos de Consultas Declaradas (@Query) y Derivadas: ProductoRepository

Cuando las consultas predeterminadas de JpaRepository no son suficientes, se pueden definir consultas personalizadas mediante anotaciones @Query en JPQL (Java Persistence Query Language) o aprovechando la convención de nombres de métodos derivados (Derived Query Methods):


@Repository
public interface ProductoRepository extends JpaRepository<Producto, Integer> {
    
    @Query("SELECT p FROM com.thecompany.entities.Producto p WHERE p.precio >= (:precioMenor) AND p.precio <= (:precioMayor)")
    List<Producto> getPrecioRango(@Param("precioMenor") Integer precioMenor, @Param("precioMayor") Integer precioMayor);

    List<Producto> findByPrecioBetween(Integer precioMenor, Integer precioMayor);
    
    @Query("SELECT p FROM com.thecompany.entities.Producto p")
    List<Producto> getAllProductos();

    @Query("SELECT p FROM com.thecompany.entities.Producto p")
    Optional<Producto> getProductoUnico();
    
    @Query("SELECT p FROM com.thecompany.entities.Producto p WHERE p.activo = (:activo)")
    List<Producto> getAllProductosActivos(@Param("activo") Boolean activo);
    
    @Query("SELECT p FROM com.thecompany.entities.Producto p WHERE p.vendedor = (:vendedor)")
    List<Producto> getProductosVendedor(@Param("vendedor") String vendedor);
    
    @Query("SELECT p FROM com.thecompany.entities.Producto p ORDER BY p.precio")
    List<Producto> getDatosOrdenados();
    
    @Query("SELECT p FROM com.thecompany.entities.Producto p WHERE p.id = (:id) AND p.precio = (:precio)")
    List<Producto> getDatosPosicionales(@Param("id") Integer id, @Param("precio") Integer precio);   
}
ProductoRepository combinando consultas JPQL con @Query y métodos derivados por nombre

Convención de Nombres de Métodos Derivados (Derived Query Methods)

Spring Data inspecciona el nombre del método en la interfaz y deduce automáticamente la consulta SQL que debe ejecutar en la base de datos. La firma del método debe estructurarse de la siguiente manera:

  • find...By: Recupera registros coincidentes. Puede devolver una lista vacía o un Optional.empty() si no encuentra coincidencias.
  • get...By: Busca registros obligatorios; si no existe, lanza una excepción en runtime.
  • read...By: Equivalente a find...By.
  • query...By: Equivalente a find...By.
  • count...By: Devuelve el número total de registros (long) que cumplen el filtro.
  • delete...By / remove...By: Elimina los registros que coinciden con el criterio y devuelve el conteo de filas borradas.

La palabra clave By actúa como delimitador para definir los criterios y campos de filtro sobre los atributos de la entidad.

Búsquedas sin criterio previo con ordenación u operaciones de límite: Se puede omitir el criterio intermedio para ordenar toda la tabla o limitar los primeros resultados:

  • Buscar por nombre ordenando por edad: findByNameOrderByAge();
  • Buscar todos los registros ordenando por edad: findByOrderByAge();
  • Obtener solo los 3 primeros registros más caros: findTop3ByOrderByPrecioDesc();

Consultas de Modificación (@Modifying y @Transactional)

Si defines una consulta @Query para ejecutar un UPDATE o DELETE, es obligatorio añadir la anotación @Modifying para avisar a JPA de que no es una consulta de lectura SELECT, y asegurar que el método esté dentro de una transacción con @Transactional:


@Modifying
@Transactional
@Query("UPDATE Pet p SET p.name = :name WHERE p.id = :id")
int updatePetName(@Param("id") Integer id, @Param("name") String name);
Consulta de modificación con @Modifying devolviendo el número de filas alteradas

¿Cuándo Usar Métodos Derivados frente a @Query o Criteria API?

Técnica ¿Cuándo Usarla? ¿Cuándo NO Usarla?
Métodos Derivados (findByName...) Consultas sencillas con 1, 2 o 3 condiciones (igualdad, rangos, ordenación). Consultas con más de 4 condiciones (nombres de método larguísimos e ilegibles como findByNameAndAgeAndCityAndStatusAnd...).
@Query (JPQL o SQL Nativo) Consultas con JOIN FETCH, agrupaciones (GROUP BY), subconsultas complejas o agregaciones. Consultas básicas que Spring Data resuelve con una sola línea de método derivado.
Criteria API / QueryDSL Filtros dinámicos con formularios donde el usuario puede rellenar o dejar vacíos 10 campos opcionales. Consultas estáticas de estructura fija.

Contraejemplo (Mala Práctica): El Problema de las N+1 Consultas en Repositorios

Si una entidad tiene una relación perezosa (FetchType.LAZY) y recuperas 100 registros con findAll(), cada vez que accedes a la relación en un bucle Hibernate ejecutará 100 consultas SQL adicionales a la base de datos (problema N+1). La solución es usar JOIN FETCH dentro de un @Query:


// ¡SOLUCIÓN AL PROBLEMA N+1!
// Trae la mascota y su dueño en una ÚNICA consulta SQL con JOIN
@Query("SELECT p FROM Pet p JOIN FETCH p.owner WHERE p.age >= :age")
List<Pet> findAllWithOwners(@Param("age") Short age);
