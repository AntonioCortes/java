Controlador REST (@RestController)

Un Controlador REST (@RestController) es el componente de la capa web de Spring Boot encargado de exponer los endpoints de una API RESTful. Su responsabilidad exclusiva es recibir peticiones HTTP (GET, POST, PUT, PATCH, DELETE), deserializar los payloads JSON entrantes en objetos DTO, delegar la lógica en la capa de Servicio y devolver los resultados directamente serializados en JSON acompañados de los códigos de estado HTTP semánticos adecuados (200 OK, 201 Created, 204 No Content, 400 Bad Request, 404 Not Found).

Analogía del Mundo Real: La Ventanilla Automatizada de Mensajería

Imagina una ventanilla de paquetería express:

  • El cliente no entra al almacén ni ve las estanterías (la base de datos). Llega a la ventanilla con una solicitud estructurada en papel (el JSON).
  • El operario de la ventanilla (@RestController) no cocina ni repara paquetes (esa es la lógica del @Service): únicamente comprueba que el formulario esté bien rellenado (validaciones con @Valid), le pasa la orden al departamento de almacén y entrega al cliente un resguardo con un sello oficial estandarizado (código HTTP 201 con la URL del nuevo recurso creado).

1. Definición a Nivel de Clase

Para definir una clase como controlador REST se aplican las siguientes anotaciones estructurales:

  • @RestController: Pertenece a Spring Framework, se encuentra en el paquete org.springframework.web.bind.annotation.RestController y registra la clase como controlador web. Introducida en Spring 4.0, es una anotación compuesta que combina @Controller y @ResponseBody. Gracias a ella, todos los métodos serializan automáticamente el objeto devuelto a JSON en el cuerpo de la respuesta HTTP sin tener que añadir @ResponseBody en cada método.
  • @RequestMapping: Pertenece a Spring Framework (paquete org.springframework.web.bind.annotation.RequestMapping). Define la ruta base URL (ej. /petshop/pet) para acceder a todos los endpoints de este controlador.
  • @CrossOrigin: Pertenece a Spring Framework (paquete org.springframework.web.bind.annotation.CrossOrigin). Por defecto, los navegadores bloquean peticiones AJAX de orígenes cruzados (CORS). Esta anotación permite autorizar peticiones desde aplicaciones front-end alojadas en otros dominios o puertos (ej. @CrossOrigin(origins = "http://localhost:4200")). Se puede aplicar a nivel de clase o sobre métodos concretos.
  • @Api, @ApiResponses, @ApiResponse: Pertenecen a SpringFox / Swagger (paquete io.swagger.annotations.*) y permiten documentar la etiqueta del recurso, las descripciones y los posibles códigos de error para que aparezcan automáticamente en Swagger UI.

@RestController
@RequestMapping("/petshop/pet")
@CrossOrigin
@Api(tags = "Pet")
@ApiResponses({ 
    @ApiResponse(code = 200, message = "OK", response = PetDTO.class),
    @ApiResponse(code = 201, message = "Created"),
    @ApiResponse(code = 204, message = "No content"),
    @ApiResponse(code = 400, message = "Bad Request"),
    @ApiResponse(code = 404, message = "Not found"), 
    @ApiResponse(code = 500, message = "Internal server error") 
})
public class PetController 
{
    //...Controller global attributes
    //...Controller methods
}
Cabecera de la clase PetController con rutas, CORS y documentación Swagger

2. Atributos Globales y Dependencias del Controlador

El controlador REST delega la lógica de negocio en la capa de servicio y la conversión de objetos en mapeadores (como ModelMapper o MapStruct):

  • @Autowired: Pertenece a Spring Framework (paquete org.springframework.beans.factory.annotation.Autowired). Inyecta las dependencias gestionadas por el contenedor de Spring. En Spring moderno se recomienda inyectar mediante constructor final en lugar de sobre atributos directos.
  • @Qualifier: Pertenece a Spring Framework (paquete org.springframework.beans.factory.annotation.Qualifier). Permite desambiguar qué bean inyectar cuando existen dos o más beans del mismo tipo registrados en el contexto (por ejemplo, dos instancias distintas de ModelMapper).

//...Other annotations
@RestController
public class PetController
{
    private static final Logger LOGGER = LoggerFactory.getLogger(PetController.class);

    @Autowired
    private final PetService petService;

    @Autowired
    @Qualifier("modelMapper")
    private final ModelMapper mapper;

    @Autowired
    @Qualifier("patchModelMapper")
    private final ModelMapper patchMapper;

    //...Controller methods
}
Inyección de servicios y mappers desambiguados con @Qualifier

3. Anotaciones a Nivel de Método y Parámetros

Anotaciones de Verbos HTTP de Spring Framework

  • @GetMapping: Mapea peticiones HTTP GET para recuperación y consulta de recursos. No debe alterar el estado del sistema (operación segura e idempotente).
  • @PostMapping: Mapea peticiones HTTP POST para crear nuevos recursos en el servidor.
  • @PutMapping: Mapea peticiones HTTP PUT para sustituir o reemplazar un recurso existente por completo (idempotente).
  • @PatchMapping: Mapea peticiones HTTP PATCH para aplicar modificaciones parciales sobre un recurso existente (solo los campos enviados en el payload).
  • @DeleteMapping: Mapea peticiones HTTP DELETE para eliminar un recurso identificado por su ID.

Anotaciones para Parámetros de Entrada

  • @PathVariable: Extrae variables incrustadas en el path de la URL (ej. en @GetMapping("/{id}"), extrae el valor de {id} en un parámetro Java @PathVariable("id") Integer pId).
  • @RequestParam: Extrae parámetros de consulta (query parameters) pasados tras el interrogante en la URL (ej. /petshop/pet/all?age=4 se captura con @RequestParam("age") Integer pAge). Permite el atributo required = true/false y valores por defecto con defaultValue.
  • @RequestHeader: Pertenece a org.springframework.web.bind.annotation.RequestHeader. Permite capturar cabeceras de la petición HTTP (como Authorization, Accept-Language o cabeceras de trazabilidad X-Request-Id).
  • @RequestBody: Deserializa el JSON enviado en el cuerpo de la llamada HTTP en un objeto Java DTO.
  • @Valid: Activa la validación automática de las restricciones del Bean Validation (@NotNull, @NotBlank, @Min, etc.) declaradas en el DTO. Si alguna regla falla, Spring lanza una excepción MethodArgumentNotValidException antes de ejecutar el código del método.

4. Casos de Uso y Métodos de PetController (Explicados Paso a Paso)

A. Método GET (Consultas y Filtros)

El método GET se utiliza para recuperar información sin modificar la base de datos:

  • Recuperar un recurso concreto por ID: Se define la variable en el path: /petshop/pet/{id} (ej. /petshop/pet/15). Si existe devuelve 200 OK con el PetDTO; si no existe devuelve 404 NOT_FOUND.
  • Filtrar colecciones: Se usa query param: /petshop/pet/all?age=4. Devuelve 200 OK con la lista de PetDTO.

Ejemplo obtener una mascota por ID:


@ApiOperation(value = "View a pet data", notes = "View a pet data")
@ApiResponses({ @ApiResponse(code = 200, message = "OK", response = PetDTO.class), 
		@ApiResponse(code = 404, message = "Not found") })
@GetMapping("/{id}")
public ResponseEntity<PetDTO> get(@PathVariable(value = "id") @ApiParam(value = "pet Id", example = "1", required = true) final Integer pId) 
{
	Optional<Pet> pet = petService.findById(pId);
	if(pet.isEmpty()) 
	{
		LOGGER.error("Pet {} not found", pId);
		return new ResponseEntity<>(HttpStatus.NOT_FOUND);
	}
	PetDTO petDTO = mapper.map(pet.get(), PetDTO.class);
	LOGGER.debug("Getting pet with id {}", pId);

	return new ResponseEntity<>(petDTO, HttpStatus.OK);
}
GET por identificador devolviendo 200 OK con el DTO o 404 NOT FOUND

Ejemplo obtener mascotas filtradas por edad:


@ApiOperation(value = "View all pets with a certain age data", notes = "View all pets with a certain age data")
@ApiResponses({ @ApiResponse(code = 200, message = "OK", response = PetDTO.class, responseContainer = "List") })
@GetMapping("/all")
public ResponseEntity<List<PetDTO>> getByAge(@RequestParam(value = "age", required = true) @ApiParam(value = "pet age", example = "1", required = true) final Integer pAge) 
{
	LOGGER.debug("Getting all pets with age {}", pAge);

	List<Pet> petList = petService.findByAge(pAge);

	return new ResponseEntity<>(
		petList.stream()
			.map(pet -> mapper.map(pet, PetDTO.class))
			.collect(Collectors.toList()), 
		HttpStatus.OK);
}
GET con @RequestParam filtrando por edad y mapeando a lista de DTOs

B. Método PATCH (Actualización Parcial)

Permite modificar únicamente los atributos enviados por el cliente sin obligar a re-enviar la foto o datos inalterados. Utiliza un patchMapper configurado con skipNullEnabled(true) para no sobreescribir con null los campos no enviados, y devuelve un 204 NO_CONTENT junto con la cabecera Location que apunta al recurso actualizado:


@ApiOperation(value = "Update a pet", notes = "Update a pet")
@ApiResponses({ @ApiResponse(code = 204, message = "No content"),
		@ApiResponse(code = 404, message = "Not found") })
@PatchMapping("/{id}")
public ResponseEntity<HttpStatus> patch(
		@PathVariable(value = "id") @ApiParam(value = "Pet id", example = "1", required = true) final Integer pId,
		@Valid @RequestBody final PetPatchDTO pPetPatchDTO) 
{
	Optional<Pet> pet = petService.findById(pId);
	if (pet.isEmpty()) 
	{
		LOGGER.error("Pet {} not found", pId);
		return new ResponseEntity<>(HttpStatus.NOT_FOUND);
	}

	patchMapper.map(pPetPatchDTO, pet.get());

	petService.save(pet.get());

	URI uri = ServletUriComponentsBuilder.fromCurrentRequestUri().build().toUri();

	HttpHeaders headers = new HttpHeaders();
	headers.setLocation(uri);

	return new ResponseEntity<>(headers, HttpStatus.NO_CONTENT);
}
PATCH aplicando actualización parcial y devolviendo 204 NO CONTENT con cabecera Location

C. Método POST (Creación de Nuevos Recursos)

Crea un nuevo registro en el sistema. Comprueba que no exista previamente, mapea el PetDTO recibido a la entidad Pet, la guarda en la base de datos y construye la cabecera Location con ServletUriComponentsBuilder apuntando a la URL del nuevo recurso creado (ej. /petshop/pet/15), devolviendo un código 201 CREATED según la especificación HTTP:


@ApiOperation(value = "Add a new pet", notes = "Add a new pet")
@ApiResponses({ @ApiResponse(code = 201, message = "Created") })
@PostMapping
public ResponseEntity<Object> post(@RequestBody @Valid final PetDTO pPetDTO) 
{
	Optional<Pet> petOp = petService.findById(pPetDTO.getId());
	if(petOp.isPresent())
	{
		LOGGER.error("Pet {} already exists", pPetDTO.getId());
		throw new UniqueConstraintException(ConstantMessages.ERROR_ALREADY_EXISTS);
	}
	
	Pet pet = mapper.map(pPetDTO, Pet.class);
	pet = petService.save(pet);
	LOGGER.debug("Pet with id {} saved correctly", pet.getId());
		
	URI uri = ServletUriComponentsBuilder.fromCurrentRequestUri().pathSegment(String.format("%s", pet.getId())).build().toUri();
	HttpHeaders headers = new HttpHeaders();
	headers.setLocation(uri);

	return new ResponseEntity<>(headers, HttpStatus.CREATED);
}
POST creando un nuevo recurso y devolviendo 201 CREATED con la cabecera Location

D. Método DELETE (Eliminación)

Elimina el recurso identificado por su ID. Si la mascota existe, la borra y devuelve un código 204 NO_CONTENT (éxito sin cuerpo de respuesta); si no existe, devuelve 404 NOT_FOUND:


@ApiOperation(value = "Delete a pet", notes = "Delete a pet")
@ApiResponses({ @ApiResponse(code = 204, message = "No content"), 
		@ApiResponse(code = 404, message = "Not found") })
@DeleteMapping("/{id}")
public ResponseEntity<HttpStatus> delete(@PathVariable(value = "id") @ApiParam(value = "Pet id", example = "1", required = true) final Integer pId)
{		
	Optional<Pet> pet = petService.findById(pId);
	
	if(pet.isPresent())
	{		
		petService.delete(pet.get());
		LOGGER.debug("Pet with id {} deleted correctly", pId);

		return new ResponseEntity<>(HttpStatus.NO_CONTENT);	
	}
	else
	{
		LOGGER.error("Pet with id {} doesn't exist", pId);

		return new ResponseEntity<>(HttpStatus.NOT_FOUND);	
	}
}
DELETE devolviendo 204 NO CONTENT si se eliminó con éxito o 404 NOT FOUND

¿Cuándo Usar @RestController y Cuándo NO?

Criterio Cuándo SÍ Usar @RestController Alternativa Recomendada
APIs REST y Microservicios Ideal para aplicaciones cliente-servidor desacopladas (Angular, React, Vue, Apps móviles). -
Vistas HTML con Thymeleaf / JSP No adecuado: @RestController serializa a JSON y no busca plantillas HTML. Usar @Controller tradicional.
Altísima Concurrencia y Streaming Reactivo Spring MVC usa un modelo de 1 hilo por petición (thread-per-request bloqueante). Usar Spring WebFlux con programación reactiva no bloqueante.

Contraejemplo (Mala Práctica): Devolver siempre 200 OK con mensajes de error en el JSON

Uno de los mayores antipatrones en APIs REST es capturar todos los errores y devolver un código HTTP 200 OK con un objeto JSON tipo {"success": false, "error": "Not found"}. Esto rompe la semántica HTTP, confunde a los balanceadores de carga, a las herramientas de monitorización y a los clientes HTTP:


// ¡ANTIPATRÓN REST! Rompe los estándares de códigos HTTP
@GetMapping("/{id}")
public ResponseEntity<Map<String, Object>> badGetPet(@PathVariable Integer id) {
    Optional<Pet> pet = petService.findById(id);
    if (pet.isEmpty()) {
        // ERROR: Devuelve 200 OK cuando el recurso NO EXISTE
        return ResponseEntity.ok(Map.of("success", false, "error", "Pet not found"));
    }
    return ResponseEntity.ok(Map.of("success", true, "data", pet.get()));
}
Antipatrón: Devolver 200 OK en lugar de 404 NOT FOUND para recursos inexistentes
