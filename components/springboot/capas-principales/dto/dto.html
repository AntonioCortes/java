DTO - Data Transfer Object

Un DTO (Data Transfer Object) es un patrón de diseño arquitectónico y un objeto plano de Java (POJO o Bean) cuyo único propósito es transportar datos entre capas o a través de la red (HTTP/JSON) sin contener lógica de negocio. En Spring Boot, los DTOs definen el contrato exacto de entrada (petición) y salida (respuesta) de los controladores REST.

Analogía del Mundo Real: El Formulario de Aduanas

Imagina que compras un producto en otro país. Para enviar el paquete a través de la frontera internacional, la tienda no envía todo su libro contable, ni las contraseñas de su almacén, ni el historial completo de sus proveedores: rellena un formulario de aduanas con los datos estrictamente necesarios para el viaje (nombre del producto, peso, dirección y precio).

El DTO es ese formulario de aduanas: viaja por la red con los datos públicos que el cliente necesita ver, protegiendo las entidades internas de base de datos de accesos no autorizados.

Caso de Uso Real: ¿Por qué NO exponer Entidades de Base de Datos directamente?

  • Contexto: Una tienda de mascotas gestiona registros de animales en una base de datos con campos como id, name, age, internalCost (coste interno para la tienda) y relaciones con tablas de historial médico.
  • El Problema (Sin DTO - Exponiendo @Entity): Si el controlador REST devuelve directamente la entidad Pet en formato JSON:
    1. Fuga de seguridad: El cliente puede ver campos privados como internalCost o datos confidenciales de auditoría.
    2. Ataque de Sobre-Asignación (Mass Assignment / Over-posting): Si un atacante envía un JSON con {"id": 999, "role": "ADMIN"} en una petición POST, Spring deserializará esos campos en la entidad y sobrescribirá datos protegidos de la base de datos.
    3. Error de recursión infinita (StackOverflowError): Si dos entidades JPA tienen relaciones bidireccionales (@OneToMany ↔ @ManyToOne), Jackson intentará serializar recursivamente los objetos hasta desbordar la pila de memoria.
  • La Solución (Con DTO): Se define un PetDTO con los campos públicos permitidos y validaciones estrictas. La capa de servicio transforma el DTO a Entidad antes de guardar, y la Entidad a DTO antes de responder.

Anotaciones de Jackson (Formato y Serialización JSON)

La librería Jackson (paquete com.fasterxml.jackson.annotation.*) permite personalizar cómo se convierten los atributos del DTO a JSON y viceversa:

  • @JsonInclude: Pertenece a la librería Jackson, se encuentra en el paquete com.fasterxml.jackson.annotation.JsonInclude y sirve para definir qué atributos se incluirán en el JSON final (por ejemplo, omitir valores nulos o cadenas vacías). Esto permite reducir el tamaño del payload HTTP y evitar transferir campos sin contenido.

    Se aplica a nivel de clase o sobre atributos individuales mediante @JsonInclude(JsonInclude.Include.NON_EMPTY). Sus valores son:

    • ALWAYS: Siempre incluye el atributo, incluso si vale null.
    • NON_NULL: Solo incluye los atributos que no sean nulos.
    • NON_ABSENT: Solo incluye atributos no ausentes (en Optional o AtomicReference, comprueba además que contengan un valor interno).
    • NON_EMPTY: Excluye null, colecciones/mapas con isEmpty() == true y arrays/strings con longitud 0.
    • NON_DEFAULT: Solo incluye valores que difieran del valor primitivo por defecto (ej. 0 para int, false para boolean).
    • CUSTOM: Aplica un filtro personalizado definido mediante valueFilter().
    • USE_DEFAULTS: Hereda el criterio del nivel superior o la configuración global de ObjectMapper.
  • @JsonIgnoreProperties: Pertenece a Jackson (paquete com.fasterxml.jackson.annotation.JsonIgnoreProperties). Se coloca habitualmente sobre la clase con @JsonIgnoreProperties(ignoreUnknown = true) para indicar que si el cliente envía campos adicionales en el JSON que no existen en el DTO, Jackson no lance una excepción UnrecognizedPropertyException y los ignore pacíficamente.
  • @JsonProperty: Pertenece a Jackson (paquete com.fasterxml.jackson.annotation.JsonProperty). Se coloca sobre los atributos del DTO para especificar el nombre exacto de la clave en el JSON cuando difiere del nombre del atributo en Java (por ejemplo, mapear el atributo Java private Integer id a la clave JSON "petId").
  • @JsonFormat: Pertenece a Jackson (paquete com.fasterxml.jackson.annotation.JsonFormat). Se coloca sobre atributos de tipo fecha (Date, LocalDate, LocalDateTime) para especificar el patrón exacto de formateo (ej. pattern = "dd/MM/yyyy") y la zona horaria (timezone = "Europe/Madrid").

Anotaciones de Jakarta / Javax Validation Constraints

Permiten validar los datos de entrada automáticamente en el controlador cuando se acompaña el parámetro con @Valid o @Validated:

  • @NotNull: El valor no puede ser null (válido para cualquier tipo de objeto, como IDs o números). Permite strings vacíos.
  • @NotBlank: Exclusivo para String. No puede ser null y su longitud tras eliminar espacios en blanco (trim) debe ser mayor que 0.
  • @NotEmpty: Para cadenas, colecciones o arrays. No puede ser null y su tamaño debe ser superior a 0.
  • @Pattern: Valida que un String cumpla una expresión regular: @Pattern(regexp = "^(image/jpeg|image/jpg|image/gif)$").
  • @Email: Verifica que la cadena cumpla la estructura estándar de una dirección de correo electrónico válida.
  • @Min y @Max: Fijan límites numéricos mínimos y máximos: @Min(1), @Max(150).
  • @Size: Limita la longitud mínima y máxima de un String, colección o array: @Size(min = 2, max = 50).

Anotaciones de Spring Format

  • @DateTimeFormat: Pertenece a Spring Framework (paquete org.springframework.format.annotation.DateTimeFormat). Sirve para parsear fechas pasadas por parámetro de consulta (query param) o formulario: 
    
@PostMapping("/date")
public void date(@RequestParam("date") @DateTimeFormat(pattern = "dd.MM.yyyy") Date date) {
    // ...
}

Anotaciones para Documentación Swagger (SpringFox)

Permiten enriquecer la documentación interactiva en Swagger UI:

  • @ApiModel: Pertenece a Swagger (paquete io.swagger.annotations.ApiModel). Se coloca a nivel de clase para describir el propósito del esquema del DTO (ej. @ApiModel(description = "Pet DTO")).
  • @ApiModelProperty: Pertenece a Swagger (paquete io.swagger.annotations.ApiModelProperty). Se coloca sobre los atributos para describir su significado, proporcionar valores de ejemplo visibles en Swagger UI e indicar si el campo es obligatorio (notes = "Pet ID", example = "1", required = true).

Anotaciones de Lombok en DTOs

Ahorran código boilerplate repetitivo en la definición del POJO:

  • @Data: Pertenece a Lombok (paquete lombok.Data). Genera automáticamente getters, setters, equals(), hashCode() y toString() para todos los atributos. En los DTOs es ideal y seguro porque no contienen relaciones JPA circulares.
  • @Accessors(chain = true): Pertenece a Lombok (paquete lombok.experimental.Accessors). Modifica los setters para que devuelvan la propia instancia (this) en lugar de void, permitiendo encadenar asignaciones de forma fluida: new PetDTO().setId(1).setName("Joe").

PetDTO: Ejemplo Completo de Creación y Consulta

Representa el contrato completo de una mascota para operaciones de lectura (GET), creación (POST) o reemplazo total (PUT), exigiendo que todos los campos requeridos estén presentes:


@ApiModel(description = "Pet DTO")
@Data
@Accessors(chain = true)
@JsonInclude(JsonInclude.Include.NON_EMPTY)
@JsonIgnoreProperties(ignoreUnknown = true)
public class PetDTO 
{   
    @ApiModelProperty(notes = "Pet ID", example = "1", required = true)
    @NotNull(message = ConstantMessages.FIELD_MANDATORY)
    @JsonProperty("petId")
    private Integer id;

    @ApiModelProperty(notes = "Pet Name", example = "Joe", required = true)
    @NotBlank(message = ConstantMessages.FIELD_MANDATORY)
    @JsonProperty("petName")
    private String name;
    
    @ApiModelProperty(notes = "Pet age", example = "1", required = true)
    @NotNull(message = ConstantMessages.FIELD_MANDATORY)
    @JsonProperty("age")
    private Short age;

    @ApiModelProperty(notes = "Date of birth", example = "1/2/2021", required = false)
    @JsonFormat(pattern = "dd/MM/yyyy", timezone="Europe/Madrid")
    @JsonProperty("birthDate")
    private Date birthDate;

    @ApiModelProperty(notes = "Picture of the pet in base64", example = "RxxsAre45fdsSef==", required = true)
    @NotNull(message = ConstantMessages.FIELD_MANDATORY)
    @JsonProperty("picture")
    private byte[] picture;

    @ApiModelProperty(notes = "Picture media type", example = "image/jpeg", required = true, allowEmptyValue = false, allowableValues = "image/jpeg, image/jpg, image/gif")
    @NotBlank(message = ConstantMessages.FIELD_MANDATORY)
    @Pattern(regexp = "^(image/jpeg|image/jpg|image/gif)$")
    @JsonProperty("pictureMediaType")
    private String pictureMediaType;
}

PetPatchDTO: Ejemplo para Actualizaciones Parciales (PATCH)

En el método HTTP PATCH, el cliente solo envía los campos concretos que desea modificar (por ejemplo, únicamente cambiar el nombre sin enviar la foto ni la fecha de nacimiento). Por ello, PetPatchDTO no incluye el ID (que viaja en la URL) y elimina las validaciones @NotNull y @NotBlank para permitir que los campos no modificados lleguen como null:


@ApiModel(description = "Pet DTO for patch method")
@Data
@Accessors(chain = true)
@JsonInclude(JsonInclude.Include.NON_EMPTY)
@JsonIgnoreProperties(ignoreUnknown = true)
public class PetPatchDTO 
{   
    @ApiModelProperty(notes = "Pet Name", example = "Joe", required = true)
    @JsonProperty("name")
    private String name;
    
    @ApiModelProperty(notes = "Pet age", example = "1", required = true)
    @JsonProperty("age")
    private Short age;

    @ApiModelProperty(notes = "Date of birth", example = "1/2/2021", required = false)
    @JsonFormat(pattern = "dd/MM/yyyy", timezone="Europe/Madrid")
    @JsonProperty("birthDate")
    private Date birthDate;

    @ApiModelProperty(notes = "Picture of the pet in base64", example = "RxxsAre45fdsSef==", required = true)
    @JsonProperty("picture")
    private byte[] picture;

    @ApiModelProperty(notes = "Picture media type", example = "image/jpeg", required = true, allowEmptyValue = false, allowableValues = "image/jpeg, image/jpg, image/gif")
    @Pattern(regexp = "^(image/jpeg|image/jpg|image/gif)$")
    @JsonProperty("pictureMediaType")
    private String pictureMediaType;
}

¿Cuándo Usar DTO y Cuándo NO Usarlo?

Escenario Recomendación Motivo
Respuestas y peticiones de Controladores REST SIEMPRE usar DTO Aísla la API pública de los cambios de esquema en la base de datos y protege campos sensibles.
Operaciones parciales (PATCH) vs completas (POST/PUT) Separar DTOs Un DTO de creación exige todos los campos (@NotNull); un DTO de parcheo debe permitir campos nulos.
Llamadas internas entre métodos de la capa de Servicio NO usar DTO Dentro de la capa de negocio se trabaja directamente con las Entidades del dominio para aprovechar el estado de persistencia de JPA.

Contraejemplo (Mala Práctica): Exponer la Entidad JPA directamente en el Controlador

Observa el grave problema que ocurre cuando un controlador devuelve la entidad Pet de base de datos directamente en lugar de un DTO:


// ¡ERROR GRAVE DE DISEÑO Y SEGURIDAD!
@RestController
@RequestMapping("/pets")
public class BadPetController {

    @Autowired
    private PetRepository petRepository;

    // 1. Expone claves foráneas internas y campos de auditoría privados
    // 2. Si Pet tiene relaciones @OneToMany con Owner, lanzará StackOverflowError por recursión cíclica
    // 3. Cualquier cambio en las columnas de la tabla romperá los clientes front-end
    @GetMapping("/{id}")
    public Pet getPet(@PathVariable Integer id) {
        return petRepository.findById(id).orElseThrow();
    }
}
