Capa de Entidad (@Entity / JPA)

Una Entidad (@Entity) en Spring Boot representa una tabla física en la base de datos relacional dentro del estándar JPA (Java Persistence API / Jakarta Persistence), habitualmente implementado por el motor Hibernate. Cada instancia de una clase Entidad corresponde a una fila (registro) de la tabla, y cada uno de sus atributos mapea a una columna de dicha tabla.

Analogía del Mundo Real: El Registro de la Propiedad

Imagina el archivo físico del Registro de la Propiedad de una ciudad:

  • En el sótano hay archivadores metálicos con miles de fichas impresas (las tablas y filas de la base de datos SQL).
  • Para no tener que viajar físicamente al sótano con una linterna cada vez que alguien pregunta por una vivienda (escribir sentencias SQL manuales SELECT * FROM casa), existe una maqueta tridimensional en miniatura (@Entity) en el despacho.
  • Cuando el arquitecto cambia el color de una pared en la maqueta Java, el sistema ORM (Hibernate) sincroniza automáticamente ese cambio en la ficha del archivador metálico de base de datos sin que el programador tenga que redactar un UPDATE a mano.

Anotaciones Fundamentales de JPA / Jakarta Persistence

Ubicadas en el paquete jakarta.persistence.* (o javax.persistence.* en versiones previas a Spring Boot 3):

  • @Entity: Se coloca obligatoriamente en la cabecera de la clase. Informa al proveedor JPA (Hibernate) de que esta clase es una entidad gestionable por el contexto de persistencia y representa una tabla en la base de datos.
  • @Table: Opcional. Permite especificar el nombre exacto de la tabla en base de datos mediante @Table(name = "pet"), además de esquemas, catálogos y restricciones de unicidad compuestas (@UniqueConstraint). Si no se indica, JPA asume por defecto el nombre de la clase Java.
  • @Id: Marca el atributo que actúa como clave primaria (Primary Key) de la entidad. Toda entidad JPA debe tener obligatoriamente un @Id.
  • @GeneratedValue: Define la estrategia para que la base de datos genere automáticamente el valor de la clave primaria. Sus estrategias son:
    • GenerationType.IDENTITY: Utiliza columnas autoincrementales nativas de la base de datos (como AUTO_INCREMENT en MySQL o SERIAL en PostgreSQL).
    • GenerationType.SEQUENCE: Utiliza una secuencia de base de datos (habitual y óptimo en Oracle y PostgreSQL).
    • GenerationType.AUTO: Deja que Hibernate elija la mejor estrategia según el dialecto de la base de datos configurada.
    • GenerationType.TABLE: Simula una secuencia utilizando una tabla auxiliar de contadores (la más lenta, desaconsejada).
  • @SequenceGenerator: Define y personaliza los parámetros de una secuencia de base de datos (nombre de la secuencia en BD, valor inicial y tamaño de asignación allocationSize) para usarla en conjunto con @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "pet_seq").
  • @Column: Mapea el atributo a una columna específica mediante name = "birth_date". Permite fijar restricciones como nullable = false, longitud length = 50 o unicidad unique = true. Si se omite, JPA genera el nombre de columna convirtiendo camelCase a snake_case.
  • @Transient: Indica a JPA que ese atributo NO debe persistirse en ninguna columna de la base de datos (es un campo calculado en memoria o transitorio).

Anotaciones de Relaciones entre Tablas

  • @OneToOne: Define una relación uno a uno (ej. un usuario y su perfil). Si la relación es bidireccional, el lado no propietario debe incluir mappedBy = "nombreAtributoEnLaOtraClase".
  • @ManyToOne: Define una relación muchos a uno (ej. muchos pedidos pertenecen a un cliente). Es siempre el lado propietario de la relación y se acompaña de @JoinColumn(name = "cliente_id") para indicar la clave foránea.
  • @OneToMany: Define una relación uno a muchos (ej. un cliente tiene muchos pedidos). Generalmente se combina con una colección (List<Pedido>) y debe llevar mappedBy para no generar tablas intermedias duplicadas.
  • @ManyToMany: Define una relación muchos a muchos (ej. estudiantes y cursos). Requiere una tabla intermedia que se configura mediante @JoinTable:
    • mappedBy: Se coloca en el lado secundario para apuntar al atributo del lado propietario.
    • @JoinTable: Nombra la tabla intermedia física en base de datos mediante name = "pet_veterinarian".
    • @JoinColumn: Apunta a la columna de clave foránea que referencia a la entidad propietaria actual.
    • @InverseJoinColumn: Apunta a la columna de clave foránea que referencia a la entidad destino relacionada.

Propagación en Cascada (CascadeType) y Eliminación de Huérfanos

Cuando se realiza una operación sobre una entidad padre (como guardar o borrar), el atributo cascade indica si esa operación debe propagarse automáticamente a las entidades hijas vinculadas:

CascadeType Comportamiento en Base de Datos
CascadeType.PERSIST Al hacer save() o persist() sobre el padre, guarda automáticamente los hijos nuevos.
CascadeType.MERGE Al actualizar el padre, sincroniza y actualiza los hijos modificados.
CascadeType.REMOVE Al borrar el padre, elimina físicamente en cascada todos sus hijos asociados.
CascadeType.ALL Aplica todas las opciones anteriores (PERSIST, MERGE, REMOVE, REFRESH y DETACH).
orphanRemoval = true Si un elemento hijo se elimina de la lista Java del padre (lista.remove(0)), JPA borra automáticamente esa fila de la base de datos al hacer commit.

¿Cuándo Usar FetchType.LAZY frente a FetchType.EAGER?

Estrategia Comportamiento en Base de Datos Buenas Prácticas
FetchType.LAZY (Carga Perezosa) No descarga los registros hijos hasta que se invoque explícitamente el método row.getProcessedJSON() dentro de una transacción activa. Recomendado siempre por defecto en todas las relaciones @OneToMany y @ManyToOne para no penalizar memoria ni tiempos de respuesta.
FetchType.EAGER (Carga Ansiosa) Ejecuta un JOIN inmediato en la primera consulta para traer todos los objetos vinculados a la vez. Usar con extrema precaución: en tablas grandes puede provocar la descarga involuntaria de miles de registros relacionados.

Contraejemplo (Mala Práctica): El Peligro de @Data en Relaciones Bidireccionales

La anotación @Data de Lombok genera automáticamente los métodos toString() y hashCode() incluyendo todos los campos de la clase. Si dos entidades tienen una relación bidireccional (como ProcessedJSON que apunta a Row, y Row que apunta de vuelta a ProcessedJSON):


// ¡ERROR CLÁSICO EN JPA CON LOMBOK!
// ProcessedJSON.toString() llama a Row.toString(), que a su vez llama a ProcessedJSON.toString()...
// Provoca: java.lang.StackOverflowError instantáneo al hacer logging o inspeccionar objetos

// LA SOLUCIÓN CORRECTA:
// En lugar de @Data, usar @Getter y @Setter, y excluir explícitamente la relación en @ToString:
@Getter
@Setter
@ToString(exclude = "rowList")
@EqualsAndHashCode(of = "id")
@Entity
public class SafeProcessedJSON {
    // ...
}
Antipatrón: Bucle infinito StackOverflowError provocado por @Data en relaciones bidireccionales

Claves Primarias Compuestas: @EmbeddedId vs @IdClass

En modelos relacionales es común encontrar tablas donde la clave primaria no es un único número autoincremental, sino la combinación de dos o más columnas (claves naturales compuestas o registros de asociación en la clínica veterinaria, por ejemplo: código de mascota + código de vacuna + número de dosis). JPA ofrece dos estrategias estándar para mapear estas claves:

Criterio @EmbeddedId (Enfoque Objeto / Recomendado) @IdClass (Enfoque Relacional Plano)
Estructura Los campos de la clave se encapsulan en una clase auxiliar anotada con @Embeddable. La entidad contiene un único atributo anotado con @EmbeddedId. Los campos de la clave se definen como atributos directos en la propia entidad con @Id, y se asocian a una clase clave externa con @IdClass(ClaveId.class).
Navegabilidad Orientado a objetos claro: entidad.getId().getPetId(). La clave es un objeto autocontenido. Plano: entidad.getPetId() directo en la entidad.
Requisitos La clase clave debe implementar Serializable, tener constructor por defecto y sobrescribir correctamente equals y hashCode. Mismos requisitos de Serializable y equals/hashCode en la clase externa auxiliar.
Cuándo usarlo Recomendado para la inmensa mayoría de casos: mayor cohesión, paso de la clave completa como parámetro único y tipado estricto en repositorios (JpaRepository<PetVaccinationScheduleEntity, PetVaccinationScheduleId>). Sistemas legados con tablas existentes donde se prefiera acceder a los campos clave de forma plana sin llamar a un objeto intermedio.

1. Estrategia con @EmbeddedId y @Embeddable (Recomendada)

Primero se define la clase que agrupa los campos de la clave primaria compuesta (calendario de vacunación de la mascota), anotada con @Embeddable: 


package com.example.petshop.model;

import jakarta.persistence.Column;
import jakarta.persistence.Embeddable;
import lombok.*;

import java.io.Serializable;

@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
@EqualsAndHashCode
@Embeddable
public class PetVaccinationScheduleId implements Serializable {

    private static final long serialVersionUID = 1L;

    @Column(name = "pet_id", nullable = false)
    private Long petId;

    @Column(name = "vaccine_code", nullable = false, length = 30)
    private String vaccineCode;

    @Column(name = "dose_number", nullable = false)
    private Integer doseNumber;
}

A continuación, la entidad principal declara su identificador utilizando @EmbeddedId: 


package com.example.petshop.model;

import jakarta.persistence.*;
import lombok.*;

import java.time.LocalDate;

@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
@ToString
@EqualsAndHashCode(onlyExplicitlyIncluded = true)
@Entity
@Table(name = "pet_vaccination_schedules")
public class PetVaccinationScheduleEntity {

    @EmbeddedId
    @EqualsAndHashCode.Include
    private PetVaccinationScheduleId id;

    private LocalDate scheduledDate;

    @Column(name = "administered_date")
    private LocalDate administeredDate;

    @Column(name = "veterinarian_license", length = 50)
    private String veterinarianLicense;

    @Column(name = "status", nullable = false, length = 20)
    private String status;
}

2. Relaciones con Claves Compuestas: @JoinColumns

Cuando una entidad relacionada (como el registro de reacciones alérgicas post-vacunales de la mascota) debe referenciar a una tabla cuya clave primaria está formada por varias columnas, se utiliza la anotación @JoinColumns agrupando múltiples @JoinColumn: 


package com.example.petshop.model;

import jakarta.persistence.*;
import lombok.*;

import java.time.LocalDateTime;

@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
@ToString
@EqualsAndHashCode(onlyExplicitlyIncluded = true)
@Entity
@Table(name = "pet_vaccine_reactions")
public class PetVaccineReactionEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @EqualsAndHashCode.Include
    private Long id;

    // Relación que referencia la clave primaria compuesta de PetVaccinationScheduleEntity
    @ToString.Exclude
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumns({
        @JoinColumn(name = "pet_id", referencedColumnName = "pet_id", nullable = false),
        @JoinColumn(name = "vaccine_code", referencedColumnName = "vaccine_code", nullable = false),
        @JoinColumn(name = "dose_number", referencedColumnName = "dose_number", nullable = false)
    })
    private PetVaccinationScheduleEntity vaccinationSchedule;

    @Column(name = "reaction_description", nullable = false, length = 500)
    private String reactionDescription;

    @Column(name = "severity_level", nullable = false, length = 20)
    private String severityLevel;

    @Column(name = "recorded_at", nullable = false)
    private LocalDateTime recordedAt;
}
