Patrón Template Method (Método Plantilla)

El patrón Template Method (Método Plantilla) es un patrón de diseño de comportamiento que define el esqueleto invariable de un algoritmo en un método de una clase base abstracta, delegando la implementación de ciertos pasos específicos en las subclases sin permitir que estas alteren el orden ni la estructura general del proceso.

Analogía del Mundo Real: Construcción de Casas Prefabricadas

Imagina una empresa de construcción de viviendas modulares:

  • El arquitecto jefe establece el orden inalterable de la obra (el Método Plantilla): 1. Cimentación → 2. Estructura portante → 3. Fontanería y Electricidad → 4. Acabados y Pintura.
  • Ningún constructor puede ponerse a pintar las paredes antes de verter los cimientos; si lo intentara, la casa colapsaría.
  • Sin embargo, cada cliente puede personalizar los pasos concretos (un cliente elige suelo de parquet y paredes blancas; otro prefiere baldosas cerámicas y paredes grises). El esqueleto del algoritmo permanece intacto.

Propósito

Reutilizar el esqueleto y la lógica de control común de un flujo complejo, evitando duplicar código boilerplate y aplicando el Principio de Hollywood ("No nos llames, nosotros te llamaremos"): la clase padre invoca a los métodos de las clases hijas, nunca al revés.

Caso de Uso Real: Procesamiento de Reportes Financieros en PetShop

Contexto: En la plataforma PetShop, exportar informes de ventas y adopciones requiere siempre el mismo ciclo: 1) conectar y autenticar con el almacén de datos, 2) extraer los registros transaccionales, 3) dar formato específico al documento (PDF o Excel CSV), y 4) registrar auditoría y cerrar la conexión.

El Problema (Sin Template Method): Si cada formato (ReportePdf y ReporteCsv) implementa su propio método generar() por libre, se duplicarán las conexiones y el manejo de excepciones, y algún programador podría olvidar cerrar los recursos o registrar la auditoría.

La Solución (Con Template Method): Se crea la clase abstracta GeneradorReportes con el método inmutable public final void generarReporte(). Las subclases solo implementan el paso abstracto de formateo.

Implementación en Java (con Métodos Abstractos y Hooks)


// 1. Clase Abstracta con el Método Plantilla 'final'
public abstract class GeneradorReportes {

    // MÉTODO PLANTILLA: 'final' para que ninguna subclase altere el orden de ejecución
    public final void generarReporte(String entidad) {
        conectarFuenteDatos();
        String datos = extraerDatos(entidad);
        darFormato(datos);

        // Método Gancho (Hook): paso opcional que las subclases pueden activar o ignorar
        if (requiereCifrado()) {
            cifrarDocumento();
        }

        cerrarConexion();
    }

    // Pasos comunes con implementación por defecto
    private void conectarFuenteDatos() {
        System.out.println("🔌 [BD] Conexión abierta con el almacén transaccional de PetShop.");
    }

    private void cerrarConexion() {
        System.out.println("🔒 [BD] Conexión liberada y devuelta al pool de conexiones.");
    }

    private void cifrarDocumento() {
        System.out.println("🛡️ [Seguridad] Cifrando archivo final con clave simétrica AES-256.");
    }

    // Pasos obligatorios que las subclases DEBEN implementar
    protected abstract String extraerDatos(String entidad);
    protected abstract void darFormato(String datos);

    // Método Gancho (Hook): por defecto no requiere cifrado, pero puede sobrescribirse
    protected boolean requiereCifrado() {
        return false;
    }
}

// 2. Subclase Concreta A: Reporte en PDF
public class ReportePdf extends GeneradorReportes {
    @Override
    protected String extraerDatos(String entidad) {
        return "Listado consolidado de " + entidad;
    }

    @Override
    protected void darFormato(String datos) {
        System.out.println("📄 [PDF Engine] Compilando vectorialmente documento PDF con fuentes y logotipos: " + datos);
    }

    @Override
    protected boolean requiereCifrado() {
        return true; // Los PDFs contienen datos confidenciales y activan el cifrado
    }
}

// 3. Subclase Concreta B: Reporte plano CSV
public class ReporteCsv extends GeneradorReportes {
    @Override
    protected String extraerDatos(String entidad) {
        return "id,nombre,especie,estado\n1,Max,Perro,Adoptado";
    }

    @Override
    protected void darFormato(String datos) {
        System.out.println("📊 [CSV Engine] Generando archivo de texto delimitado por comas:\n" + datos);
    }
}

Ejemplo de Uso y Trazas de Consola


public class Main {
    public static void main(String[] args) {
        System.out.println("--- 1. Generando Reporte Confidencial en PDF ---");
        GeneradorReportes pdf = new ReportePdf();
        pdf.generarReporte("Adopciones de Octubre");

        System.out.println("\n--- 2. Generando Volcado Rápido en CSV ---");
        GeneradorReportes csv = new ReporteCsv();
        csv.generarReporte("Inventario Mascotas");
    }
}

El Patrón en el Ecosistema Spring: Clases "Template"

Spring Framework utiliza masivamente este patrón en sus componentes más populares para gestionar recursos de red y conexiones a bases de datos sin fugas de memoria:

  • JdbcTemplate: Abre la conexión JDBC, ejecuta la transacción, cierra el ResultSet y libera la conexión, delegando en el usuario únicamente el mapeo fila a fila (RowMapper).
  • TransactionTemplate: Demarca begin, commit y rollback, delegando la lógica atómica mediante un callback TransactionCallback.
  • RestTemplate: Resuelve cabeceras, serializa JSON, abre el socket HTTP y cierra el stream, delegando en el cliente la interpretación del body.

Diferencias Clave: Template Method vs Strategy

Característica Template Method Strategy
Mecanismo de Reutilización Herencia de Clases: Se extiende de una clase abstracta común. Composición de Objetos: Se inyecta una interfaz en el contexto.
Nivel de Cambio Permite alterar únicamente pasos puntuales del algoritmo; la estructura es rígida. Permite sustituir el algoritmo completo de principio a fin.
Momento del Cambio Fijo en tiempo de compilación según la subclase instanciada. Dinámico e intercambiable en tiempo de ejecución (runtime).

¿Cuándo usarlo y cuándo NO usarlo?

Cuándo SÍ Usar Template Method Cuándo NO Usarlo
Cuando varios flujos de la aplicación compartan exactamente la misma secuencia de pasos y solo difieran en implementaciones puntuales. Cuando el flujo general cambie radicalmente entre un caso y otro (en tal caso usar Strategy).
Para garantizar que pasos críticos (como abrir/cerrar transacciones, auditar o liberar conexiones) se ejecuten siempre sin olvidos. Si la jerarquía de herencia se vuelve demasiado profunda y frágil (violando la recomendación de favorecer composición sobre herencia).
