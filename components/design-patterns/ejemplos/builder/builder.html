Patrón Builder (Constructor Fluido)

El patrón Builder (Constructor) es un patrón creacional de diseño que permite construir objetos complejos paso a paso. En lugar de forzar al desarrollador a utilizar un constructor gigante repleto de parámetros confusos (muchos de ellos opcionales o nulos), proporciona una interfaz fluida (Fluent Interface) para configurar solo los atributos necesarios y garantizar la inmutabilidad del objeto resultante.

Analogía del Mundo Real: Pedido en una Pizzería Artesanal

Imagina que pides una pizza en una pizzería a medida:

  • Sin Builder (Antipatrón Telescópico): Tendrías que rellenar un formulario con 30 casillas obligatorias marcando: "Masa fina, tomate sí, queso sí, anchoas NO, champiñones NO, piña NO, cebolla NO...". Si el camarero confunde la casilla 14 con la 15, te pondrá salsa picante en lugar de orégano.
  • Con Builder: Indicas únicamente los ingredientes que deseas en el orden que prefieras: "Quiero masa fina, salsa barbacoa, doble de queso y bacon" y al terminar dices "¡Hornear!" (el método build()). El resultado es un producto terminado, caliente y que ya no puede ser alterado en la mesa.

Propósito

Separar la construcción de un objeto complejo de su representación final, eliminando el antipatrón de Constructores Telescópicos (Telescoping Constructor) y permitiendo crear objetos inmutables con campos final sin necesidad de exponer métodos setter públicos.

Caso de Uso Real: Construcción de una Petición HTTP o Entidad Mascota

Contexto: En la plataforma PetShop, un objeto Pet o PetDTO cuenta con identificador, nombre, especie, edad, chip identificativo, estado de vacunación, alergias y dirección de entrega.

El Problema (Sin Builder): Escribir new Pet(1, "Max", "Perro", 3, null, true, null, null) es una pesadilla de mantenimiento. Si dos parámetros consecutivos son de tipo String o boolean, el compilador de Java no detectará si has invertido el orden, provocando errores silenciosos en tiempo de ejecución.

La Solución (Con Builder): Se crea una clase constructora estática interna (Static Nested Builder) que encadena métodos descriptivos (name("Max"), breed("Labrador"), vaccinated(true)) y valida el estado completo antes de devolver la instancia inmutable con build().

Implementación Canónica en Java Moderno (Objeto Inmutable)


// 1. Producto Inmutable: Atributos 'final' y constructor privado
public class Pizza {
    private final String masa;
    private final String salsa;
    private final String ingrediente;
    private final boolean quesoExtra;

    // Constructor privado: SOLO el Builder puede invocar a new Pizza(...)
    private Pizza(Builder builder) {
        this.masa = builder.masa;
        this.salsa = builder.salsa;
        this.ingrediente = builder.ingrediente;
        this.quesoExtra = builder.quesoExtra;
    }

    public String getMasa() { return masa; }
    public String getSalsa() { return salsa; }
    public String getIngrediente() { return ingrediente; }
    public boolean isQuesoExtra() { return quesoExtra; }

    @Override
    public String toString() {
        return "Pizza { masa='" + masa + "', salsa='" + salsa + "', ingrediente='" + ingrediente + "', quesoExtra=" + quesoExtra + " }";
    }

    // 2. Builder estático interno (Static Nested Class)
    public static class Builder {
        private String masa;
        private String salsa;
        private String ingrediente;
        private boolean quesoExtra = false; // Valor por defecto

        public Builder masa(String masa) {
            this.masa = masa;
            return this; // Fluent Interface: permite encadenar llamadas
        }

        public Builder salsa(String salsa) {
            this.salsa = salsa;
            return this;
        }

        public Builder ingrediente(String ingrediente) {
            this.ingrediente = ingrediente;
            return this;
        }

        public Builder quesoExtra(boolean quesoExtra) {
            this.quesoExtra = quesoExtra;
            return this;
        }

        // Método terminal de construcción con validación de integridad
        public Pizza build() {
            if (this.masa == null || this.masa.isBlank()) {
                throw new IllegalStateException("No se puede hornear una pizza sin tipo de masa.");
            }
            return new Pizza(this);
        }
    }
}

El Rol Opcional del "Director"

El Director es una clase opcional recomendada cuando en tu aplicación existen recetas o configuraciones típicas estandarizadas que se repiten con frecuencia:


public class PizzeriaDirector {
    public Pizza construirMargaritaClasica(Pizza.Builder builder) {
        return builder.masa("Fina Italiana")
                      .salsa("Tomate San Marzano")
                      .ingrediente("Albahaca fresca")
                      .quesoExtra(true)
                      .build();
    }
}
Director automatizando la construcción de una configuración estándar

Equivalencia Automática en Spring Boot con Project Lombok (@Builder)

En proyectos empresariales con Spring Boot no es necesario escribir las 50 líneas del Builder a mano; la anotación @Builder de Lombok genera exactamente la clase interna estática durante la compilación:


@Getter
@Builder
@AllArgsConstructor(access = AccessLevel.PRIVATE)
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class PetDTO {
    private String name;
    private String species;
    private Integer age;
}

// Uso inmediato idéntico al patrón Builder:
PetDTO dto = PetDTO.builder()
        .name("Bobby")
        .species("Canino")
        .age(4)
        .build();
Generación automática del patrón Builder mediante Project Lombok

Ejemplo de Uso y Comprobación en Consola


public class Main {
    public static void main(String[] args) {
        // Pedido 1: Configuración personalizada paso a paso
        Pizza pizzaCustom = new Pizza.Builder()
                .masa("Masa de Espelta")
                .salsa("Barbacoa Ahumada")
                .ingrediente("Pollo y Cebolla Caramelizada")
                .quesoExtra(true)
                .build();
        System.out.println("1. Pedido a medida:\n   " + pizzaCustom);

        // Pedido 2: Utilizando el Director con receta estándar
        PizzeriaDirector director = new PizzeriaDirector();
        Pizza margarita = director.construirMargaritaClasica(new Pizza.Builder());
        System.out.println("\n2. Receta estándar del Director:\n   " + margarita);
    }
}

Contraejemplo: El Antipatrón del Constructor Telescópico


// ANTIPATRÓN CRÍTICO: Constructores sobrecargados infinitos
public class TelescopingPizza {
    public TelescopingPizza(String masa) { ... }
    public TelescopingPizza(String masa, String salsa) { ... }
    public TelescopingPizza(String masa, String salsa, String ingrediente) { ... }
    public TelescopingPizza(String masa, String salsa, String ingrediente, boolean quesoExtra, boolean bordeQueso, String picante) {
        // ¿Qué significan 'true, false, null'? Código propenso a errores y confuso
    }
}

// Invocación ilegible:
TelescopingPizza p = new TelescopingPizza("Fina", "Tomate", null, true, false, null);
Antipatrón Telescópico: Imposible discernir qué hace cada argumento sin abrir el código fuente

¿Cuándo usarlo y cuándo NO usarlo?

Cuándo SÍ Usar Builder Cuándo NO Usarlo
Clases con más de 3 o 4 atributos opcionales o del mismo tipo básico (String, int, boolean). Clases muy simples con 1 o 2 atributos obligatorios (ej. un par clave-valor Point(x, y)) donde un constructor clásico es más directo.
Cuando se requiera garantizar la inmutabilidad de la clase sin exponer métodos setter. Cuando la clase deba ser obligatoriamente serializada por herramientas antiguas que exijan JavaBean estándar con constructor por defecto y setters mutables.
En APIs y DTOs de microservicios para construir respuestas y peticiones limpias y fluidas. En estructuras temporales de alto rendimiento creadas miles de veces por segundo donde el objeto intermedio Builder añada presión innecesaria al recolector de basura (GC).
