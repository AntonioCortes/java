Patrón Context Object

El patrón Context Object (Objeto de Contexto) es un patrón de la arquitectura Java EE que encapsula información del entorno o de la petición (como el usuario autenticado, su idioma o el ID de trazabilidad) en un objeto agnóstico del protocolo web, evitando acoplar las capas de negocio a clases como HttpServletRequest.

Analogía del Mundo Real

Piensa en la pulsera identificativa que te ponen al ingresar en un hospital o en un hotel Todo Incluido. Cuando vas al comedor o a la piscina (las capas internas de negocio), no tienes que llevar encima el contrato original firmado en recepción ni pasárselo en mano a cada camarero: simplemente llevas puesta tu pulsera en la muñeca (el Context Object asociado a ti) y cualquier empleado puede consultarla cuando lo necesite.

Propósito

Evitar dos malas prácticas muy comunes: 1) pasar el objeto HttpServletRequest a los servicios de negocio, y 2) ensuciar todos los métodos de la aplicación añadiendo parámetros extra como (..., String currentUser, String locale).

Caso de Uso Real: Propagación del Usuario Logueado (ContextoSeguridad) para Auditoría

Contexto: Cuando un usuario crea un pedido, la capa más profunda de base de datos (AuditoriaDAO) necesita registrar en una tabla de auditoría qué usuario ejecutó la operación.

El Problema (Sin Context Object): Si pasas HttpServletRequest desde el Controlador hasta el Servicio y luego hasta el DAO, tu DAO dependerá de la librería de Servlets web y no podrás reutilizarlo en un proceso por lotes (Batch) ni en tests unitarios simples.

La Solución (Con Context Object): Al entrar la petición, el filtro web guarda el usuario en ContextoSeguridad (almacenado en un ThreadLocal propio del hilo actual). El Servicio y el DAO mantienen sus firmas de métodos limpias, y cuando AuditoriaDAO necesita saber quién es el usuario, llama directamente a ContextoSeguridad.getUser().

Implementación en Java


// 1. Objeto de datos del Contexto (POJO limpio, sin dependencias de Servlets/HTTP)
class UserContext {
    private String username;
    private String role;

    public UserContext(String username, String role) {
        this.username = username;
        this.role = role;
    }

    public String getUsername() { return username; }
    public String getRole() { return role; }
}

// 2. Context Object Holder: almacena el contexto aislado para el hilo actual
class ContextoSeguridad {
    private static final ThreadLocal<UserContext> currentContext = new ThreadLocal<>();

    public static void set(UserContext context) {
        currentContext.set(context);
    }

    public static UserContext get() {
        return currentContext.get();
    }

    public static void clear() {
        currentContext.remove();
    }
}

// 3. Capa de Acceso a Datos (consulta el contexto sin recibirlo por parámetro)
class AuditoriaDAO {
    public void guardarRegistro(String operation) {
        UserContext user = ContextoSeguridad.get();
        System.out.println("📝 [AuditoriaDAO] Guardando en BD -> Acción: '" + operation
                + "' ejecutada por usuario: " + user.getUsername() + " (" + user.getRole() + ")");
    }
}

// 4. Capa de Negocio (firma del método 100% limpia de datos de protocolo)
class ServicioPedidos {
    private AuditoriaDAO auditDAO = new AuditoriaDAO();

    public void crearPedido(String product) {
        System.out.println("⚙️ [ServicioPedidos] Procesando compra del producto: " + product);
        auditDAO.guardarRegistro("CREAR_PEDIDO_" + product.toUpperCase());
    }
}

Análisis Paso a Paso para Principiantes

  • 1. ¿Qué es ThreadLocal y por qué se usa aquí?

    En un servidor web hay muchos usuarios haciendo peticiones al mismo tiempo, cada uno en su propio hilo (thread). ThreadLocal es una "taquilla privada" por cada hilo: lo que el hilo de Ana guarda en ContextoSeguridad.set(...) solo puede verlo el hilo de Ana cuando llama a ContextoSeguridad.get(), sin mezclarse jamás con la petición de otro usuario.

  • 2. Uso real en Spring Security y Logback (MDC):

    ContextoSeguridadHolder.getContext().getAuthentication() en Spring Security y MDC.put("traceId", ...) en SLF4J funcionan exactamente así.

Ejemplo de Uso


public class Main {
    public static void main(String[] args) {
        ServicioPedidos orderService = new ServicioPedidos();

        try {
            // 1. Al entrar la petición, el filtro web inicializa el Context Object
            System.out.println(">> [Filtro Web] Inicializando ContextoSeguridad para la petición actual...");
            ContextoSeguridad.set(new UserContext("antonio.dev", "ADMIN"));

            // 2. Llamamos al servicio pasando SOLO datos de negocio (el producto)
            orderService.crearPedido("Portátil Gaming");

        } finally {
            // 3. Buena práctica: limpiar siempre el ThreadLocal al terminar la petición
            ContextoSeguridad.clear();
            System.out.println(">> [Filtro Web] ContextoSeguridad limpiado al finalizar la petición.");
        }
    }
}

¿Cuándo usarlo y cuándo NO usarlo?

  • Cuándo usarlo: Para propagar metadatos transversales de infraestructura (usuario autenticado, idioma/región, ID de correlación de logs o transacciones) a través de las capas de la aplicación.
  • Cuándo evitarlo: Nunca uses un Context Object como "bolsa oculta" para pasar parámetros normales de negocio (como el ID del producto a comprar); los parámetros de negocio deben seguir pasándose explícitamente en los argumentos del método.
