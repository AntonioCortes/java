Patrón Singleton

El patrón Singleton es un patrón de diseño creacional que garantiza que una clase tenga una única instancia en toda la aplicación y proporciona un punto de acceso global y centralizado a ella.

Analogía del Mundo Real

Imagina el Gobierno de un país o la Torre de Control de un aeropuerto. Aunque existan millones de ciudadanos o cientos de aviones que necesiten comunicarse con esa entidad, solo existe una única instancia oficial en funcionamiento. Cuando alguien necesita interactuar con "el Gobierno" o "la Torre de Control", no funda un gobierno nuevo ni construye otra torre: siempre acude a la instancia única ya existente.

Propósito

Controlar estrictamente la creación de un objeto para asegurar que nunca exista más de una instancia en memoria, ofreciendo a la vez un método accesible desde cualquier parte del programa para obtenerla.

Caso de Uso Real: Gestor Centralizado de Conexiones a Base de Datos

Contexto: En una aplicación empresarial, abrir y cerrar conexiones hacia la base de datos es una operación muy costosa en tiempo de CPU y memoria. Además, el motor de base de datos tiene un límite estricto de conexiones simultáneas.

El Problema (Sin Singleton): Si cada módulo de la aplicación (usuarios, facturación, inventario) ejecuta libremente new ConexionBaseDatos() cada vez que necesita hacer una consulta, se abrirán decenas o cientos de conexiones duplicadas. Esto agotará rápidamente los recursos del servidor de base de datos y provocará la caída del sistema.

La Solución (Con Singleton): Bloqueamos el uso libre de new haciendo que el constructor sea privado. La propia clase ConexionBaseDatos guarda en su interior su única instancia y expone el método estático ConexionBaseDatos.obtenerInstancia(). El primer módulo que lo llame inicializará la conexión; todos los demás módulos recibirán exactamente ese mismo objeto ya creado.

Las 3 Variantes de Implementación en Java Moderno

Variante 1: Double-Checked Locking (Doble Comprobación de Bloqueo)

Utiliza evaluación perezosa (Lazy Initialization), garantizando que la instancia no consuma memoria hasta que alguien la solicita por primera vez. Es segura para entornos multihilo gracias a volatile y al bloque synchronized:


public class ConexionBaseDatos {
    // 1. Atributo estático volatile: garantiza visibilidad entre hilos y previene reordenación de instrucciones
    private static volatile ConexionBaseDatos instancia;
    private final String cadenaConexion;

    // 2. Constructor privado: prohíbe el uso de new fuera de esta clase
    private ConexionBaseDatos() {
        this.cadenaConexion = "jdbc:postgresql://localhost:5432/petshop_db";
        System.out.println(">> [INIT] Conexión física a PostgreSQL iniciada: " + cadenaConexion);
    }

    // 3. Doble comprobación: solo sincroniza en la primera invocación
    public static ConexionBaseDatos obtenerInstancia() {
        if (instancia == null) { // Primera comprobación (sin penalización de bloqueo)
            synchronized (ConexionBaseDatos.class) {
                if (instancia == null) { // Segunda comprobación con cerrojo exclusivo
                    instancia = new ConexionBaseDatos();
                }
            }
        }
        return instancia;
    }

    public void ejecutarConsulta(String query) {
        System.out.println("Ejecutando SQL en [" + cadenaConexion + "]: " + query);
    }
}
Implementación clásica Thread-Safe con Double-Checked Locking

Variante 2: Bill Pugh Singleton (Holder Idiom - Recomendada en Java Clásico)

Aprovecha los mecanismos del ClassLoader de la JVM: la clase interna estática Holder solo se carga en memoria en el momento exacto en que alguien llama al método obtenerInstancia(). Es 100% thread-safe y no requiere ningún bloque synchronized:


public class ConfiguracionGlobal {

    private ConfiguracionGlobal() {
        System.out.println(">> [INIT] Cargando fichero de configuración global en memoria...");
    }

    // Clase estática interna: la JVM solo la carga cuando se invoca obtenerInstancia()
    private static class Holder {
        private static final ConfiguracionGlobal INSTANCIA = new ConfiguracionGlobal();
    }

    public static ConfiguracionGlobal obtenerInstancia() {
        return Holder.INSTANCIA;
    }
}
Bill Pugh Singleton: inicialización perezosa ultrarrápida sin sobrecarga de sincronización

Variante 3: Enum Singleton (Recomendación Oficial de Joshua Bloch en Effective Java)

En Java, los enumerados son inherentemente instancias únicas administradas por la JVM. Es la **única forma** que resiste automáticamente ataques por reflexión y deserialización sin escribir código adicional:


public enum GestorSeguridad {
    INSTANCIA; // Única instancia garantizada por la JVM

    private String claveSecreta = "JWT_SECRET_KEY_PRODUCCION";

    public void validarToken(String token) {
        System.out.println("Validando token con clave única: " + claveSecreta);
    }
}
Enum Singleton: inmune a ataques de reflexión y deserialización

Ejemplo de Uso y Comprobación en Consola


public class Main {
    public static void main(String[] args) {
        System.out.println("1. Solicitando primera referencia (db1)...");
        ConexionBaseDatos db1 = ConexionBaseDatos.obtenerInstancia();
        db1.ejecutarConsulta("SELECT * FROM pets WHERE status = 'AVAILABLE'");

        System.out.println("\n2. Solicitando segunda referencia (db2) desde otra parte del sistema...");
        ConexionBaseDatos db2 = ConexionBaseDatos.obtenerInstancia();
        db2.ejecutarConsulta("INSERT INTO pets (name) VALUES ('Firulais')");

        System.out.println("\n3. Verificando si db1 y db2 son exactamente el mismo objeto en memoria:");
        if (db1 == db2) {
            System.out.println("¡ÉXITO! db1 y db2 apuntan a la misma dirección física de memoria (==).");
        } else {
            System.out.println("ERROR: Se han creado instancias distintas.");
        }
    }
}

Contraejemplo: Cómo Romper un Singleton y Cómo Protegerlo

1. Ataque por Reflexión

Un desarrollador o biblioteca maliciosa puede cambiar la visibilidad del constructor privado mediante reflexión (constructor.setAccessible(true)) y crear una segunda instancia:


// VULNERABILIDAD: Un atacante usa reflexión para forzar el constructor privado
Constructor<ConexionBaseDatos> constructor = ConexionBaseDatos.class.getDeclaredConstructor();
constructor.setAccessible(true);
ConexionBaseDatos instancia2 = constructor.newInstance(); // ¡Se crea una segunda instancia!

// SOLUCIÓN: Lanzar excepción si ya existe la instancia en el constructor
private ConexionBaseDatos() {
    if (instancia != null) {
        throw new IllegalStateException("¡Violación de Singleton! Usa obtenerInstancia().");
    }
    // Inicialización normal...
}
Protección contra violación de Singleton mediante Java Reflection

2. Ataque por Serialización / Deserialización

Si la clase implementa Serializable, al deserializarla en disco o red Java crea una copia nueva sin invocar el constructor:


// SOLUCIÓN: Implementar readResolve() para devolver siempre la instancia única
protected Object readResolve() {
    return obtenerInstancia();
}
readResolve asegura que la deserialización no duplique el objeto

¿Cuándo usarlo y cuándo NO usarlo?

Cuándo SÍ usar Singleton Cuándo NO usarlo (Antipatrón)
Para recursos compartidos físicamente únicos: gestores de configuración de solo lectura, pools de hilos o drivers de hardware. Como almacén de variables globales mutables: acopla módulos y dificulta depurar qué hilo modificó los datos.
Para fábricas de objetos sin estado (como Abstract Factory). En aplicaciones Spring Boot: no implementes Singleton a mano en clases marcadas con @Service o @Component; el contenedor de Spring ya gestiona el alcance Singleton (Singleton Scope) de forma limpia y testeable.
Cuando la creación del objeto es sumamente costosa en CPU/I-O y debe ser compartido. En pruebas unitarias: los Singletons manuales conservan estado entre tests y no pueden sustituirse por mocks fácilmente sin reflexión.
