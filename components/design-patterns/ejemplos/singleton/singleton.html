Patrón Singleton

El patrón Singleton es un patrón de diseño creacional que garantiza que una clase tenga una única instancia en toda la aplicación y proporciona un punto de acceso global a ella.

Analogía del Mundo Real

Imagina el Gobierno de un país o la Torre de Control de un aeropuerto. Aunque existan millones de ciudadanos o cientos de aviones que necesiten comunicarse con esa entidad, solo existe una única instancia oficial en funcionamiento. Cuando alguien necesita interactuar con "el Gobierno" o "la Torre de Control", no funda un gobierno nuevo ni construye otra torre: siempre acude a la instancia única ya existente.

Propósito

Controlar estrictamente la creación de un objeto para asegurar que nunca exista más de una instancia en memoria, ofreciendo a la vez un método accesible desde cualquier parte del programa para obtenerla.

Caso de Uso Real: Gestor Centralizado de Conexiones a Base de Datos

Contexto: En una aplicación empresarial, abrir y cerrar conexiones hacia la base de datos es una operación muy costosa en tiempo de CPU y memoria. Además, el motor de base de datos tiene un límite estricto de conexiones simultáneas.

El Problema (Sin Singleton): Si cada módulo de la aplicación (usuarios, facturación, inventario) ejecuta libremente new ConexionBaseDatos() cada vez que necesita hacer una consulta, se abrirán decenas o cientos de conexiones duplicadas. Esto agotará rápidamente los recursos del servidor de base de datos y provocará la caída del sistema.

La Solución (Con Singleton): Bloqueamos el uso libre de new haciendo que el constructor sea privado. La propia clase ConexionBaseDatos guarda en su interior su única instancia y expone el método estático ConexionBaseDatos.obtenerInstancia(). El primer módulo que lo llame inicializará la conexión; todos los demás módulos recibirán exactamente ese mismo objeto ya creado.

Implementación en Java (Segura para Hilos / Thread-Safe)

En aplicaciones reales donde varios hilos (threads) se ejecutan a la vez, dos hilos podrían llamar a obtenerInstancia() en el mismo milisegundo y crear dos instancias por accidente. Para evitarlo sin perder rendimiento, utilizamos la técnica Double-Checked Locking (Doble Comprobación de Bloqueo) junto con la palabra clave volatile.


public class ConexionBaseDatos {
    // 1. Atributo estático y volatile que guardará la ÚNICA instancia en memoria
    private static volatile ConexionBaseDatos instancia;
    
    // Datos internos de nuestra conexión
    private String cadenaConexion;

    // 2. Constructor PRIVADO: impide hacer 'new ConexionBaseDatos()' desde fuera
    private ConexionBaseDatos() {
        this.cadenaConexion = "jdbc:mysql://localhost:3306/mi_tienda_db";
        System.out.println(">> [INIT] Conexión física a la base de datos iniciada: " + cadenaConexion);
    }

    // 3. Punto de acceso global estático
    public static ConexionBaseDatos obtenerInstancia() {
        // Primera comprobación (sin bloqueo) para no penalizar el rendimiento si ya existe
        if (instancia == null) {
            // Solo bloqueamos si la instancia aún no se ha creado
            synchronized (ConexionBaseDatos.class) {
                // Segunda comprobación dentro del bloque sincronizado
                if (instancia == null) {
                    instancia = new ConexionBaseDatos();
                }
            }
        }
        return instancia;
    }

    // Método de negocio del Singleton
    public void ejecutarConsulta(String query) {
        System.out.println("Ejecutando SQL en [" + cadenaConexion + "]: " + query);
    }
}

Análisis Paso a Paso para Principiantes

  • 1. ¿Por qué el constructor es private?

    En Java, si un constructor es public, cualquier programador puede escribir new ConexionBaseDatos() y crear copias infinitas. Al declararlo private, el compilador prohíbe usar new fuera de esta clase.

  • 2. ¿Por qué el atributo instancia y el método obtenerInstancia() son static?

    Como nadie puede crear un objeto primero para llamar a un método normal, necesitamos un método que pertenezca a la clase en sí misma (static). Así podemos invocarlo directamente como ConexionBaseDatos.obtenerInstancia().

  • 3. ¿Qué hace volatile y synchronized?

    La primera vez que se llama a obtenerInstancia(), instancia vale null. El bloque synchronized pone un "cerrojo" para que solo un hilo entre a ejecutar el new ConexionBaseDatos(), y volatile asegura que todos los demás hilos vean inmediatamente la instancia recién creada en memoria principal.

Ejemplo de Uso


public class Main {
    public static void main(String[] args) {
        System.out.println("1. Solicitando primera referencia (db1)...");
        ConexionBaseDatos db1 = ConexionBaseDatos.obtenerInstancia();
        db1.ejecutarConsulta("SELECT * FROM usuarios");

        System.out.println("\n2. Solicitando segunda referencia (db2) desde otra parte del sistema...");
        ConexionBaseDatos db2 = ConexionBaseDatos.obtenerInstancia();
        db2.ejecutarConsulta("INSERT INTO pedidos VALUES (101, 'Completado')");

        System.out.println("\n3. Verificando si db1 y db2 son exactamente el mismo objeto en memoria:");
        if (db1 == db2) {
            System.out.println("¡ÉXITO! db1 y db2 apuntan a la misma instancia única.");
        } else {
            System.out.println("ERROR: Se han creado instancias distintas.");
        }
    }
}

¿Cuándo usarlo y cuándo NO usarlo?

  • Cuándo usarlo: Cuando deba existir exactamente un recurso compartido en todo el programa (un gestor de configuración global, un pool de conexiones, una caché en memoria o un sistema de registro de logs).
  • Cuándo evitarlo: No lo uses como sustituto de variables globales para guardar datos temporales. Abusar de Singleton oculta las dependencias entre clases y dificulta los tests unitarios (en frameworks como Spring Boot suele preferirse delegar el ciclo de vida único al contenedor de Inyección de Dependencias con @Service o @Component).
