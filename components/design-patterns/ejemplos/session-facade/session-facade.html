Patrón Session Facade

El patrón Session Facade (Fachada de Sesión) es un patrón de diseño fundamental de la capa de negocio de Java EE que proporciona una interfaz unificada, de grano grueso (coarse-grained) y transaccional sobre múltiples objetos de dominio y servicios internos, aislando a los clientes de la complejidad interna y reduciendo el tráfico de red en aplicaciones distribuidas.

Analogía del Mundo Real: La Transferencia Bancaria Móvil

Imagina que quieres transferir dinero a un amigo desde la aplicación de tu teléfono móvil:

  • Desde la aplicación tú solo pulsas un botón: "Transferir 100 €" (una única petición de alto nivel enviada a la Session Facade).
  • Dentro del servidor central del banco, esa fachada abre una transacción blindada: verifica que tienes saldo, resta 100 € de tu cuenta, abona 100 € en la cuenta del amigo y genera el apunte contable y el justificante fiscal. Si el último paso falla, la fachada ejecuta un rollback automático deshaciendo todos los pasos previos.
  • Si no existiera la fachada, la app móvil tendría que hacer 4 llamadas por red móvil individualmente; si se corta la cobertura 4G a mitad del proceso, tu dinero se habría restado pero nunca habría llegado a tu amigo.

Propósito

Resolver los dos grandes desafíos de la arquitectura en capas y los sistemas distribuidos:

  1. Optimización de Red (Evitar el problema Chatty I/O): Sustituir múltiples llamadas remotas de grano fino por una sola llamada consolidada.
  2. Límite Transaccional Atómico (Frontera de Transacción): Demarcar el inicio y final de una transacción ACID en el servidor para que todas las operaciones internas se confirmen (commit) o cancelen (rollback) de forma indivisible.

Caso de Uso Real: Formalización de un Pedido en la Tienda de Mascotas

Contexto: En la plataforma PetShop, la adopción o compra de una mascota (formalizarPedido) requiere: 1) reservar el animal o producto en ServicioInventario, 2) cobrar el importe mediante pasarela en ServicioPagos, y 3) emitir la orden logística en ServicioEnvios.

El Problema (Sin Session Facade): Si el front-end web o móvil invoca secuencialmente cada microservicio o componente por separado, se triplica la latencia de red. Además, si falla la llamada a envíos, el cliente ya habrá sufrido el cargo bancario y el inventario quedará bloqueado sin posibilidad de reversión atómica.

La Solución (Con Session Facade): Se expone un único método FachadaSesionPedido.realizarPedido(...). La fachada asume la responsabilidad transaccional y orquesta localmente a todos los participantes en el servidor.

Implementación en Java


// 1. Servicios de Negocio de Grano Fino (Fine-Grained Services)
class ServicioInventario {
    public void reservarItem(String item) {
        System.out.println("   1️⃣ [Inventario] Stock reservado para producto/mascota: " + item);
    }
}

class ServicioPagos {
    public void cobrarCliente(double importe) {
        if (importe <= 0) {
            throw new IllegalArgumentException("Importe inválido para el cobro.");
        }
        System.out.println("   2️⃣ [Pagos] Cobro completado por importe de: " + importe + " EUR");
    }
}

class ServicioEnvios {
    public void programarEnvio(String item) {
        System.out.println("   3️⃣ [Envíos] Albarán y guía de transporte generados para: " + item);
    }
}

// 2. Session Facade: Servicio de Grano Grueso con Frontera Transaccional
class FachadaSesionPedido {
    private final ServicioInventario inventario = new ServicioInventario();
    private final ServicioPagos pagos = new ServicioPagos();
    private final ServicioEnvios envios = new ServicioEnvios();

    // En EJB clásico equivale a @Stateless; en Spring Boot equivale a @Service + @Transactional
    public boolean realizarPedido(String item, double importe) {
        System.out.println("🔒 [SessionFacade] >> INICIANDO TRANSACCIÓN ATÓMICA EN SERVIDOR <<");
        try {
            inventario.reservarItem(item);
            pagos.cobrarCliente(importe);
            envios.programarEnvio(item);

            System.out.println("✅ [SessionFacade] >> COMMIT: Pedido procesado íntegramente con éxito <<");
            return true;
        } catch (Exception e) {
            System.err.println("❌ [SessionFacade] >> ROLLBACK: Operación abortada. Motivo: " + e.getMessage());
            return false;
        }
    }
}

Diferencias Clave: Session Facade vs Facade Clásica (GoF)

Característica Facade Clásica (Gang of Four) Session Facade (Enterprise J2EE / Spring)
Capa Arquitectónica Cualquier nivel (estructural / clases locales). Exclusivamente en la Capa de Negocio / Servicios.
Propósito Principal Ocultar la complejidad de una librería o subsistema bajo una interfaz cómoda. Frontera transaccional (ACID) y reducción de latencia de red (grano grueso).
Equivalente en Spring Boot Clases adaptadoras o clientes enriquecidos. Clase anotada con @Service que contiene métodos @Transactional.

Contraejemplo: El Antipatrón "Chatty I/O" (Llamadas Conversacionales por Red)


// ANTIPATRÓN GRAVE: El cliente remoto (ej. app móvil o front-end) orquesta las llamadas por red
public class ClienteMovilSinFachada {

    public void comprar(String item, double precio) {
        // ERROR 1: 3 saltos de red por Internet (3x latencia)
        // ERROR 2: Si la conexión cae entre el paso 2 y el paso 3, el cliente paga pero no recibe envío
        // ERROR 3: No existe transacción ACID unificada que coordine los 3 microservicios
        inventarioClient.reservar(item);
        pagoClient.cobrar(precio);
        envioClient.generarGuia(item);
    }
}
Antipatrón Chatty: Múltiples llamadas remotas sin transacción global

¿Cuándo usarlo y cuándo NO usarlo?

Cuándo SÍ Usar Session Facade Cuándo NO Usarlo
Operaciones que involucran múltiples tablas, repositorios o servicios que deben ejecutarse bajo una misma transacción ACID. Lecturas atómicas simples (ej. findById) que solo consultan un dato en un repositorio sin orquestación.
Sistemas distribuidos o microservicios donde exponer operaciones de grano grueso ahorra cientos de milisegundos de latencia. Aplicaciones locales monohilo donde no existe frontera de red ni transacciones concurrentes.
