Patrón Adapter (Adaptador / Wrapper)

El patrón Adapter (Adaptador o Envoltorio/Wrapper) es un patrón estructural de diseño que permite que dos clases con interfaces incompatibles puedan colaborar estrechamente sin modificar el código fuente de ninguna de ellas. Actúa como un traductor intermedio que recibe las invocaciones del cliente bajo una interfaz estándar y las delega hacia la interfaz específica que exige la clase adaptada.

Analogía del Mundo Real: El Adaptador de Enchufe de Viaje

Imagina que viajas desde España (enchufes con dos clavijas cilíndricas) a Estados Unidos o al Reino Unido (tomas de pared con clavijas planas o triangulares):

  • No derribas la pared del hotel para cambiar el enchufe ni cortas con tijeras el cable de tu ordenador portátil.
  • Utilizas un Adaptador de viaje: se enchufa físicamente en la toma americana por un lado y ofrece una toma europea estándar por el otro.
  • Tanto la pared como tu cargador siguen funcionando según sus normas nativas sin ser modificados.

Propósito

Reutilizar clases existentes, SDKs de terceros, clientes HTTP o bibliotecas legadas cuya firma de métodos o modelos de datos no encajan con las interfaces del dominio de tu aplicación, respetando el principio de Inversión de Dependencias (DIP).

Caso de Uso Real: Integración de una Pasarela de Pagos Externa

Contexto: En la plataforma PetShop, la interfaz interna estándar para cobros es ProcesadorPago con el método void procesarCobro(String clienteId, double importe). Para procesar cobros internacionales se contrata una pasarela de pagos externa (StripeSdkApi).

El Problema (Sin Adapter): La librería StripeSdkApi viene compilada en un archivo .jar cerrado. Sus métodos son completamente distintos: stripeCharge(String customerToken, long cents, String currency). No podemos editar el código de Stripe ni queremos contaminar nuestro dominio con sus tipos específicos.

La Solución (Con Adapter): Creamos StripeAdapter. Implementa nuestra interfaz ProcesadorPago, almacena una referencia a StripeSdkApi y traduce los euros en céntimos y los identificadores al formato que Stripe exige.

Implementación en Java


// 1. Target: Interfaz estándar del dominio de PetShop
public interface ProcesadorPago {
    void procesarCobro(String clienteId, double importeEuros);
}

// 2. Adaptee: Librería de terceros (incompatible y cerrada)
public class StripeSdkApi {
    public void createStripeCharge(String customerToken, long amountInCents, String currency) {
        System.out.println("⚡ [SDK Stripe Oficial] Cargo de " + amountInCents + " céntimos (" + currency + ") para token: " + customerToken);
    }
}

// 3. Adapter: Traduce entre la interfaz del dominio y la librería externa
public class StripeAdapter implements ProcesadorPago {
    private final StripeSdkApi stripeApi;

    public StripeAdapter(StripeSdkApi stripeApi) {
        this.stripeApi = stripeApi;
    }

    @Override
    public void procesarCobro(String clienteId, double importeEuros) {
        // Traducción de datos: euros → céntimos enteros requeridos por Stripe
        long centimos = Math.round(importeEuros * 100);
        String tokenStripe = "tok_cust_" + clienteId.toLowerCase();

        stripeApi.createStripeCharge(tokenStripe, centimos, "EUR");
    }
}
Implementación canónica de Object Adapter en Java

Ejemplo de Uso y Trazas de Consola


public class Main {
    public static void main(String[] args) {
        // Instanciamos el SDK externo y lo envolvemos con el Adaptador
        StripeSdkApi stripeSdk = new StripeSdkApi();
        ProcesadorPago procesador = new StripeAdapter(stripeSdk);

        // El cliente invoca el método estándar de su dominio
        System.out.println("--- Procesando cobro de consulta veterinaria ---");
        procesador.procesarCobro("CLI-8841", 65.50);
    }
}

Object Adapter vs Class Adapter

  • Object Adapter (Recomendado): Utiliza composición (el adaptador tiene una instancia de la clase adaptada). Es el estándar en Java porque respeta la sustitución y no requiere herencia múltiple.
  • Class Adapter: Utiliza herencia (el adaptador hereda de la clase adaptada e implementa la interfaz objetivo). En Java solo es posible si el adaptado es una interfaz o si no se hereda de ninguna otra clase, pero acopla fuertemente el adaptador a la implementación concreta.

Ejemplos del Patrón Adapter en el JDK y en Spring Framework

  • java.util.Arrays.asList(T... a): Adapta un array tradicional de Java a la interfaz List<T> de colecciones.
  • java.io.InputStreamReader(InputStream in): Adapta un stream de bytes binarios (InputStream) para que pueda leerse como caracteres de texto a través de la interfaz Reader.
  • HandlerAdapter en Spring MVC: Adapta distintos tipos de controladores (anotados con @Controller, HttpRequestHandler, etc.) para que el DispatcherServlet central los invoque de forma uniforme.

Contraejemplo: Acoplamiento Directo al SDK de Terceros en Toda la Aplicación


// ANTIPATRÓN: Clases de negocio acopladas a la API propietaria de Stripe
public class OrderServiceMalDisenado {

    public void checkout(StripeSdkApi stripe, String token, long centimos) {
        // ERROR GRAVE: Si mañana la empresa decide cambiar Stripe por PayPal o Redsys,
        // habrá que reescribir todos los métodos de todas las clases del dominio.
        stripe.createStripeCharge(token, centimos, "EUR");
    }
}
Antipatrón: Fuga de tipos de terceros dentro de la lógica del dominio

¿Cuándo usarlo y cuándo NO usarlo?

Cuándo SÍ Usar Adapter Cuándo NO Usarlo
Integración de bibliotecas de terceros, SDKs o APIs externas cerradas cuyas firmas no coinciden con las de tu arquitectura. Cuando seas el autor y propietario de ambas clases y puedas refactorizarlas directamente para que coincidan sin intermediarios.
Para migrar sistemas legados gradualmente manteniendo compatibilidad con código nuevo. Cuando la diferencia entre interfaces sea tan grande que el adaptador requiera reinventar la lógica de negocio completa (en tal caso se requiere un rediseño de dominio).
