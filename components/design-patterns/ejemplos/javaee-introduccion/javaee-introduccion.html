Patrones Java EE / Enterprise: Cuándo y Para Qué Usarlos

Los Patrones de Diseño Java EE (Core J2EE Patterns) constituyen el estándar de arquitectura para aplicaciones empresariales multinivel (n-tier architectures). Formalizados a principios de los años 2000 por Deepak Alur, John Crupi y Dan Malks en el catálogo oficial de Sun Microsystems Press, estos patrones no se centran en pequeños detalles de código o algoritmos locales (como los patrones GoF), sino en resolver los grandes retos estructurales de los sistemas corporativos distribuidos: latencia de red, límites transaccionales ACID, concurrencia masiva, seguridad perimetral y desacoplamiento estricto entre capas.

Analogía del Mundo Real: La Organización de un Gran Aeropuerto Internacional

Imagina la operativa logística de un aeropuerto internacional:

  • Capa de Presentación / Entrada (Control de Fronteras): Cuando los pasajeros llegan a la terminal, no entran directamente a la pista de aterrizaje: pasan por un único arco de seguridad central (Front Controller) y varios arcos de detección de equipaje y visados (Intercepting Filter). Si un pasajero tiene un vuelo local directo, se le despacha a la puerta de embarque sin trámites pesados (Dispatcher View).
  • Capa de Negocio / Tráfico Aéreo (Torre de Control y Operaciones): Una vez autorizada la entrada, la torre de control coordina los despegues, la asignación de combustible y las pistas bajo un estricto protocolo de seguridad indivisible donde todo se cumple o se aborta el despegue (Session Facade y Application Service). Para no colapsar la radio enviando datos de cada maleta uno a uno, transmiten un manifiesto consolidado con todos los pasajeros del vuelo (Transfer Object / DTO).
  • Capa de Integración / Hangares y Radar (Acceso a Infraestructura): Los mecánicos se conectan con almacenes de repuestos externos y proveedores de combustible que hablan dialectos heterogéneos mediante adaptadores homologados (Web Service Broker y Data Access Object / DAO).

¿Para Qué Sirven los Patrones Java EE en Arquitecturas Empresariales?

  1. Eliminación del Tráfico de Red Conversacional (Problema Chatty I/O): En sistemas cliente-servidor o microservicios, hacer 10 llamadas de red pequeñas para consultar atributos individuales genera una latencia inaceptable. Patrones como Transfer Object (DTO) y Session Facade consolidan la comunicación en una única llamada de grano grueso (coarse-grained).
  2. Fronteras Transaccionales Atómicas (ACID): Definen con exactitud quirúrgica dónde inicia y dónde finaliza una transacción en el servidor (commit o rollback), garantizando que si falla un paso intermedio (ej. cobro con tarjeta o reserva de stock) la base de datos no quede corrupta.
  3. Desacoplamiento Estricto entre Presentación, Negocio y Persistencia: Impiden que código de presentación (HTML, JSON o controladores web) contenga sentencias SQL directas, y evitan que la capa de persistencia conozca detalles de la interfaz de usuario.
  4. Aislamiento de Sistemas Heterogéneos y Heredados (Legacy): Permiten modernizar o sustituir bases de datos o mainframes sin obligar a reescribir la capa de negocio ni las aplicaciones móviles o clientes web.

Las 3 Capas Arquitectónicas de Java EE

1. Capa de Presentación (Presentation)

Propósito: Gestionar el ciclo de vida de las peticiones HTTP entrantes, aplicar seguridad y auditoría perimetral, coordinar la navegación y generar la respuesta visual o estructurada.

Intercepting Filter, Front Controller, Context Object, Application Controller, View Helper, Composite View, Dispatcher View, Service to Worker.
2. Capa de Negocio (Business Tier)

Propósito: Orquestar casos de uso, ejecutar reglas y cálculos de dominio, gestionar fronteras transaccionales y reducir saltos de red mediante operaciones consolidadas.

Business Delegate, Service Locator, Session Facade, Application Service, Business Object, Composite Entity, Transfer Object (DTO), Transfer Object Assembler, Value List Handler.
3. Capa de Integración (Integration Tier)

Propósito: Conectar la aplicación de forma agnóstica con almacenes de datos persistentes (SQL/NoSQL) y orquestar comunicaciones con sistemas externos heterogéneos o legados.

Data Access Object (DAO), Web Service Broker, MVC.

Matriz de Decisión: ¿Cuándo Usar y Cuándo NO Usar Cada Patrón Java EE?

Patrón Enterprise Capa ¿Para qué sirve? (Problema que resuelve) Cuándo SÍ usarlo Cuándo NO usarlo (Alternativa Moderna)
Intercepting Filter Presentación Aplica filtros previos o posteriores a la petición HTTP de forma encadenada y declarativa. Validación de tokens JWT/OAuth2, compresión GZIP, cabeceras CORS o registro de logs de auditoría. No usar para validar reglas de negocio profundas de entidades; eso pertenece a los servicios o validadores de dominio.
Front Controller Presentación Punto centralizado de entrada única que gestiona y enruta todas las peticiones del sistema. En cualquier framework web MVC para aplicar seguridad, resolución de vistas y locale internacional unificado. No reimplementar a mano en Spring Boot; el framework ya proporciona DispatcherServlet de serie.
Context Object Presentación Encapsula información contextual de la petición (sesión, cabeceras, usuario) en un objeto independiente del protocolo. Para compartir el contexto de seguridad o trazabilidad (como SecurityContextHolder o MDC de Slf4j) sin pasar HttpServletRequest por toda la aplicación. No usar para almacenar datos transitorios de negocio que deban pasarse como argumentos directos en métodos de servicio.
Application Controller Presentación Centraliza y desacopla las reglas de navegación y la selección de comandos y vistas complejas. Asistentes paso a paso (Wizards) o flujos conversacionales dinámicos guiados por el estado del usuario. En APIs REST sin estado (Stateless) donde cada endpoint responde de forma determinista mediante su URI.
View Helper Presentación Aísla a las vistas del código Java complejo encapsulando formateo, paginación o adaptación de datos para la pantalla. Dar formato a monedas, fechas territoriales, traducciones o cálculos auxiliares de renderizado HTML. No usar para invocar transacciones ni realizar actualizaciones en base de datos desde la vista.
Composite View Presentación Construye pantallas complejas a partir de fragmentos visuales modulares e independientes (cabecera, menú, pie). Plantillas maestras en motores como Thymeleaf (th:replace), JSP Tiles o componentes de SPAs (React/Angular). En vistas extremadamente simples de una sola página sin componentes reutilizables en otras pantallas.
Dispatcher View Presentación Enruta y despacha inmediatamente la vista destino cuando la petición no requiere lógica de negocio previa pesada. Pantallas informativas, páginas estáticas de ayuda, login o navegación basada en roles ligeros. En operaciones transaccionales donde se requiera persistir datos o validar stock antes de la vista (usar Service to Worker).
Service to Worker Presentación El controlador ejecuta primero todo el procesamiento pesado de negocio y solo al final despacha a una vista pasiva. Confirmación de pedidos, cobros bancarios, altas transaccionales en bases de datos o formularios con validaciones. En navegación estática directa donde no existen consultas a bases de datos ni transacciones previas.
Business Delegate Negocio Oculta a los clientes de presentación la complejidad de localización y comunicación remota con los servicios de negocio. Clientes declarativos para microservicios externos o clientes REST que aíslan excepciones y serialización técnica. En aplicaciones monolíticas donde controladores y servicios residen en la misma memoria JVM y se inyectan con @Autowired.
Service Locator Negocio Centraliza la búsqueda y obtención de recursos y servicios distribuidos (JNDI, registros de nombres). Sistemas legados que debían resolver referencias remotas mediante árboles JNDI en servidores de aplicaciones clásicos. Antipatrón en proyectos modernos: Sustituido al 100% por la Inyección de Dependencias por Constructor de Spring Boot (IoC).
Session Facade Negocio Proporciona una interfaz unificada de grano grueso que demarca la frontera transaccional ACID de la operación. Operaciones que coordinan múltiples repositorios o entidades que deben confirmarse o revertirse juntas. En consultas simples de lectura directa (ej. findById) que solo leen un registro sin coordinación.
Application Service Negocio Orquesta el flujo de ejecución completo de un caso de uso manteniéndose agnóstico del protocolo de transporte. En el núcleo de la capa de servicio de cualquier aplicación empresarial con múltiples puntos de entrada (REST, Batch, Kafka). No convertirlo en un servicio anémico absorbiendo toda la lógica de validación que le corresponde a las entidades de dominio.
Business Object Negocio Encapsula los datos y el comportamiento de las entidades centrales del dominio del negocio. Modelado rico de negocio (Rich Domain Model) donde las entidades validan su propia coherencia interna. No usar como simples sacos de datos vacíos (Anemic Domain Model) dejando todo el comportamiento en los servicios.
Composite Entity Negocio Representa un grafo de entidades de negocio persistentes dependientes gobernadas por una raíz de agregado. Concepto de Agregado en DDD (ej. un Pedido que gobierna a sus LineasPedido de forma indivisible). No crear agregados gigantescos con decenas de relaciones que sobrecarguen la memoria y provoquen bloqueos en base de datos.
Transfer Object (DTO) Negocio Portador de datos plano serializable que transfiere información entre capas evitando exponer entidades de base de datos. Cualquier API REST pública, respuestas JSON/XML, desacoplamiento de contraseñas o campos internos de la base de datos. En llamadas estrictamente locales entre métodos de la misma clase donde no se requiere transformar ni proteger datos.
Transfer Object Assembler Negocio Agrega y compone múltiples objetos de negocio independientes para ensamblar un DTO compuesto de grano grueso. Construir vistas de resumen (ej. un DashboardClienteDTO que agrupa saldo, últimas 5 compras y citas veterinarias). Si el DTO es plano y procede de una única entidad directa; en ese caso basta un mapeador simple (como MapStruct).
Value List Handler Negocio Controla la paginación, navegación hacia adelante/atrás y caché de grandes listados de datos. Tablas corporativas con miles o millones de registros donde la base de datos debe entregar páginas acotadas. Sustituido en Spring Boot: El módulo Spring Data JPA lo resuelve automáticamente con Pageable y Page<T>.
Data Access Object (DAO) Integración Aísla completamente a la capa de negocio del dialecto SQL y de la tecnología concreta de persistencia. Siempre que la aplicación necesite consultar o almacenar información en bases de datos relacionales o NoSQL. No mezclar llamadas a múltiples tablas o lógica de control de flujo transaccional dentro del propio DAO (eso es rol del servicio).
Web Service Broker Integración Intermediario público que expone, traduce y adapta sistemas internos heterogéneos o legados hacia estándares web. Exponer mainframes COBOL, sistemas ERP o protocolos propietarios hacia clientes móviles o SPAs mediante REST/JSON. En comunicaciones directas entre dos microservicios que ya comparten el mismo contrato REST o gRPC sin disparidad de formatos.

Evolución: De J2EE Clásico (EJB / JSP) a Spring Boot y Clean Architecture

Muchos de los patrones Java EE originales nacieron para mitigar la extrema complejidad de la especificación EJB 2.x y los servidores de aplicaciones pesados (como WebLogic, WebSphere o JBoss). En el desarrollo moderno con Spring Boot 3 y Java 17/21+, estos patrones se han simplificado y formalizado en la arquitectura estándar del ecosistema:

Patrón Clásico Java EE Implementación Tradicional (Año 2002) Equivalente Estándar en Spring Boot Moderno
Front Controller Un HttpServlet manual centralizado con un enorme bloque service(). El DispatcherServlet nativo de Spring MVC que enruta las peticiones de forma declarativa.
Intercepting Filter Filtros javax.servlet.Filter configurados en el fichero XML web.xml. Filtros de Spring Security (SecurityFilterChain) o OncePerRequestFilter.
Session Facade EJB de sesión sin estado (Stateless Session Bean) desplegado en un servidor de aplicaciones. Clase anotada con @Service y métodos con @Transactional en Spring Boot.
Data Access Object (DAO) Clases JDBC manuales con Connection, PreparedStatement y ResultSet a mano. Interfaces de Spring Data JPA extendiendo de JpaRepository<Entidad, ID>.
Transfer Object (DTO) Clases Java serializables con 40 líneas de getters y setters manuales. Records inmutables de Java (public record PetDTO(...) {}) o clases con Lombok @Data.
Service Locator Búsquedas reflexivas complejas en el árbol JNDI (InitialContext.lookup(...)). Inyección de Dependencias por Constructor: @RequiredArgsConstructor de Lombok y contenedor IoC de Spring.
Business Delegate Clase wrapper manual para ocultar las interfaces remotas RMI/IIOP de los EJBs. Clientes declarativos como Spring Cloud OpenFeign o RestClient / WebClient.
Value List Handler Objetos de sesión con cursores manuales para paginar registros en memoria. Parámetro Pageable pageable y retorno Page<T> directo en repositorios Spring Data.

¿Cuándo NO Usar Patrones Java EE? El Error del Antipatrón Monolítico Desordenado

El error conceptual más grave en el desarrollo empresarial es saltarse la separación de capas introducida por los patrones Java EE, acoplando controladores con SQL directo:


// CONTRAEJEMPLO (ANTIPATRÓN GRAVE): Controlador web que mezcla presentación, negocio y persistencia directa
@RestController
@RequestMapping("/api/pets")
public class BrokenPetController {

    @PostMapping
    public void registrarMascota(@RequestBody Map<String, Object> payload) throws Exception {
        // ERROR CRÍTICO 1: No usa DTO (expone el mapa crudo y sin tipar)
        // ERROR CRÍTICO 2: Lógica de negocio mezclada en la capa web
        // ERROR CRÍTICO 3: Conexión JDBC directa en el controlador sin transacción ni DAO/Repository
        Connection conn = DriverManager.getConnection("jdbc:postgresql://localhost:5432/petshop");
        Statement stmt = conn.createStatement();
        stmt.executeUpdate("INSERT INTO pets (name) VALUES ('" + payload.get("name") + "')");
    }
}
Antipatrón Monolítico Desordenado: Destruye la seguridad, testabilidad y arquitectura multinivel

La Solución con Patrones Enterprise:

  1. El Front Controller recibe la petición y la valida con un Transfer Object (PetDTO).
  2. El Application Service / Session Facade (@Service @Transactional) abre la transacción y ejecuta las reglas de negocio.
  3. El DAO / Repository (PetRepository) ejecuta la persistencia de forma desacoplada y segura frente a inyección SQL.
