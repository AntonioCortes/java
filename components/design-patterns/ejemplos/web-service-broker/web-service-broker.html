Patrón Web Service Broker

El patrón Web Service Broker (Intermediario de Servicios Web) es un patrón de integración de Java EE que actúa como una puerta de enlace pública estándar (REST/JSON o SOAP/XML) para exponer y coordinar uno o varios sistemas internos heterogéneos (como microservicios internos o sistemas bancarios antiguos legacy).

Analogía del Mundo Real

Piensa en un Intérprete Diplomático en la ONU o la ventanilla única de un Ayuntamiento. Un ciudadano extranjero llega a la ventanilla hablando en inglés (una petición estándar HTTP/JSON desde una App móvil). El funcionario de la ventanilla (Web Service Broker) traduce esa solicitud al formato interno antiguo de cada departamento del edificio, coordina las firmas necesarias y le devuelve al ciudadano un certificado limpio en su propio idioma.

Propósito

Permitir que aplicaciones externas modernas (Apps móviles iOS/Android, SPAs en Angular/React o empresas asociadas) se comuniquen mediante protocolos web estándar (HTTP + JSON) con sistemas internos que usan protocolos propietarios, tramas de texto fijo o arquitecturas heterogéneas.

Caso de Uso Real: Exposición de un Mainframe Bancario COBOL y un Microservicio como API REST

Contexto: La nueva App móvil de un banco necesita hacer transferencias enviando un JSON limpio. Sin embargo, dentro del banco primero hay que validar el riesgo en un microservicio moderno (MicroservicioAntifraude) y luego ejecutar el movimiento contable en un Mainframe central de los años 80 (SistemaCobolAntiguo) que solo entiende tramas de texto fijo separadas por tuberías (|).

El Problema (Sin Web Service Broker): Una App móvil no puede conectarse directamente por sockets propietarios a un Mainframe COBOL, y además sería gravísimo exponer el Mainframe directamente a Internet.

La Solución (Con Web Service Broker): Creamos BrokerServiciosBancarios. Expone al exterior un endpoint REST/JSON limpio, valida la operación contra MicroservicioAntifraude, traduce los datos a la trama fija que exige SistemaCobolAntiguo y transforma el código de respuesta en un JSON estándar.

Implementación en Java


// 1. Sistema Interno A: Microservicio moderno de control de fraude
class MicroservicioAntifraude {
    public boolean isTransactionSafe(double amount) {
        System.out.println("   🛡️ [MicroservicioAntifraude] Analizando riesgo para importe: " + amount + " EUR -> APROBADO");
        return amount <= 10000.0;
    }
}

// 2. Sistema Interno B: Mainframe Bancario Legacy (solo entiende tramas planas de texto)
class SistemaCobolAntiguo {
    public String ejecutarTramaFija(String cobolFrame) {
        System.out.println("   🖥️ [SistemaCobolAntiguo] Procesando trama propietaria: [" + cobolFrame + "]");
        return "COD_00_OK_AUTH_8841";
    }
}

// 3. Web Service Broker: Expone interfaz REST/JSON estándar al exterior y coordina por dentro
class BrokerServiciosBancarios {
    private MicroservicioAntifraude fraudService = new MicroservicioAntifraude();
    private SistemaCobolAntiguo mainframe = new SistemaCobolAntiguo();

    // En Spring Boot sería un @PostMapping(produces = "application/json")
    public String transferMoneyRestEndpoint(String originAccount, String destAccount, double amount) {
        System.out.println("🌐 [WebServiceBroker] Recibida petición HTTP POST /api/transfer en formato JSON.");

        // Paso 1: Verificar en el microservicio de fraude
        if (!fraudService.isTransactionSafe(amount)) {
            return "{ \"status\": \"REJECTED\", \"reason\": \"Importe supera límite antifraude\" }";
        }

        // Paso 2: Traducir los datos al protocolo antiguo del Mainframe COBOL
        String cobolFrame = "TX|" + originAccount + "|" + destAccount + "|" + amount;
        String mainframeCode = mainframe.ejecutarTramaFija(cobolFrame);

        // Paso 3: Traducir la respuesta cruda del Mainframe a un JSON estándar para el móvil
        return "{ \"status\": \"SUCCESS\", \"mainframeRef\": \"" + mainframeCode + "\", \"amount\": " + amount + " }";
    }
}

Análisis Paso a Paso para Principiantes

  • 1. Combina Facade + Adapter en la frontera de red:

    Si te fijas bien, el Web Service Broker hace dos cosas a la vez: actúa como una Fachada (coordina el microservicio de fraude y el mainframe) y como un Adaptador (traduce de JSON a trama COBOL y viceversa).

  • 2. Evolución sin romper las Apps móviles:

    Cuando el banco jubile por fin el Mainframe COBOL y lo sustituya por un microservicio moderno en Java, solo cambiará el interior de BrokerServiciosBancarios. Los millones de usuarios con la App instalada en su móvil no tendrán ni que actualizar la aplicación.

Ejemplo de Uso


public class Main {
    public static void main(String[] args) {
        BrokerServiciosBancarios broker = new BrokerServiciosBancarios();

        System.out.println("--- App Móvil solicita transferencia de 250.00 EUR ---");
        String jsonResponse = broker.transferMoneyRestEndpoint("ES11-0001", "ES99-0002", 250.00);

        System.out.println("\n📱 [App Móvil] Respuesta JSON estándar recibida:");
        System.out.println("   " + jsonResponse);
    }
}

¿Cuándo usarlo y cuándo NO usarlo?

  • Cuándo usarlo: Siempre que necesites exponer capacidades de sistemas internos heterogéneos, ERPs o sistemas legados hacia clientes externos mediante una API web estándar y segura (patrón base de los API Gateways e integradores empresariales).
  • Cuándo evitarlo: Para comunicación puramente interna entre dos clases que viven dentro del mismo monolito.
