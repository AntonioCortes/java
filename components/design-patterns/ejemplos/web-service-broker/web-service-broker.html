Patrón Web Service Broker

El patrón Web Service Broker (Intermediario de Servicios Web) es un patrón arquitectónico de integración de Java EE que actúa como una puerta de enlace pública normalizada (REST/JSON o SOAP/XML) para exponer, orquestar y adaptar uno o varios sistemas internos heterogéneos (microservicios internos, bases de datos o sistemas centrales legados como mainframes COBOL).

Analogía del Mundo Real: El Intérprete Diplomático

Imagina un intérprete diplomático en una cumbre internacional:

  • Un embajador extranjero solicita información oficial hablando en inglés (una petición estándar HTTP/JSON emitida desde una aplicación móvil o SPA).
  • El intérprete (Web Service Broker) recibe la pregunta en inglés, consulta en dialectos locales internos a tres ministerios distintos (sistemas heterogéneos y legados), traduce las respuestas, valida la confidencialidad y le entrega al embajador un documento oficial perfectamente traducido y formateado en inglés estándar.
  • El embajador nunca necesita aprender dialectos antiguos ni entrar físicamente a los archivos confidenciales de cada ministerio.

Propósito

Desacoplar la tecnología y protocolos de los clientes externos de la tecnología interna corporativa, traduciendo formatos heterogéneos, unificando políticas de seguridad y permitiendo evolucionar o sustituir sistemas heredados sin romper las aplicaciones clientes.

Caso de Uso Real: Exposición de un Mainframe y Microservicios como API REST

Contexto: En la plataforma bancaria de PetShop, los usuarios pueden solicitar un seguro de salud veterinario para sus mascotas desde la app móvil enviando un JSON a /api/seguros/contratar. Sin embargo, internamente el banco debe: 1) evaluar el scoring en un microservicio de riesgo moderno, y 2) formalizar la póliza contable en un Mainframe central de los años 80 que solo acepta tramas binarias o texto plano de longitud fija delimitado por |.

El Problema (Sin Web Service Broker): Una app móvil no puede abrir conexiones directas por socket propietario hacia un mainframe bancario; violaría las directrices de seguridad de red y cualquier cambio en el mainframe obligaría a actualizar millones de aplicaciones móviles instaladas.

La Solución (Con Web Service Broker): Se implementa BrokerServiciosBancarios. Publica un endpoint REST limpio, valida el riesgo en el microservicio interno, traduce el payload JSON a la trama fija del Mainframe y devuelve una respuesta HTTP normalizada.

Implementación en Java


// 1. Sistema Interno A: Microservicio moderno de análisis de riesgo
class MicroservicioAntifraude {
    public boolean esOperacionSegura(double importe) {
        System.out.println("   🛡️ [MicroservicioAntifraude] Analizando riesgo de póliza para importe: " + importe + " EUR → APROBADO");
        return importe <= 5000.0;
    }
}

// 2. Sistema Interno B: Mainframe bancario legado (solo entiende tramas de longitud fija)
class SistemaCobolAntiguo {
    public String procesarTramaFija(String tramaPlana) {
        System.out.println("   🖥️ [SistemaCobolAntiguo] Procesando trama propietaria en Mainframe: [" + tramaPlana + "]");
        return "RET_CODE_00_OK_POLIZA_9941";
    }
}

// 3. Web Service Broker: Expone API REST pública y orquesta internamente
class BrokerServiciosBancarios {
    private final MicroservicioAntifraude antifraude = new MicroservicioAntifraude();
    private final SistemaCobolAntiguo mainframe = new SistemaCobolAntiguo();

    // En Spring Boot equivale a @PostMapping(value = "/api/seguros", produces = MediaType.APPLICATION_JSON_VALUE)
    public String contratarSeguroRestEndpoint(String dniCliente, String idMascota, double cuotaAnual) {
        System.out.println("🌐 [WebServiceBroker] Recibida petición HTTP POST /api/seguros (JSON)");

        // Paso 1: Validación contra microservicio interno
        if (!antifraude.esOperacionSegura(cuotaAnual)) {
            return "{ \"status\": \"RECHAZADO\", \"mensaje\": \"Importe excede los límites automáticos de riesgo\" }";
        }

        // Paso 2: Traducción bidireccional (JSON → Trama COBOL propietaria)
        String tramaCobol = "POLIZA|" + dniCliente + "|" + idMascota + "|" + cuotaAnual;
        String respuestaMainframe = mainframe.procesarTramaFija(tramaCobol);

        // Paso 3: Retorno normalizado en JSON estándar para el cliente móvil
        return "{ \"status\": \"CONFIRMADO\", \"polizaId\": \"" + respuestaMainframe + "\", \"cuota\": " + cuotaAnual + " }";
    }
}

public class Main {
    public static void main(String[] args) {
        BrokerServiciosBancarios broker = new BrokerServiciosBancarios();

    }
}

Evolución Arquitectónica: Broker vs API Gateway vs BFF

Concepto Arquitectónico Ámbito y Propósito Tecnologías Típicas
Web Service Broker (Java EE) Intermediario de integración que adapta y traduce protocolos heterogéneos o sistemas legados hacia servicios web estándar. Apache Camel, MuleSoft, Servlets/Spring REST con mappers de tramas.
API Gateway Punto de entrada perimetral que gestiona enrutamiento dinámico, limitación de tasa (rate limiting), autenticación OAuth2 y métricas de cientos de microservicios. Spring Cloud Gateway, Kong, Apigee, AWS API Gateway.
Backend For Frontend (BFF) Variante donde existe un broker específico optimizado para cada tipo de interfaz (uno para iOS/Android con payloads reducidos y otro para Web/Desktop enriquecido). Node.js/Express, Spring Boot WebFlux, GraphQL Gateway.

¿Cuándo usarlo y cuándo NO usarlo?

Cuándo SÍ Usar Web Service Broker Cuándo NO Usarlo
Integración de sistemas heredados (ERP, COBOL, AS400, SOAP) con aplicaciones modernas móviles o web (REST, JSON). Comunicación directa entre microservicios de última generación que ya comparten estándares REST o gRPC sin disparidad de protocolos.
Cuando se requiere una capa de traducción estable para poder sustituir un sistema antiguo sin impacto en los clientes. En monolitos simples donde todas las clases residen en la misma JVM y no existen fronteras de red.
