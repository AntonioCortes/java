Patrón Service to Worker

El patrón Service to Worker (Servicio al Trabajador) es un patrón arquitectónico de la capa de presentación de Java EE en el que un controlador de acción (el Worker Controller) recibe la petición entrante, coordina e invoca los servicios de negocio pesados previamente, construye un modelo de datos estructurado y finalmente delega el resultado en una vista pasiva (Passive View) cuya única función es renderizar el HTML.

Analogía del Mundo Real: El Chef Ejecutivo y el Camarero

Imagina la cocina de un restaurante de alta gama:

  • El Chef Ejecutivo (Worker Controller) recibe la comanda de la mesa. Antes de sacar el plato, pide la carne a la parrilla, exige la guarnición al repostero, prepara la salsa, emplata cuidando la presentación y verifica que todo esté perfecto.
  • El Camarero (Vista Pasiva) únicamente recoge la bandeja ya emplatada y la deposita sobre la mesa del comensal. El camarero no cocina, no asa ni sazona: es un transmisor pasivo que garantiza que el comensal disfrute del plato terminado sin esperas caóticas.

Propósito

Garantizar una separación estricta de responsabilidades impidiendo que las vistas (plantillas JSP, Thymeleaf o HTML) contengan código de acceso a datos o lógica de negocio, asegurando que todo procesamiento crítico ocurra antes de iniciar la generación de la respuesta visual.

Caso de Uso Real: Adopción y Check-Out de Mascota en PetShop

Contexto: Cuando un cliente pulsa "Confirmar Adopción" en la plataforma PetShop, el sistema debe: 1) validar que la mascota sigue disponible en PetService, 2) tramitar la fianza en PaymentService, y 3) registrar el contrato legal en ContractService antes de pintar la pantalla de confirmación.

El Problema (Sin Service to Worker): Si se despacha la vista primero y desde el propio archivo HTML/JSP se intenta invocar al servicio de base de datos o pasarela de pagos, si el cobro falla cuando ya se ha transmitido la mitad del HTML, el usuario verá una página rota e inconsistente y el servidor no podrá emitir una cabecera de error HTTP limpia.

La Solución (Con Service to Worker): El controlador AdopcionWorkerController ejecuta todas las operaciones de negocio de forma previa y atómica. Si todo es exitoso, inyecta el recibo en el Model y despacha a la vista pasiva VistaReciboAdopcion.

Implementación en Java


// 1. Servicios de Negocio (Capa de Negocio)
class ServicioInventarioMascotas {
    public boolean reservarMascota(String idMascota) {
        System.out.println("🐾 [Inventario] Reservando mascota ID '" + idMascota + "' para adopción.");
        return true;
    }
}

class ServicioPagos {
    public String procesarFianza(double importe) {
        System.out.println("💳 [PasarelaPagos] Cargo de fianza procesado: " + importe + " EUR.");
        return "RECIBO-PET-77189";
    }
}

// 2. Vista Pasiva: Solo renderiza datos entregados listos en el modelo
class VistaReciboAdopcion {
    public void render(String idMascota, double total, String codigoRecibo) {
        System.out.println("🖥️ [VistaRecibo - HTML Generado]");
        System.out.println("   Mascota Adoptada : " + idMascota);
        System.out.println("   Fianza Abonada   : " + total + " EUR");
        System.out.println("   Localizador      : " + codigoRecibo);
    }
}

// 3. Worker Controller: Orquestación previa completa antes de renderizar
class AdopcionWorkerController {
    private final ServicioInventarioMascotas inventario = new ServicioInventarioMascotas();
    private final ServicioPagos pagos = new ServicioPagos();
    private final VistaReciboAdopcion vista = new VistaReciboAdopcion();

    // En Spring MVC equivale a un método @PostMapping que puebla el Model y devuelve la vista
    public void procesarAdopcion(String idMascota, double fianza) {
        System.out.println(">> [AdopcionWorkerController] Procesando solicitud pesada de adopción...");

        // Fase 1: Coordinar servicios de negocio antes de la vista
        boolean disponible = inventario.reservarMascota(idMascota);
        if (disponible) {
            String reciboId = pagos.procesarFianza(fianza);

            // Fase 2: Despachar a la vista pasiva con el modelo completo
            vista.render(idMascota, fianza, reciboId);
        }
    }
}

}

Diferencias Clave: Service to Worker vs Dispatcher View

Criterio Arquitectónico Service to Worker Dispatcher View
Lógica Previa a la Vista Intensa y transaccional: orquesta múltiples servicios de negocio, repositorios y pagos. Mínima o nula: solo validaciones ligeras de rol, sesión o enrutamiento estático.
Rol de la Vista Vista Pasiva (Passive View): solo pinta el modelo entregado por el controlador. Vista Activa con View Helper: la vista puede pedir datos complementarios de presentación bajo demanda.
Equivalente Spring MVC Métodos @PostMapping o @GetMapping con consultas cruzadas y servicios. Controladores estáticos o métodos que devuelven directamente un nombre de vista sin llamar a la base de datos.

¿Cuándo usarlo y cuándo NO usarlo?

Cuándo SÍ Usar Service to Worker Cuándo NO Usarlo
En formularios de registro, compras, transacciones financieras o cualquier caso de uso donde el resultado dependa de procesamientos previos en la capa de negocio. En navegación estática simple (pantalla de ayuda, login, páginas de inicio sin datos) donde Dispatcher View es mucho más simple y rápido.
Cuando se requiera garantizar que las vistas sean pasivas y desacopladas de las capas inferiores del sistema. En APIs REST puras donde no existen vistas HTML ni renderizado en servidor (allí se utiliza el controlador REST directo delegando en el Application Service).
