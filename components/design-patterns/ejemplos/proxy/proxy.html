Patrón Proxy (Apoderado / Sustituto)

El patrón Proxy (Sustituto o Apoderado) es un patrón estructural de diseño que proporciona un objeto representante que controla e intercepta el acceso a otro objeto real. Al implementar exactamente la misma interfaz que el objeto real, el Proxy actúa de forma transparente para el cliente, pudiendo ejecutar acciones antes o después de la llamada (como carga perezosa, control de seguridad, caché, telemetría o demolición/apertura de transacciones).

Analogía del Mundo Real: La Tarjeta de Débito Bancaria

Piensa en una tarjeta de débito bancaria frente a un fajo de billetes en efectivo:

  • La tarjeta física es un Proxy del dinero real guardado en la cámara acorazada del banco central (el Objeto Real).
  • Para el comercio, pagar con tarjeta o pagar en efectivo cumple el mismo contrato ("pagar"), pero la tarjeta intercepta la operación: comprueba el código PIN de seguridad, verifica que tu cuenta tiene saldo suficiente y solo entonces autoriza la transferencia.
  • Además, evita que tengas que cargar físicamente con 5.000 € en billetes por la calle a menos que realmente los vayas a gastar (Virtual Proxy / Carga perezosa).

Propósito y Principales Variantes

Actuar como intermediario transparente para controlar el ciclo de vida, la seguridad o el rendimiento del objeto subyacente:

  • Virtual Proxy (Lazy Loading): Retrasa la creación de un objeto pesado (lectura de disco, descarga de red) hasta el milisegundo exacto en que se solicita su uso.
  • Protection Proxy (Seguridad): Verifica credenciales o roles de usuario antes de permitir la ejecución de métodos críticos.
  • Caching Proxy (Caché): Guarda en memoria los resultados de operaciones costosas para no repetirlas si los parámetros no cambian.
  • Remote Proxy: Representa un objeto que reside en otra máquina o proceso (RMI, gRPC).

Caso de Uso Real: Carga Diferida (Lazy Loading) de Imágenes de Mascotas

Contexto: En el catálogo de PetShop se muestran 500 fotografías en resolución 4K (ImagenReal). Descargar cada fotografía consume 15 MB de ancho de banda y 200 milisegundos de CPU.

El Problema (Sin Proxy): Si la pantalla inicial carga los 500 objetos ImagenReal en memoria de golpe, la aplicación colapsará por consumo de RAM y el usuario esperará 30 segundos de pantalla congelada.

La Solución (Con Virtual Proxy): La aplicación lista 500 objetos ImagenProxy ultraligeros. Solo cuando el usuario hace scroll y la imagen entra en el viewport llamando a mostrar(), el proxy descarga e inicializa la ImagenReal.

Implementación en Java


// 1. Interfaz común (Subject)
interface Imagen {
    void mostrar();
}

// 2. Objeto Real (Real Subject): Muy costoso de instanciar
class ImagenReal implements Imagen {
    private final String nombreArchivo;

    public ImagenReal(String nombreArchivo) {
        this.nombreArchivo = nombreArchivo;
        cargarDesdeDisco(nombreArchivo);
    }

    private void cargarDesdeDisco(String archivo) {
        System.out.println(">> [DISCO I/O] Leyendo fichero binario pesado de 15MB: " + archivo + "...");
    }

    @Override
    public void mostrar() {
        System.out.println("🖼️ Mostrando en pantalla la imagen: " + nombreArchivo);
    }
}

// 3. Proxy Virtual y de Caché
class ImagenProxy implements Imagen {
    private ImagenReal imagenReal;
    private final String nombreArchivo;

    public ImagenProxy(String nombreArchivo) {
        this.nombreArchivo = nombreArchivo;
    }

    @Override
    public void mostrar() {
        // Carga perezosa (Lazy Loading): solo se instancia al solicitar el método
        if (imagenReal == null) {
            imagenReal = new ImagenReal(nombreArchivo);
        } else {
            System.out.println(">> [PROXY CACHÉ] Imagen reutilizada desde la memoria (0 lecturas a disco).");
        }
        imagenReal.mostrar();
    }
}

        System.out.println("1. Instanciando el ImagenProxy...");
        Imagen imagen = new ImagenProxy("perro_golden_retriever_4k.jpg");
        System.out.println("   Objeto Proxy listo en 0 milisegundos (disco intacto).\n");

        System.out.println("2. Primera llamada a mostrar() (Provoca carga en disco):");
        imagen.mostrar();

        System.out.println("\n3. Segunda llamada a mostrar() (Aprovecha caché en memoria):");
        imagen.mostrar();
    }
}

El Patrón Proxy en Spring Boot: Dinámicos (JDK vs CGLIB) y el Fallo de Autoinvocación

Spring Boot genera proxies dinámicos automáticamente alrededor de tus clases con anotaciones como @Transactional, @Cacheable o @Async:

  • Si la clase implementa una interfaz, Spring utiliza por defecto JDK Dynamic Proxies (paquete java.lang.reflect.Proxy).
  • Si es una clase concreta sin interfaz, utiliza CGLIB generando una subclase en bytecode al vuelo.

El Error más Común en Spring: Autoinvocación (Self-Invocation Pitfall)

Si un método dentro de un @Service llama directamente a otro método de la misma clase anotado con @Transactional, la transacción NO se abre porque la llamada se produce internamente mediante this.metodoB() sin pasar por el Proxy de Spring:


@Service
public class PetService {

    public void registrarMascota() {
        // ¡ERROR GRAVE! Invocación directa 'this.guardarEnBBDD()'.
        // No pasa a través del Proxy de Spring; la anotación @Transactional se IGNORA por completo.
        guardarEnBBDD();
    }

    @Transactional
    public void guardarEnBBDD() {
        petRepository.save(new Pet());
    }
}
Antipatrón de Autoinvocación: El Proxy de Spring no puede interceptar llamadas internas 'this'

Solución: Extraer guardarEnBBDD() a otro servicio inyectado o inyectar el propio bean (Self-Injection) para obligar a que la llamada atraviese el Proxy.

¿Cuándo usarlo y cuándo NO usarlo?

Cuándo SÍ Usar Proxy Cuándo NO Usarlo
Objetos o conexiones pesadas que deben cargarse bajo demanda (Lazy Loading en Hibernate). Objetos ligeros en memoria que se utilizan siempre nada más crearse.
Aspectos transversales (AOP): auditoría, control de accesos por rol (@PreAuthorize) y transacciones (@Transactional). Cuando se busque agregar funcionalidades acumulables en tiempo de ejecución (para eso se debe usar Decorator).
Para implementar cachés en memoria transparentes para el cliente consumidor. Cuando añada complejidad innecesaria en flujos simples sin requerimientos de seguridad ni rendimiento.
