Patrones Gang of Four (GoF): Cuándo y Para Qué Usarlos

Los Patrones de Diseño Gang of Four (GoF) constituyen el catálogo fundacional de la ingeniería de software orientada a objetos. Publicados en 1994 por Erich Gamma, Richard Helm, Ralph Johnson y John Vlissides en el libro "Design Patterns: Elements of Reusable Object-Oriented Software", estos 23 patrones clásicos representan soluciones arquitectónicas universales y refinadas para resolver problemas de acoplamiento, extensibilidad y mantenimiento a nivel de clases, interfaces y objetos en memoria.

Analogía del Mundo Real: La Caja de Herramientas del Maestro Mecánico

Imagina a un maestro mecánico reparando motores en un taller de automoción:

  • Cuando necesita unir dos piezas metálicas sometidas a vibración constante, no inventa una aleación química nueva ni funde metal desde cero: utiliza un tornillo autorroscante con arandela de presión (un patrón probado durante siglos).
  • Si necesita transferir giro perpendicularmente, acude a un engranaje cónico; si necesita amortiguar un impacto, monta un muelle helicoidal.
  • En el desarrollo de software orientado a objetos, los patrones GoF son exactamente esas piezas mecánicas estandarizadas: cuando necesitas garantizar una única instancia global recurres a Singleton; si requieres intercambiar algoritmos de cálculo acudes a Strategy; y si debes coordinar objetos complejos paso a paso utilizas Builder.

¿Para Qué Sirven los Patrones GoF en el Día a Día?

  1. Vocabulario Técnico Universal (Lenguaje Ubicuo): Permite que dos ingenieros se comuniquen instantáneamente con máxima precisión. Decir "vamos a aplicar un Decorator sobre el generador de reportes" transmite en 3 segundos una arquitectura completa que de otro modo requeriría 40 minutos de diagramas en una pizarra.
  2. Cumplimiento Natural de los Principios SOLID: Proporcionan la estructura exacta para no violar el principio Open/Closed (extender código sin modificar el existente), el principio de Responsabilidad Única (separar algoritmos de la lógica de dominio) y el de Inversión de Dependencias (programar contra interfaces abstractas).
  3. Alta Testabilidad y Mantenibilidad: Al desacoplar la creación y el comportamiento de las clases concretas, los patrones permiten inyectar dobles de prueba (Mocks y Stubs) con Mockito o JUnit 5 de manera trivial.
  4. Prevención de Deuda Técnica: Evitan la degeneración del código en clases monstruo ("God Objects") repletas de sentencias switch y condicionales infinitos.

Las 3 Familias de Patrones GoF

1. Patrones Creacionales (5)

Propósito: Abstraer y gobernar los mecanismos de creación e instanciación de objetos. Aíslan al código cliente del operador new directo, evitando el acoplamiento a clases concretas.

Singleton, Factory Method, Abstract Factory, Builder, Prototype.
2. Patrones Estructurales (7)

Propósito: Ensamblar clases e interfaces en estructuras más amplias, flexibles y eficientes mediante composición y herencia controlada.

Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy.
3. Patrones de Comportamiento (11)

Propósito: Gestionar algoritmos, flujos de control y la asignación limpia de responsabilidades y comunicación entre objetos distribuidos.

Chain of Resp., Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor.

Matriz de Decisión: ¿Cuándo Usar y Cuándo NO Usar Cada Patrón GoF?

La siguiente tabla desglosa los 23 patrones del catálogo, indicando el problema exacto que resuelven, sus escenarios idóneos de aplicación y los casos en los que su uso resulta contraproducente:

Patrón Familia ¿Para qué sirve? (Problema que resuelve) Cuándo SÍ usarlo Cuándo NO usarlo (Antipatrón / Alternativa)
Singleton Creacional Garantiza una única instancia global compartida en toda la aplicación. Recursos de hardware físicos únicos, gestores de configuración inmutables o pools de hilos. No usar como sustituto de variables globales mutables ni en Spring Boot (donde el ciclo de vida se delega al contenedor IoC con @Service).
Factory Method Creacional Delega en un método la decisión de qué clase concreta instanciar devolviendo una interfaz común. Cuando el tipo exacto del objeto no se conoce hasta el momento de ejecución (según parámetros de entrada o configuración). No usar si solo existe una clase concreta fija que nunca variará; añadir una interfaz y factoría para una sola clase es sobreingeniería.
Abstract Factory Creacional Produce familias completas de objetos relacionados o compatibles sin especificar sus clases concretas. Kits de componentes gráficos multitema (Dark/Light) o conectores cruzados compatibles entre sí. Cuando la aplicación solo crea objetos individuales independientes o cuando añadir nuevos productos obligue a redefinir toda la factoría.
Builder Creacional Construye objetos complejos paso a paso separando su construcción de su representación final. Constructores con más de 3 o 4 parámetros, presencia de campos opcionales o para crear objetos inmutables seguros (DTOs, entidades). En clases muy simples de 1 o 2 atributos obligatorios (un par clave-valor) o cuando se dispone de la anotación @Builder de Lombok.
Prototype Creacional Copia o clona objetos existentes complejos sin acoplar el código a sus clases concretas. Cuando instanciar un objeto desde cero con new sea muy costoso en tiempo de CPU o requiera consultas pesadas a red o base de datos. En objetos con grafos circulares complejos o si basta con instanciar directamente con un constructor o builder ligero.
Adapter Estructural Permite que dos clases con interfaces incompatibles colaboren traduciendo llamadas entre ellas. Integración de SDKs de terceros cerrados, librerías legadas o pasarelas de pago cuya firma difiere de la del dominio. Cuando seas el autor y propietario de ambas clases y puedas refactorizar directamente sus métodos para que coincidan de forma nativa.
Bridge Estructural Desacopla una abstracción de su implementación para que ambas puedan variar independientemente. Sistemas multiplataforma con jerarquías ortogonales (ej. Formas geométricas y Motores de renderizado vectoriales/ráster). En proyectos monolíticos simples con una sola dimensión de cambio; añade un nivel de indirección innecesario.
Composite Estructural Compone objetos en estructuras de árbol para representar jerarquías parte-todo de forma uniforme. Árboles de directorios y ficheros, menús con submenús anidados o cálculo de precios en paquetes de productos y componentes individuales. Cuando los elementos de la colección difieran radicalmente en comportamiento y no compartan una interfaz común significativa.
Decorator Estructural Añade responsabilidades a un objeto dinámicamente en tiempo de ejecución envolviéndolo en otra clase. Sistemas de flujos de E/S (como BufferedReader(new FileReader(...))), capas acumulables de compresión, cifrado o café con complementos. Cuando el orden de los decoradores importe de manera crítica o cuando la jerarquía de envoltorios haga muy difícil la depuración con debugger.
Facade Estructural Proporciona una interfaz simplificada de alto nivel frente a un subsistema complejo de clases. Ocultar librerías complejas (como conversión de vídeo, parsers XML complejos o pasarelas financieras) bajo 1 único método cómodo. No convertir la Facade en una clase "dios" monolítica que asuma responsabilidades de negocio que pertenecen a los subsistemas.
Flyweight Estructural Comparte partes comunes del estado entre múltiples objetos para ahorrar cantidades ingentes de memoria RAM. Renderizado de texto con millones de caracteres tipográficos, partículas en motores de videojuegos o mapas con miles de árboles idénticos. En aplicaciones con memoria suficiente o pocos miles de objetos; el coste en tiempo de CPU para calcular el estado extrínseco superará el ahorro.
Proxy Estructural Proporciona un sustituto que controla el acceso, ciclo de vida o seguridad hacia el objeto real. Carga perezosa (Lazy Loading en Hibernate), control de acceso por roles, transacciones declarativas (@Transactional) o caché. Para objetos sencillos en memoria local donde interceptar llamadas no aporte valor y degrade la latencia.
Chain of Responsibility Comportamiento Pasa una petición a lo largo de una cadena de manejadores donde cada uno decide procesarla o derivarla. Pipelines de filtros web (Spring Security Filters), validaciones secuenciales de solicitudes o procesadores de eventos. Si la cadena es muy larga y la petición puede llegar al final sin ser atendida por ningún manejador sin un mecanismo de fallback.
Command Comportamiento Encapsula una solicitud como un objeto independiente con todos sus parámetros, permitiendo parametrizar y encolar acciones. Sistemas con soporte de deshacer/rehacer (Undo/Redo), colas de tareas asíncronas, macros de comandos o transacciones transitorias. Para llamadas a métodos directas y simples donde no se necesite encolar, serializar ni revertir la ejecución.
Interpreter Comportamiento Define una representación gramatical y un intérprete para evaluar oraciones en un lenguaje específico. Motores de expresiones regulares simples, evaluadores de fórmulas matemáticas o lenguajes específicos de dominio (DSL). Cuando la gramática sea compleja o extensa; en tal caso es obligatorio utilizar generadores de parsers consolidados como ANTLR.
Iterator Comportamiento Recorre secuencialmente los elementos de una colección sin exponer su representación interna física. Colecciones complejas (grafos, árboles binarios) con múltiples estrategias de recorrido (anchura, profundidad). En colecciones lineales estándar donde el bucle for-each o el API nativo de Stream de Java ya lo resuelven directamente.
Mediator Comportamiento Centraliza las comunicaciones complejas y dependencias caóticas entre múltiples objetos (evita la red en espagueti). Formularios de interfaz gráfica complejos donde el cambio en un desplegable altera el estado de 5 botones y campos de texto. Si el Mediador crece descontroladamente hasta convertirse en un objeto monolítico inmanejable ("God Object").
Memento Comportamiento Captura y externaliza el estado interno de un objeto sin violar el encapsulamiento para poder restaurarlo después. Puntos de restauración de partidas de juegos, borradores de editores de texto o rollbacks de transacciones en memoria. Si los estados consumen mucha memoria RAM al duplicarse con frecuencia; en ese caso se requieren estados diferenciales.
Observer Comportamiento Define una suscripción uno-a-muchos para notificar automáticamente a múltiples interesados ante cambios de estado. Arquitecturas dirigidas por eventos, interfaces reactivas de usuario o publicación de eventos en Spring (ApplicationEventPublisher). Si los observadores se registran pero nunca se dan de baja, provocando graves fugas de memoria (el antipatrón Lapsed Listener).
State Comportamiento Permite que un objeto altere su comportamiento cuando cambia su estado interno, pareciendo cambiar de clase. Máquinas de estados finitos (máquinas expendedoras, pedidos en flujo NUEVO → PAGADO → ENVIADO → ENTREGADO). Si la clase solo tiene 2 estados sencillos que casi nunca cambian; un simple condicional booleano basta.
Strategy Comportamiento Define una familia de algoritmos, los encapsula independientemente y los hace intercambiables en tiempo de ejecución. Diferentes tarifas o descuentos, múltiples pasarelas de pago (PayPal, Tarjeta, Bizum) o algoritmos de compresión y ordenación. Si los algoritmos son triviales y estáticos; en Java moderno se prefiere pasar expresiones lambda o referencias a métodos.
Template Method Comportamiento Define el esqueleto inmutable de un algoritmo en una clase base abstracta delegando pasos específicos en subclases. Procesadores de archivos con cabecera, cuerpo y cierre estándar, o componentes *Template de Spring (JdbcTemplate). Si el orden de los pasos varía de forma radical entre casos; en ese escenario es más apropiado recurrir a Strategy.
Visitor Comportamiento Separa un algoritmo de la estructura de objetos sobre la que opera, añadiendo operaciones sin modificar las clases. Compiladores de código, recorridos de árboles sintácticos (AST) o generación de reportes sobre jerarquías de clases estables. Si la jerarquía de clases cambia frecuentemente; cada nueva clase obliga a redefinir el método visit() en todos los visitantes.

Evolución de los Patrones GoF en Java Moderno (Java 17 / 21+) y Spring Boot

Muchos patrones del catálogo original de 1994 fueron concebidos para suplir carencias de lenguajes orientados a objetos tempranos (como C++ o Java 1.1). En el desarrollo moderno con Java 17/21+ y Spring Boot 3, el propio lenguaje o framework absorbe o simplifica drásticamente varios de estos patrones:

Patrón Clásico GoF Cómo se Implementaba en 1994 Cómo se Resuelve en Java Moderno y Spring Boot
Strategy Crear una interfaz y 5 clases .java separadas para cada variante algorítmica. Interfaces Funcionales y Lambdas: Basta con pasar un Function<T, R>, Predicate<T> o Comparator directo en una línea.
Singleton Código manual complejo con volatile, constructores privados y doble comprobación de bloqueo. Inyección de Dependencias (Spring IoC): Se anota la clase con @Service o @Component y Spring administra el alcance Singleton de forma transparente y testeable.
Builder Escribir a mano 60 líneas de una clase interna estática con métodos fluidos return this. Project Lombok y Records: Anotación @Builder de Lombok sobre DTOs o entidades, o records inmutables para portadores de datos planos.
Proxy Implementar la misma interfaz a mano y reenviar cada llamada al objeto real con cerrojos. Spring AOP y CGLIB: Anotaciones declarativas como @Transactional, @Cacheable, @Async o @PreAuthorize gestionan el proxy dinámicamente.
Iterator Programar a mano punteros con hasNext(), next() y banderas de fin de colección. Java Streams y bucles for-each: Métodos fluidos como stream().filter(...).map(...).toList() nativos del JDK.
Observer Mantener listas manuales de observadores y sincronizar iteraciones en multihilo. Spring Application Events y Reactive Streams: ApplicationEventPublisher con @EventListener o librerías reactivas como Project Reactor.

¿Cuándo NO Usar Patrones de Diseño? El Peligro de la "Patronitis"

El error más habitual entre desarrolladores que acaban de estudiar patrones es querer forzar su uso en cualquier línea de código, produciendo una arquitectura hipercompleja, ilegible y difícil de mantener conocida como "Patronitis" o Sobreingeniería (Overengineering).

Debes seguir siempre la regla del Principio YAGNI (You Aren't Gonna Need It) y el principio KISS (Keep It Simple, Stupid):


// CONTRAEJEMPLO (SOBREINGENIERÍA ABSURDA): Crear Abstract Factory + Strategy para una suma aritmética
public interface CalculoFactory {
    Operacion crearOperacion();
}
public class SumaFactory implements CalculoFactory {
    public Operacion crearOperacion() { return new OperacionSuma(); }
}
// ¡15 clases creadas para terminar haciendo return a + b!

// SOLUCIÓN LIMPIA Y ELEGANTE: Una función directa
public class CalculadoraSimple {
    public static int sumar(int a, int b) {
        return a + b;
    }
}
