Patrón Strategy (Estrategia)

El patrón Strategy (Estrategia) es un patrón de diseño de comportamiento que permite definir una familia de algoritmos intercambiables, encapsular cada uno de ellos en una clase independiente y hacer que los objetos puedan intercambiar su comportamiento dinámicamente en tiempo de ejecución sin alterar a los clientes que los consumen.

Analogía del Mundo Real: Las Rutas en Google Maps

Imagina que abres Google Maps para planificar un viaje al aeropuerto:

  • El destino y el origen son idénticos ("ir desde casa al aeropuerto"), pero puedes pulsar diferentes iconos de transporte: Coche, Transporte Público, Bicicleta o Caminando.
  • El mapa (el Contexto) no implementa internamente las fórmulas matemáticas de los 4 medios de transporte: simplemente delega en la Estrategia de Enrutamiento seleccionada. Si cambias de Coche a Bicicleta en mitad de la consulta, la aplicación recalcula la ruta al instante usando el nuevo algoritmo sin tener que reinstalar la aplicación.

Propósito

Dar cumplimiento estricto al Principio Open/Closed (OCP) de SOLID: permitir agregar nuevos algoritmos, cálculos o políticas de negocio simplemente creando una nueva clase que implemente el contrato común, eliminando bloques monolíticos de if-else o switch.

Caso de Uso Real: Pasarela de Pagos en PetShop

Contexto: En la tienda de mascotas PetShop, los clientes pueden abonar su compra mediante Tarjeta de Crédito, PayPal o Bizum.

El Problema (Sin Strategy): Si dentro de OrderService.procesarPago() escribes un switch (tipoPago) con 50 líneas por cada pasarela, cada vez que el banco añade un nuevo método (ej. Apple Pay o Criptomonedas) hay que reabrir, modificar y arriesgar la estabilidad de la clase de pedidos completa.

La Solución (Con Strategy): Se define la interfaz EstrategiaPago. Cada método de pago implementa el contrato de forma aislada. El servicio de pedidos recibe la estrategia (o la resuelve dinámicamente) y delega el cobro con estrategia.pagar(importe).

Implementación en Java


// 1. Contrato Strategy común
public interface EstrategiaPago {
    void pagar(double importe);
}

// 2. Estrategias Concretas Aisladas
public class PagoTarjeta implements EstrategiaPago {
    private final String numeroTarjeta;

    public PagoTarjeta(String numeroTarjeta) {
        this.numeroTarjeta = numeroTarjeta;
    }

    @Override
    public void pagar(double importe) {
        System.out.println("💳 [Tarjeta] Cobro de " + importe + " € procesado en tarjeta terminada en: " + numeroTarjeta);
    }
}

public class PagoPayPal implements EstrategiaPago {
    private final String email;

    public PagoPayPal(String email) {
        this.email = email;
    }

    @Override
    public void pagar(double importe) {
        System.out.println("🅿️ [PayPal] Cobro de " + importe + " € procesado para la cuenta: " + email);
    }
}

public class PagoBizum implements EstrategiaPago {
    private final String telefono;

    public PagoBizum(String telefono) {
        this.telefono = telefono;
    }

    @Override
    public void pagar(double importe) {
        System.out.println("📱 [Bizum] Cobro de " + importe + " € enviado al número: " + telefono);
    }
}

// 3. Contexto: procesador de pedidos desacoplado
public class ProcesadorPedidos {
    private EstrategiaPago estrategiaPago;

    // Permite inyectar o cambiar la estrategia en runtime
    public void setEstrategiaPago(EstrategiaPago estrategiaPago) {
        this.estrategiaPago = estrategiaPago;
    }

    public void formalizarCompra(double total) {
        if (estrategiaPago == null) {
            throw new IllegalStateException("Debe seleccionar un método de pago antes de continuar.");
        }
        estrategiaPago.pagar(total);
    }
}

Evolución en Java Moderno y Spring Boot

1. Con Expresiones Lambda (Java 8+)

Si la interfaz de la estrategia tiene un único método abstracto (Functional Interface), no es obligatorio crear clases concretas separadas para algoritmos sencillos; se pueden pasar expresiones lambda directamente:


// Estrategia instanciada al vuelo mediante una lambda:
procesador.setEstrategiaPago(importe -> System.out.println("🎁 [Cupón Regalo] Saldo canjeado por: " + importe + " €"));
Strategy funcional mediante expresiones lambda de Java

2. Inyección Automática de Estrategias con Spring Boot (Map Injection)

Spring Boot permite implementar el patrón Strategy de forma automática: si anotas cada estrategia con @Component("TARJETA") y @Component("PAYPAL"), Spring inyecta automáticamente un Map<String, EstrategiaPago> en el servicio, resolviendo la estrategia en una sola línea sin ningún if:


@Service
@RequiredArgsConstructor
public class PaymentServiceSpring {

    // Spring puebla el Map con todas las clases que implementen EstrategiaPago indexadas por nombre de bean
    private final Map<String, EstrategiaPago> estrategias;

    public void pagar(String metodo, double importe) {
        EstrategiaPago estrategia = estrategias.get(metodo.toUpperCase());
        if (estrategia == null) {
            throw new IllegalArgumentException("Método de pago no soportado: " + metodo);
        }
        estrategia.pagar(importe);
    }
}

Contraejemplo: El Antipatrón del Switch Gigante


// ANTIPATRÓN: Código acoplado que viola el Principio Open/Closed
public class BrokenOrderService {
    public void procesarPago(String tipo, double importe) {
        switch (tipo) {
            case "CARD":
                // 30 líneas de conexión a tarjeta
                break;
            case "PAYPAL":
                // 40 líneas de token OAuth2 de PayPal
                break;
            case "BIZUM":
                // 25 líneas de API Bizum
                break;
            default:
                throw new IllegalArgumentException();
        }
    }
}
Antipatrón: Para añadir Apple Pay hay que modificar una clase crítica ya en producción

¿Cuándo usarlo y cuándo NO usarlo?

Cuándo SÍ Usar Strategy Cuándo NO Usarlo
Múltiples variantes de un algoritmo (pasarelas de pago, cálculo de impuestos territoriales, algoritmos de compresión o filtrado). Cuando solo existan 1 o 2 variantes estáticas muy breves que nunca van a cambiar a lo largo del ciclo de vida del proyecto.
Para eliminar estructuras complejas de if-else o switch y cumplir el principio Open/Closed. Si el código cliente no necesita conocer ni elegir entre diferentes estrategias.
Cuando los algoritmos utilicen datos privados que no deban ser visibles para la clase contexto. En funciones matemáticas triviales donde una función pura o lambda directa sea más simple y legible.
