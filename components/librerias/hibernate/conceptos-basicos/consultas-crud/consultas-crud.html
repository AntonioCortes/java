Operaciones CRUD y Consultas (HQL y Criteria)

Además de la inserción de registros, Hibernate y JPA proporcionan métodos directos en Session y EntityManager para recuperar entidades por clave primaria, actualizarlas, eliminarlas y ejecutar consultas complejas orientadas a objetos mediante HQL (Hibernate Query Language) / JPQL o mediante el API Criteria.

1. Operaciones CRUD Básicas

Lectura por ID: get() / find() frente a load() / getReference()

Para buscar un registro concreto por su clave primaria (@Id), Hibernate ofrece dos métodos con comportamientos de carga distintos:

  • session.get(Pet.class, id) (o entityManager.find(Pet.class, id) en JPA): Realiza una carga inmediata (Eager). Busca primero en la caché de primer nivel de la sesión y, si no está, ejecuta inmediatamente el SELECT en la base de datos. Si el registro no existe en la base de datos, devuelve null.
  • session.load(Pet.class, id) (o entityManager.getReference(Pet.class, id) en JPA): Realiza una carga perezosa (Lazy). No ejecuta ningún SELECT en el momento de llamarlo, sino que devuelve un objeto Proxy temporal con el ID relleno. Solo lanza la consulta a la base de datos si se invoca algún getter distinto del ID (como pet.getName()). Si el registro no existe en el momento de inicializar el proxy, lanza la excepción ObjectNotFoundException / EntityNotFoundException. Es muy útil cuando solo se necesita asociar una clave foránea sin necesidad de traer todos los datos de la fila. 

try (Session session = HibernateUtil.getSessionFactory().openSession()) 
{
	// Consulta inmediata: ejecuta SELECT y devuelve el objeto Pet o null si no existe
	Pet pet = session.get(Pet.class, 15);
	if (pet != null) 
	{
		System.out.println("Mascota encontrada: " + pet.getName());
	}
}

Actualización de Entidades: Dirty Checking, update() y merge()

  • Actualización automática por Dirty Checking (Entidad Persistente): Cuando se recupera una entidad dentro de una sesión abierta con get() o find(), el objeto está en estado Persistent. Basta con modificar cualquiera de sus atributos mediante sus métodos set...() (por ejemplo, pet.setAge((short) 5)) y hacer commit() de la transacción. Hibernate detecta automáticamente qué campos han cambiado respecto al estado original y genera la sentencia UPDATE sin necesidad de llamar a ningún método de guardado.
  • session.merge(entidad) (Estándar JPA e Hibernate para Entidades Detached): Si el objeto fue modificado fuera de la sesión (estado Detached), merge() copia el estado del objeto separado sobre una instancia gestionada por la sesión actual y devuelve dicha instancia gestionada, programando el UPDATE correspondiente.
  • session.update(entidad) (Propio de Hibernate): Vuelve a adjuntar directamente la instancia Detached a la sesión actual para actualizarla (si en la sesión ya había otra instancia en memoria con ese mismo ID, lanza NonUniqueObjectException, motivo por el cual se prefiere merge()). 

try (Session session = HibernateUtil.getSessionFactory().openSession()) 
{
	session.beginTransaction();

	// 1. Recuperamos la entidad (entra en estado Persistent)
	Pet pet = session.get(Pet.class, 15);
	if (pet != null) 
	{
		// 2. Modificamos el atributo en memoria
		pet.setAge((short) 5);
		// Al hacer commit, el Dirty Checking de Hibernate ejecuta automáticamente el UPDATE
	}

	session.getTransaction().commit();
}

Borrado de Entidades: remove() y delete()

Para eliminar un registro de la base de datos se pasa la instancia al método session.remove(pet) (estándar JPA) o session.delete(pet) (clásico de Hibernate) dentro de una transacción:


try (Session session = HibernateUtil.getSessionFactory().openSession()) 
{
	session.beginTransaction();

	Pet pet = session.get(Pet.class, 15);
	if (pet != null) 
	{
		session.remove(pet); // Ejecuta DELETE FROM pet WHERE id = 15 al hacer commit
	}

	session.getTransaction().commit();
}

2. Consultas con HQL (Hibernate Query Language) / JPQL

HQL (y su subconjunto estándar JPQL) es un lenguaje de consultas similar a SQL pero totalmente orientado a objetos: en lugar de escribir nombres de tablas y columnas de base de datos, en las consultas HQL se escriben los nombres de las clases Java (respetando mayúsculas/minúsculas) y los nombres de sus atributos.

Para evitar vulnerabilidades de inyección SQL y permitir a Hibernate reutilizar el plan de ejecución de la consulta, siempre se deben pasar los filtros mediante parámetros con nombre (:nombreParametro) asignados con setParameter():


import java.util.List;
import org.hibernate.Session;
import org.hibernate.query.Query;

try (Session session = HibernateUtil.getSessionFactory().openSession()) 
{
	// En HQL usamos el nombre de la clase "Pet" y su atributo "age", no el nombre de la tabla
	String hql = "FROM Pet p WHERE p.age = :petAge ORDER BY p.name ASC";

	Query<Pet> query = session.createQuery(hql, Pet.class);
	query.setParameter("petAge", (short) 4);

	// Obtener la lista de resultados
	List<Pet> pets = query.getResultList();
}

Métodos principales de la interfaz org.hibernate.query.Query<T>:

  • getResultList(): Ejecuta el SELECT y devuelve una List<T> con todas las entidades encontradas (o una lista vacía si no hay coincidencias).
  • uniqueResultOptional(): Devuelve un Optional<T> cuando se espera como máximo un único resultado (por ejemplo al buscar por un campo único como el email o código).
  • setFirstResult(int offset) y setMaxResults(int limit): Permiten paginar los resultados de la consulta en base de datos (equivalente a OFFSET y LIMIT en SQL).
  • executeUpdate(): Permite ejecutar sentencias masivas UPDATE o DELETE en HQL dentro de una transacción, devolviendo el número de filas afectadas.

3. Consultas Dinámicas con Criteria API

Cuando una búsqueda tiene múltiples filtros opcionales (por ejemplo, buscar mascotas filtrando opcionalmente por nombre, rango de edad y fecha de nacimiento según lo que el usuario haya rellenado en el formulario), concatenar Strings en HQL resulta complejo. Para ello se utiliza Criteria API (paquete javax.persistence.criteria.* / jakarta.persistence.criteria.*), que permite construir la consulta de forma programática y segura en tipos:


import java.util.ArrayList;
import java.util.List;
import javax.persistence.criteria.CriteriaBuilder;
import javax.persistence.criteria.CriteriaQuery;
import javax.persistence.criteria.Predicate;
import javax.persistence.criteria.Root;

try (Session session = HibernateUtil.getSessionFactory().openSession()) 
{
	// 1. Obtener el constructor de criterios a partir de la sesión
	CriteriaBuilder cb = session.getCriteriaBuilder();

	// 2. Definir el tipo de retorno de la consulta (Pet.class) y la raíz del FROM
	CriteriaQuery<Pet> cr = cb.createQuery(Pet.class);
	Root<Pet> root = cr.from(Pet.class);

	// 3. Construir la lista de condiciones (WHERE) dinámicamente
	List<Predicate> predicates = new ArrayList<>();
	predicates.add(cb.greaterThanOrEqualTo(root.get("age"), (short) 2));
	predicates.add(cb.like(root.get("name"), "J%"));

	cr.select(root)
			.where(predicates.toArray(new Predicate[0]))
			.orderBy(cb.asc(root.get("name")));

	// 4. Ejecutar la consulta
	List<Pet> result = session.createQuery(cr).getResultList();
}

¿Cuándo usar HQL, Criteria o SQL nativo y cuándo NO usarlos?

Opción Cuándo usarla Cuándo NO usarla
HQL / JPQL Consultas con filtros fijos y legibles (FROM Pet p WHERE p.age = :age). Cuando los filtros son opcionales y obligarían a concatenar fragmentos de texto.
Criteria API Búsquedas con filtros dinámicos que se activan según lo que el usuario rellene. Consultas sencillas y estáticas: añade verbosidad sin aportar nada.
SQL nativo Funciones específicas del motor, informes complejos o optimizaciones muy concretas. Cuando se busca independencia del motor de base de datos.
get() / find() Cuando se necesita el objeto completo por su @Id. Cuando solo se necesita la referencia (usar load() / getReference()).
Cuándo elegir cada forma de consultar con Hibernate

Ejemplo y Contraejemplo en Consultas HQL (Inyección SQL y Rendimiento)

Contraejemplo (Mala práctica): Concatenar variables en la cadena HQL

Concatenar directamente el valor recibido del usuario dentro del String de la consulta HQL abre una vulnerabilidad crítica de Inyección HQL/SQL y además impide que Hibernate y el motor de base de datos reutilicen la caché de planes de ejecución (PreparedStatement cache), ya que cada búsqueda genera una cadena de consulta distinta:


// CONTRAEJEMPLO (PELIGROSO): Vulnerable a inyección HQL y rompe la caché de consultas
String userInputName = "Joe' OR '1'='1";
String badHql = "FROM Pet p WHERE p.name = '" + userInputName + "'";
List<Pet> pets = session.createQuery(badHql, Pet.class).getResultList(); // ¡Devuelve toda la tabla!

Ejemplo (Buena práctica): Uso obligatorio de parámetros enlazados (setParameter)

Utilizando parámetros con nombre (:name), Hibernate traduce la consulta a un PreparedStatement parametrizado (?) donde el texto del usuario se escapa de forma totalmente segura y el plan de ejecución se reutiliza en memoria:


// EJEMPLO (SEGURO Y ÓPTIMO): Uso de parámetros con nombre (:name)
String safeHql = "FROM Pet p WHERE p.name = :name";
List<Pet> pets = session.createQuery(safeHql, Pet.class)
		.setParameter("name", userInputName)
		.getResultList();
