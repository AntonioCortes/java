Hibernate ORM - Introducción y Arquitectura

Hibernate ORM es el framework de Mapeo Objeto-Relacional (ORM) más utilizado en el ecosistema Java. Su objetivo principal es resolver el desajuste de impedancia objeto-relacional, permitiendo asociar clases Java (Entidades como Pet o EmployeeEntity) directamente con tablas de una base de datos relacional (PostgreSQL, MySQL, Oracle, H2, SQL Server) y traducir automáticamente las operaciones sobre objetos en sentencias SQL optimizadas.

Relación entre JPA e Hibernate

Es muy común confundir los términos JPA e Hibernate, pero cumplen roles distintos y complementarios:

  • JPA (Jakarta Persistence API / anteriormente Javax Persistence API): Es únicamente una especificación oficial compuesta por interfaces (como EntityManagerFactory, EntityManager, EntityTransaction) y anotaciones estándar (@Entity, @Table, @Id, @Column, @OneToMany) en el paquete javax.persistence.* (o jakarta.persistence.* desde JPA 3.0 / Spring Boot 3). JPA por sí sola no ejecuta nada; define el contrato.
  • Hibernate ORM: Es la implementación real más popular de la especificación JPA. Provee todo el motor que ejecuta por debajo las interfaces de JPA y, además, ofrece su propia API nativa (SessionFactory, Session, Transaction en el paquete org.hibernate.*) con funcionalidades adicionales avanzadas.

Dependencias necesarias

1. En un proyecto Java estándar (Hibernate puro)

En Maven (pom.xml) se añade hibernate-core junto con el driver JDBC de la base de datos (por ejemplo MySQL o PostgreSQL):


<dependencies>
	<!-- Motor principal de Hibernate ORM -->
	<dependency>
		<groupId>org.hibernate.orm</groupId>
		<artifactId>hibernate-core</artifactId>
		<version>6.2.7.Final</version>
	</dependency>

	<!-- Driver JDBC (Ejemplo con MySQL) -->
	<dependency>
		<groupId>com.mysql</groupId>
		<artifactId>mysql-connector-j</artifactId>
		<version>8.0.33</version>
	</dependency>
</dependencies>

En Gradle (build.gradle):


dependencies {
	implementation 'org.hibernate.orm:hibernate-core:6.2.7.Final'
	runtimeOnly 'com.mysql:mysql-connector-j:8.0.33'
}

2. En un proyecto Spring Boot

En Spring Boot se utiliza el starter spring-boot-starter-data-jpa, el cual ya incluye transitivamente Hibernate ORM como proveedor de persistencia por defecto, además de Spring Data JPA y el pool de conexiones HikariCP:


<dependency>
	<groupId>org.springframework.boot</groupId>
	<artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>

Componentes Principales de la Arquitectura

  • SessionFactory (Hibernate) / EntityManagerFactory (JPA): Ubicados en org.hibernate.SessionFactory y javax.persistence.EntityManagerFactory. Es un objeto pesado e inmutable (thread-safe) que se crea una única vez al arrancar la aplicación (patrón Singleton) tras leer el archivo de configuración (hibernate.cfg.xml o persistence.xml). Contiene los metadatos de todas las entidades mapeadas, la configuración del dialecto SQL, el pool de conexiones y la caché de segundo nivel.
  • Session (Hibernate) / EntityManager (JPA): Ubicados en org.hibernate.Session y javax.persistence.EntityManager. Es un objeto ligero y de corta vida (no es thread-safe) que se abre por cada petición o unidad de trabajo a partir de la factoría. Representa una conexión activa con la base de datos y mantiene la caché de primer nivel (Contexto de Persistencia) donde residen las entidades gestionadas.
  • Transaction (Hibernate) / EntityTransaction (JPA): Ubicados en org.hibernate.Transaction y javax.persistence.EntityTransaction. Agrupa un conjunto de operaciones de escritura (inserciones, actualizaciones, borrados) para que se ejecuten de forma atómica mediante begin(), commit() y, en caso de fallo, rollback().

Estados del Ciclo de Vida de una Entidad

Figura 2: Estados de una entidad y métodos que provocan cada transición

Cualquier instancia de una clase anotada con @Entity (como Pet) pasa por cuatro posibles estados respecto al contexto de persistencia (Session / EntityManager):

Estado ¿Está en el Contexto de Persistencia (Session)? ¿Tiene fila asociada en Base de Datos? Cómo llega a este estado y comportamiento
1. Transient (Transitorio) No No Objeto recién instanciado con new Pet(). Hibernate aún no sabe nada de él; si no se guarda, el recolector de basura lo eliminará.
2. Persistent / Managed (Persistente) Sí Sí (o se insertará al hacer commit) Tras llamar a persist() / save() o al recuperarlo con find() / get(). Cualquier cambio en sus atributos con set...() es detectado automáticamente por Hibernate (Dirty Checking) y sincronizado con la BD al cerrar la transacción.
3. Detached (Separado) No Sí Cuando se cierra la sesión (session.close()) o se llama a detach() / evict(). El objeto sigue existiendo en memoria con su ID, pero los cambios que se le hagan no se guardarán en BD a menos que se vuelva a asociar con merge() o update().
4. Removed (Eliminado) Sí (marcado para borrado) Se borrará al hacer commit Tras invocar remove() o delete() sobre una entidad persistente. Al confirmar la transacción se ejecutará la sentencia DELETE FROM ....

Propiedades Clave de Configuración (hibernate.cfg.xml)

  • hibernate.connection.driver_class, url, username, password: Datos de conexión JDBC hacia el motor de base de datos.
  • hibernate.dialect: Clase del paquete org.hibernate.dialect.* (ej. MySQLDialect, PostgreSQLDialect) que indica a Hibernate cómo generar el SQL específico de ese fabricante (paginación, tipos de datos, secuencias).
  • hibernate.show_sql y hibernate.format_sql: Si están a true, muestran por consola las consultas SQL que Hibernate genera y ejecuta internamente.
  • hibernate.hbm2ddl.auto: Controla cómo actúa Hibernate sobre el esquema DDL de la base de datos al arrancar la SessionFactory:
    • none: No realiza ninguna acción ni validación sobre el esquema.
    • validate: Valida que las tablas y columnas existentes en la base de datos coincidan con las clases @Entity; si falta algo, lanza una excepción al arrancar (opción recomendada en producción junto con Flyway).
    • update: Añade automáticamente tablas o columnas nuevas si se han añadido en las entidades Java, sin borrar los datos existentes (útil en desarrollo rápido, desaconsejado en producción).
    • create: Elimina las tablas existentes al arrancar y las vuelve a crear desde cero limpias.
    • create-drop: Crea las tablas al arrancar la aplicación y las elimina automáticamente al cerrar la SessionFactory (ideal para tests de integración con bases de datos en memoria como H2).

¿Cuándo usar Hibernate ORM y cuándo NO usarlo?

Escenario ¿Cuándo SÍ usarlo? (Recomendado) ¿Cuándo NO usarlo? (Desaconsejado / Alternativas)
Aplicaciones de Negocio y Dominio Rico Cuando se trabaja con un modelo de dominio orientado a objetos con relaciones entre entidades (1:1, 1:N, N:M), operaciones transaccionales CRUD y se busca independencia del motor SQL. En procesos de extracción y carga masiva de millones de filas (ETL / Batch pesado) o generación de informes analíticos con decenas de subconsultas y funciones ventana, donde el contexto de persistencia de Hibernate consumiría demasiada memoria RAM (allí es mejor usar Spring JDBC / JdbcTemplate, jOOQ o MyBatis).
Carga de Relaciones (FetchType) Configurar las relaciones como FetchType.LAZY para cargar los objetos hijos únicamente cuando se necesiten, o traerlos en una sola consulta con JOIN FETCH. No usar FetchType.EAGER en todas las relaciones: provoca que una simple consulta de una entidad dispare decenas de JOIN o consultas secundarias innecesarias (el problema de las N+1 queries).

Ejemplo y Contraejemplo: Creación de SessionFactory y Ciclo de Vida de Session

Contraejemplo (Mala práctica): Crear un SessionFactory en cada método y no cerrar la Session en caso de error

Construir una SessionFactory requiere parsear el XML, inspeccionar todas las clases @Entity por reflexión y abrir el pool de conexiones. Si se crea dentro de un método de negocio o si no se hace rollback() ni se cierra la Session dentro de un bloque try-with-resources / finally, la aplicación agotará todas las conexiones disponibles de la base de datos en pocos segundos:


// CONTRAEJEMPLO (INCORRECTO): Crea una SessionFactory por llamada y deja la conexión abierta si salta una excepción
public void savePetBad(Pet pet) 
{
	// ¡Error grave! Crear SessionFactory aquí tarda segundos y abre un nuevo pool entero
	SessionFactory sf = new Configuration().configure().buildSessionFactory();
	Session session = sf.openSession();
	session.beginTransaction();

	session.persist(pet); // Si aquí lanza ConstraintViolationException, nunca se llega al close()
	session.getTransaction().commit();
	session.close();
}

Ejemplo (Buena práctica): Reutilizar el Singleton SessionFactory y gestionar transacciones con try-with-resources

La SessionFactory se instancia una sola vez para toda la aplicación, mientras que cada operación abre una Session ligera dentro de un bloque try-with-resources garantizando el rollback en caso de error y el cierre automático de la sesión:


// EJEMPLO (CORRECTO): Reutiliza el Singleton SessionFactory, hace rollback si falla y cierra siempre la Session
public void savePetGood(Pet pet) 
{
	Transaction tx = null;
	try (Session session = HibernateUtil.getSessionFactory().openSession()) 
	{
		tx = session.beginTransaction();
		session.persist(pet);
		tx.commit();
	} 
	catch (Exception ex) 
	{
		if (tx != null && tx.isActive()) 
		{
			tx.rollback();
		}
		throw ex;
	}
}
