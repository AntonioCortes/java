Introducción a las Librerías en Java

En el ecosistema de Java y Spring Boot, el uso de librerías de terceros es fundamental para evitar reinventar la rueda, reducir el código repetitivo (boilerplate), estandarizar el acceso a datos, automatizar la documentación de APIs y facilitar la comunicación entre servicios.

En este apartado se documentan en detalle las librerías más utilizadas en proyectos empresariales y microservicios Java, abarcando desde su configuración e instalación en Maven (pom.xml) y Gradle (build.gradle) hasta el desglose de sus anotaciones, clases principales y ejemplos prácticos.

Resumen de Librerías Documentadas

Librería Propósito Principal Artefacto Maven Habitual Cuándo utilizarla Cuándo NO utilizarla
Project Lombok Generación automática de código repetitivo en tiempo de compilación (getters, setters, constructores, toString, equals/hashCode, patrones Builder y loggers). org.projectlombok:lombok En prácticamente cualquier proyecto Java o Spring Boot para mantener las clases (DTOs, Entidades, Servicios) limpias, legibles y fáciles de mantener. No usar @Data sobre entidades JPA con relaciones perezosas (usar @Getter/@Setter); en Java 16+ para DTOs inmutables simples es preferible usar un record nativo.
ModelMapper Mapeo automático e inteligente de objetos entre distintas capas de la aplicación (por ejemplo, convertir entre una entidad JPA Pet y un PetDTO o PetPatchDTO). org.modelmapper:modelmapper Cuando se necesita desacoplar la capa de persistencia (Entidades) de la capa de exposición (DTOs) o aplicar actualizaciones parciales (PATCH) sin escribir decenas de get/set. En sistemas de ultra baja latencia o procesamientos batch de millones de objetos donde el coste de la reflexión importa (allí es mejor usar MapStruct en compilación).
Flyway Control de versiones y migraciones incrementales de esquemas de bases de datos relacionales mediante scripts SQL o clases Java. org.flywaydb:flyway-core En cualquier aplicación con base de datos relacional para garantizar que todos los entornos (local, integración, producción) tengan exactamente la misma estructura de tablas y datos maestros. En prototipos efímeros en memoria (H2 con create-drop), bases de datos NoSQL, o nunca combinado con ddl-auto: update en Hibernate.
SpringFox / Swagger (OpenAPI) Generación automática de documentación técnica e interfaz web interactiva (Swagger UI) para APIs REST desarrolladas con Spring Boot. io.springfox:springfox-boot-starter / org.springdoc:springdoc-openapi-starter-webmvc-ui Al desarrollar microservicios o APIs REST para documentar cada endpoint, sus parámetros, modelos JSON y códigos de respuesta HTTP, permitiendo probar la API desde el navegador. No usar SpringFox en proyectos con Spring Boot 3+ (usar SpringDoc OpenAPI), y no exponer Swagger UI públicamente en entornos de producción sin seguridad.
Hibernate ORM Framework de Mapeo Objeto-Relacional (ORM) e implementación de referencia de la especificación JPA para persistir objetos Java en bases de datos relacionales. org.hibernate.orm:hibernate-core / spring-boot-starter-data-jpa Para gestionar la capa de persistencia, transacciones, relaciones entre tablas y consultas orientadas a objetos (HQL / JPQL / Criteria) sin escribir SQL manual acoplado al motor de base de datos. En procesos ETL o cargas masivas de millones de registros en bloque donde la caché de primer nivel agote la memoria RAM (allí es preferible JDBC batch o StatelessSession).
Apache HttpClient Cliente HTTP robusto y configurable para realizar llamadas a servidores externos o APIs REST desde código Java. org.apache.httpcomponents:httpclient / httpclient5 Cuando una aplicación Java necesita consumir servicios HTTP externos con control avanzado sobre pools de conexiones, timeouts, cabeceras, proxies, autenticación o subida de ficheros multipart. Cuando en microservicios Spring Cloud basta un cliente declarativo por interfaz como OpenFeign, o en llamadas triviales en Java 11+ donde basta java.net.http.HttpClient.

Cómo se integran estas librerías en una Arquitectura por Capas

En un proyecto típico de microservicios (como el dominio de ejemplo de la tienda de mascotas PetShop utilizado a lo largo de esta web), todas estas librerías trabajan de forma conjunta y coordinada en cada petición:

  • Capa de Presentación / Controladores (PetController):
    • Utiliza SpringFox / Swagger (@Api, @ApiOperation, @ApiResponses, @ApiParam) para documentar los endpoints REST (GET, POST, PATCH, DELETE).
    • Utiliza Lombok (@Slf4j, @RequiredArgsConstructor) para registrar trazas de log e inyectar dependencias limpiamente por constructor.
    • Utiliza ModelMapper (mapper y patchMapper) para transformar las entidades recibidas del servicio en objetos PetDTO de respuesta o volcar los cambios parciales de un PetPatchDTO sobre la entidad existente.
  • Objetos de Transferencia de Datos (PetDTO, PetPatchDTO):
    • Utilizan Lombok (@Data, @Accessors(chain = true), @Builder) para generar automáticamente los métodos de acceso y constructores fluidos.
    • Utilizan Swagger (@ApiModel, @ApiModelProperty) para describir cada propiedad del JSON y mostrar valores de ejemplo en Swagger UI.
  • Capa de Negocio y Clientes Externos (PetService):
    • Si el servicio necesita comunicarse con una pasarela externa o un servicio legado vía HTTP, puede apoyarse en Apache HttpClient para construir la petición (HttpGet, HttpPost, URIBuilder) y gestionar la respuesta de forma segura.
  • Capa de Persistencia y Base de Datos (Pet, PetRepository):
    • Al arrancar la aplicación, Flyway inspecciona la carpeta db/migration y ejecuta los scripts SQL pendientes (V1__create_pet_table.sql) registrándolos en la tabla flyway_schema_history.
    • A continuación, Hibernate ORM valida que la entidad Java Pet (anotada con @Entity, @Table, @Id, @Column) coincide con la tabla creada por Flyway y se encarga de ejecutar las inserciones, actualizaciones, borrados y consultas transaccionales.

Gestión Centralizada de Dependencias

Para incorporar cualquiera de estas librerías en un proyecto, se declara su coordenada (groupId, artifactId y version) en el gestor de construcción del proyecto. Si se utiliza el POM padre de Spring Boot (spring-boot-starter-parent) o el bloque dependencyManagement con spring-boot-dependencies, muchas de estas librerías (como Lombok, Hibernate o Flyway) ya tienen su versión gestionada automáticamente para asegurar la compatibilidad entre ellas, por lo que no es necesario indicar la etiqueta <version> manualmente.

Ejemplo de declaración combinada en Maven (pom.xml):


<dependencies>
    <!-- Lombok: Generación de código en compilación -->
    <dependency>
        <groupId>org.projectlombok</groupId>
        <artifactId>lombok</artifactId>
        <optional>true</optional>
    </dependency>

    <!-- ModelMapper: Conversión entre Entidades y DTOs -->
    <dependency>
        <groupId>org.modelmapper</groupId>
        <artifactId>modelmapper</artifactId>
        <version>3.1.1</version>
    </dependency>

    <!-- Flyway: Migraciones de Base de Datos -->
    <dependency>
        <groupId>org.flywaydb</groupId>
        <artifactId>flyway-core</artifactId>
    </dependency>

    <!-- SpringFox Swagger: Documentación de APIs REST -->
    <dependency>
        <groupId>io.springfox</groupId>
        <artifactId>springfox-boot-starter</artifactId>
        <version>3.0.0</version>
    </dependency>

    <!-- Hibernate / JPA: Persistencia ORM -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-data-jpa</artifactId>
    </dependency>

    <!-- Apache HttpClient: Cliente HTTP -->
    <dependency>
        <groupId>org.apache.httpcomponents</groupId>
        <artifactId>httpclient</artifactId>
        <version>4.5.14</version>
    </dependency>
</dependencies>

Equivalente en Gradle (build.gradle):


dependencies {
    // Lombok
    compileOnly 'org.projectlombok:lombok'
    annotationProcessor 'org.projectlombok:lombok'

    // ModelMapper
    implementation 'org.modelmapper:modelmapper:3.1.1'

    // Flyway
    implementation 'org.flywaydb:flyway-core'

    // SpringFox Swagger
    implementation 'io.springfox:springfox-boot-starter:3.0.0'

    // Hibernate / JPA
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'

    // Apache HttpClient
    implementation 'org.apache.httpcomponents:httpclient:4.5.14'
}

Ejemplo y Contraejemplo: Versiones de las dependencias

Contraejemplo (Mala práctica): Fijar a mano la versión de una librería que ya gestiona Spring Boot

Cuando el proyecto hereda de spring-boot-starter-parent, Spring Boot ya elige versiones compatibles entre sí para Lombok, Hibernate o Flyway. Escribir una versión distinta en cada dependencia puede mezclar versiones incompatibles (por ejemplo, un Hibernate más nuevo que el que espera spring-boot-starter-data-jpa) y provocar errores como NoSuchMethodError al arrancar:


<!-- CONTRAEJEMPLO (INCORRECTO): versiones manuales que chocan con las gestionadas por Spring Boot -->
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
    <version>5.0.0</version>
</dependency>
<dependency>
    <groupId>org.hibernate.orm</groupId>
    <artifactId>hibernate-core</artifactId>
    <version>4.3.11.Final</version>
</dependency>

Ejemplo (Buena práctica): Omitir la versión y dejar que la gestione el POM padre

Se omite la etiqueta <version> en las librerías gestionadas por Spring Boot y solo se indica explícitamente en las que no lo están (como modelmapper o springfox):


<!-- EJEMPLO (CORRECTO): Spring Boot gestiona la versión de Flyway y Hibernate -->
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>

<!-- ModelMapper no está gestionado por Spring Boot: se indica su versión -->
<dependency>
    <groupId>org.modelmapper</groupId>
    <artifactId>modelmapper</artifactId>
    <version>3.1.1</version>
</dependency>
