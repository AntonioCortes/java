ModelMapper - Introducción y Configuración

ModelMapper es una librería de Java que automatiza el mapeo (conversión) de objetos entre distintas capas de una aplicación, especialmente entre las Entidades de persistencia (JPA / Hibernate) y los DTOs (Data Transfer Objects) que se exponen en los controladores REST.

En una arquitectura limpia por capas, nunca se debe devolver directamente una entidad de base de datos (como Pet) en un endpoint REST ni recibirla directamente desde el cliente. Sin embargo, copiar manualmente cada atributo mediante llamadas repetitivas a dto.setName(entity.getName()) genera código difícil de mantener y propenso a errores cuando se añaden nuevos campos. ModelMapper soluciona esto analizando automáticamente ambos objetos mediante reflexión y convenciones de nombres para transferir los valores de un objeto a otro en una sola línea.

Dependencias necesarias

Para utilizar ModelMapper es necesario añadir el artefacto modelmapper del grupo org.modelmapper en el archivo de construcción del proyecto.

En Maven (pom.xml):


<dependency>
	<groupId>org.modelmapper</groupId>
	<artifactId>modelmapper</artifactId>
	<version>3.1.1</version>
</dependency>

En Gradle (build.gradle):


dependencies {
	implementation 'org.modelmapper:modelmapper:3.1.1'
}

Clases e Interfaces Principales de Configuración

  • ModelMapper: Clase principal de la librería, ubicada en el paquete org.modelmapper.ModelMapper. Es el motor central encargado de ejecutar las conversiones mediante su método map() y almacenar las reglas de configuración y mapas de tipos (TypeMap). Es thread-safe una vez configurado, por lo que en Spring Boot se declara como un Singleton Bean.
  • Configuration: Interfaz ubicada en el paquete org.modelmapper.config.Configuration (accesible mediante modelMapper.getConfiguration()). Permite personalizar el comportamiento global del mapeador: cómo empareja nombres de campos, si debe ignorar valores nulos, o si debe acceder por métodos getter/setter o directamente a los atributos privados.

    Sus métodos de configuración más importantes son:

    • setMatchingStrategy(MatchingStrategy): Define la estrategia de emparejamiento de nombres entre los atributos de origen y destino (por defecto usa MatchingStrategies.STANDARD).
    • setSkipNullEnabled(boolean): Por defecto es false. Si se establece a true, cuando un atributo en el objeto de origen vale null, ModelMapper lo ignora y no sobrescribe el valor que ya tuviera ese atributo en el objeto de destino. Esta opción es imprescindible para implementar actualizaciones parciales (método HTTP PATCH).
    • setFieldMatchingEnabled(boolean): Por defecto es false (solo usa getters y setters). Si se activa a true, permite a ModelMapper comparar y copiar campos directamente aunque no tengan getters o setters.
    • setFieldAccessLevel(AccessLevel): Ubicado en org.modelmapper.config.Configuration.AccessLevel. Define el nivel de visibilidad de los atributos o métodos a los que puede acceder ModelMapper:
      • PUBLIC: Solo accede a miembros públicos (valor por defecto).
      • PROTECTED: Accede a miembros públicos y protegidos.
      • PACKAGE_PRIVATE: Incluye miembros con visibilidad de paquete.
      • PRIVATE: Permite acceder directamente a atributos private mediante reflexión.
    • setAmbiguityIgnored(boolean): Por defecto es false. Si dos propiedades de origen podrían coincidir con el mismo atributo de destino, ModelMapper lanza una excepción de validación; al ponerlo a true, ignora las propiedades ambiguas.
  • MatchingStrategies: Clase de utilidades ubicada en el paquete org.modelmapper.convention.MatchingStrategies que define las tres estrategias de coincidencia de nombres:
    • MatchingStrategies.STANDARD: Es la estrategia por defecto. Divide los nombres de los atributos en tokens (palabras) y permite que coincidan en cualquier orden, siempre que todos los tokens de destino tengan correspondencia y al menos un nombre de propiedad coincida. Es ideal para la mayoría de conversiones entre Entidades y DTOs.
    • MatchingStrategies.LOOSE: Estrategia laxa. Solo exige que coincida el último token de la jerarquía de nombres. Es muy útil para aplanar objetos complejos con varios niveles de anidación hacia un DTO plano (por ejemplo, mapear automáticamente order.getCustomer().getAddress().getCity() a orderDTO.setCity()), pero puede provocar mapeos accidentales si existen varios campos con nombres parecidos.
    • MatchingStrategies.STRICT: Estrategia estricta. Exige que los tokens de origen y destino coincidan exactamente en nombre y en el mismo orden. Garantiza que jamás se produzca un mapeo inesperado o ambiguo, siendo la opción más segura cuando las clases comparten estructura idéntica.
Estrategia Orden de Tokens Todos los tokens origen deben coincidir Todos los tokens destino deben coincidir Caso de uso recomendado
STRICT Debe ser exacto Sí Sí Mapeos críticos, actualizaciones parciales (PATCH) o clases con múltiples campos de nombres similares.
STANDARD Cualquier orden No (mínimo el nombre del atributo) Sí Comportamiento por defecto para mapear entre Entidades y DTOs convencionales.
LOOSE Cualquier orden No No (solo el último token) Aplanar jerarquías profundas de objetos anidados en un único DTO plano.

Configuración en Spring Boot (@Bean y @Qualifier)

En una aplicación Spring Boot, la práctica recomendada es crear una clase anotada con @Configuration donde se expongan una o varias instancias de ModelMapper como Spring Beans para poder inyectarlas posteriormente con @Autowired en los controladores o servicios.

Tal y como se observa en PetController, es muy habitual definir dos Beans distintos de ModelMapper diferenciados por nombre:

  1. modelMapper: Mapeador estándar para crear un PetDTO a partir de un Pet (en peticiones GET) o crear un nuevo Pet a partir de un PetDTO (en peticiones POST / PUT).
  2. patchModelMapper: Mapeador configurado con setSkipNullEnabled(true) y estrategia STRICT. Se utiliza en peticiones PATCH para volcar los cambios de un PetPatchDTO sobre una entidad Pet recuperada de base de datos, modificando únicamente los campos enviados en el JSON y respetando los campos que venían a null.

package com.petshop.config;

import org.modelmapper.ModelMapper;
import org.modelmapper.convention.MatchingStrategies;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Primary;

@Configuration
public class MapperConfig 
{
	@Bean(name = "modelMapper")
	@Primary
	public ModelMapper modelMapper() 
	{
		ModelMapper mapper = new ModelMapper();
		mapper.getConfiguration()
				.setMatchingStrategy(MatchingStrategies.STANDARD);
		return mapper;
	}

	@Bean(name = "patchModelMapper")
	public ModelMapper patchModelMapper() 
	{
		ModelMapper patchMapper = new ModelMapper();
		patchMapper.getConfiguration()
				.setMatchingStrategy(MatchingStrategies.STRICT)
				.setSkipNullEnabled(true);
		return patchMapper;
	}
}

Una vez registrados ambos beans en el contenedor de Spring, se pueden inyectar en PetController utilizando la anotación @Qualifier de Spring Framework (paquete org.springframework.beans.factory.annotation.Qualifier) para indicar cuál de los dos mapeadores se desea utilizar en cada atributo:


@RestController
@RequestMapping("/petshop/pet")
public class PetController 
{
	@Autowired
	private PetService petService;

	@Autowired
	@Qualifier("modelMapper")
	private ModelMapper mapper;

	@Autowired
	@Qualifier("patchModelMapper")
	private ModelMapper patchMapper;
}

¿Cuándo usar ModelMapper y cuándo NO usarlo?

Escenario ¿Cuándo SÍ usarlo? (Recomendado) ¿Cuándo NO usarlo? (Desaconsejado / Alternativas)
Microservicios CRUD y APIs REST Cuando existen múltiples Entidades y DTOs con nombres de atributos equivalentes y se quiere ahorrar escribir decenas de métodos manuales de conversión, o para aplicar cambios parciales en endpoints PATCH con setSkipNullEnabled(true). Cuando una clase solo tiene 2 o 3 atributos simples o solo se mapea en un único punto del proyecto (un método toDTO() manual o un constructor es más explícito y rápido).
Rendimiento y Tiempo de Ejecución En aplicaciones empresariales estándar donde la latencia dominante es la base de datos o la red HTTP, el coste de la reflexión de ModelMapper es despreciable. En sistemas de ultra baja latencia o procesamientos por lotes (batch) que convierten millones de objetos por segundo en memoria: al usar reflexión en ejecución es más lento que MapStruct (que genera código Java en compilación).
Estrategia de Coincidencia Usar STANDARD para mapeos generales y STRICT cuando hay campos con nombres parecidos o en actualizaciones parciales. No usar MatchingStrategies.LOOSE por defecto en el mapper global, ya que empareja cualquier atributo cuyo último token coincida (pudiendo mapear accidentalmente owner.id sobre pet.id).
Cuándo utilizar ModelMapper y cuándo evitarlo

Ejemplo y Contraejemplo: Ciclo de vida del Bean y Estrategia de Mapeo

Contraejemplo (Mala práctica): Instanciar new ModelMapper() en cada petición y usar estrategia LOOSE

Crear un objeto new ModelMapper() dentro de un método del controlador obliga a la librería a volver a analizar por reflexión las clases en cada llamada HTTP, degradando gravemente el rendimiento y la memoria. Además, usar MatchingStrategies.LOOSE puede sobrescribir el ID o el nombre de la mascota con el del dueño si ambos objetos tienen un campo llamado name:


// CONTRAEJEMPLO (INCORRECTO): Instanciar ModelMapper en cada llamada HTTP y usar LOOSE sin control
@GetMapping("/{id}")
public ResponseEntity<PetDTO> getBad(@PathVariable final Integer id) 
{
	// ¡Mala práctica! Costoso en CPU/memoria al no reutilizar el Singleton Bean de Spring
	ModelMapper localMapper = new ModelMapper();
	localMapper.getConfiguration().setMatchingStrategy(MatchingStrategies.LOOSE);

	Pet pet = petService.findById(id).orElseThrow();
	// Con LOOSE, pet.getOwner().getName() puede terminar sobrescribiendo petDTO.setName()
	PetDTO dto = localMapper.map(pet, PetDTO.class);
	return ResponseEntity.ok(dto);
}

Ejemplo (Buena práctica): Inyectar el Singleton Bean preconfigurado con STANDARD o STRICT

Al inyectar el bean configurado en MapperConfig, todas las peticiones reutilizan la caché de tipos de una única instancia thread-safe:


// EJEMPLO (CORRECTO): Reutilización del Singleton Bean inyectado por Spring
@RestController
@RequestMapping("/petshop/pet")
public class PetController 
{
	@Autowired
	@Qualifier("modelMapper")
	private ModelMapper mapper;

	@GetMapping("/{id}")
	public ResponseEntity<PetDTO> getGood(@PathVariable final Integer id) 
	{
		Pet pet = petService.findById(id).orElseThrow();
		PetDTO dto = mapper.map(pet, PetDTO.class);
		return ResponseEntity.ok(dto);
	}
}
