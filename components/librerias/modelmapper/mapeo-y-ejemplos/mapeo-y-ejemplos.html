Mapeo de Objetos y Personalización en ModelMapper

Una vez configurado el objeto ModelMapper, la librería ofrece distintas sobrecargas del método map() así como herramientas avanzadas (TypeMap, PropertyMap, Converter y Condition) para adaptar la conversión de datos a cualquier necesidad del negocio.

Métodos Principales de Mapeo

1. Mapear creando una nueva instancia (map(Object source, Class<D> destinationType))

Es el método más utilizado. Recibe el objeto de origen y la clase del objeto de destino (que debe disponer de un constructor sin argumentos accesible), instancia automáticamente un nuevo objeto de la clase destino y copia en él todas las propiedades coincidentes.

Se utiliza habitualmente en los métodos GET (para transformar la entidad Pet recuperada de base de datos en un PetDTO antes de devolver la respuesta HTTP) y en los métodos POST (para convertir el PetDTO recibido en el body de la petición en una nueva entidad Pet lista para guardarse):


// 1. De Entidad (Pet) a DTO (PetDTO) en una petición GET
Optional<Pet> petOpt = petService.findById(pId);
if (petOpt.isPresent()) 
{
	PetDTO petDTO = mapper.map(petOpt.get(), PetDTO.class);
	return new ResponseEntity<>(petDTO, HttpStatus.OK);
}

// 2. De DTO (PetDTO) a Entidad (Pet) en una petición POST
Pet newPet = mapper.map(pPetDTO, Pet.class);
newPet = petService.save(newPet);

2. Mapear sobre una instancia ya existente (map(Object source, Object destination))

En lugar de recibir una clase y crear un objeto nuevo, esta sobrecarga recibe una instancia de destino que ya existe en memoria y vuelca sobre ella los atributos del objeto de origen.

Combinado con el bean patchMapper (que tiene activado setSkipNullEnabled(true)), este método es la pieza clave para implementar el endpoint PATCH: primero se recupera la mascota existente de la base de datos (con su ID, nombre, edad y fecha de nacimiento actuales), y luego se vuelcan sobre ella únicamente los campos no nulos enviados en el PetPatchDTO:


@PatchMapping("/{id}")
public ResponseEntity<HttpStatus> patch(
		@PathVariable(value = "id") final Integer pId,
		@Valid @RequestBody final PetPatchDTO pPetPatchDTO) 
{
	Optional<Pet> petOpt = petService.findById(pId);
	if (petOpt.isEmpty()) 
	{
		return new ResponseEntity<>(HttpStatus.NOT_FOUND);
	}

	Pet existingPet = petOpt.get();
	
	// Copia sobre existingPet solo los atributos de pPetPatchDTO que NO sean null
	patchMapper.map(pPetPatchDTO, existingPet);

	// Guarda la entidad actualizada conservando el resto de sus datos originales
	petService.save(existingPet);

	return new ResponseEntity<>(HttpStatus.NO_CONTENT);
}

3. Mapeo de Colecciones y Listas

En Java, debido al borrado de tipos genéricos en tiempo de ejecución (Type Erasure), no se puede hacer directamente mapper.map(petList, List<PetDTO>.class). Existen dos formas recomendadas de mapear una lista de entidades a una lista de DTOs:

Opción A: Usando el API Stream de Java 8+ (Recomendada)

Es la forma más clara, legible y utilizada en los controladores de Spring Boot. Se recorre el Stream de la lista de entidades aplicando mapper.map() a cada elemento individual:


List<Pet> petList = petService.findByAge(pAge);

List<PetDTO> petDTOList = petList.stream()
		.map(pet -> mapper.map(pet, PetDTO.class))
		.collect(Collectors.toList());

return new ResponseEntity<>(petDTOList, HttpStatus.OK);

Opción B: Usando la clase TypeToken de ModelMapper

ModelMapper incluye la clase TypeToken (en el paquete org.modelmapper.TypeToken) que captura el tipo genérico mediante una clase anónima para pasárselo al método map():


import java.lang.reflect.Type;
import org.modelmapper.TypeToken;

List<Pet> petList = petService.findByAge(pAge);

Type listType = new TypeToken<List<PetDTO>>() {}.getType();
List<PetDTO> petDTOList = mapper.map(petList, listType);

Personalización Avanzada del Mapeo

Cuando los nombres de los atributos entre la entidad y el DTO son completamente diferentes, cuando se quiere ignorar un campo concreto, o cuando hace falta transformar el tipo de dato (por ejemplo, convertir un byte[] a Base64 o calcular un valor), ModelMapper proporciona las siguientes herramientas:

  • TypeMap: Interfaz ubicada en el paquete org.modelmapper.TypeMap. Representa la relación de mapeo específica entre un tipo de origen <S> y un tipo de destino <D>. Se crea u obtiene llamando a mapper.createTypeMap(Origen.class, Destino.class) o mapper.typeMap(Origen.class, Destino.class) y permite añadir reglas mediante expresiones lambda con addMappings():
    • mapper.map(getterOrigen, setterDestino): Vincula explícitamente un campo de origen con uno de destino aunque se llamen distinto.
    • mapper.skip(setterDestino): Indica que un atributo concreto de la clase destino nunca debe ser modificado durante el mapeo (por ejemplo, ignorar el campo id o una contraseña).
  • PropertyMap: Clase abstracta ubicada en el paquete org.modelmapper.PropertyMap. Permite definir un conjunto de reglas de mapeo dentro de su método configure() utilizando los objetos protegidos source y destination, y registrarlo en el mapeador mediante mapper.addMappings(new PropertyMap<S, D>() { ... }).
  • Converter y AbstractConverter: Ubicados en el paquete org.modelmapper.Converter y org.modelmapper.AbstractConverter. Permiten programar lógica de transformación a medida entre un tipo de dato S y un tipo de dato D (por ejemplo, convertir una imagen byte[] a un String codificado en Base64 o transformar una fecha).
  • Condition y Conditions: Ubicados en el paquete org.modelmapper.Condition y org.modelmapper.Conditions. Permiten establecer una condición booleana que debe cumplirse sobre el contexto de mapeo (MappingContext) para que el atributo se copie (por ejemplo, Conditions.isNotNull() o comprobar que un String no esté vacío).

Ejemplo completo de personalización con TypeMap, Converter y skip

En el siguiente ejemplo se configura un TypeMap entre la entidad Pet y un DTO de resumen PetSummaryDTO donde:

  • El atributo name de Pet se mapea al atributo petFullName del DTO (que tiene un nombre distinto).
  • El atributo internalCode del destino se ignora explícitamente con skip().
  • El array de bytes picture de la mascota se transforma automáticamente a un texto en Base64 mediante un Converter personalizado.

import java.util.Base64;
import org.modelmapper.Converter;
import org.modelmapper.ModelMapper;
import org.modelmapper.TypeMap;

// 1. Definición de un Converter personalizado de byte[] a String Base64
Converter<byte[], String> bytesToBase64Converter = context -> {
	if (context.getSource() == null) 
	{
		return null;
	}
	return Base64.getEncoder().encodeToString(context.getSource());
};

// 2. Creación del TypeMap entre Pet y PetSummaryDTO
TypeMap<Pet, PetSummaryDTO> typeMap = mapper.createTypeMap(Pet.class, PetSummaryDTO.class);

// 3. Registro de reglas personalizadas mediante expresiones lambda
typeMap.addMappings(mapping -> {
	// Mapear campos con nombres distintos
	mapping.map(Pet::getName, PetSummaryDTO::setPetFullName);

	// Ignorar un campo concreto en el destino
	mapping.skip(PetSummaryDTO::setInternalCode);

	// Aplicar el conversor personalizado al campo picture
	mapping.using(bytesToBase64Converter)
			.map(Pet::getPicture, PetSummaryDTO::setPictureBase64);
});

// 4. Validación opcional para comprobar que ningún campo del destino quedó sin mapear por error
mapper.validate();

¿Cuándo usar cada herramienta de personalización y cuándo NO usarla?

  • Mapeo automático (map() sin configuración): Cuando los atributos de ambas clases se llaman igual. No usarlo si los nombres difieren: o queda sin mapear o se mapea mal.
  • TypeMap / PropertyMap: Cuando hay nombres distintos o campos que ignorar. No usarlos para una conversión que solo ocurre una vez: un método manual es más claro.
  • Converter: Cuando hay que transformar el tipo (byte[] a Base64, fechas). No meter lógica de negocio dentro del conversor.
  • TypeToken o Stream: Para listas. Se prefiere Stream por legibilidad; TypeToken solo si se quiere una única llamada.

Ejemplo y Contraejemplo: Actualizaciones parciales (HTTP PATCH)

Contraejemplo (Mala práctica): Usar el mapper estándar o crear una instancia nueva en un PATCH

En una petición PATCH /petshop/pet/15, el cliente envía un JSON únicamente con el campo que desea cambiar (por ejemplo, {"age": 5}), por lo que en el objeto recibido PetPatchDTO el resto de atributos (name, birthDate, picture) valdrán null. Si usamos el mapper normal (que tiene skipNullEnabled = false), ModelMapper copiará esos valores null encima de la entidad Pet y borrará el nombre y la foto que la mascota ya tenía en la base de datos:


// CONTRAEJEMPLO (INCORRECTO): Como skipNullEnabled es false en el mapper normal,
// los campos no enviados en el JSON (que vienen a null en pPetPatchDTO) machacarán con null los datos en BD
@PatchMapping("/{id}")
public ResponseEntity<HttpStatus> patchBad(
		@PathVariable("id") final Integer pId,
		@RequestBody final PetPatchDTO pPetPatchDTO) 
{
	Pet pet = petService.findById(pId).orElseThrow();

	// ¡Error grave! Si pPetPatchDTO.getName() es null, pet.getName() pasará a ser null
	mapper.map(pPetPatchDTO, pet);
	petService.save(pet);

	return new ResponseEntity<>(HttpStatus.NO_CONTENT);
}

Ejemplo (Buena práctica): Usar patchMapper con setSkipNullEnabled(true) sobre la entidad recuperada

Al utilizar el bean patchMapper (configurado con setSkipNullEnabled(true) y MatchingStrategies.STRICT) pasando como segundo argumento la instancia pet recuperada de base de datos, solo se modifican los campos que el usuario envió en el JSON y el resto conserva su valor original:


// EJEMPLO (CORRECTO): patchMapper ignora los campos null de pPetPatchDTO y conserva los datos previos de pet
@PatchMapping("/{id}")
public ResponseEntity<HttpStatus> patchGood(
		@PathVariable("id") final Integer pId,
		@Valid @RequestBody final PetPatchDTO pPetPatchDTO) 
{
	Pet pet = petService.findById(pId).orElseThrow();

	// Solo actualiza los campos que NO son null en pPetPatchDTO
	patchMapper.map(pPetPatchDTO, pet);
	petService.save(pet);

	return new ResponseEntity<>(HttpStatus.NO_CONTENT);
}
