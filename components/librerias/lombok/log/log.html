Log

En cualquier aplicación empresarial en Java o Spring Boot es imprescindible registrar eventos, trazas de depuración y errores mediante un sistema de logging. Tradicionalmente, esto obliga a declarar al inicio de cada clase una constante estática indicando explícitamente el nombre de la clase actual (por ejemplo, private static final Logger LOGGER = LoggerFactory.getLogger(PetController.class);).

Además de ser código repetitivo, declarar el logger manualmente suele provocar errores de copia y pega cuando un desarrollador copia la línea de una clase a otra y olvida actualizar el parámetro OtraClase.class, haciendo que las trazas aparezcan en los ficheros de log asociadas a una clase equivocada.

Project Lombok soluciona este problema mediante un conjunto de anotaciones en los subpaquetes de lombok.extern.* que generan automáticamente la constante estática llamada log (en minúsculas) lista para ser utilizada en cualquier método de la clase.

Anotaciones de Logging en Lombok

Dependiendo de la librería de registro que utilice el proyecto, se debe elegir la anotación correspondiente colocándola sobre la declaración de la clase:

  • @Slf4j: Esta anotación pertenece a la librería Project Lombok, se encuentra dentro del paquete lombok.extern.slf4j.Slf4j y genera un logger de SLF4J (Simple Logging Facade for Java).
    Es la anotación más utilizada en proyectos con Spring Boot, ya que Spring Boot incluye SLF4J con Logback por defecto dentro de spring-boot-starter-web y spring-boot-starter-logging sin necesidad de añadir dependencias adicionales.
  • @Log4j2: Esta anotación pertenece a la librería Project Lombok, se encuentra dentro del paquete lombok.extern.log4j.Log4j2 y genera un logger nativo de Apache Log4j 2 utilizando org.apache.logging.log4j.LogManager.
  • @Log: Esta anotación pertenece a la librería Project Lombok, se encuentra dentro del paquete lombok.extern.java.Log y genera un logger del sistema estándar incluido en el propio JDK de Java (java.util.logging.Logger), por lo que no requiere ninguna librería externa de logging.
  • @CommonsLog: Esta anotación pertenece a la librería Project Lombok, se encuentra dentro del paquete lombok.extern.apachecommons.CommonsLog y genera un logger de Apache Commons Logging.
  • @JBossLog: Esta anotación pertenece a la librería Project Lombok, se encuentra dentro del paquete lombok.extern.jbosslog.JBossLog y genera un logger de JBoss Logging (habitual en entornos WildFly, Hibernate o Quarkus).
  • @Flogger: Esta anotación pertenece a la librería Project Lombok, se encuentra dentro del paquete lombok.extern.flogger.Flogger y genera una instancia de Google Fluent Logger.

Parámetro topic

Todas las anotaciones de log anteriores (excepto @Flogger) admiten el parámetro opcional topic:

  • topic: Recibe un String con el nombre personalizado del logger. Por defecto, el logger toma como identificador el nombre completo de la clase donde se ubica (NombreClase.class). Si se especifica por ejemplo @Slf4j(topic = "AuditoriaMascotas"), Lombok inicializará el logger con esa cadena de texto (LoggerFactory.getLogger("AuditoriaMascotas")), permitiendo agrupar las trazas de distintas clases bajo un mismo canal o fichero de log configurado en logback-spring.xml.

Ejemplo práctico en Spring Boot (@Slf4j)

A continuación se compara un controlador y servicio de la tienda de mascotas escrito en Java estándar frente al uso de @Slf4j junto con @RequiredArgsConstructor. Con SLF4J se recomienda utilizar siempre los marcadores de posición {} (placeholders) en lugar de concatenar cadenas con +, ya que así solo se evalúa y construye el texto si el nivel de log correspondiente está activo:

Vanilla Java:


import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;
import java.util.Optional;

@Service
public class PetService {

    private static final Logger log = LoggerFactory.getLogger(PetService.class);

    private final PetRepository petRepository;

    public PetService(PetRepository petRepository) {
        this.petRepository = petRepository;
    }

    public Optional<Pet> findById(Integer id) {
        log.debug("Buscando mascota con id {}", id);
        Optional<Pet> pet = petRepository.findById(id);
        if (pet.isEmpty()) {
            log.warn("No se ha encontrado ninguna mascota con id {}", id);
        }
        return pet;
    }
}

Con Lombok (@Slf4j y @RequiredArgsConstructor):


import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Service;
import java.util.Optional;

@Slf4j
@Service
@RequiredArgsConstructor
public class PetService {

    private final PetRepository petRepository;

    public Optional<Pet> findById(Integer id) {
        // La variable estática 'log' está disponible automáticamente
        log.debug("Buscando mascota con id {}", id);
        Optional<Pet> pet = petRepository.findById(id);
        if (pet.isEmpty()) {
            log.warn("No se ha encontrado ninguna mascota con id {}", id);
        }
        return pet;
    }

    public Pet save(Pet pet) {
        try {
            Pet savedPet = petRepository.save(pet);
            log.info("Mascota guardada correctamente con id {}", savedPet.getId());
            return savedPet;
        } catch (Exception e) {
            log.error("Error al guardar la mascota {}: {}", pet.getName(), e.getMessage(), e);
            throw e;
        }
    }
}

¿Cuándo usar @Slf4j y cuándo NO usarlo?

  • Cuándo usarlo: En todos los controladores, servicios, consumidores de colas y componentes de negocio donde se necesite registrar actividad o errores sin ensuciar la clase con la línea de declaración de LoggerFactory.
  • Cuándo NO usarlo (Malas prácticas de Logging):
    • No concatenar Strings con + dentro del log: Concatenar log.debug("Mascota: " + pet.toString()) evalúa el método toString() y reserva memoria en el Heap incluso cuando el nivel DEBUG está desactivado en producción. Siempre deben usarse placeholders {}.
    • No hacer Log and Throw repetido en cada capa: Si el repositorio hace log.error y relanza la excepción, el servicio hace log.error y la relanza, y el controlador también la registra, la misma traza de pila aparecerá triplicada en los logs dificultando el diagnóstico.
