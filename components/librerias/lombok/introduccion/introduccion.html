Introducción

Project Lombok es una librería de Java que se integra de forma automática en el editor (IDE) y en las herramientas de construcción (Maven, Gradle) para eliminar el código repetitivo (conocido como boilerplate code) típico de las clases Java.

En el desarrollo tradicional con Java, al crear modelos de datos, entidades JPA, DTOs o servicios, es habitual escribir decenas o cientos de líneas de código rutinario: métodos get y set para cada atributo, múltiples constructores, implementaciones de toString(), equals() y hashCode(), patrones de diseño como Builder o la declaración manual de instancias de Logger en cada clase. Esto ensucia el código fuente y dificulta su lectura y mantenimiento.

Lombok resuelve este problema mediante el uso de anotaciones. Al anotar una clase o sus atributos, Lombok genera automáticamente todo ese código repetitivo sin que tengamos que escribirlo ni mantenerlo manualmente en el archivo .java.

¿Cómo funciona internamente?

A diferencia de otros frameworks que utilizan reflexión en tiempo de ejecución (lo que penaliza el rendimiento), Lombok actúa exclusivamente en tiempo de compilación:

  • Utiliza la API de procesamiento de anotaciones de Java (JSR 269 - Pluggable Annotation Processing API).
  • Cuando el compilador (javac) analiza el código fuente y construye el Árbol de Sintaxis Abstracta (AST - Abstract Syntax Tree), el procesador de Lombok intercepta ese árbol en memoria e inyecta directamente los nuevos nodos (métodos getters, setters, constructores, loggers, etc.).
  • Posteriormente, el compilador genera el archivo de bytecode (.class) final como si el programador hubiera escrito todos esos métodos a mano.
  • Coste cero en tiempo de ejecución: Como el código ya queda compilado de forma nativa dentro del archivo .class, no existe ninguna penalización de rendimiento en ejecución ni es necesario empaquetar el JAR de Lombok en producción.

Para que el entorno de desarrollo (IntelliJ IDEA, Eclipse, Spring Tool Suite o VS Code) reconozca los métodos generados mientras se escribe código sin marcar errores de compilación, es necesario tener instalado el plugin oficial de Lombok en el IDE (en las versiones recientes de IntelliJ IDEA ya viene integrado de serie).

Dependencias necesarias

Dado que Lombok solo actúa durante la fase de compilación del proyecto, la dependencia org.projectlombok:lombok se configura con ámbito de compilación (provided en Maven o compileOnly en Gradle) junto con el procesador de anotaciones correspondiente.

Maven en un proyecto Java estándar (pom.xml)

En un proyecto Maven estándar se declara la dependencia con <scope>provided</scope> y se registra como procesador de anotaciones en el maven-compiler-plugin:


<dependencies>
    <dependency>
        <groupId>org.projectlombok</groupId>
        <artifactId>lombok</artifactId>
        <version>1.18.30</version>
        <scope>provided</scope>
    </dependency>
</dependencies>

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>3.11.0</version>
            <configuration>
                <annotationProcessorPaths>
                    <path>
                        <groupId>org.projectlombok</groupId>
                        <artifactId>lombok</artifactId>
                        <version>1.18.30</version>
                    </path>
                </annotationProcessorPaths>
            </configuration>
        </plugin>
    </plugins>
</build>

Maven en un proyecto Spring Boot (pom.xml)

Si el proyecto utiliza el padre spring-boot-starter-parent, Spring Boot ya gestiona automáticamente la versión compatible de Lombok, por lo que basta con añadir la dependencia marcándola como <optional>true</optional>:


<dependency>
    <groupId>org.projectlombok</groupId>
    <artifactId>lombok</artifactId>
    <optional>true</optional>
</dependency>

Gradle (build.gradle)

En proyectos con Gradle se debe añadir tanto en compileOnly como en annotationProcessor (y sus equivalentes de test si se utilizan anotaciones de Lombok dentro de las clases de pruebas):


dependencies {
    compileOnly 'org.projectlombok:lombok:1.18.30'
    annotationProcessor 'org.projectlombok:lombok:1.18.30'

    testCompileOnly 'org.projectlombok:lombok:1.18.30'
    testAnnotationProcessor 'org.projectlombok:lombok:1.18.30'
}

Resumen de las principales anotaciones de Lombok

En la siguiente tabla se resumen las anotaciones más utilizadas de la librería junto con el paquete donde se encuentran y el código que generan en tiempo de compilación:

Anotación Paquete Propósito y código generado
@Getter / @Setter lombok.Getter / lombok.Setter Genera los métodos de lectura (getCampo() / isCampo()) y escritura (setCampo(...)) para los atributos de la clase.
@NoArgsConstructor lombok.NoArgsConstructor Genera un constructor vacío (sin parámetros).
@AllArgsConstructor lombok.AllArgsConstructor Genera un constructor que recibe un parámetro por cada atributo definido en la clase.
@RequiredArgsConstructor lombok.RequiredArgsConstructor Genera un constructor exclusivamente para los atributos obligatorios (declarados como final o anotados con @NonNull). Muy utilizado para inyección de dependencias en Spring Boot.
@ToString lombok.ToString Genera una implementación legible del método toString() mostrando el nombre de la clase y el valor de sus atributos.
@EqualsAndHashCode lombok.EqualsAndHashCode Genera las implementaciones de los métodos equals(Object) y hashCode() cumpliendo el contrato oficial de Java.
@Data lombok.Data Anotación envolvente que combina @Getter, @Setter, @ToString, @EqualsAndHashCode y @RequiredArgsConstructor en una sola línea.
@Value lombok.Value Variante inmutable de @Data: convierte la clase y todos sus campos en final y no genera métodos setter.
@Builder / @SuperBuilder lombok.Builder / lombok.experimental.SuperBuilder Implementa el patrón de diseño creacional Builder para instanciar objetos de forma fluida y segura (incluyendo soporte de herencia con @SuperBuilder).
@Accessors lombok.experimental.Accessors Personaliza la generación de getters y setters (por ejemplo, encadenamiento de setters con chain = true o estilo fluido sin prefijos con fluent = true).
@Slf4j / @Log4j2 / @Log lombok.extern.* Genera automáticamente la constante estática log del framework de registro correspondiente.
@NonNull lombok.NonNull Genera una comprobación automática de nulidad (lanzando NullPointerException si el valor recibido es null) en métodos y constructores.

¿Cuándo usar Project Lombok y cuándo NO usarlo?

Escenario ¿Cuándo SÍ usarlo? (Recomendado) ¿Cuándo NO usarlo? (Desaconsejado / Alternativas)
DTOs y Modelos de Petición/Respuesta Ideal usar @Data, @Builder y @Accessors(chain = true) para mapear JSONs limpiamente sin escribir decenas de getters y setters. En proyectos con Java 16 o superior donde el DTO sea puramente inmutable y no requiera herencia ni setters, es preferible usar un record nativo de Java en lugar de @Value.
Servicios, Controladores y Componentes de Spring Muy recomendable combinar @RequiredArgsConstructor (para inyección de dependencias por constructor en campos private final) y @Slf4j (para trazas de log). Cuando el constructor requiere lógica de inicialización personalizada compleja o cuando es necesario desambiguar múltiples beans del mismo tipo con @Qualifier sin configuración adicional de Lombok.
Entidades de Base de Datos (JPA / Hibernate) Usar de forma selectiva únicamente @Getter, @Setter y @NoArgsConstructor, controlando manualmente qué campos entran en equals y toString. Nunca usar @Data ni @Value a ciegas sobre una @Entity JPA: genera equals/hashCode sobre campos mutables y toString() sobre relaciones perezosas (LAZY), provocando LazyInitializationException o StackOverflowError.

Ejemplo y Contraejemplo: Uso de Lombok en Entidades y DTOs

Contraejemplo (Mala práctica): Usar @Data y @Builder sin control en una Entidad JPA

Uno de los errores más frecuentes al empezar con Lombok es colocar @Data y @Builder directamente sobre una entidad JPA con relaciones bidireccionales. Este código tiene tres fallos graves:

  1. Al poner @Builder sin constructores explícitos, Lombok solo genera un constructor con todos los argumentos y elimina el constructor vacío, por lo que Hibernate y Jackson lanzarán una excepción de instanciación al intentar leer de la base de datos o deserializar un JSON.
  2. El @ToString y @EqualsAndHashCode incluidos dentro de @Data recorrerán la lista pets de Owner, y cada Pet volverá a imprimir a su Owner, provocando un bucle infinito (StackOverflowError).
  3. Si la relación es FetchType.LAZY, invocar toString() fuera de una transacción disparará una LazyInitializationException.

// CONTRAEJEMPLO (INCORRECTO): Provoca StackOverflowError y fallo por falta de constructor vacío
@Data
@Builder
@Entity
public class Pet {
    @Id
    private Integer id;
    private String name;

    @ManyToOne(fetch = FetchType.LAZY)
    private Owner owner; // Ciclo infinito si Owner también tiene @Data y List<Pet>
}

Ejemplo (Buena práctica): Configuración segura y explícita con Lombok

La forma correcta consiste en usar @Data (junto con @NoArgsConstructor y @AllArgsConstructor si se usa @Builder) en los DTOs, mientras que en las Entidades JPA se emplean @Getter y @Setter por separado, excluyendo las relaciones perezosas de @ToString y basando la igualdad únicamente en la clave primaria (@Id):


// EJEMPLO (CORRECTO): Entidad JPA segura, compatible con Hibernate y Jackson
import lombok.AllArgsConstructor;
import lombok.Builder;
import lombok.EqualsAndHashCode;
import lombok.Getter;
import lombok.NoArgsConstructor;
import lombok.Setter;
import lombok.ToString;

@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
@ToString
@EqualsAndHashCode(onlyExplicitlyIncluded = true)
@Entity
public class Pet {

    @Id
    @EqualsAndHashCode.Include
    private Integer id;

    private String name;
    private Short age;

    // Se excluye la relación LAZY del toString() para evitar bucles infinitos y consultas no deseadas
    @ToString.Exclude
    @ManyToOne(fetch = FetchType.LAZY)
    private Owner owner;
}
