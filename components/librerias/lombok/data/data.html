Data

@Data es la anotación de acceso directo que agrupa las características de @ToString, @EqualsAndHashCode, @Getter / @Setter y @RequiredArgsConstructor juntas: en otras palabras, @Data genera todos los estándares que normalmente se asocian con POJOs y beans:

  • Getters para todos los campos.
  • Setters para todos los campos no finales y las implementaciones toString.
  • equals y hashCode que involucran los campos de la clase.
  • Un constructor que inicializa todos los campos finales.
  • Así como todos los campos no finales sin inicializador que hayan sido marcados con @NonNull, para garantizar que el campo nunca sea nulo.

Detalle de la anotación @Data

  • @Data: Esta anotación pertenece a la librería Project Lombok, se encuentra dentro del paquete lombok.Data y se coloca exclusivamente a nivel de clase. Anotar una clase con @Data es funcionalmente equivalente a anotarla con las siguientes cinco anotaciones simultáneamente:
    • @Getter (lombok.Getter): Genera los métodos getCampo() (o isCampo() para booleanos primitivos) de todos los atributos no estáticos.
    • @Setter (lombok.Setter): Genera los métodos setCampo(...) de todos los atributos no estáticos que no sean final.
    • @RequiredArgsConstructor (lombok.RequiredArgsConstructor): Genera un constructor con los campos obligatorios (final o @NonNull sin valor inicial). Si la clase no tiene ningún campo obligatorio ni otros constructores explícitos, el constructor resultante será un constructor vacío sin argumentos.
    • @ToString (lombok.ToString): Genera el método toString() incluyendo todos los atributos no estáticos.
    • @EqualsAndHashCode (lombok.EqualsAndHashCode): Genera los métodos equals(Object) y hashCode() evaluando todos los atributos no estáticos ni transitorios.

Parámetros y personalización de @Data

  • staticConstructor: Es el único parámetro directo que recibe @Data (por defecto ""). Si se especifica un nombre, como por ejemplo @Data(staticConstructor = "of"), el constructor generado por @RequiredArgsConstructor pasa a ser private y se crea un método factoría estático público con ese nombre (por ejemplo, PetDTO.of(...)) que devuelve una nueva instancia de la clase.
  • Sobrescritura de comportamientos individuales: Aunque @Data no expone directamente todos los parámetros de las anotaciones que engloba (como callSuper o includeFieldNames), es totalmente válido añadir explícitamente cualquiera de esas anotaciones sobre la clase o sobre un atributo para afinar su comportamiento. Por ejemplo:
    • Colocar @Setter(AccessLevel.NONE) sobre un atributo concreto dentro de una clase @Data evitará que se genere el setter de ese atributo.
    • Añadir @EqualsAndHashCode(callSuper = true) o @ToString(onlyExplicitlyIncluded = true) junto a @Data en la cabecera de la clase aplicará esa configuración específica sin perder el resto de ventajas de @Data.
  • Combinación con @Accessors y @Builder:
    • En DTOs es muy habitual combinar @Data con @Accessors(chain = true) para permitir el encadenamiento de métodos set.
    • Precaución al combinar @Data con @Builder: Cuando se añade @Builder a una clase sin constructores explícitos, @Builder genera internamente un constructor con todos los argumentos de visibilidad de paquete, lo cual anula el constructor vacío que generaría @Data. Si la clase va a ser deserializada por librerías como Jackson (en un controlador REST) o gestionada por JPA/Hibernate, es necesario añadir explícitamente @NoArgsConstructor y @AllArgsConstructor junto a @Data y @Builder.

Ejemplos prácticos con @Data

1. Uso de @Data en un DTO de Spring Boot (PetDTO)

En el siguiente ejemplo se define la clase PetDTO combinando @Data y @Accessors(chain = true). Con solo dos anotaciones de Lombok, la clase dispone de todos los getters, setters encadenables, constructor vacío, equals, hashCode y toString listos para trabajar con Jackson y Spring Validation:


import com.fasterxml.jackson.annotation.JsonInclude;
import com.fasterxml.jackson.annotation.JsonProperty;
import lombok.Data;
import lombok.experimental.Accessors;

@Data
@Accessors(chain = true)
@JsonInclude(JsonInclude.Include.NON_EMPTY)
public class PetDTO {

    @JsonProperty("petId")
    private Integer id;

    @JsonProperty("petName")
    private String name;

    @JsonProperty("age")
    private Short age;
}

2. Uso de staticConstructor en @Data

Si una clase tiene campos obligatorios (declarados como final o anotados con @NonNull) y utilizamos el parámetro staticConstructor = "of", podemos instanciar objetos de forma muy concisa mediante su método factoría estático:


import lombok.Data;
import lombok.NonNull;

@Data(staticConstructor = "of")
public class PetSummary {

    private final Integer id;

    @NonNull
    private String name;

    private Short age;
}

// Instanciación mediante el método factoría estático generado:
PetSummary summary = PetSummary.of(1, "Joe");
summary.setAge((short) 4);

Variante inmutable: @Value

Cuando se necesita diseñar objetos de transferencia o de dominio completamente inmutables, Lombok ofrece la anotación @Value:

  • @Value: Pertenece a la librería Project Lombok y se encuentra dentro del paquete lombok.Value (no debe confundirse con @Value de Spring Framework para inyectar propiedades). Es la variante inmutable de @Data:
    • Convierte automáticamente la clase en final (no se puede heredar de ella).
    • Convierte automáticamente todos los atributos no estáticos en private final (salvo que un atributo concreto se anote con @NonFinal del paquete lombok.experimental.NonFinal).
    • Genera un constructor público con todos los argumentos (equivalente a @AllArgsConstructor).
    • Genera métodos @Getter, @ToString y @EqualsAndHashCode, pero no genera ningún método setter.

import lombok.Value;

@Value
public class ImmutablePet {
    Integer id;
    String name;
    Short age;
}

// Todos los campos son private final y se inicializan por constructor:
ImmutablePet pet = new ImmutablePet(1, "Joe", (short) 2);
String petName = pet.getName();

¿Cuándo usar @Data y cuándo NO usarlo?

  • Cuándo usarlo: En DTOs (como PetDTO o PetPatchDTO), objetos de configuración, comandos de petición/respuesta o POJOs simples en memoria que no tienen ciclo de vida gestionado por un ORM ni relaciones circulares.
  • Cuándo NO usarlo:
    • En Entidades JPA / Hibernate (@Entity): Porque @Data genera hashCode() y equals() usando todos los campos mutables (lo que rompe las colecciones Set cuando Hibernate asigna el ID al persistir) y genera toString() sobre asociaciones @OneToMany / @ManyToOne. En entidades usa siempre @Getter y @Setter.
    • En clases con herencia sin configurar callSuper: Por defecto el equals y hashCode generado por @Data ignora los atributos de la clase padre (callSuper = false), pudiendo considerar iguales dos objetos que tienen distinto ID en la superclase.

Ejemplo y Contraejemplo: Combinar @Data con @Builder para Jackson

Contraejemplo (Mala práctica): Poner solo @Data y @Builder en un DTO recibido por REST

Si anotamos un DTO únicamente con @Data y @Builder, el código compilará pero fallará en tiempo de ejecución cuando Spring Boot / Jackson intente convertir el JSON de una petición POST en un objeto PetDTO (lanzando InvalidDefinitionException: Cannot construct instance of PetDTO). Esto ocurre porque @Builder crea un constructor con todos los parámetros y desactiva el constructor vacío que Jackson necesita:


// CONTRAEJEMPLO (INCORRECTO): Jackson fallará al deserializar el JSON porque no existe constructor vacío
@Data
@Builder
public class PetDTO {
    private Integer id;
    private String name;
    private Short age;
}

Ejemplo (Buena práctica): Añadir @NoArgsConstructor y @AllArgsConstructor

Para que una clase tenga simultáneamente las ventajas de @Data, el patrón @Builder y el constructor vacío requerido por Jackson y ModelMapper, se deben declarar explícitamente los dos constructores:


// EJEMPLO (CORRECTO): Dispone de constructor vacío para Jackson y constructor completo para @Builder
@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class PetDTO {
    private Integer id;
    private String name;
    private Short age;
}
