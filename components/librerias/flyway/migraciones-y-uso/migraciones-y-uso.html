Migraciones SQL y Comandos de Flyway

Para que Flyway reconozca y ejecute los scripts en el orden adecuado, todos los archivos deben ubicarse dentro del directorio src/main/resources/db/migration/ y cumplir estrictamente su convención de nombres.

Estructura de Carpetas y Nomenclatura de Archivos

La estructura estándar en un proyecto Maven o Gradle con Spring Boot es la siguiente:


src/main/resources/
├── application.yml
└── db/
    └── migration/
        ├── V1__create_pet_table.sql
        ├── V2__insert_initial_pets.sql
        ├── V2.1__add_picture_columns_to_pet.sql
        └── R__create_pet_summary_view.sql

El patrón de nombre de cualquier archivo de migración se compone de: <Prefijo><Versión>__<Descripción>.sql. Es fundamental destacar que el separador entre la versión y la descripción son dos guiones bajos seguidos (__), mientras que dentro de la descripción se utiliza un único guion bajo (_) que Flyway transformará en espacios al guardarlo en la tabla de historial.

Tipos de Migraciones según su Prefijo

  • V - Migraciones Versionadas (Versioned Migrations): Son las migraciones más habituales. Representan un cambio evolutivo en el esquema o en los datos y se ejecutan una única vez en orden ascendente de versión. La versión puede ser un número entero (V1, V2), decimal (V1.1, V2.0.1) o una marca de tiempo (V202610221200). Una vez aplicadas, su contenido es inmutable.
  • R - Migraciones Repetibles (Repeatable Migrations): No llevan número de versión (su formato es R__<Descripción>.sql). Se ejecutan siempre después de todas las migraciones versionadas pendientes, y se vuelven a ejecutar automáticamente cada vez que cambia su checksum (es decir, cuando el desarrollador modifica el archivo). Son ideales para mantener actualizadas vistas (CREATE OR REPLACE VIEW), funciones o procedimientos almacenados.
  • U - Migraciones de Deshacer (Undo Migrations): Tienen el formato U<Versión>__<Descripción>.sql y contienen las sentencias inversas para revertir una migración versionada con el mismo número (disponibles en ediciones avanzadas de Flyway, aunque en entornos productivos se recomienda crear siempre una nueva migración hacia adelante, como V4__..., en lugar de deshacer versiones pasadas).
Tipo de Migración Prefijo Patrón de Nombre Cuándo se ejecuta Uso principal
Versionada V V1__create_pet_table.sql Una sola vez, por orden de versión. CREATE TABLE, ALTER TABLE, DROP, inserción de datos iniciales.
Repetible R R__vista_mascotas.sql Cada vez que cambia su contenido (checksum). CREATE OR REPLACE VIEW, procedimientos almacenados, triggers.
Undo (Deshacer) U U1__drop_pet_table.sql Solo al invocar explícitamente el comando undo. Revertir los cambios introducidos por la versión V equivalente.

Ejemplos Prácticos de Scripts SQL

1. Creación de la tabla inicial (V1__create_pet_table.sql)

Primer script que crea la tabla pet coincidiendo con los atributos básicos de la entidad Pet:


CREATE TABLE pet (
    id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    age SMALLINT NOT NULL,
    birth_date DATE NOT NULL
);

2. Inserción de datos maestros iniciales (V2__insert_initial_pets.sql)

Segundo script que puebla la tabla recién creada con registros de prueba o catálogo inicial:


INSERT INTO pet (id, name, age, birth_date) VALUES (1, 'Joe', 2, '2024-02-01');
INSERT INTO pet (id, name, age, birth_date) VALUES (2, 'Luna', 4, '2022-05-15');

3. Evolución del esquema en una versión posterior (V3__add_picture_columns_to_pet.sql)

Si más adelante el equipo añade soporte para guardar la foto de la mascota en PetDTO y Pet, nunca se modifica el archivo V1, sino que se añade un nuevo archivo V3 con el ALTER TABLE correspondiente:


ALTER TABLE pet
    ADD COLUMN picture BYTEA,
    ADD COLUMN picture_media_type VARCHAR(50);

Comandos Principales de Flyway

Tanto a través de su integración con Spring Boot como mediante el plugin de Maven (mvn flyway:<comando>) o Gradle (gradle flyway<Comando>), Flyway dispone de 6 operaciones fundamentales:

  • migrate: Escanea el classpath, valida las migraciones previas y aplica en orden todas las migraciones pendientes hasta dejar el esquema en la última versión. Es el comando que Spring Boot ejecuta automáticamente al arrancar.
  • info: Muestra una tabla detallada con el estado actual de todas las migraciones (cuáles ya están aplicadas, en qué fecha se instalaron y cuáles están pendientes de ejecución).
  • validate: Comprueba que los archivos de migración presentes en el proyecto coinciden exactamente en nombre y checksum con los registrados en la tabla flyway_schema_history de la base de datos.
  • baseline: Inicializa la tabla flyway_schema_history en una base de datos que ya contenía tablas antes de incorporar Flyway al proyecto, marcando el estado actual como versión base para no intentar recrear tablas existentes.
  • repair: Corrige problemas en la tabla flyway_schema_history, eliminando entradas de migraciones fallidas (en bases de datos sin transacciones DDL como MySQL) y realineando los checksums de las migraciones aplicadas con los archivos actuales del disco.
  • clean: Elimina todos los objetos (tablas, vistas, secuencias, procedimientos) del esquema configurado dejándolo completamente vacío. Es útil en entornos de test locales, pero nunca debe habilitarse en producción.

Migraciones Basadas en Java (BaseJavaMigration)

En ocasiones una migración no puede resolverse únicamente con SQL estático porque requiere leer datos, procesarlos con lógica de negocio en Java, cifrar valores o transformar blobs antes de volver a guardarlos. Para estos casos, Flyway proporciona la clase abstracta BaseJavaMigration en el paquete org.flywaydb.core.api.migration.BaseJavaMigration.

Basta con crear una clase dentro del paquete Java db.migration siguiendo la misma nomenclatura (por ejemplo, V4__EncryptPetNotes.java) e implementar el método migrate(Context context):


package db.migration;

import java.sql.PreparedStatement;
import org.flywaydb.core.api.migration.BaseJavaMigration;
import org.flywaydb.core.api.migration.Context;

public class V4__NormalizePetNames extends BaseJavaMigration 
{
	@Override
	public void migrate(Context context) throws Exception 
	{
		try (PreparedStatement statement = context.getConnection().prepareStatement(
				"UPDATE pet SET name = INITCAP(TRIM(name)) WHERE name IS NOT NULL")) 
		{
			statement.executeUpdate();
		}
	}
}

¿Cuándo usar cada tipo de migración y comando y cuándo NO usarlos?

  • Migración V: Para cualquier cambio de esquema o dato que debe ejecutarse una sola vez. No editarla tras aplicarla.
  • Migración R: Para vistas, funciones o procedimientos que se redefinen con CREATE OR REPLACE. No usarla para CREATE TABLE ni ALTER TABLE.
  • Migración Java (BaseJavaMigration): Cuando hace falta lógica que SQL no cubre bien. No usarla si un UPDATE en SQL lo resuelve.
  • baseline: Al incorporar Flyway a una base de datos que ya tenía tablas.
  • repair: Para corregir el historial tras un fallo o un cambio legítimo de checksum.
  • clean: Solo en entornos locales o de test. Nunca en producción.

Ejemplo y Contraejemplo: Evolución de Scripts en Flyway

Contraejemplo (Mala práctica): Editar un archivo V1__...sql que ya ha sido ejecutado

Una regla de oro en Flyway es que una migración versionada (V) ya aplicada en base de datos jamás se debe editar. Si un desarrollador abre el archivo V1__create_pet_table.sql que se ejecutó la semana pasada y le añade una columna nueva, el checksum CRC32 del archivo cambiará. Al arrancar el microservicio, Flyway detectará que el checksum del archivo en disco no coincide con el guardado en flyway_schema_history y abortará el arranque con una excepción FlywayValidateException: Migration checksum mismatch:


-- CONTRAEJEMPLO (INCORRECTO): Modificar V1__create_pet_table.sql después de que ya se ejecutó en BD
-- Provoca el error: Validate failed: Migration checksum mismatch for migration version 1
CREATE TABLE pet (
    id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    age SMALLINT NOT NULL,
    birth_date DATE NOT NULL,
    microchip_code VARCHAR(50) -- ¡Error! Nunca añadir columnas editando un script ya ejecutado
);

Ejemplo (Buena práctica): Crear un nuevo script incremental V4__...sql

Para añadir, modificar o eliminar cualquier columna o restricción de una tabla existente, el archivo V1__create_pet_table.sql se deja intacto y se crea un archivo nuevo con el siguiente número de versión disponible:


-- EJEMPLO (CORRECTO): Nuevo archivo V4__add_microchip_code_to_pet.sql
ALTER TABLE pet
    ADD COLUMN microchip_code VARCHAR(50) UNIQUE;
