Flyway - Control de Versiones de Base de Datos

Flyway es una herramienta de código abierto para la gestión y automatización de migraciones de bases de datos. Su objetivo es aplicar al esquema de la base de datos el mismo control de versiones que Git aplica al código fuente Java.

En proyectos donde trabajan varios desarrolladores o existen múltiples entornos (local, desarrollo, integración, preproducción y producción), modificar las tablas manualmente o depender de que Hibernate regenere el esquema automáticamente (ddl-auto=update) provoca inconsistencias graves. Con Flyway, cada cambio en la base de datos (creación de tablas, alteración de columnas, inserción de datos maestros) se escribe en un script SQL numerado secuencialmente que viaja dentro del repositorio junto al código de la aplicación.

¿Cómo funciona Flyway internamente?

Cuando arranca una aplicación con Flyway activado, ocurre el siguiente proceso automático:

  1. Flyway se conecta a la base de datos configurada en el proyecto y comprueba si existe su tabla de control interno llamada por defecto flyway_schema_history. Si la base de datos está vacía, crea esa tabla automáticamente.
  2. Escanea la carpeta del proyecto donde se alojan las migraciones (por defecto src/main/resources/db/migration) en busca de scripts SQL o clases Java de migración.
  3. Compara los scripts encontrados con los registros ya guardados en la tabla flyway_schema_history y valida su suma de comprobación (checksum CRC32). Si alguien ha modificado un script que ya se había ejecutado en el pasado, Flyway detiene el arranque lanzando un error de validación para proteger la integridad de la base de datos.
  4. Ordena las migraciones nuevas por su número de versión y las ejecuta una por una dentro de una transacción, registrando cada ejecución exitosa en flyway_schema_history.

Dependencias necesarias

Para integrar Flyway en un proyecto Spring Boot o Java estándar se requiere la dependencia principal flyway-core del grupo org.flywaydb. A partir de Flyway 9+ / Spring Boot 3+, algunos motores de base de datos como MySQL/MariaDB o PostgreSQL requieren además su módulo específico (como flyway-mysql o flyway-database-postgresql).

En Maven (pom.xml):


<dependencies>
	<!-- Dependencia principal de Flyway -->
	<dependency>
		<groupId>org.flywaydb</groupId>
		<artifactId>flyway-core</artifactId>
	</dependency>

	<!-- Opcional en versiones recientes si se usa MySQL / MariaDB -->
	<dependency>
		<groupId>org.flywaydb</groupId>
		<artifactId>flyway-mysql</artifactId>
	</dependency>
</dependencies>

<!-- Plugin opcional de Maven para ejecutar comandos mvn flyway:migrate por consola -->
<build>
	<plugins>
		<plugin>
			<groupId>org.flywaydb</groupId>
			<artifactId>flyway-maven-plugin</artifactId>
		</plugin>
	</plugins>
</build>

En Gradle (build.gradle):


plugins {
	id 'org.flywaydb.flyway' version '9.22.3'
}

dependencies {
	implementation 'org.flywaydb:flyway-core'
	implementation 'org.flywaydb:flyway-mysql'
}

Configuración en Spring Boot

En Spring Boot, el mero hecho de incluir flyway-core en las dependencias activa la autoconfiguración de Flyway al iniciar la aplicación, ejecutándose justo antes de que se inicialice el EntityManagerFactory de JPA/Hibernate. Su comportamiento se personaliza desde application.properties o application.yml mediante el prefijo spring.flyway.*:

  • spring.flyway.enabled: Activa (true, valor por defecto) o desactiva (false) la ejecución automática de Flyway al arrancar la aplicación.
  • spring.flyway.locations: Indica la ruta o rutas donde Flyway buscará los archivos de migración. Por defecto es classpath:db/migration, pero permite separar scripts según el motor de base de datos usando el comodín {vendor} (por ejemplo, classpath:db/migration/{vendor}).
  • spring.flyway.baseline-on-migrate: Por defecto es false. Si se activa a true al conectarse a una base de datos que ya existía previamente y tenía tablas pero no tenía la tabla flyway_schema_history, Flyway crea la línea base inicial (por defecto en la versión 1) e aplica solo las migraciones superiores.
  • spring.flyway.validate-on-migrate: Por defecto es true. Verifica antes de migrar que los scripts ya ejecutados no hayan sido alterados comparando su checksum.
  • spring.flyway.table: Permite cambiar el nombre de la tabla de historial (por defecto flyway_schema_history).
  • spring.flyway.clean-disabled: Por seguridad, desde Flyway 9 su valor por defecto es true para impedir el borrado accidental de toda la base de datos mediante el comando clean.
  • spring.jpa.hibernate.ddl-auto: Cuando se gestiona la base de datos con Flyway, es una buena práctica obligatoria configurar Hibernate en modo validate (o none). Así Flyway es el único responsable de crear y modificar las tablas, mientras que Hibernate únicamente comprueba al arrancar que las entidades Java coinciden con las tablas creadas por Flyway.

Ejemplo de configuración en application.yml:


spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/petshop_db
    username: postgres
    password: secret
    driver-class-name: org.postgresql.Driver

  jpa:
    hibernate:
      # Hibernate solo valida el esquema creado por Flyway, nunca lo modifica por su cuenta
      ddl-auto: validate
    show-sql: true

  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: true
    validate-on-migrate: true
    clean-disabled: true

¿Cuándo usar Flyway y cuándo NO usarlo?

Escenario ¿Cuándo SÍ usarlo? (Recomendado) ¿Cuándo NO usarlo? (Desaconsejado / Alternativas)
Proyectos en Equipo y Producción En cualquier aplicación o microservicio con base de datos relacional que pase por entornos de desarrollo, integración y producción, garantizando que todos tengan exactamente el mismo esquema. En pruebas de concepto (PoC) rápidas o ejercicios académicos con base de datos en memoria H2 que se destruye al apagar la aplicación (donde basta con ddl-auto: create-drop).
Control del SQL Nativo Cuando el equipo prefiere escribir scripts SQL nativos claros y aprovechar características propias del motor (índices específicos, particiones, triggers en PostgreSQL/Oracle/MySQL). Si un proyecto corporativo exige definir los cambios de esquema en formato XML/YAML agnóstico al motor de base de datos para desplegar el mismo cambio en Oracle, SQL Server y PostgreSQL sin tocar SQL, en cuyo caso suele preferirse Liquibase.
Cuándo utilizar Flyway frente a otras alternativas

Ejemplo y Contraejemplo: Convivencia entre Flyway e Hibernate

Contraejemplo (Mala práctica): Usar Flyway dejando ddl-auto: update o create en Hibernate

Si activamos Flyway pero dejamos que Hibernate modifique las tablas por su cuenta con ddl-auto: update o create, se pierde todo el control del versionado: Hibernate creará o alterará columnas automáticamente basándose en las clases @Entity sin que queden registradas en ningún script de db/migration, o borrará las tablas creadas por Flyway al arrancar:


# CONTRAEJEMPLO (INCORRECTO): Hibernate modificará las tablas a espaldas de Flyway
spring:
  jpa:
    hibernate:
      ddl-auto: update # ¡Peligro! Desincroniza el esquema real respecto a los scripts de Flyway
  flyway:
    enabled: true
    clean-disabled: false # ¡Peligro crítico! Permite que un comando clean borre toda la base de datos

Ejemplo (Buena práctica): Flyway crea el esquema e Hibernate solo lo valida (ddl-auto: validate)

En una configuración profesional, Flyway es el único dueño del esquema DDL y a Hibernate se le asigna ddl-auto: validate. Así, si un desarrollador añade un campo en la clase Java Pet pero olvida crear el script V4__...sql en Flyway, la aplicación fallará inmediatamente al arrancar avisando de la discrepancia:


# EJEMPLO (CORRECTO): Flyway aplica los scripts SQL e Hibernate verifica que las entidades coincidan
spring:
  jpa:
    hibernate:
      ddl-auto: validate
  flyway:
    enabled: true
    validate-on-migrate: true
    clean-disabled: true
