Guía Práctica de Comandos y Uso de Gradle desde Cero

En esta sección tienes un tutorial práctico paso a paso para usar Gradle desde el primer minuto y una tabla chuleta (Cheatsheet) con todos los comandos de consola que necesitarás en tu día a día.

1. Cómo Crear un Proyecto Gradle Nuevo desde Cero

Tienes dos formas principales de empezar un proyecto con Gradle:

  • Opción A — Desde interfaz gráfica o web (La más habitual):

    Si vas a crear un proyecto Java normal, abre IntelliJ IDEA → New Project → selecciona Build System: Gradle. Si vas a crear un microservicio con Spring Boot, entra en start.spring.io, elige Project: Gradle - Groovy, añade tus dependencias y pulsa Generate. En ambos casos el proyecto ya vendrá con la estructura de carpetas y el gradlew listos para usar.

  • Opción B — Desde la terminal con gradle init:

    Si tienes Gradle instalado en tu sistema y quieres inicializar un proyecto desde una carpeta vacía por consola, ejecuta el asistente interactivo:


$ mkdir mi-aplicacion && cd mi-aplicacion
$ gradle init

2. El Flujo de Trabajo Diario en 4 Comandos

Una vez estás dentro de la carpeta de cualquier proyecto Gradle, recuerda usar siempre ./gradlew (en Linux/Mac) o .\gradlew.bat (en Windows):


# 1. Descargar dependencias, compilar todo el código, pasar los tests y crear el .jar
./gradlew build

# 2. Compilar rápido y crear el .jar SALTÁNDOSE los tests (muy útil en local cuando tienes prisa)
./gradlew build -x test

# 3. Arrancar la aplicación en local (si usas el plugin 'application' o 'spring-boot')
./gradlew run        # Para aplicaciones Java normales
./gradlew bootRun    # Para aplicaciones Spring Boot

# 4. Borrar la carpeta build/ y recompilar todo limpio desde cero
./gradlew clean build
Los 4 comandos esenciales que usarás el 95% del tiempo

3. Chuleta Completa de Comandos de Gradle (Cheatsheet)

Comando en Terminal ¿Para qué sirve exactamente?
./gradlew tasks Muestra la lista de todas las tareas disponibles en tu proyecto (las de Java, las de Spring Boot y las tuyas propias).
./gradlew build Compila el código fuente, ejecuta todos los tests y empaqueta el archivo .jar o .war.
./gradlew clean Elimina la carpeta build/ para limpiar cualquier archivo compilado anterior.
./gradlew assemble Compila y genera el archivo .jar pero sin ejecutar los tests.
./gradlew test Ejecuta todas las pruebas unitarias y crea el reporte en build/reports/tests/test/index.html.
./gradlew test --tests "MiClaseTest" Ejecuta únicamente la clase o método de test que le indiques (ahorra muchísimo tiempo en proyectos grandes).
./gradlew dependencies Dibuja en la consola el árbol completo de librerías (incluyendo qué sub-librerías trae cada una y cómo se han resuelto los conflictos de versión).
./gradlew build -x test La opción -x <tarea> excluye (salta) la tarea indicada durante esa ejecución.
./gradlew build --refresh-dependencies Fuerza a Gradle a comprobar de nuevo en internet las librerías ignorando la caché local.
./gradlew build --info / --stacktrace Muestra logs detallados o la traza completa del error cuando algo falla al compilar.
./gradlew build --scan Genera un enlace web interactivo gratuito (Build Scan) con estadísticas visuales de cuánto ha tardado cada tarea y cada librería.
./gradlew --stop Detiene el proceso en segundo plano (Gradle Daemon) si quieres liberar memoria RAM en tu ordenador.

¿Cuándo Usar Flags Avanzados de Diagnóstico?

Flag Propósito ¿Cuándo conviene usarlo?
--scan Auditoría cloud visual de la compilación Cuando un build tarda demasiado y quieres ver qué tarea concreta consume los segundos.
--dry-run (o -m) Simulación del DAG sin ejecutar código Para comprobar qué tareas se ejecutarían y en qué orden sin compilar nada.
--no-daemon Apaga el proceso background tras finalizar Obligatorio en runners efímeros de CI/CD (Docker containers) para no dejar procesos zombi.
--parallel Compilación simultánea de módulos En proyectos multi-módulo para aprovechar todos los núcleos del procesador.

4. Preguntas Frecuentes cuando Empiezas con Gradle

  • "Acabo de añadir una librería en build.gradle, pero mi editor (IntelliJ / Eclipse) sigue marcando el import en rojo. ¿Qué hago?"

    En IntelliJ IDEA, cuando modificas el archivo build.gradle, aparece un pequeño icono flotante de un elefante con dos flechas en la esquina superior derecha del editor (Load Gradle Changes o atajo Ctrl + Shift + O). Púlsalo para que el IDE descargue la librería recién añadida y actualice el autocompletado.

  • "¿Cómo paso variables dinámicas a mi archivo application.yml durante la compilación?"

    Puedes configurar la tarea processResources para que reemplace variables automáticamente dentro de tus archivos de configuración:


processResources {
    filesMatching('application.yml') {
        expand(project.properties)
    }
}
Expansión automática de propiedades de Gradle dentro de application.yml

Ejemplo y Contraejemplo en el flujo de Integración Continua (CI/CD)

Ejemplo (Buena Práctica): Pipeline seguro con verificación completa


# En el runner de GitHub Actions / GitLab CI:
./gradlew --no-daemon check
Pasa todos los tests unitarios, de integración y análisis estático sin dejar demonios residentes

Contraejemplo (Mala Práctica): Saltar tests en pipelines con -x test


# ¡GRAVE ERROR en CI/CD! Genera el artefacto aunque los tests fallen
./gradlew bootJar -x test
Antipatrón: Despliega binarios corruptos o con regresiones en producción por ahorrar tiempo
