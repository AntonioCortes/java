Plugins Esenciales de Gradle (Java, Spring Boot, JaCoCo, Sonar, Flyway)

En Gradle, los Plugins son extensiones que le "enseñan" a Gradle nuevas habilidades. Sin plugins, Gradle es un lienzo en blanco; cada vez que añades una línea al bloque plugins { ... }, desbloqueas automáticamente nuevas tareas y nuevos bloques de configuración en tu proyecto.

Figura 1: Cómo los plugins inyectan nuevas tareas ejecutables dentro del motor de Gradle
Elemento del Diagrama Origen Aportación al Ciclo de Construcción
Motor Base de Gradle Core Engine Proporciona el ciclo de vida, resolución de dependencias y ejecución de tareas.
Plugin Java Core Plugin Inyecta el grafo de compilación Java estándar (compileJava, test, jar).
Plugin Spring Boot Comunidad (Spring) Agrega bootJar (empaquetado Fat JAR con Tomcat embebido) y bootRun.
Plugins de Calidad (JaCoCo / Sonar) Herramientas QA Calculan métricas de cobertura de tests e inspeccionan vulnerabilidades estáticas de código.

1. Plugins Oficiales Incluidos en Gradle (Core Plugins)

Estos plugins vienen integrados de fábrica dentro de Gradle, por lo que no necesitan número de versión al declararlos:

Plugin Declaración ¿Qué añade a tu proyecto?
Java id 'java' Compilación de src/main/java, ejecución de tests JUnit y generación de archivos .jar. Es la base de todo proyecto Java.
Application id 'application' Añade la tarea ./gradlew run para arrancar tu clase Main directamente y genera un ZIP/TAR instalable con scripts de inicio.
Java Library id 'java-library' Se usa cuando estás creando una librería para otros programadores. Habilita la palabra clave api además de implementation.
JaCoCo id 'jacoco' Mide qué porcentaje de las líneas de tu código Java están cubiertas por tus tests unitarios y genera un reporte web en colores verde/rojo.
Maven Publish id 'maven-publish' Permite subir y publicar el .jar de tu librería en el servidor privado de tu empresa (Nexus, Artifactory, GitHub Packages).
Eclipse / IDEA id 'eclipse' / id 'idea' Genera los archivos de configuración del proyecto para importarlo en los editores Eclipse o IntelliJ IDEA.

2. Plugins de Comunidad y Empresa (Spring Boot, SonarQube, Flyway, Avro)

Los plugins creados por terceros se descargan automáticamente del Gradle Plugin Portal y sí requieren indicar su versión:


plugins {
    id 'java'
    id 'jacoco'

    // 1. Plugins de Spring Boot y gestión automática de versiones de Spring
    id 'org.springframework.boot' version '3.3.4'
    id 'io.spring.dependency-management' version '1.1.6'

    // 2. Plugin de SonarQube para auditoría de calidad y seguridad de código
    id 'org.sonarqube' version '5.1.0.4882'

    // 3. Plugin de Flyway para ejecutar scripts SQL de migración de Base de Datos
    id 'org.flywaydb.flyway' version '10.18.0'

    // 4. Plugin de Apache Avro para autogenerar clases Java desde esquemas .avsc de Kafka
    id 'com.github.davidmc24.gradle.plugin.avro' version '1.9.1'
}

¿Qué hace exactamente el Plugin de Spring Boot (org.springframework.boot)?

Cuando trabajas con Spring Boot, este plugin transforma tu proyecto y te regala dos tareas fundamentales que usarás todos los días:

  • ./gradlew bootRun: Levanta tu microservicio o servidor web local directamente en tu ordenador sin tener que empaquetarlo antes.
  • ./gradlew bootJar: Por defecto en Java, un archivo .jar normal solo contiene tus clases, pero NO contiene las librerías externas (por lo que al llevarlo a otro servidor fallaría). La tarea bootJar crea un Fat JAR (JAR Ejecutable Autónomo) que mete dentro de un único archivo .jar tu código, el servidor Tomcat embebido y todas las librerías de Spring listas para arrancar con java -jar app.jar.

¿Cómo configurar JaCoCo para ver el Informe de Cobertura de tus Tests?

Al añadir id 'jacoco', puedes configurar en tu build.gradle que cada vez que pasen los tests se genere una página web en build/reports/coverage/index.html donde verás línea por línea qué partes de tu código han sido probadas:


jacocoTestReport {
    dependsOn test // Asegura que primero se ejecuten los tests antes de medir la cobertura
    reports {
        xml.required = true  // Necesario si luego envías los datos a SonarQube
        csv.required = false
        html.outputLocation = layout.buildDirectory.dir('reports/coverage')
    }
}
Configuración del reporte de cobertura de código con JaCoCo

Nota importante: plugins { id ... } vs el antiguo apply plugin:

Si abres proyectos de empresa creados hace unos años, es muy probable que veas dos formas distintas de aplicar plugins:

  • Forma moderna y recomendada: El bloque plugins { id 'java' } arriba del todo del archivo.
  • Forma antigua (Legacy): Un bloque buildscript { dependencies { classpath ... } } seguido más abajo de apply plugin: 'eclipse'. Sigue funcionando por compatibilidad, pero en proyectos nuevos debes usar siempre el bloque plugins { ... }.
  • Dividir configuración en varios archivos (apply from:): Cuando un build.gradle crece mucho, las empresas suelen separar la configuración de SonarQube o Artifactory en archivos aparte (por ejemplo, gradle/sonar.gradle) y los importan en el archivo principal escribiendo apply from: "gradle/sonar.gradle".

Ejemplo y Contraejemplo en el uso del plugin Spring Boot

Ejemplo (Buena Práctica): Dejar que bootJar genere el artefacto ejecutable


// Al aplicar el plugin de Spring Boot, la tarea jar estándar se deshabilita para evitar confusión
tasks.named('jar') {
    enabled = false
}
// bootJar genera el fat-jar completo con Tomcat y todas las dependencias
tasks.named('bootJar') {
    archiveFileName = 'pet-service.jar'
}
Despliegue unívoco de un único ejecutable Fat JAR

Contraejemplo (Mala Práctica): Usar el JAR estándar de java en lugar de bootJar

Si se fuerza la creación del jar normal sin el empaquetado de Spring Boot, el archivo solo contendrá tus clases y al intentar arrancarlo en un contenedor Docker con java -jar app.jar fallará inmediatamente:


java -jar build/libs/pet-service.jar
# Error fatal:
Error: A JNI error has occurred, please check your installation and try again
Exception in thread "main" java.lang.NoClassDefFoundError: org/springframework/boot/SpringApplication
Fallo en tiempo de ejecución por no empaquetar dependencias con bootJar
