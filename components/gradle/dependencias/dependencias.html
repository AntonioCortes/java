Cómo Añadir Librerías y Gestión de Dependencias

Añadir librerías externas es la tarea más habitual cuando trabajas con Gradle. Sin embargo, no todas las librerías se usan en el mismo momento: algunas las necesitas en todo momento, otras solo para compilar (como Lombok), otras solo al arrancar la base de datos (como el driver de PostgreSQL) y otras exclusivamente para los tests (como JUnit o Mockito).

1. ¿Dónde busco una librería y cómo sé qué texto poner?

Cualquier librería de Java en el mundo se identifica por tres datos separados por dos puntos ('grupo:artefacto:versión'), conocidos como coordenadas GAV (Group, Artifact, Version):

  1. Entra en el buscador mvnrepository.com o en Maven Central.
  2. Escribe el nombre de la librería que buscas (por ejemplo, Apache Commons Lang o Jackson Databind).
  3. Haz clic en la versión que quieras usar y selecciona la pestaña Gradle (Short).
  4. Copia esa línea y pégala dentro del bloque dependencies { ... } de tu archivo build.gradle.

2. Todas las Palabras Clave para Añadir Librerías (Explicadas)

En la siguiente tabla tienes todas las formas de declarar una dependencia en Gradle, qué significan y cómo equivalen a los antiguos nombres por si ves un proyecto viejo:

Configuración Actual Nombre Antiguo (Obsoleto) ¿Cuándo debes usarla? Ejemplo Típico
implementation compile El 90% de las veces. Cuando tu código en src/main/java importa clases de esa librería y además la necesita cuando el programa está en marcha. Spring Web, Jackson, Gson, Apache Commons, Hibernate.
compileOnly providedCompile Cuando la librería solo hace falta mientras se compila el código, pero no hace falta meterla en el .jar final porque ya ha hecho su trabajo al compilar. Lombok (genera getters/setters al compilar y luego ya no se necesita).
annotationProcessor (Se mezclaba con compile) Obligatorio añadirlo junto a compileOnly cuando una librería lee anotaciones (@Data, @Mapper) para autogenerar código Java durante la compilación. Lombok y MapStruct.
runtimeOnly runtime Cuando tu código Java no hace import directo de esa librería al compilar (porque usas interfaces estándar como JDBC o SLF4J), pero el programa la necesita al arrancar para conectarse. Drivers de Base de Datos (PostgreSQL, MySQL).
testImplementation testCompile Librerías que solo usas para escribir y ejecutar tus pruebas en src/test/java. Nunca se empaquetan en el archivo .jar de producción. JUnit 5, Mockito, RestAssured, H2 Database.
testRuntimeOnly testRuntime Motor interno necesario para lanzar los tests en ejecución, aunque no lo importes en tus clases de test. junit-platform-launcher.

¿Cuándo usar implementation vs api?

Al aplicar el plugin java-library, aparece la configuración api:

Configuración Fuga de Dependencia Impacto en Tiempos de Compilación ¿Cuándo usarla?
implementation NO: Oculta la librería. Quien dependa de este módulo no ve sus clases transitivas. Óptimo: Si cambias la librería interna, Gradle NO necesita recompilar los módulos consumidores. Por defecto siempre para cualquier dependencia interna de servicio o lógica.
api SÍ: Expone la librería transitivamente a cualquiera que importe este proyecto. Pesado: Cualquier cambio interno fuerza a Gradle a recompilar todo el grafo de proyectos hijos. Solo cuando tus propios métodos públicos devuelven o reciben clases de esa librería externa en su firma.

3. Ejemplos Prácticos de los Casos Más Habituales


dependencies {
    // CASO A: Librería normal que importamos en nuestras clases
    implementation 'org.apache.commons:commons-lang3:3.14.0'

    // CASO B: Configurar Lombok correctamente (necesita las 2 líneas)
    compileOnly 'org.projectlombok:lombok:1.18.34'
    annotationProcessor 'org.projectlombok:lombok:1.18.34'

    // CASO C: Driver de Base de Datos PostgreSQL (solo necesario al arrancar la app)
    runtimeOnly 'org.postgresql:postgresql:42.7.3'

    // CASO D: Librerías exclusivas para nuestros Tests Unitarios
    testImplementation 'org.junit.jupiter:junit-jupiter:5.10.2'
    testImplementation 'org.mockito:mockito-core:5.11.0'
    testRuntimeOnly 'org.junit.platform:junit-platform-launcher'

    // CASO E: Añadir un archivo .jar que tienes descargado en una carpeta 'libs/' de tu proyecto
    implementation files('libs/libreria-antigua-empresa.jar')
}

4. ¿Por qué algunas librerías NO llevan número de versión al final? (BOMs)

Si miras un proyecto de Spring Boot, verás que muchas dependencias se escriben sin número de versión al final, por ejemplo: implementation 'org.springframework.boot:spring-boot-starter-web'. ¿Cómo sabe Gradle qué versión descargar?

Porque se utiliza un BOM (Bill of Materials o Lista de Materiales). Al aplicar el plugin io.spring.dependency-management o usar platform(...), Gradle descarga un catálogo oficial que ya sabe qué versiones exactas de cientos de librerías son 100% compatibles entre sí:


dependencies {
    // 1. Importamos el catálogo (BOM) oficial de Spring Boot 3.3.4
    implementation platform('org.springframework.boot:spring-boot-dependencies:3.3.4')

    // 2. Ahora podemos pedir cualquier librería de Spring SIN poner la versión
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'
}
Uso de platform (BOM) para delegar las versiones compatibles automáticamente

5. Cómo Excluir una Sub-Librería que da Conflicto (exclude)

A veces añades una librería (por ejemplo, de Kafka) que internamente trae una librería antigua de logs (slf4j-log4j12) que choca con el sistema de logs de Spring Boot. Para decirle a Gradle "descarga esta librería, pero NO descargues esa sub-librería interna", abres llaves y usas exclude:


dependencies {
    implementation('io.confluent:kafka-avro-serializer:7.6.0') {
        // Excluimos la dependencia transitiva conflictiva por su grupo y nombre (module)
        exclude group: 'org.slf4j', module: 'slf4j-log4j12'
    }
}

Ejemplo y Contraejemplo en Versiones de Dependencias

Ejemplo (Buena Práctica): Versión fija y determinista


// La versión queda fijada de manera explícita: compilará igual hoy y dentro de 3 años
implementation 'com.fasterxml.jackson.core:jackson-databind:2.17.2'
Build reproducible y seguro

Contraejemplo (Mala Práctica): Usar comodines dinámicos (+)


// ¡ERROR PELIGROSO! Pide a Gradle que baje la última sub-versión disponible en internet
implementation 'com.fasterxml.jackson.core:jackson-databind:2.+'
Antipatrón: si el creador de la librería publica un parche con bugs un viernes, tu CI/CD romperá producción automáticamente
