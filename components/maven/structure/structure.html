Estructura Estándar de Directorios en Maven

Una de las mayores fortalezas de Apache Maven es la estandarización universal de su estructura de archivos. Gracias al principio de Convención sobre Configuración (Convention over Configuration), Maven asume por defecto dónde reside el código fuente Java, dónde se ubican los recursos de configuración y dónde deben depositarse los binarios compilados sin necesidad de escribir cientos de líneas de configuración en el pom.xml.

Figura 1: Árbol canónico de directorios según el Standard Directory Layout de Maven
Ruta del Directorio Rol y Contenido ¿Se empaqueta en el JAR final?
src/main/java Paquetes y clases Java reales de la aplicación (código de producción). SÍ: Se compila a .class y forma el núcleo ejecutable del paquete.
src/main/resources Archivos de configuración (application.properties, .yml, esquemas SQL de Flyway). SÍ: Se copian directamente a la raíz del .jar (classpath).
src/main/webapp Vistas JSP, CSS, JS e imágenes para aplicaciones Web clásicas empaquetadas en .war. SÍ: Solo en proyectos con <packaging>war</packaging>.
src/test/java Clases de pruebas unitarias y de integración (JUnit 5, Mockito, Testcontainers). NO: Solo se usan al ejecutar mvn test; nunca viajan al cliente ni a producción.
src/test/resources Archivos de configuración exclusivos para tests (ej. application-test.yml, BD H2). NO: Se aíslan exclusivamente para el classpath de la fase de pruebas.
target/ Directorio de salida: clases compiladas, reportes y el archivo .jar o .war final. NO: Se borra por completo al ejecutar mvn clean (debe excluirse en .gitignore).
pom.xml Descriptor del Proyecto (Project Object Model): dependencias, plugins y configuración. SÍ: Se incluye automáticamente dentro de META-INF/maven/ para trazabilidad.

Estructura Estándar en Proyectos Multi-Módulo

En proyectos empresariales de mediana y gran envergadura (como plataformas de microservicios o arquitecturas limpias), el código se divide en múltiples submódulos dentro de una misma raíz física:


petshop-parent/
├── pom.xml                 # POM Padre agregador con <modules> y <dependencyManagement>
├── petshop-domain/         # Entidades de negocio puras (sin dependencias de frameworks)
│   ├── pom.xml
│   └── src/main/java/
├── petshop-repository/     # Acceso a base de datos (Spring Data JPA, Hibernate)
│   ├── pom.xml
│   └── src/main/java/
└── petshop-api/            # Controladores REST y configuración Spring Boot (Empaqueta el JAR)
    ├── pom.xml
    └── src/main/java/

Filtrado de Recursos (Resource Filtering) en src/main/resources

Maven permite inyectar dinámicamente variables del pom.xml (como la versión del proyecto ${project.version}) dentro de los archivos de configuración en src/main/resources activando la etiqueta <filtering>true</filtering>:


<!-- En el pom.xml -->
<build>
    <resources>
        <resource>
            <directory>src/main/resources</directory>
            <filtering>true</filtering>
        </resource>
    </resources>
</build>
Activación de sustitución de variables Maven en ficheros de configuración

En tu archivo application.properties:


# La variable ${project.version} se sustituirá automáticamente por 1.0.0 al compilar
app.name=@project.name@
app.version=@project.version@

¿Cuándo Modificar la Estructura Estándar y Cuándo NO?

Situación Recomendación Explicación
Proyectos nuevos o microservicios modernos NUNCA alterar Respetar src/main/java permite compilar sin configurar ninguna etiqueta <sourceDirectory>.
Proyectos heredados (Legacy) con carpetas antiguas SÍ redefinir en <build> Maven permite anular rutas con <sourceDirectory> o <testSourceDirectory> si no es posible mover archivos físicamente en el disco.
Generación automática de código (OpenAPI, Avro, MapStruct) Usar target/generated-sources/ Los generadores automáticos deben emitir código dentro de target/generated-sources/ para que mvn clean pueda eliminarlos y regenerarlos limpiamente sin ensuciar el control de versiones Git.

Ejemplo y Contraejemplo en el Control de Versiones (.gitignore)

Ejemplo (Buena Práctica): Ignorar siempre la carpeta target/

La carpeta target/ contiene binarios transitorios específicos de la compilación y nunca debe subirse al repositorio de código:


# .gitignore estándar para cualquier proyecto Maven
target/
*.class
*.jar
*.war
*.ear

# Archivos específicos de entornos de desarrollo (IDE)
.idea/
*.iml
.project
.classpath
.settings/
.vscode/
Reglas indispensables en .gitignore para proyectos Maven

Contraejemplo (Mala Práctica): Mezclar recursos de configuración dentro de src/main/java


# ¡ERROR COMÚN!
src/main/java/com/petshop/application.properties

Por defecto, el compilador de Maven (maven-compiler-plugin) solo procesa y copia archivos con extensión .java dentro de src/main/java. Si colocas un archivo .properties, .xml o .json dentro de src/main/java, Maven lo ignorará y no lo copiará a target/classes, provocando un error FileNotFoundException al arrancar tu aplicación en producción.
