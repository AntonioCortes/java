Mecanismo de Dependencias en Maven

La gestión de dependencias externas es una de las funciones más potentes de Apache Maven. En lugar de obligar al desarrollador a descargar y gestionar manualmente decenas de archivos .jar, Maven resuelve automáticamente las librerías necesarias, descarga sus dependencias transitivas (las librerías que a su vez necesitan esas librerías) y arbitra los conflictos de versiones.

Árbol de Dependencias y Resolución de Conflictos

Cuando declaras una dependencia directa, Maven construye un grafo o árbol en memoria. Para resolver colisiones de versiones (cuando dos dependencias piden versiones distintas de la misma librería), Maven aplica la regla de "La definición más cercana prevalece" (Nearest Definition Wins):

Los 6 Ámbitos de Dependencia (Scopes)

La etiqueta <scope> controla en qué momentos del ciclo de vida (compilación, pruebas o ejecución) estará disponible la librería y si se empaqueta en el .jar final:

Scope Classpath de Compilación Classpath de Tests Classpath de Ejecución (JAR) ¿Transitivo? Ejemplo Típico
compile (Por defecto) Sí Sí Sí (se empaqueta) Sí Spring Web, Jackson, Apache Commons, Guava.
provided Sí Sí NO (externo) No Lombok, Servlet API (la provee Tomcat).
runtime NO Sí Sí (se empaqueta) Sí Drivers de Base de Datos (PostgreSQL, MySQL).
test NO (solo en src/test) Sí NO (nunca viaja) No JUnit 5, Mockito, AssertJ, H2 Database.
system Sí Sí NO No Librerías locales fuera de repositorios (antipatrón).
import - - - - Solo en <dependencyManagement> para BOMs.

<dependencyManagement> vs <dependencies>

Es muy común confundir estas dos secciones:

  • <dependencies>: Declara librerías que se descargan e incluyen físicamente en el proyecto actual.
  • <dependencyManagement>: Actúa como un catálogo centralizado de versiones. No añade ninguna librería al proyecto por sí misma; simplemente indica: "Si algún módulo hijo decide pedir la librería X, debe usar obligatoriamente la versión Y". Permite omitir la etiqueta <version> en los submódulos.

<!-- En el POM Padre: define la versión recomendada -->
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>com.google.guava</groupId>
            <artifactId>guava</artifactId>
            <version>33.3.0-jre</version>
        </dependency>
    </dependencies>
</dependencyManagement>

<!-- En el POM Hijo: solo pide la librería SIN indicar versión -->
<dependencies>
    <dependency>
        <groupId>com.google.guava</groupId>
        <artifactId>guava</artifactId>
    </dependency>
</dependencies>
Uso correcto de dependencyManagement para centralizar versiones en proyectos multi-módulo

Cómo Excluir Dependencias Transitivas Conflictivas (<exclusions>)

Si una librería externa arrastra una versión obsoleta o incompatible de otra biblioteca (por ejemplo, el viejo commons-logging en lugar de slf4j), se bloquea con <exclusions>:


<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <exclusions>
        <exclusion>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-tomcat</artifactId>
        </exclusion>
    </exclusions>
</dependency>
<!-- Sustituimos Tomcat por Jetty como servidor embebido -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-jetty</artifactId>
</dependency>
Exclusión de Tomcat para sustituirlo por el servidor web ligero Jetty

Comandos de Diagnóstico del Árbol de Dependencias

Para inspeccionar qué librerías exactas están viajando a tu aplicación y por qué, ejecuta por consola:


# Dibuja el árbol completo de dependencias directas y transitivas
mvn dependency:tree

# Filtra solo las dependencias que incluyan la palabra 'jackson'
mvn dependency:tree -Dincludes=*jackson*
Comando fundamental para depurar colisiones de dependencias en Maven

Ejemplo y Contraejemplo en la Selección de Scopes

Ejemplo (Buena Práctica): Uso de provided para Lombok

Lombok solo actúa durante la compilación sustituyendo anotaciones por getters/setters y no debe viajar al ejecutable de producción:


<dependency>
    <groupId>org.projectlombok</groupId>
    <artifactId>lombok</artifactId>
    <version>1.18.34</version>
    <scope>provided</scope>
</dependency>
Configuración limpia: el JAR de producción no se infla con librerías innecesarias

Contraejemplo (Mala Práctica): Dejar dependencias de test con scope compile


<!-- ¡ERROR GRAVE! Olvidar <scope>test</scope> en librerías de prueba -->
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.10.2</version>
</dependency>

Si omites la etiqueta <scope>test</scope>, Maven asumirá el scope por defecto (compile). Como consecuencia, las clases de JUnit y de prueba se empaquetarán dentro del JAR de producción, aumentando el tamaño del artefacto, exponiendo posibles vulnerabilidades de seguridad y permitiendo por error que clases de negocio llamen a aserciones de test.
