El Ciclo de Vida de Construcción en Maven (Build Lifecycle)

El Ciclo de Vida de Maven es una secuencia ordenada y predefinida de pasos (llamados Fases) que dictan cómo se valida, compila, prueba, empaqueta y publica una aplicación. A diferencia de scripts manuales de compilación, en Maven las fases son acumulativas: si pides ejecutar una fase avanzada (como mvn package), Maven ejecutará primero de forma automática y secuencial todas las fases anteriores (validate → compile → test).

Los 3 Ciclos de Vida Integrados en Maven

Maven no tiene un único ciclo de vida, sino tres ciclos completamente independientes entre sí:

Figura 1: Los 3 ciclos de vida independientes y la secuencia lineal del ciclo default
Ciclo de Vida Fases Destacadas Responsabilidad y Propósito
1. clean pre-clean, clean, post-clean Elimina el directorio target/ para borrar cualquier rastro de compilaciones anteriores.
2. default (build) validate, compile, test, package, verify, install, deploy El ciclo principal de desarrollo. Se encarga de transformar el código fuente en un artefacto distribuible.
3. site pre-site, site, post-site, site-deploy Genera la documentación web del proyecto (estadísticas, reportes Javadoc y métricas).

Las 7 Fases Clave del Ciclo Default (Paso a Paso)

  1. validate: Verifica que el pom.xml sea sintácticamente correcto y que todas las dependencias declaradas existan en los repositorios.
  2. compile: Invoca a javac a través de maven-compiler-plugin para compilar el código de src/main/java a archivos .class dentro de target/classes.
  3. test: Compila las pruebas de src/test/java y ejecuta las pruebas unitarias mediante maven-surefire-plugin. Si un solo test falla, Maven detiene la construcción inmediatamente.
  4. package: Toma las clases compiladas y los recursos de src/main/resources y los empaqueta en el formato indicado en <packaging> (habitualmente un archivo .jar o .war en target/).
  5. verify: Ejecuta pruebas de integración más pesadas (con maven-failsafe-plugin) contra el paquete generado para verificar su integridad.
  6. install: Copia el archivo .jar generado en el repositorio local del usuario (~/.m2/repository), permitiendo que otros proyectos Java locales en tu ordenador puedan usarlo como dependencia.
  7. deploy: Copia el archivo .jar definitivo al repositorio remoto corporativo (como Nexus, JFrog Artifactory o Maven Central) para que todo el equipo y los entornos de producción tengan acceso a él.

Tabla de Comandos de Consola Más Frecuentes

Comando de Terminal ¿Qué hace exactamente?
mvn clean Borra la carpeta target/ completa para forzar una compilación limpia.
mvn compile Compila únicamente las clases de producción en target/classes.
mvn test Ejecuta todos los tests unitarios con JUnit y genera los informes de Surefire.
mvn test -Dtest=PetServiceTest Ejecuta únicamente la clase de test especificada.
mvn package Compila, ejecuta tests y empaqueta el archivo .jar o .war en target/.
mvn package -DskipTests Empaqueta el .jar saltándose la ejecución de los tests (solo para desarrollo local).
mvn install Compila, testea, empaqueta y copia el .jar en tu caché local ~/.m2/repository.
mvn clean install El comando rey: limpia todo lo anterior y construye el proyecto de forma segura.
mvn dependency:tree Muestra en consola el árbol jerárquico de librerías y resuelve posibles colisiones.
mvn help:effective-pom Muestra el XML final resultante combinando el Super POM, el POM padre y tu pom.xml.

¿Cuándo Usar mvn clean y Cuándo NO?

Escenario ¿Usar mvn clean? Motivo
Construcción en Servidores de CI/CD (GitHub Actions / Jenkins) SIEMPRE Garantiza que no queden clases residuales compiladas de commits anteriores.
Cambio de rama en Git o renombrado de paquetes/clases SÍ Evita que clases antiguas eliminadas permanezcan en target/classes.
Desarrollo iterativo local rápido (cambio de 1 línea de código) NO necesariamente Lanzar mvn test directo reutiliza clases no modificadas y ahorra tiempo.

Ejemplo y Contraejemplo en la Invocación de Fases

Ejemplo (Buena Práctica): Encadenar fases de ciclos distintos

Como clean pertenece a un ciclo y package a otro, se invocan conjuntamente en un solo comando:


mvn clean package
Garantiza que el JAR generado no contenga restos de clases antiguas

Contraejemplo (Mala Práctica): Ejecutar install cuando solo se necesita el JAR local

Muchos desarrolladores escriben mvn install por costumbre cuando solo quieren generar un .jar para probarlo con Docker o ejecutarlo en local. Al hacer esto, Maven copia cada versión snapshot en la caché global de su disco duro (~/.m2/repository), llenando el disco con gigabytes de binarios temporales innecesarios. Si solo quieres el archivo ejecutable, basta con ejecutar mvn package.
